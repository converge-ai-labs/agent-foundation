# Operation performance reports

Performance means the duration of one explicit storage call or one Service operation. Each execution automatically writes `operations.json`, `performance.md`, `performance.csv` and the input source list. The Markdown/CSV report has exactly six columns: **Scenario, Test configuration, P50, P95, P99, Performance result**. Rows are grouped by scenario, with distinct configurations and outcomes kept separate.

## Run and select evidence

```sh
make live-test-performance
make live-test-performance LIVE_TEST_ARGS='--performance-profile=dev/live_tests/performance/operations.example.toml'
make live-test-s3 LIVE_TEST_ARGS='--performance-profile=dev/live_tests/performance/operations.example.toml'
make live-test-report REPORT_ARGS='dev/live_tests/.state/round-two/<execution>/operations.json --output dev/live_tests/.state/review/performance.md'
```

`live-test-performance` owns PostgreSQL 17, Redis, RustFS and a preparation-only Control. It starts no Worker and runs no model. Native Service calls use the production relational/object helpers against those real backends. `live-test-s3` uses only explicit credentials in the shared private Provider `[s3]` section; missing/blank settings skip, partial settings fail. Its reports live under `.state/s3-benchmarks/<execution>/`. Profiles contain no credentials. Set `scenarios = ["pg.update", "run.complete", "steer.consume"]` to run a focused selection; omit it for the full catalog in `operation_config.py`. Unknown or duplicate IDs fail before infrastructure starts.

Select JSON paths from the execution being reviewed. `--input-list` accepts a JSON list of paths relative to that list. The converter never scans historical output directories and deduplicates identical paths. It rejects old Run-duration, queue-residence, workload-capacity and barrier-inclusive contention artifacts. Failure reports retain partial samples; an empty failed cell remains visible.

## Timing boundaries

| Scenario                 | Included in each sample                                                                                                                                                      | Prepared or checked outside timing                                                                                                                                     |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| PG SELECT                | One indexed point lookup and result transfer through `AsyncConnection.execute`                                                                                               | Connection acquisition, transaction BEGIN, input row and read-back verification                                                                                        |
| PG INSERT / UPDATE       | One statement on an independent key; UPDATE changes payload contents                                                                                                         | Connection acquisition, BEGIN and COMMIT; mutation verification                                                                                                        |
| PG COMMIT                | One COMMIT for a transaction containing one UPDATE                                                                                                                           | Connection acquisition and the UPDATE itself                                                                                                                           |
| S3 PUT                   | One signed PUT request and response                                                                                                                                          | Body generation and read-back; no follow-up HEAD in the timer                                                                                                          |
| S3 GET                   | One signed GET, complete body consumption and close                                                                                                                          | Object creation and content verification                                                                                                                               |
| S3 HEAD / DELETE         | One request and response                                                                                                                                                     | Object creation and verification                                                                                                                                       |
| S3 conditional PUT       | One `If-Match` PUT, independently or competing on one key                                                                                                                    | Current ETag and payload generation; exact one-winner/read-back verification                                                                                           |
| S3 stale conditional PUT | One rejected `If-Match` request                                                                                                                                              | Stale ETag preparation and unchanged-object verification                                                                                                               |
| Thread creation          | `allocate_thread`: authorization, Session/Thread/inbox-counter/idempotency writes and PG commit                                                                              | Actor and command setup; persisted empty Thread verification                                                                                                           |
| Attempt claim            | `AttemptScheduler.claim`: authority lookup, native locks, Attempt allocation, lifecycle and PG commit                                                                        | Accepted Run preparation; excludes scan, Worker startup, S3 writer claim and execution                                                                                 |
| Attempt heartbeat        | `AttemptExecutionService.heartbeat`: authority locks, lease update and PG commit                                                                                             | Running Attempt preparation and lease verification                                                                                                                     |
| Run completion           | `publish_checkpoint`, then `commit_state_outcome`: PG authority reads, canonical state serialization, S3 conditional PUT/HEAD, terminal PG transaction and lifecycle intents | Accepted/running Attempt, claimed writer, prepared plugins, applied initial input and ready terminal candidate; empty queue; sealed digest/Attempt/Thread verification |
| Steer append             | `ThreadInboxStore.append_steer`: one canonical input to committed PG `pending`                                                                                               | Already-authorized input; no optional Redis wakeup, delivery, model or HTTP middleware                                                                                 |
| Steer consume            | `DatabaseThreadInboxReconciler.confirm_inbox_receipts`: pending-to-consumed PG transaction with authority locks and inbox counter changes                                    | One pending steer and its already-durable S3 checkpoint with matching tagged input and receipt; no model or delivery wait                                              |
| Queue enqueue            | `QueuedSubmissionStore.enqueue`: intent validation, native locks and PG insert/commit                                                                                        | Running Thread; no Run creation or queue drain                                                                                                                         |
| Queue full rejection     | Same enqueue method through rollback, including locks/reads over the 256-entry full queue                                                                                    | Full queue preparation once per cell; exact unchanged queue verification                                                                                               |

Raw PG samples use a benchmark-owned indexed table with a `bytea` payload. They measure the stated statement shape, not every production query. Service rows cover production business schemas and multi-statement transactions. PG statement connections are pre-acquired to isolate single calls; Service samples include normal PG pool acquisition. S3 samples include HTTP pool waits and signing, with SDK total attempts fixed to one. Service S3 publication uses the ordinary adapter, including its required verification HEAD, and is named as a Service action rather than a single S3 request.

The preparation-only Control uses a separate PG pool capped at eight connections. The owned PostgreSQL sets `max_connections` to the configured PG pool plus 16 (at least 100 total), leaving room for Control and administration. The default PG/S3 pools each allow 256 connections. The preparation HTTP pool also allows and retains 256 connections (`http_pool_size`), with a 60-second client keepalive expiry and a 15-second request timeout. Before each independent Run fixture wave, concurrent streaming health probes hold distinct HTTP/1.1 connections until all callers are connected, then consume the bodies to return reusable connections. All Run fixtures are then prepared concurrently. Raw reports record the number warmed, additional TCP connections opened by Run requests, completion count, preparation duration and any failure. Preparation and connection warmup remain outside measured operation clocks.

Thread creation runs both `thread_connection_states = ["cold", "warm"]` by default. Every wave first disposes the measured engine's idle connections. Cold waves start with zero pooled connections. Warm waves acquire and hold one connection per caller, execute `SELECT 1`, and release all connections before timing. These are connection states, independently of `warmup_waves`, which counts unmeasured business-operation waves. Cold mode resets connections even after an unmeasured wave. Reports identify the state; a cold connection failure remains an error, not a successful slow sample. To obtain both results when a cold run fails fast, execute separate profiles with `["cold"]` and `["warm"]`. Attempt claims prewarm their measured PG connections after HTTP Run preparation so a separate PG connection burst cannot mask verification of HTTP preparation.

The default matrix is 1/8/32/64/256 concurrent callers, 256 calls per cell and one unmeasured warmup wave. PG and S3 payloads are 1 KiB/1 MiB. Run completion uses those sizes as **history padding**, not exact serialized checkpoint size. Steer/queue inputs contain 1 KiB of text plus their normal JSON envelope. Independent Service scenarios prepare one Thread per caller. Same-Thread steer/queue success starts empty and grows to the wave size; full-queue rejection shares one Thread containing 256 entries. Same-key S3 and same-Run claim races verify one winner per wave; successful/losing samples remain separate.

Each wave prepares every operation first, then releases all tasks. All timers stop before verification or cleanup begins. There is no deliberately held database lock or model gate in a performance sample. The report retains requested concurrency, observed peak in-flight calls, wave sizes, pool configuration, outcomes, raw milliseconds and per-cell timing semantics. A final partial wave is recorded at its actual size. Calls have a 60-second deadline, with a second wave cancellation after five additional seconds if a driver stalls while cancelling; interrupted samples and partial failure evidence remain in the report. Warmup, Control HTTP preparation, process startup, data generation, model/tool work, polling and cleanup are excluded.

## Percentiles and verdicts

Percentiles use nearest rank. `N` is the count for that row's outcome, **not concurrency**. A shared-key race can have many rejected samples but only one success per wave. Empty distributions use null values, never fabricated zeroes. Low-N P95/P99 are observations and often equal the maximum; they do not establish tail-latency compliance.

Profiles may configure `[budgets_ms."<scenario id>"]` with `p95` and/or `p99` limits. The same limit applies independently to each nonempty outcome row for that scenario. P95 requires at least 100 samples and P99 at least 1,000 samples for a gate to qualify. A configured, eligible violation fails the test and its table row. Passing all eligible gates cannot turn an unqualified remaining gate into a pass.

- **Pass**: persistence checks passed and every configured latency gate has enough samples and passes.
- **Fail**: unexpected operation error, failed persistence/one-winner assertion, cleanup failure, incomplete execution, or an eligible latency-budget violation.
- **Not evaluated**: persistence checks passed, but no latency budget was selected or samples are insufficient. A pytest pass alone is not a performance pass.

The old end-to-end budgets are deliberately not inherited by these narrower operations. Run comparative measurements on an otherwise idle host and use the same backend/pool settings. The configured matrix establishes observations at those concurrency levels; it does not infer an unsampled maximum capacity.

## Correctness coverage stays separate

`make live-test-contention` owns recovery and adversarial transaction races. Its intentional lock holds and failure recovery waits are correctness diagnostics, not performance samples. `make live-test-session` retains real sequential history and built-in compaction verification under `harness_integration/`; it reports memory, lineage and checkpoint evidence without end-to-end latency gates.
