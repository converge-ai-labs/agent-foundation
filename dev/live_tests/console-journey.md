# Console browser journey

Run `make live-test-console CONSOLE_LIVE_DIR=/tmp/a13n-console-review` with Docker available. Use a new directory each time. The command prints the actual localhost URL, model endpoint and counted MCP peer URL. It owns its stores and processes; never use shared application storage for these steps.

1. Sign in as `console@example.com` with `console-fixture-password`. Reload and verify the workspace is restored. The fixture's workspace key intentionally collides with an inaccessible workspace in another organization. Its ID link succeeds; `/workspace/ambiguous/sessions` must show a conflict without switching scopes.
2. In Models, add the deployment's OpenAI provider. Enter the printed model endpoint and a fixture-only API key, or select no authentication. Save, reopen the creation dialog and check that no credential remains. Add a named model with API Chat Completions, model ID `scripted` and a positive context window.
3. Create an Agent with that model and instructions. Open it in two tabs. Edit both, save the second, then save the first. The first must report a conflict and preserve its text. Explicitly discard/reload, then select an existing default revision without creating a copy.
4. In Sessions, create a conversation. Submit with Enter; Shift+Enter and an active IME composition must not submit. Observe canonical input status and actual completion. Reload and send a second message. The new Run must continue the completed parent in the same Thread. In a fresh Thread, send `[slow] [interruptible] [steer-proof] First question`, then send `[steer-update] Revise the answer` while it runs. The two distinct answers (`Initial answer: cobalt.` and `Revised answer: amber.`) must each appear once, before and after reload, with both canonical inputs consumed once. Separately choose Queue for next run during execution and verify Pending becomes consumed by a successor Run.
5. Submit a message containing `[interruptible]`. Refresh while it executes, then return to the same Thread. Navigation and reload must not cancel it. In a separate run, click Stop run and observe a cancelled terminal state for that exact Run.
6. For stream-loss recovery, send `[slow] Stream a long answer` and, while it streams, delete only that thread's Redis stream key (`a13n_service.runs.stream.stream_key(thread_id)`). Keep Control, Worker and objects running. The browser must receive `gap`, re-read the run's `/items`, and show the final answer from durable state exactly once without resubmitting input. Retain the Run ID and the final public representation beside the fixture logs.
7. Sign out, then sign in as `viewer@example.com` using the same fixture password. The Viewer can read existing resources/history but has no create, send or interrupt control. Direct unauthorized mutations must still be refused by Service.
8. Inspect the actual pages at desktop and 390×844, light and dark themes. Check the narrow navigation drawer, form labels, wrapping, keyboard focus, visible errors and absence of horizontal page overflow. Save screenshots beside the logs.

The launcher records `control.log`, `worker.log`, `console.log` and `state.json`. Console's proxy log records actual API method/path/status without bodies, cookies or credentials. Configuration files contain disposable database/encryption secrets and are mode0600; do not publish them. Close the browser tabs and stop the launcher when finished.

## Remote MCP journey

Create a Connection using the printed `mcp_url` plus `/none/mcp`. Test it, inspect the discovered tools, edit its name, and save an explicit allowlist. For bearer and header authentication use `/bearer/mcp` or `/headers/mcp` with synthetic `fixture-secret`; custom authentication uses `X-API-Key`. Never use real credentials in this fixture. In the Agent editor choose this Connection and `increment`, save, then send `[service-mcp:increment]` in a new conversation. The production Worker must record one external effect, show tool arguments and count1 result, and retain both on reload. The peer's `/fixture/state` reports durable effect/call counts without plaintext credentials.

## Personal OAuth journey

The fixture also exposes `oauth_url` with a real authorization page, counted one-use codes, rotating refresh tokens and deterministic response barriers. Create an OAuth Connection pointing to `<oauth_url>/tools/none/mcp`, issuer `<oauth_url>`, public client `fixture-client`, scope `tools`. Save, connect the current account, approve at the fixture, return to the Console and reopen the Connection. Verify active status, test and select a tool in an Agent, execute a conversation and reload its durable result. Disconnect, verify fresh use is refused, then reconnect. A consumed token response lost at the fixture must show reconnection required; the Service must not silently retry it. The browser substitutes only for a human and external issuer; Control, Worker, Harness and stores remain production paths.

## Composio managed account journey

The launcher also prints `composio_url` and routes native Composio API/Connect constants to this counted local peer through `dev.fixtures.composio_service`; production provider origins remain fixed. Add a Composio Connection with synthetic project key `fixture-project-key`. Load applications, select GitHub's existing authentication configuration and `GITHUB_CREATE_ISSUE`, then save. Connect the personal account, authorize on the hosted fixture page and return through the fixed verifier. The returned Console URL must contain no session URI. Reopen, test the account, then choose its action on an Agent revision. Send `[service-composio]`; verify the native action's arguments, successful result and dated version remain after reload. Disconnect and verify access is refused, then reconnect with a fresh enrollment. The peer counts setup, completion, revoke and action effects in `/fixture/state` without logging credentials or verifier bodies.
