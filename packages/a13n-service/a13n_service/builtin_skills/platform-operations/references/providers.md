# Providers

Read `/platform-instance/catalog.json` for installed provider types, configuration schemas and authentication requirements. List workspace providers before proposing a create. Model, Environment, Connector and Web Providers support the Composer credential card; Memory is outside Composer's scope. Browser Provider reads and tests use the providers group, but Browser account creation and human control require an integrating application. Check the instance catalog before proposing a Browser: the built-in distribution registers Browserbase, Kernel, and Browser Use Cloud. A provider account is not an allocated Browser.

To test a saved provider, call the corresponding `test_model_provider`, `test_environment_provider`, `test_connector_provider`, `test_web_provider` or `test_browser_provider` with `provider_id`. This operation requires review and Provider `run` permission. The Service uses the saved configuration and credentials for one non-billable probe and returns `{provider_id, provider_version, status, message}`. Report `succeeded`, `failed` or `unsupported` as returned; success does not prove a particular model can complete inference. Check `supports_test` in the installed type catalog first. Model discovery is a separate capability and must not substitute for this test.

Omitted model Provider `config.forward_context_headers` inherits `A13N_HARNESS_FORWARD_CONTEXT_HEADERS` (unset: true); explicit booleans override that default and remain stored. Service forwards explicitly submitted `options.context.headers` only when this setting and deployment `providers.forward_model_context_headers` are both enabled. Model request headers take precedence over context; credentials, static secret headers, protocol headers and affinity remain authoritative. Disabling forwarding leaves trusted runtime access to the context unchanged.

`credential_configured` is a boolean describing whether a credential is saved, not whether it is valid. Never request the secret to verify it. OpenRouter tests validate the saved key through `/key`; its public model catalog cannot establish key validity.

Use `configure_provider` to request a Console card. Supply `action` (`create` or `update`), `kind`, `type`, `name` and the complete desired non-secret `config`. For an update, read the existing provider first, preserve unrelated configuration, and include its `provider_id` and exact original `etag`, constructed from the returned `id` and `version`. Never put API keys, tokens, client secrets or secret header values into arguments or chat. The card collects schema-defined credentials directly from the user; custom secret headers and browser OAuth authorization use the existing Console pages.

The user reviews the proposal and saves through the existing Provider API under their own workspace authority. The card then returns `{status: "saved", provider_id}` through the normal client-tool response, or `{status: "cancelled"}` before a save attempt. Stopping after an unconfirmed save returns `{status: "unknown"}`; inspect provider state before proposing any further write. The Run may wait for other questions or approvals in the same batch. Do not claim a provider was saved before receiving its result. Other hosts must implement this client tool themselves or report that it is unavailable.

A confirmed save and Run resume are separate operations. Retry only resume after a confirmed save. There is no create idempotency: an uncertain save or page reload requires checking the Providers page before explicitly retrying, since another create may duplicate it. A stale update requires a fresh read and proposal. Never substitute a newer ETag into an already reviewed request. If the user cancels, do not repeat the request without their instruction.

Provider deletion and other account administration are outside the internal platform catalog. Use the existing trusted Console workflow when authorized; do not fall back to raw HTTP tools.
