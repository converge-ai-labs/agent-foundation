# Models

List configured Models and read the selected key before changing an Agent. The model catalog is descriptive; creating or selecting a configured Model still requires an authorized Provider resource. Model settings follow the deployed Provider's calling API schema in the instance catalog. Do not invent fields.

To look up public prices and characteristics, call `GET /api/v1/model-catalog` with `provider` (the catalog channel, such as `openrouter`) and `model` (the exact upstream model ID). Both filters are optional, case-sensitive exact matches and combine with AND. Prefer both when known; use `view=compact`, `query`, `capability`, `limit` and `cursor` to discover model IDs when needed. For a selected provider/model, `section=all|characteristics|pricing` returns a versioned fragment (`offset`, `text_limit`, `version`). Default detailed reads retain `{items, status}`; an empty match does not mean the model is free, and `stale` or `unavailable` must be reported when relevant. Filtering does not change full-directory refreshes or cache contents.

Use the selected item's `ref.model` as `config.model_name`, `characteristics` as `config.characteristics`, `pricing` as `pricing`, and `ref` as `catalog_ref` when creating a Model with `POST /api/v1/models`. Choose the authorized workspace `provider_id` and its supported `config.model_api` separately. For an existing Model, read it first and use `PATCH /api/v1/models/{key}` with its ETag, preserving unrelated configuration and user-entered values. Copy prices only from the requested channel; do not substitute another channel's prices. If `pricing` is null, report the missing price or `pricing_warning` instead of inventing a value. Catalog reads never save or update a Model automatically.

Model resources are shared by key. Explain the affected shared settings before updating one. To change one Agent's sampling or model behavior, prefer that Agent's `model_settings` when appropriate. Keep unrelated settings intact. Read the Model's ETag and pass it to updates. Provider credentials are entered in the Console, never in chat.

Provider updates preserve omitted credentials and extra header values, including when connection settings change. An empty `extra_headers` object also keeps saved values. Submit only intended secret changes; a header value of `null` removes that header. The updated configuration must still permit the retained credential and header names.

The `anthropic` Provider automatically sends its one saved API key in both `X-Api-Key` and `Authorization: Bearer`, including on connection probes and custom gateway URLs. Do not ask for or configure a separate Authorization header. Both names are reserved; remove an existing custom Authorization entry when upgrading.

Service defaults effective model settings to `cache: true` for primary and auxiliary calls. Prefer native `cache` settings for prompt caching: `false` disables library-managed caching and a retention value selects its duration. Model defaults and Agent overrides remain authoritative. For Anthropic Messages, the default also enables `anthropic_cache_instructions`, `anthropic_cache_tool_definitions` and `anthropic_cache_messages`, placing markers on content blocks instead of sending top-level `cache_control` for gateway compatibility. An explicit unified `cache` setting or any of these provider settings (including `anthropic_cache`) keeps the native authored policy. Pydantic AI owns provider-specific marker placement; provider support and repeated prefixes determine cache hits.
