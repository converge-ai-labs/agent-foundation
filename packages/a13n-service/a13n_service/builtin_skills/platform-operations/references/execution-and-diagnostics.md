# Execution and diagnostics

Use `service_run_id` from automatic Service context for the current Run. `harness_run_id` identifies a separate Harness execution and is never a Service Run ID. Session, Thread, Run and Attempt identifiers are distinct. An Attempt exposes its root Harness execution; inline subagents have their own Harness IDs within the same Service Run.

Start with authorized IDs or use `list_runs` with Agent, status, principal, Session, Thread or creation-time filters. Time windows include `created_after` and exclude `created_before`. Keep every filter unchanged while following cursors. Run lists, thread Run lists and lineage return metadata with an input preview; the loaded page length is not a total. Read a selected Run to obtain its Session, Thread, frozen Agent Revision, status and current Attempt. A failed recovery Attempt does not imply the final Run failed.

Use `list_sessions` with `sort=updated_at|runs|cost` and `direction=asc|desc` to find recently active, busy or expensive Sessions. Cost is recorded model cost, not a claim that all requests are priced. Preserve null cost and `unpriced_requests`; unknown metrics sort last. `list_thread_runs` accepts an exact Run `anchor` or whole-Thread ranking with `sort=cost|calls|duration`. Its chronological number, total and directional cursors describe more than the loaded page.

When the user remembers message content, use `text_query` on Session, Thread or Run lists. Prefer a Run list to locate a match directly. For example, `{"text_query":"南京 部署","limit":10}` requires both terms. Parent lists return Sessions or Threads with at least one matching Run; their latest Run need not be the matching one. Filter Run lists by the returned parent with the same text query to locate the evidence.

Text search tokenizes Chinese and code identifiers and requires all terms within one Run, possibly across messages. It is not arbitrary substring or phrase search. Keep queries concise: at most 1024 characters and 64 terms. Only retained user-input and visible root-assistant excerpts are indexed; tool results, reasoning, inline-child output and inherited history are excluded. Historical Runs are not backfilled and long or evicted text can be absent. A miss does not establish that a conversation never occurred. Session `q`, `application` and `label` provide additional structured discovery.

Use `list_session_threads` for navigation within a Session, filtering `origin` or exact `thread_id` values. Use `list_threads(session_id=..., origin=["child"], origin_run_id=...)` to inspect delegation. `origin_number` and `origin_count` describe all Threads of that origin. Query `list_inbox` and `get_inbox_entry` for queued, assigned, withdrawn or submitted input. Use `get_message_authors` with `session_id` and 1–100 inbox `entry_id` values to identify message senders. It returns current name, email, kind, status and image when available. A Run's execution principal or Session's creator does not identify every sender. Missing or out-of-Session entries are omitted; unavailable profiles are null. This is not a general member-directory lookup.

`get_run`, `get_inbox_entry`, `get_run_configuration`, `get_trace` and `get_trace_span` return bounded summaries with a `content` map. Select a returned opaque reference and call `read_content(reference=...)` or `search_content(reference=..., query=...)`. Follow `continuation` unchanged for more text or matches. The `fragment` contains the bounded text, source version and truncation facts. A reference is tied to the originating Run, workspace, source and representation; every read rechecks current source authorization. Do not construct or decode it. If content changes, obtain a new reference from the parent and restart. Partial JSON is not a complete object.

Use `get_run_configuration` to compare original and effective selections or overrides; `part` chooses a configuration field for its returned references. Omitted `options.context` in Run, inbox, Schedule and occurrence tool results is deliberate redaction, not proof that no context was accepted. Context may persist through recovery, resume and child execution. Ordinary trusted submission owns caller context headers.

`list_run_items` accepts `kind`, `state`, `tool_name`, and exclusive `before`/`after` ordinals. Its `page` contains compact display items and continuations; `content` maps item IDs and fields to opaque references. Scans are bounded, so continue even after an empty matching page when a continuation exists. Read selected text, arguments, results or metadata through the returned references. Never substitute an ordinal or item from another Run.

Use `list_run_attempts`, `get_run_attempt` and `list_attempt_spans` to inspect all relevant attempts. Use `list_traces` for bounded discovery and `search_traces` to rank slow or expensive traces across an explicit range of at most 31 days. Filters include Session/Thread/Run IDs, attributes, status, kind and tool name where the declared schema supports them. Ranking accepts `order_by=duration|cost`, direction and inclusive numeric bounds. Costs are observation costs, not Run billing. Unknown metrics sort last and do not satisfy numeric thresholds. Keep filters and ordering fixed when following the cursor; live changes can still cause repeats or omissions.

`list_trace_spans(view="overview")` retains exact timeline fields, models, status, parent links and costs without payloads. `get_trace_span` returns a bounded summary and content references for one selected observation. Analysis Runs remain restricted to their selected traces. Retention, redaction and backend availability can limit evidence. `payload_too_large` means an observation exceeds the backend's bound; inspect it in the trace backend rather than retrying the same read indefinitely. Absence of retained trace data is not proof of correct execution.

Use `list_tool_executions`, `get_tool_execution` and `get_tool_execution_result` within the exact Thread. `run_id` is a Service Run ID; `active` filters live calls. Status reads do not consume results. Explicit result reads acknowledge delivery and begin the configured reread-retention window; use the returned content references for remaining text. A lost owner or unknown outcome means effects may have occurred, so never automatically replay the call. Cancellation is outside these tools.

Run failures retain endpoint-policy reasons and upstream status classes. `provider_endpoint_denied` requires a changed endpoint or deployment policy; repeating the same configuration cannot fix it. An upstream status alone does not prove the cause. Inspect authorized Provider readiness and settings without requesting secrets. `create_finding` records evidence-backed findings with limitations; `list_findings`, `get_finding` and `list_finding_analyses` preserve the existing review workflow. Findings are hypotheses, not authority to change configuration.

These tools diagnose execution. They do not start, interrupt, fork or resume Runs, follow live streams, administer members or transfer files. Use supported trusted product workflows for those separately authorized tasks. Present names from context or authorized results, include email only when useful, and retain IDs for precise references.
