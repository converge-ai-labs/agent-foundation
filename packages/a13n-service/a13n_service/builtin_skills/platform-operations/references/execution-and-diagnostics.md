# Execution and diagnostics

Start with the IDs selected in Console. Without IDs, list Runs by Agent, status, principal or creation time. Time ranges are UTC-aware, include created_after and exclude created_before. Lists are newest first and paginated; keep the same filters while following next_cursor. Session, Thread and Run IDs are distinct.

Session lists also accept `sort=updated_at|runs|cost` and `direction=asc|desc`, defaulting to most recently updated. Use cost or run count to find expensive or busy Sessions across the whole filtered collection; keep ordering unchanged while following a cursor. Session `cost` is the recorded model-cost subtotal and is null when nothing is priced. `unpriced_requests` identifies incomplete pricing; unknown cost always sorts last.

For the current execution, use `service_run_id` from the automatic Service context as the `run_id` parameter of Run queries. The Harness context's `harness_run_id` identifies a separate Harness execution; it is not a Service Run resource ID and cannot be used with `/api/v1/runs/{run_id}`. An Attempt exposes its root Harness execution as `harness_run_id`. Inline subagents have their own Harness execution IDs under the same Service Run.

When the user remembers message content, use `text_query` on Session, Thread or Run lists. Prefer a Run list to locate the matching Run directly, combining supported Agent, status or time filters. For example, `{"text_query":"南京 部署","limit":10}` searches Runs for both terms. Session and Thread lists return parents with at least one matching Run; a parent's latest Run need not be the matching one, so use its ID to filter the Run list with the same `text_query`. Follow `next_cursor` without changing search terms or other filters.

Search tokenizes Chinese and code identifiers and requires all query terms within one Run, possibly across messages. It does not guarantee phrase or arbitrary substring matches and keeps time ordering rather than relevance ranking. Use concise terms: at most 1024 characters and 64 distinct terms; empty or punctuation-only input matches nothing. Session `q` finds exact Session/Thread IDs, title/source/label substrings, or retained Run text. Filter `application` to an exact source application and use `label` for project or role. A detail reader's literal `query` searches that selected content, not the workspace; it is separate from list `text_query`.

Only retained excerpts of the Run's user input and visible root-assistant text are indexed. Tool results, reasoning, inline child output and inherited history are excluded. Existing historical Runs are not backfilled; long-message middles and terms from evicted older messages may be absent. Streaming text becomes searchable only after completed or interrupted text is committed with display content. A miss is not proof that the conversation never occurred: broaden or remove text terms, use known IDs and structured filters, then inspect the relevant input, items or trace evidence.

Read a Run to obtain its Session, Thread, frozen Agent Revision, status and current Attempt. Query the Thread inbox for submitted, pending or withdrawn input, and Run items and saved content for the displayed request and response. Read every relevant Attempt: a failed recovery attempt does not imply that the final Run failed. Attempt detail and trace operations require both the Run and Attempt IDs. Trace evidence can be incomplete, expired or unavailable. Findings are hypotheses with evidence; inspect the cited execution before proposing a change.

The platform MCP surface omits `options.context` from Run, inbox, Schedule and occurrence responses before fragmenting or searching them. Ordinary authorized HTTP reads retain it. An omitted context in a tool response does not establish that none was accepted. Context persists through recovery, resume and child execution; a new ordinary message starts with only its submitted context.

Use `list_tool_executions`, `get_tool_execution` and `get_tool_execution_result` to inspect retained calls in the exact Thread. The optional `run_id` filter is a Service Run ID; `active` filters live calls and `cursor` continues the same query. These routes do not accept `view`. Status reads do not consume results; explicit result reads acknowledge delivery and start the configured reread retention window. Read result fragments with `offset`, `limit` and the returned `version`. A `lost` owner means effects may have occurred; do not replay the call automatically. Cancellation is not exposed by the platform MCP query surface.

Run failure messages retain endpoint-policy reasons and model HTTP status codes. A `provider_endpoint_denied` failure needs a changed endpoint or deployment policy; repeating the same configuration does not help. An HTTP status identifies the upstream response class, not the exact cause; inspect the Provider's authentication and endpoint settings before attributing it to a bad key.

When the user asks who sent a message or which user's conversation matched, call `get_message_authors` with the Session ID and 1–100 message `entry_id` values from the Thread inbox. For example: `{"session_id":"sess_FROM_RESULT","entry_id":["inb_FROM_RESULT"]}`. Each match returns `entry_id`, `principal_id`, `submitted_at` and `principal`, containing the sender's current `id`, `kind`, `name`, `email`, `status` and `image_url`. `name` is a display name; service accounts have no email. Profiles reflect current values, including disabled accounts, rather than a snapshot at submission. Use the matched message's author; a Run's execution principal or Session's creator does not identify every message sender.

This query requires workspace `read` and returns only message entries in the named Session. Missing IDs, entries from other Sessions and non-message entries are omitted; an unavailable profile is null. It cannot resolve an arbitrary `principal_id` or list all members. The absence of a member-directory tool does not mean sender names are unavailable: use this lookup before reporting that only IDs can be shown. Present the returned name, adding email when useful for the request or disambiguation; retain the ID when needed for a precise reference. Use known workspace, organization and resource names in the same way, without inventing names when no authorized lookup or context provides them.

Use only these read operations for diagnosis. Do not start, interrupt, fork or resume executions. Explain evidence limits and partial results; absence of retained trace data is not proof of correct execution.

Use `list_session_threads` for lightweight navigation within one Session. Filter `origin` to roots, forks or children, or `thread_id` to known Threads. Use `list_threads` with `session_id`, `origin=child` and `origin_run_id` for a bounded delegation lookup. Follow `next_cursor` with unchanged filters. `origin_number` and `origin_count` describe the complete Session's Threads of that origin; do not infer names or totals from the loaded page length. Read the selected Thread for its latest Run, execution settings or headers.

`summarize_usage` returns only model totals for the selected Run, Thread, Session or ingestion window. Use `list_run_usage` for a paginated Run breakdown with the same filters. A page contains complete per-model groups for each returned Run, and `run_number` counts all Runs in that Thread, including those with no matching usage. Totals cover the whole filter scope, not just the loaded pages.

Run lists, thread Run lists and lineage return metadata plus `input_preview` (at most 200 Unicode code points); follow their cursors and use a selected Run for full values. Thread Run lists accept `anchor` for an exact Run and return chronological numbering, a total and cursors in both directions. To rank the whole Thread, omit `anchor` and use `sort=cost|calls|duration` with `direction=asc|desc`; follow `next_cursor` without changing the ordering. Each Thread list item includes its original `number`, `cost`, `model_calls` and `unpriced_requests`. Unknown metrics sort last. Use `view=compact` on Run detail, inbox, item, content and trace queries. A Run's `section` selects input, output, failure, pending or other named fields. `/runs/{run_id}/agent` selects `section=original|effective|overrides`; `part` selects a configuration field within original/effective. Compact Run configuration reports changed top-level field paths and bounded resource references.

Item reads accept `kind`, `state`, `tool_name`, and exclusive `before`/`after` ordinals. Compact and filtered reads scan a strict bounded window (compact starts at the oldest ordinal unless a position is given), without attaching the full tail. Follow the returned directional continuation even when no matching item was found. Read `/runs/{run_id}/items/{item_id}/content` with that item's `ordinal` and `field=text|arguments|result|metadata|all`. Saved content reads use `offset`, `limit`, `version` and optional literal `query`; a field reference is resolved under the same Run's authorization.

Trace lists accept `status`, `kind` and `tool_name`. Read a root's named section directly. For a selected span use `/traces/{trace_id}/spans/{span_id}/content`; it queries the backend for that span alone. Empty `items` means the trace has no such span. Continue fragments with `version` and `next_offset`. A `payload_too_large` error means that observation alone exceeds the backend response limit; inspect it in the trace backend instead of retrying. Trace search remains subject to retention and the configured backend's availability.

For exact timeline fields without observation payloads, `/traces/{trace_id}/spans` also accepts `view=overview`. It preserves complete names, models, level, status, timing, parent links and per-observation costs; it does not include input/output or diagnostic metadata. `/traces/{trace_id}/spans/{span_id}` reads one full redacted observation directly. Prefer compact discovery and the fragment route for model-visible content that may be large; overview and direct detail do not use compact response budgets. Both require the same workspace scope and an analysis Run may still read only its selected traces.

Use `search_traces` for slow or expensive traces across an explicit time range (at most 31 days). Set `order_by=duration|cost`, `direction=asc|desc` and optional inclusive `min_duration_seconds`, `max_duration_seconds`, `min_cost_usd`, `max_cost_usd`. Costs sum reported observation costs, not Run billing. Unknown values sort last and do not match numeric thresholds. Follow the returned keyset cursor with unchanged filters. It continues after the last sort value and trace/span IDs, independently of insertions or deletions ahead of that position. Every page queries the backend again without a result cache; changes to sort values or filter membership can still cause repeats or omissions. Narrow the range or add an ID filter if collection exceeds its bounds; an error never provides a partial ranking. Root summaries omit payloads; read a selected trace for evidence.
