# Environment templates

Templates describe how later Environment instances are created. Query the authorized environment Providers and use their deployed recipe schema from the instance catalog. Read the template and its ETag before updating it. A template update does not create, start or reconfigure an existing instance. Explain which future instances use it. Agent default environment selection and lazy startup have their existing lifecycle rules; preserve unrelated values. Instance start/stop/delete, shell and file access are outside this platform tool selection.

Service reads the default mount's working-directory `AGENTS.md` and discovers project-local guidance paths before inference. Child `AGENTS.md` and `.agents/skills` entries are path-only hints, not loaded bodies or additional selected Skills. The default is `workspace` when present, otherwise the sole user mount. This preparation can activate that Environment even when the model uses no tools; other mounts remain lazy unless `lazy_environment: false` requests eager instance preparation. Guidance discovery grants no additional permissions.

For Docker Computer Use, select a desktop variant of `a13n-sandbox` and set recipe `desktop: true`. The existing Provider `docker_host` selects the local or remote Engine; no separate desktop endpoint or published port is needed. Do not override the desktop image's user, display or envd environment variables. A template grants no Agent tools or mount permissions. Native recipes default to `desktop: false`; selecting a desktop image alone does not change that mode.

For native E2B Computer Use, enable recipe `desktop: true` and select the E2B `desktop` template or a compatible custom template. Omitting `template` in a desktop recipe selects `desktop`; explicit `base` is not changed. The existing E2B connection supplies credentials; no Docker image, a13n-envd endpoint or VNC port is required. Desktop width, height, DPI and display are advanced recipe settings. Service prepares the desktop and checks readiness; Agent Computer tools and mount action ceilings must still permit the intended operations. This mode does not enable Console desktop streaming or human takeover.

For Chinese desktop rendering, select a custom E2B desktop template with CJK fonts installed at build time (for example, `fonts-noto-cjk`). The official `desktop` template may lack these fonts; Service does not install them during connection or input. Create a new environment after selecting the custom template. Text input keeps the official SDK's typing pace, isolates non-ASCII characters into separate SDK calls, and maps line endings to Enter keystrokes, which can submit forms or terminal commands. Confirm focus first, split long text, and never replay an uncertain input.

For native Daytona Computer Use, enable recipe `desktop: true`. An omitted `snapshot` uses Daytona's default desktop-capable sandbox; custom snapshots must include the desktop packages and any required CJK fonts. Service initializes the desktop during create/start; execution attachment only checks readiness. The adapter uses Daytona's official Computer Use API. Enable the Agent's Computer toolset and the matching mount permissions separately. Existing headless recipes remain unchanged.

For Daytona Console viewing, Agent-requested assistance and user takeover, also set `desktop_assistance: true` and select an operator-built `snapshot` that preinstalls and starts the desktop access supervisor. A default snapshot or a native signed preview URL alone does not provide the required input and revocation controls. Service reuses its safe pause, exclusive control and resume flow; input with an unknown outcome blocks handoff. Snapshot construction requires separate build authority and is not performed by template creation or runtime attachment. After a template change, create a new environment to use the snapshot.
