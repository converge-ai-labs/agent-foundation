# a13n Console

## Product Boundary

`a13n-console` is the browser application for a13n Service. It consumes the public Native API through the TypeScript SDK and uses the shared [design system](design-system.md). Service remains API-only; production ingress serves Console assets and proxies `/api` on the same origin. Development uses a Vite proxy rather than permissive Service CORS.

Console owns navigation, forms, resource cache, localized presentation, and interaction rendering. Service owns authentication, permissions, resource versions, execution, durable state and object storage. Closing a page, stream, or SDK client never interrupts a Run.

## Navigation and Scope

Workspace pages use `/workspace/{workspaceKey}/…`; Agent detail uses `/workspace/{workspaceKey}/agents/{agentKey}` and Skill detail uses `/workspace/{workspaceKey}/skills/{skillKey}`. Organization settings use `/organization/settings`, and personal settings remain `/settings/profile`. The authenticated single Organization supplies organization scope; its key is not part of browser paths. Console generates Workspace and Agent paths from current resource keys, including links from Run history and resource references. Deep links match the exact keys without selecting a default Workspace or accepting ID aliases. The root page can select the remembered accessible Workspace or the first accessible Workspace.

Name and URL key are independent profile fields. Workspace and Agent key changes explain that existing links will stop working, refresh affected resource caches, and move the current page to the new canonical address. IDs remain the identity of cached resource data, permissions, revisions, and execution references; key-dependent lookups are invalidated after key changes.

The sidebar contains Agents, Sessions, resource management (Models, Skills, Assets, Environments), integrations (Application Accounts, Connectors, MCP Connections), and Traces. Provider management lives in Workspace and Organization settings under `section=providers`, with Model, Search, Environment, and Connector categories selected by the `category` query. The settings route determines ownership; there is no separate scope selector. Both settings surfaces reuse the same provider management components. Organization administrators can manage shared providers without workspace membership. Workspace collections identify inherited organization providers and preserve their ownership and editing permissions. Models, Environments, and Connectors retain contextual management links into the matching settings category. The standalone `/providers` route is removed. Environments retains Template and Instance child routes. Organization settings retain shared Models and Environment Templates. Usage and Schedules are absent from the primary navigation until available; their existing deep links display a Coming soon view without API calls or simulated data. Console exposes no Plugin editor, Secret management, or Webhook subscription editor.

Workspace and User menus open on pointer hover while retaining click and keyboard activation. The workspace name opens a same-width menu with Settings and an always-visible Switch workspace submenu. Workspace-menu Settings opens the current Workspace profile; User-menu Settings opens the Personal profile. The primary sidebar has no standalone Settings entry. The submenu includes the current workspace with a check mark, including when only one workspace is available. The User menu identifies the signed-in user, opens personal settings, and signs out. Language selection lives in personal Preferences. OSS has one Organization and no Organization switcher. Settings replace the primary sidebar and breadcrumb header with one searchable navigation containing Personal, Workspace, and authorized Organization groups, plus a return action. All authorized groups remain available across settings pages; primary and contextual sidebars are never shown together. Resource names within a scope do not repeat that scope in every link. The desktop sidebar stays expanded without collapse controls or shortcuts. Navigation uses compact rows and group spacing; narrow screens retain an accessible navigation drawer. Sidebar selection changes background and color while retaining the same font size and weight.

Personal settings contain profile, browser-local appearance and language preferences, email and password management, browser sessions and personal security activity. Workspace settings contain profile, members, invitations, Personal API Keys, Service Accounts and their keys, and security audit. Organization settings contain profile, members, invitations, Workspaces, shared configuration and security audit. Organization-shared configuration reuses the resource editor with an explicit scope.

Key creation offers 1 day, 7 days, 30 days, 3 months, 1 year, and no-expiration choices. Expiration is calculated when creation is submitted; day presets are elapsed 24-hour periods, while month and year presets use UTC calendar arithmetic with month-end clamping.

A Personal API Key belongs to its User and is bounded to one Workspace. Its creation and list live in that Workspace's settings. Administrators can inspect member-key metadata and revoke keys but cannot create another User's Personal API Key or recover its bearer value. Service Account keys live under their owning Workspace Service Account. Newly created bearer values appear once and are not persisted by Console.

## Sessions and Runs

Sessions present Service Sessions directly. The Session list replaces the primary sidebar, with a return-to-workspace action at its top. List labels and excerpts use the authorized, bounded preview returned with each Session; rendering a row does not fetch its Threads or Runs. A missing preview displays the empty label rather than searching older or inaccessible content. Session links open a Thread and its current or head Run without intermediate selection pages. The detail identifies the current request and its Agent before compact Thread and Run-history controls, semantic Items, the composer, pending actions and queued submissions. Request text used as a heading is a presentation of retained input, not a separately persisted Session title. Each Run is inspected inside that Session through a panel containing input/output, available configuration evidence, RunAttempts, lifecycle events and linked Trace details. Console provides no independent Run-list navigation. A Run deep link selects its Session, Thread and Run within the same layout.

Agent trial execution opens this same Session surface. Continue, historical Continue, Fork, Retry, Feedback, Steer, Interrupt and queue operations use the owning Native contracts and exact current version evidence. The UI distinguishes queue acceptance from Run acceptance and delivery receipt from command consumption. Waiting interactions expose their required feedback; Console never automatically executes arbitrary Client Tools.

Stream cursors advance only after events are applied. Replay gaps and explicit reconnection fetch current resource and Item snapshots even when cached values are fresh, with unavailable retained content shown explicitly. Views and recovery share resource reads; detaching one stream does not cancel another consumer's resource request. Lifecycle events, notifications and successful commands refresh the affected Session, Thread and Run resources. An observation gap refreshes the Workspace's cached interaction resources. Notifications are wake-ups, not durable history, and users without notification subscription permission retain Run streaming and recovery. Trace absence is not execution success, and unavailable cost or usage is not zero.

## Resource Editing

Agent authoring uses a full-page form with aligned section descriptions and configuration controls, stacking each section on narrow screens. The header contains identity, version and management actions, and a link to trial execution on the dedicated Session page; there is no embedded conversation panel. A pencil action beside the name edits the name, description and resource key. The default environment is configured directly on the page and saves independently without clearing the executable configuration draft. Availability, archive and duplicate actions have a separate entry. Save or discard a configuration draft before opening management actions that could reload the form; trial execution requires saving the draft. Save status and pending-change actions stay in a sticky footer. Instructions support Markdown source and use the [shared field and scrolling rules](design-system.md#scrolling-and-long-content). Search, Skills, MCP connections, and Connectors are configured directly on the page. Capability sections show selected resources; adding resources opens a searchable inline selection. Each selected Skill or MCP connection exposes its version constraint or tool scope directly in its resource card; single-field configuration does not require an extra disclosure. Controls follow the [shared interaction affordances](design-system.md#control-meaning-and-configuration). Search Provider selection and parameters expand on demand. Configured references remain visible and editable even when their resources are no longer listed. Empty Skill, MCP, and Connector categories link to the corresponding resource setup in a new tab so the draft remains open; Search Provider management also opens in a new tab and refreshes choices on return without changing the draft. Model settings and advanced configuration remain collapsed by default. Validation expands the relevant section and identifies the field. Collapsing preserves the draft. Editing one field preserves other configuration, including Plugin and Secret requirements that Console does not expose. Saving executable configuration creates a Revision; restoring historical content creates a new Revision rather than moving the head backward.

Skill collections use two-column cards, stacking on narrow screens, and search names and keys through the paginated Service collection. Each card identifies the current revision source as GitHub or ZIP upload. An All, GitHub, or ZIP upload filter combines with search before pagination. Detail pages open the current version's file browser with `SKILL.md` selected. Files, Versions, and Used by agents are the detail views; selecting a version opens its own immutable package through an addressable revision query. The file browser presents a navigable directory outline and file contents, with Markdown preview and full source views. Binary and oversized files retain an explicit download fallback. Skill content is never executed, and preview does not automatically load remote media. A rename action beside the title edits the display name; deletion remains a confirmed action in the management menu. Import Skill and New version present ZIP and GitHub as source tabs; Publish version is the final revision action.

Provider types and model parameter schemas come from Service. A discovered candidate is not a saved Model. Skills retain immutable package revisions; Assets are immutable uploads without overwrite, rename, or revision actions. Environments distinguish configured Providers, template recipes, and actual instances. Integration authorization and credential ownership follow their Service contracts.

Mutations retain exact ETags or expected versions. A conflict keeps the draft and offers an explicit reload; Console does not silently overwrite newer data. Permission projections guide visible controls but never replace server authorization. Cache identity includes the authentication session and resource scope; sign-out clears sensitive state, and Workspace switching does not reuse another Workspace's resource data.

## Search Setup

The Agent editor presents first-party search as an optional Search Provider selection with bounded per-Agent parameters. It lists currently visible Search Providers with their type and ownership under [Search Provider Management](../a13n-service/41-search-provider-management.md). Only enabled, credential-configured providers are offered for new selections; an existing unavailable reference remains visible with its configuration error and can be changed or cleared. Clearing search changes only the Agent selection. Provider creation and testing live exclusively in Providers, outside the Agent editor. The management link opens the Search category in a new tab with the current workspace, preserving the Agent draft. Returning to the draft refreshes available providers without automatically changing the selection.

The Search category supports provider creation, name/configuration editing, write-only credential rotation, enable/disable, tests, and authorized referencing-Agent navigation. The form reads the selected type's safe configuration and credential schemas from Service, asks only for required values, and links to its account/setup URL. Secret input is never prefilled from a resource read or stored in browser persistence. The create/update request holds it only for submission; the input clears after success or form dismissal. Provider save, explicit quota-consuming test, and Agent revision save show separate outcomes. A failed test leaves the saved provider available for correction. After a lost provider-create response, the form reconciles the visible provider collection and identifies the uncertain result rather than creating another name or claiming credential equality. Conflicts retain the draft and require an explicit refresh; tests are never automatically repeated.

Each provider category retains its Service API and type-specific configuration and actions, including model discovery and connector catalogs. Centralized management does not merge their domain models. The UI shows actual ownership and sends mutations through that scope. Workspace users can use permitted Organization providers while only Organization administrators can edit them. Enabled and credential-configured indicators do not imply a successful test, remaining quota, or current upstream availability. Provider selection does not require a Connector, Plugin editor, or separate Secret form. Search Provider management and testing are independent of Environment setup; running the selected Web tools requires an Environment and exposes search, fetch, and download together. Model-native search and custom external tools retain their separate labels and configuration. MCP Connections and Application Accounts remain separate resources.

## Experience

English is default and fallback; Simplified Chinese is supported. Date and time pickers follow the Console language, display the browser time zone, and preserve conversion from local selections to API timestamps. Shared tokens, primitives, menus, settings compositions and keyboard interactions provide consistent presentation. Search fields and collection filters retain visible borders. Collection headers place primary actions beside the title. Search and filters form a compact row above the collection; toolbar copy does not repeat the page description. On narrow screens, settings navigation collapses behind an expandable control and closes after selecting a section. Settings use the shared grouped sections and compact labeled rows for scalar fields, including theme, language, profile and security controls, and show profile save actions when the name changes. Related rows have fine inset dividers; section headings remain outside their surfaces. Model and environment configuration use shared sections and disclosures. Run tool calls and reasoning use the shared disclosure indicator, and long native content uses the shared scrollbar treatment. Password changes open from a settings action into a modal; password fields remain absent from the resting page and clear when the modal closes. Displayed settings identifiers provide a compact, muted copy icon that darkens on hover and keyboard focus. Successful copying briefly shows a check before restoring the copy icon; failures expose retryable feedback. Editable profile images open the file picker directly when clicked or activated from the keyboard, with a visible edit affordance on hover and focus. Resource collections emphasize names, descriptions and status; model collections group saved models by Provider without inventing capabilities or treating an enabled Provider as a verified connection. Relative timestamps retain the full date and time in their title; security and audit views keep their exact timestamps. Run inspection opens in a named dialog with focus restoration and a layout that fits narrow viewports. Lists and forms provide loading, empty, error, forbidden and stale-data states. The supplied a13n brand SVG is bundled locally.

Session transcripts keep a readable content width and follow live output while the reader remains near the bottom. Scrolling up preserves the reading position and exposes an explicit return-to-latest action. The composer remains available at the bottom, with attachments and next-run options in named dialogs. Cmd/Ctrl+Enter sends outside IME composition; ordinary Enter inserts a newline. Completed assistant messages offer copy feedback. Approval decisions are explicit per-action choices before submitting the complete response set.

Agent avatars appear consistently in the Agent list and detail heading, with a saturated color background and the first letter or character of the Agent name when no image is available. The fallback color is deterministically selected from the Agent ID, stays stable across reloads and renames, and uses a contrasting white initial. Creation previews derive the color from the draft name until an ID exists. Edit Agent details provides upload and removal under `agent.update`; successful image mutations refresh those surfaces and the metadata ETag while preserving unsaved name and description fields. Avatar uploads use the shared profile image picker and display progress and errors in the details dialog. New Agent authoring offers the same picker with a local preview before creation. After the Agent is created, Console uploads the selected image using the returned Agent ETag; a failed upload preserves the created Agent and selected file, provides a retry without duplicate creation, and allows continuing without an avatar.
