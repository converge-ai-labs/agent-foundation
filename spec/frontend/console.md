# a13n Console

## Product Boundary

Console is the browser application for Service, consuming the public API through a private client generated from `proto/a13n-service/`. API-serving Service roles serve the production build and API on one origin ([09](../a13n-service/09-runtime.md#console)); development uses a Vite proxy. The [design system](design-system.md) owns shared visual foundations and reusable UI components; [Console design](console-design-guidelines.md) owns Console-specific visual presentation.

Service owns permissions, resource versions, execution, durable state, and storage. Console owns navigation, forms, resource cache, localized presentation, and interaction rendering. Closing a page or stream leaves any active Run running.

### Shared Interaction Rules

Unless a section specifies otherwise, Console forms and mutations share these rules:

- **Optimistic concurrency:** Edits retain the resource version or strong ETag observed when the form opened; background refreshes leave that precondition unchanged. Conflicts preserve local edits and require an explicit reload before retrying.
- **Uncertain outcomes:** An unconfirmed creation directs the user to inspect the collection before creating again; an unconfirmed mutation requires reading current state before resubmission.
- **Secrets:** Write-only credentials and one-time plaintext values stay in mounted component state—outside query caches, mutation caches, and browser persistence—and clear on submit or dismissal.
- **Authorization:** Visible controls reflect viewer, runner, builder, and admin projections from [tenancy](../a13n-service/03-tenancy.md); the Service enforces all permissions.

## Navigation and Scope

A signed-out visitor sees sign-in. While the Service is uninitialized, sign-in creates the first administrator through the public bootstrap route and signs them in ([bootstrap](../a13n-service/03-tenancy.md#bootstrap)). Password and OIDC sign-in return to the requested Console path, including its query and fragment; OIDC carries the destination in its one-use flow and falls back to Console home for non-local targets.

### URLs and Workspace Scope

- Workspace pages use `/workspace/{workspaceId}/…`. Console lists readable workspaces in the Organization and selects the requested ID ([tenancy](../a13n-service/03-tenancy.md)); an unmatched ID renders a not-found view with workspace choices. Deep links preserve their requested scope; the root page selects the remembered accessible Workspace or the first accessible one.
- Every business request sends the selected workspace ID in `X-Workspace-ID` ([API](../a13n-service/10-api.md#paths-and-scope)), so avatars and downloads are fetched through the client with that header.
- Agent, Skill, and Memory details address resources by ID. Settings use `/settings/{section}` (personal), `/workspace/{workspaceId}/settings/{section}`, and `/organization/settings/{section}`. OSS runs a single Organization.
- Cache keys include authentication session and scope. Sign-out clears sensitive state, and workspace switches isolate cached resource data. Renaming a Workspace or Organization keeps existing links and cache identities stable.

### Sidebar and Settings Layout

- **Primary sidebar:** Starts with ungrouped Agents, Sessions, and Schedules; **Capabilities** groups Models, Skills, Memories, Connections, Credentials, Browsers, and Environments (Templates, Instances, Metrics) in that order; **Insights** groups Usage, Traces, and Findings. **API keys** sits fixed at the bottom and opens `/workspace/{workspaceId}/api-keys`.
- **Menus:** Workspace and User menus support pointer, click, and keyboard activation. The Workspace menu lists accessible workspaces with the current one marked. The User menu identifies the user and offers in-place Light, Dark, or Follow system theme selection, Settings, a Language link (`/settings/language`), and sign-out; Profile and Preferences live inside Settings.
- **Settings navigation:** Settings replaces the primary sidebar with a single searchable navigation ordered Personal, Workspace, and authorized Organization, plus a return action. Desktop offers an expanded sidebar and a persisted collapsed icon rail; narrow screens use an accessible drawer.
- **Personal settings:** Owns profile, security, appearance, and language. Theme changes apply immediately without losing drafts and persist in the browser; Follow system tracks OS changes while selected. Display language defaults to the browser's preferred languages (falling back to English); explicit English, Simplified Chinese, or Hindi overrides it until returned to System.
- **Workspace settings:** Owns profile, grants, invitations, member-key administration, service accounts and their keys, Providers, Webhooks, and audit. Providers group Model, Web, Environment, Connector, Memory, and Browser categories (editing requires workspace `write`, [resources](../a13n-service/04-resources.md#provider-resources)); Connections expose MCP or Composio setup. All categories use the label **Provider** consistently, and empty Credentials/Configuration groups are omitted. Cloudflare Containers supports automatic deployment only (using Account ID and API token from workspace administrators); its gateway is internal, deployment progress stays on the Providers page, and a verified Provider can launch the template editor preselected.
- **Organization settings:** Owns profile, grants, invitations, Workspaces, and audit. In both Organization and Workspace settings, **Members** contains member and invitation tabs with a direct Invite action. In **General**, organization administrators see a quiet link when a newer stable Service version is available and an inline notice for each [applicable security advisory](../a13n-service/09-runtime.md#update-notices). Release and advisory links open GitHub in a new tab. Administrators can hide an advisory for the current account and organization in that browser until the installed version or the advisory changes.

### Workspace Files

**Workspace Settings → Files** is available with workspace `read`. The page lists conversation uploads and files published by agents newest first, with the creator and a link to the source Thread when available. Search by filename and filter by source, status, or creator across the full collection; results use cursor pagination. Readers can download active and retired files. Writers can retire active files after confirmation, moving their bytes from active to retired storage and preventing new attachments.

The usage strip shows workspace totals for active assets, retired assets, and staged uploads. A disclosure shows the same breakdown per creator. The list filters do not change usage totals.

### Members, Grants, and API Keys

- **Members and SSO grants:** Organization and Workspace Members use the grants API to add, change, or remove roles at that scope. Organization administrators can select existing users from the organization directory; Workspace administrators without directory access can add an existing user by principal ID. Service account roles are managed in their home workspace. Member lists label synchronized grants **SSO** and overrides **Manual**; administrators can override a synchronized grant in **Change role** or restore it with **Restore SSO default**. **Invitations** shows history and allows revocation even when password sign-in is disabled; creating and resending require password sign-in.
- **Connect to app:** Agents with a default revision expose **Connect to app** in the list menu and detail header to users with `run` authority (archived Agents and Agents without a default revision omit it). The dialog shows the `a13n.dev` integration guide, current Service origin, and copyable coding-assistant instructions with the Agent ID, Workspace ID, and server-side environment variable references (excluding API-key values). It checks the user's keys for the Workspace, lets users reuse a key or create one in place, and **Create key** creates immediately with a random `auto-app-` name and no expiration. Dismissal is blocked while creation is pending so the one-time key is visible.
- **API keys:** Every API-key form requires exactly one Workspace. User keys belong to their signed-in owner; administrators can inspect authorized metadata and revoke them, while service-account keys use the account's home Workspace. Expiry presets are 1 day, 7 days, 30 days, 3 months, 1 year, and no expiry (day presets use elapsed days; month/year presets use UTC calendar arithmetic with month-end clamping at submission). Organization administration uses a login session. Revoking a credential stops new use; already accepted delegation follows the Service contract.

## Member password recovery

In Organization and Workspace **Members**, organization administrators can issue a one-time reset link for an active local password user when password sign-in is enabled. The confirmation identifies the selected member and, once confirmed, reports whether email delivery was queued; on single-organization deployments it also offers to copy the link inside the issuing dialog only. OIDC members recover access through their identity provider, and recipients use the standard password reset page. On single-organization deployments without SMTP, Forgot password directs the user to their organization administrator.

## App plugins

Console reads the organization's installed [App catalog](../a13n-service/15-app-plugins.md#organization-policy-and-management) through its authenticated client. Enabled entries with frontend metadata supply a prebuilt ESM default export, `AppContribution`, using bridge version `1`. Each entry and its styles load independently so a failed import, incompatible bridge, or invalid contribution leaves core routes and other Apps available. Disabling unmounts an App's contributions, and a failed background refresh retains the last confirmed catalog. Plugin modules run as trusted application code and share the document CSS.

### Host bridge

The production HTML import map resolves `@a13n/console` to that build's content-hashed ESM bridge entry under `/assets/` so the bridge and main app share one module graph; open pages keep their build's bridge identity across Service upgrades. Development maps `@a13n/console` to the Vite source. App bundles externalize `@a13n/console` and use its exported React with classic JSX inside the host's single React root and providers.

Service distributions ship a generated TypeScript declaration for the bundled bridge, exported via `python -m a13n_service.console_sdk <destination>` for editor and compiler types. Bridge version `1` identifies the contribution contract shape; Apps targeting newer named exports must require a matching Service release.

`useApp()` exposes the mounted App, current organization/workspace, `queryKey(...parts)` (scoped by App, organization, and workspace ID), and `request(path, init)`. `request()` normalizes relative paths under `/api/v1/apps/{app_id}/`, rejects paths escaping that namespace or containing backslashes, attaches `X-Workspace-ID`, and reuses the host transport (session auth, CSRF, read retries, error handling, cancellation, and logout shutdown). Organization settings use the remembered or default landing workspace (`workspaceId` is undefined if none is selected); business requests require a selected workspace.

### Contributions and ownership

| Contribution    | Address and behavior                                                                                                |
| --------------- | ------------------------------------------------------------------------------------------------------------------- |
| `pages`         | Workspace routes `/workspace/{workspaceId}/apps/{appId}/{pageId}/*`, listed under Apps in primary navigation        |
| `settings`      | Workspace or Organization sections keyed `app.{appId}.{sectionId}`, rendered in the existing settings layout        |
| `workspaceHome` | Replaces `/workspace/{workspaceId}` only; root workspace selection lands there, while Agents stays at its own route |

Each page declares a local `id`, `label`, optional `description` and `permission`, and a React component; settings sections add `scope: "workspace" | "organization"`. Local IDs match `^[a-z][a-z0-9-]*$` and must be unique within their contribution kind and settings scope; duplicates fail loading. Labels and descriptions accept literal strings or `{en, zhCN}` translations.

App navigation filters pages by workspace permission: zero visible pages hides the entry, one shows a direct link, and multiple appear in declared order under one collapsible group (defaulting to the catalog name, optionally overridden by `navigation.label` and `navigation.icon` from `puzzle`, `robot`, `chart`, `calendar`, or `lightning`). Deep links expand the active group and match subroutes; in the icon rail, opening a multi-page App expands the sidebar; mobile drawers close on selection.

Unknown or disabled App routes render a not-found view with a link back into Console. Subroute navigation preserves component state within the same App page and organization/workspace scope and resets it on scope change. Module and render errors are isolated to local recovery boundaries so an App failure cannot take down the primary shell. Multiple enabled `workspaceHome` owners render a conflict view with a link to Agents.

### Organization management

Organization settings lists installed App plugins with identity, version, and enablement. Updates use the organization ETag and policy endpoint, wait for the committed response before updating the registry, and keep the last confirmed state visible on failure or uncertainty. Installation and upgrades are operator actions followed by Service restart; active Runs retain their accepted activation.

## Egress Credentials

Capabilities → Credentials manages workspace [egress credentials](../a13n-service/04-resources.md#egress-credentials). The searchable, paginated list displays name, allowed domains, state, credential version, and update time, with search and state filters applied across the full collection. Workspace `read` allows metadata and application-state inspection; `write` allows creation, metadata edits, rotation, revocation, and explicit active-Session synchronization.

- **Lifecycle and forms:** Creation requires a name, token, and immutable exact allowed domains. Rotation accepts a replacement token without pre-filling the previous value. A collection refresh preserves open creation drafts; a pending request may finish after dismissal (updating caches without reopening the dialog) while blocking reopening the same operation until it settles. Metadata conflict recovery preserves only fields changed by the user. Revocation confirmation states that new use stops and the stored token is removed, active Sessions apply removal asynchronously, idle Sessions may keep the old value until next use or expiry, and upstream tokens remain managed externally; revoked credentials stay readable and cannot be restored or rotated.
- **Session application view:** Saving commits a new credential version in Service; each Session reports its applied version independently. The mounted application view polls paginated metadata every 10 seconds while mounted (and the Environment inspector's Credentials disclosure polls only while expanded). Rows show environment, Thread, binding version, variable, injection domains, applied/current credential versions, confirmed time, and retry state, distinguishing applied, awaiting synchronization, retry pending, next use, native creation, and unconfirmed states. Whole-collection summary counts appear above the paged list, counting each selected binding version once and marking it confirmed only when every referenced variable is applied (with revocation shown as removed only after the revocation version is confirmed). Reads and manual synchronization never connect or attach idle Sessions.
- **Agent and Thread bindings:** The Agent editor's Environment section edits optional default Session configuration for new primary bindings (outbound mode, destination policy, and credential references with variable names and injection domains) plus a schema-validated JSON dialog for other Session settings; a usage preview shows variable references and HTTPS header examples without secrets, unavailable saved references stay preserved, removing defaults publishes explicit `null`, and Agent import supports remapping unavailable credential IDs. Each Thread environment mount edits its persistent Session binding under the Thread ETag (requiring an interactive Thread and workspace `run`), applying to later admissions while Run details display the frozen binding version and current credential versions separately.

## Browsers

The workspace Browser page manages [Browser resources](../a13n-service/14-browsers.md): managed creation, external CDP attachment, status and classified failure, retained-profile start/stop, and terminal release. Retention views separate idle stop from terminal deletion (including legacy `idle_seconds`). Provider configuration uses registered Browser type schemas.

A Session's Thread Browser action edits the desired binding, tab access, and preparation separately from any accepted Run's frozen binding, pairing a Thread version read before the binding read so refreshes cannot mix versions.

Take control, renew, and return control follow the Service Browser control episode and finite lease. Only the authorized controller opens sensitive viewer credentials. `iframe` viewers keep supplier presentation; self-hosted `vnc` viewers use the authenticated same-origin WebSocket relay and noVNC (`wss` over HTTPS). Closing the viewer releases only the local connection and credentials. Console displays control state and lease expiry explicitly and requires manual renewal.

## Webhooks

Workspace administrators manage [subscriptions](../a13n-service/04-resources.md#subscriptions) in Settings → Webhooks. The paginated collection shows name, endpoint, event count, filter scope, and enabled state; detail pages split into Deliveries and Configuration tabs. Non-administrators have no access to these settings or reads.

- **Subscription forms:** Create and edit forms group Run, Attempt, Schedule, and Occurrence lifecycle events using wire names and require at least one event. Optional Agent, Session, Thread, and Schedule filters combine with AND (empty matches the Workspace; unavailable Agent catalogs preserve saved filters). The form clarifies Attempt vs. Run completion and Schedule vs. Occurrence completion; Schedule detail entry points preselect Schedule/Occurrence events and the Schedule ID. An empty secret field generates a secret on creation and keeps the existing secret on edit; creation reveals the signing secret once in the open dialog. Stale edit recovery adopts newer values for untouched fields. Disabling and deletion note that already queued deliveries continue.
- **Schedule detail layout:** Schedule details keep Enable/Pause and Run once visible when authorized, and place Edit schedule, Add Webhook, and Archive in the More actions menu. Timing, next trigger, and unfinished work form one responsive summary; manual pause appears in header status while exceptional pause reasons and completion context stay visible. Execution-permission guidance is expandable.
- **Deliveries:** Delivery views follow [lifecycle webhooks](../a13n-service/07-facts-and-delivery.md#lifecycle-webhooks), distinguishing pending, delivered, and stopped retries with endpoint, attempt count, timestamps, last error, and event payload. Dead deliveries with a saved signing secret offer confirmed redelivery (reusing original ID, endpoint, payload, and secret so receivers must deduplicate); acceptance queues a new attempt, and refused redelivery refreshes the list.

## Resource Editing

### Agents, Subagents, Tools, and Presets

Agent authoring uses a full-page form with a sticky save/discard footer, header metadata editing, version history, and a trial link to a dedicated Session page (requiring saved executable changes). Management actions that reload the form require saving or discarding first.

- **Layout and sections:** Creation shows name, optional description, and avatar followed by instructions; details place the resource-reference copy marker beside the title. Model and each peer capability use separate surfaces; Model settings disclose beneath the model choice with labeled parameter rows and in-place request JSON. Environment follows Connections and separates existing instances from templates (mutually exclusive, showing runtime providers, preserving saved selections if provider metadata is missing, and keeping offline eligible clients selectable). Capabilities lists Skills and Connections with inline searchable additions; attached Connections expose a header remove action while collapsed (effective on save, without deleting the shared Connection). Tools lists built-in groups from the [Service catalogue](../a13n-service/04-resources.md#agents) (showing `model_name` beside the localized description or `display_name` fallback). Media understanding is a separate capability section collapsed by default. **Advanced** (collapsed on edit, expanded read-only) contains Memory (spaces and individual memories), Auto review, Tool availability, Execution, Context summary (`Summarize` tool switch; automatic compaction remains active when disabled), and JSON. Validation expands the section containing an error and preserves input.
- **Subagents:** Dedicated section after Capabilities. Parent execution mode is **Async** (`async`, default for new drafts) or **Inline (sync)** (`inline`, preserved when omitted on saved configs). Each named child pins an exact Agent revision from the workspace directory, with a unique model-facing name, optional description, and disclosed context, environment, and usage settings (inline borrows the parent environment and cannot suspend for deferred feedback; async chooses shared, dedicated template, or none, and limits usage overrides to model request counts). Switching modes preserves fields and flags incompatible limits. Dynamic policy configures `enabled`, additional allowed Models, default Model, and default thinking effort (parent Model is always eligible; enabling dynamic spawning in inline mode fails validation).
- **Tool controls and Auto review:** Controls distinguish Allow, Ask, Automatic review, and Deny per catalogue support. Automatic review requires an Agent-level reviewer model and configures risk threshold, flagged action, custom instructions, per-tool rules, and advanced shell/failure/timeout/model settings in a dedicated panel. Missing saved references stay visible; catalog failures preserve selections.
- **Tool availability:** Offers **Provide tools directly**, **Discover tools on demand** (proxy), and **Native tool discovery** (`tool_search: {"mode": "native", "sources": {...}}`). Source choices and proxy drafts survive mode switches. On-demand discovery enables automatic grouping by default (Computer, Browser, Platform tools, MCP tools) using Service catalogue labels and defaults; **Add tool source** offers Files, Terminal, Web, Memory, or Asset, while a **Provided directly** summary shows the rest. MCP supports individual connection exclusions. Manual grouping lives under collapsed **Advanced grouping**.
- **Platform toolsets and Plugins:** Platform toolsets sit under collapsed **Advanced / Platform Features**; `inherit` displays the catalogue default. In editable Agent forms, `platform-operations` is derived automatically (included while any enabled platform group has an enabled tool) and saved with the draft; read-only Run and preset views show their recorded selections. The **Plugins** section edits named instances from the [installed Harness plugin catalog](../a13n-service/08-providers.md#installed-harness-plugins) with scalar forms and JSON, updates tool-discovery memberships on rename/removal, and keeps unavailable saved instances inspectable for explicit removal.
- **Revisions and managed presets:** Saving creates an immutable revision (optionally set as default; **Set as default** switches to an existing revision without copying, while creating from an earlier revision is distinct). Archive, unarchive, duplicate, and retirement preserve readable history. Composer and Finding reuse this editor for model, supported settings, and supplemental instructions ([managed preset revision edits](../a13n-service/04-resources.md#managed-preset-revision-edits)); official deployment instructions appear read-only, Composer also edits its workspace-wide default environment, and Export merges official guidance with the saved supplement into a standalone custom config.

### Skills and Memories

- **Skills:** Skill collections display a read-only built-in catalog alongside workspace Skills (with GitHub/ZIP source and version filters before pagination). Detail views show Files (`SKILL.md` selected initially, Markdown preview/source, download fallback for binary/oversized files), Versions, and Used by agents. Imported content is never executed and never fetches remote media automatically. ZIP/GitHub import and new-version forms validate before publication.
- **Memories:** Collections show name, kind, type, update time, and (for file memories) file count and stored size, filtered before pagination. Creation picks file memory (PostgreSQL with guidance and always-loaded paths) or record memory (bound to an enabled memory Provider, optionally adopting an existing namespace with a deletion warning).
  - *File memory details* offer Files (tree with always-loaded markers, Markdown preview/source; `run` users create/edit/rename/delete under file ETag), History (filtered by file and Run in URL, with diffs, precondition-checked restore, and configuration-authorized history purge noting existing Run histories retain prior reads), Organization, and Configuration.
  - *Record memory details* offer Records (provider-ordered pages or semantic search with scores; `run` users add, replace full text up to contract bounds, or confirm deletion; unconfirmed provider writes prompt reload) and Configuration (read-only kind/type/provider/namespace, ETag-checked edits, deletion warning).
  - *Guidance policy:* File memories and Spaces use the backend guidance catalog (General or General with daily records, visible Custom guide, collapsed Advanced for browser-initialized time zone and full system rules). Guidance modules independently toggle topic knowledge, dated events, and session notes (`null` inherits preset; empty keeps common rules; full system override disables modules until restored). Switching presets resets modules to inherited while preserving Custom guide and time zone. Stale configuration saves merge only user-changed draft fields.
- **Memory organization and candidate review:** File memories and Spaces share the Organization flow (model, optional instructions, direct or candidate output—Console defaults to candidate while API defaults to direct—explicit Sessions with timezone-aware seal-time bounds, and run limit; requires `write` and `run`, plus enabled Space). Opening a task navigates to `/workspace/{workspaceId}/memory-organizations/{organizationId}/review` (`?path=` deep-links files, including unchanged/deleted). Each exact-sequence read shows complete saved-baseline and candidate text with split/inline diff, Markdown preview/source in File mode, and session-local review marks. **Apply all changes** publishes atomically against the reviewed sequences (blocked if target changed since admission); **Replace entire target** requires destructive confirmation listing exact deletions, overwrites, and restores. Unconfirmed applications block retries until explicit reload. Standalone automatic policies carry their own configuration ETag, separate from the Memory ETag; Space policies live in Space configuration.

### Models, Providers, and Environment Templates

- **Model creation and details:** One modal flow selects an enabled Provider (or creates one inline), then chooses a discovered/catalog model or enters an upstream ID manually. Provider `supports_model_discovery` selects account discovery (scoped by Workspace and Provider; reauthorization clears old choices; discovery failures keep manual entry available and never fall back to public metadata). Catalog/discovery selection prefills capabilities and context except `document_understanding` (PDF stays off by default). Saved details group name/description, enablement on the left of the fixed Cancel/Save footer, connection (Provider + upstream ID), capabilities/context grid, pricing, and collapsed Advanced controls. Switching schemas preserves local overrides and flags incompatible fields; explicit `null`, `false`, `0`, and `""` values survive editing. Optional connectivity tests run explicitly against saved configuration. Multi-alternative credential schemas clear the previous secret draft when switching auth methods.
- **Model Advanced:** Edits `config.settings` via common fields (thinking effort, output limits; Responses adds reasoning summary, response storage defaulting off, and Use WebSocket mapped to `config.settings.openai_transport` as `"websocket"`/`"http"` without materializing omitted transport) plus a full Settings JSON editor that preserves unrepresented fields. Also edits `config.characteristics.image_input` (preparation toggle where off writes explicit `null`, GIF support, max image count, max base64 size in MiB = 1,048,576 bytes stored as exact integer bytes; numeric inputs reject blank, negative, non-finite, and fractional counts).
- **OpenRouter Model routing:** For `openrouter.chat_completions`, Advanced exposes sort, data collection, zero data retention, fallbacks, and provider allow and ignore lists when the API schema includes `openrouter_provider`. These fields edit the same Settings JSON, preserving other routing keys. Provider default or an empty list input removes the corresponding key; removing the last key omits `openrouter_provider`.
- **Providers and Web tools:** Provider types are immutable after creation; name, config, credential replacement, and enablement submit atomically under the resource precondition. Web search and scrape select compatible providers independently; fetch/download need no provider. Connection tool scopes use the selected MCP/Composio catalog while keeping absent saved tools and catalog errors visible.
- **Environment templates:** One configuration panel with a global **Fields / JSON** switch (preserving drafts across switches). Fields groups **Provider platform settings** (image/template/snapshot, CPU/memory, network, mounts, lifetime, provider advanced fields, collapsed Environment variables—ordinary readable config, empty values valid, blank/invalid/duplicate names blocked, preserved across Docker preset switches—and Kubernetes native editors), **Runtime settings** (desktop enablement/viewing, execution connection, advanced Host integration, reclamation policy), and **Envd settings** (static heading with collapsed disclosures for capacity, file/output sizes, retention/cleanup, deadlines, Session lifetime, and protocol sizing; inputs label bytes/seconds and show effective defaults without writing overrides; [Envd startup settings](../a13n-service/06-environments.md#envd-startup-settings)). Schema-driven arrays expose per-item controls (e.g., Docker host mounts with source, target, read-only) or validated JSON fallback.

### Command environment overrides

Execution fields use behavior-oriented labels and descriptions for long-running tools, new-message handling, and foreground wait. Agent controls display Service defaults for omitted tool mode and steering and `"Default"` for omitted wait; Thread and Run overrides label inheritance as `"Use agent settings"` and `"Use thread settings"` without writing overrides when untouched.

The shared execution-policy form edits ordinary readable environment-variable maps across Agent defaults, Thread policy (whole-map replacement on save; removing all rows resets that layer), and single-Run options, and renders the accepted map in Run details. ## Agent Configuration Transfer

When creation is authorized, the Agent list and empty state expose one **Create agent** menu (**Create with AI** when available, **Create manually**, and **Import YAML**); readable saved revisions offer **Export**. Console owns the YAML transfer format ([resources](../a13n-service/04-resources.md#operations)): a mapping with exactly `schema_version` (`1`), `name`, `description`, and `config` ([AgentConfig](../a13n-service/04-resources.md#agents)), at most 1 MB, YAML core schema with string keys, finite numbers, bounded nesting, and no aliases or custom tags. Export serializes the selected saved revision (excluding credentials and dependent resource creation) with overview, YAML copy, and download.

Import accepts a file or pasted YAML, showing editable name/description, searchable replacement references, and full config inspection; switching back to YAML preserves edits and remappings. File text stays in form state only. In-flight creation blocks duplicate submission and dismissal; success refreshes the list and opens the created Agent.

## Connections and Environment Inspection

### Connections

Connections separate configured source from authorization state ([connection contract](../a13n-service/04-resources.md#connections)). MCP and Composio share one collection and editor. Setup explains upstream prerequisites including the exact Service OAuth callback URL. OAuth uses the Service's returned action and one-use callback/state contract; callback parameters are stripped before rendering, lost completions direct to status inspection, and reauthorization keeps the Connection identity.

- **Row actions:** An always-visible trailing menu exposes **Details** plus `write`-gated **Enable/Disable** and **Revoke** (omitted when neither credential nor active flow exists unless reauthorization is required; labeled **Cancel authorization** when only a flow exists without a credential, and **Revoke authorization** when a credential exists).
- **Status labels:** Uses `status`, `authorization_pending`, and `enabled`: disabled shows **Disabled**; enabled `pending` shows **Not authorized** or **Authorizing**; `reauthorization_required` shows **Reauthorization required** or **Reauthorizing**; `ready` shows **Connected** (plus a **Reauthorization in progress** note while a new flow is active). Mounted views refresh while a flow is active. Without the original in-memory redirect URL, authorization offers **Restart authorization** (replacing the prior request).

### Environments, Pairing, and Diagnostics

Environment pages separate Providers, Templates, and instances using Provider schemas plus a JSON editor (preserving local input across type switches).

- **Instances and lifecycle:** Details separate desired Thread mounts from frozen Run mounts, active use, retained policy, lifecycle state, and external ownership. Pending stop/destroy stays pending until confirmed; deleted instances remain tombstones. Trailing row menus expose **Details** plus capability- and `write`-gated **Stop/Delete** (reading the single instance's current state and ETag when opened; external targets omit Stop). Desktop preview uses `desktop_preview` (`connection_unsupported` disables with explanation; `not_configured` omits it).
- **Template creation and preparation:** Combines runtime selection (mutually exclusive cloud sandbox vs. own infrastructure tabs; unclassified extensions separate; tab switches restore or clear the active runtime so hidden configs cannot submit), enabled Provider selection (with inline Provider creation), and recipe configuration. Automatic preparation distinguishes headless Envd from desktop preparation and preserves custom image/snapshot/template drafts; instance progress uses server-frozen stages and timestamps with fenced retry on confirmed failure.
- **Working directory and Run options:** Reusing an existing instance or external target offers an optional working directory (empty uses provider default; switching targets clears it). Run options allow choosing a primary environment for the next Run (inherit Thread mounts, omit primary mount, reserve from template, or reuse an existing instance) without mutating Thread mounts. HTTP envd registration is connect-only (endpoint, credential, working directory, bounded discovery) with no managed lifecycle controls.
- **Connect my computer:** Instances offers **Connect my computer**, creating a short-lived [Console connection request](../a13n-service/06-environments.md#console-pairing) and opening the installed macOS app (with a visible link and credential-free terminal fallback) to prove any saved registration. Recognized computers show live online/offline state and skip pairing; new registrations display claimed machine, directory, and permissions, require entering the six-digit code from the native app/terminal, and state that workspace `run` principals may use the computer and that the directory is not a filesystem confinement boundary. After approval, connection observation continues until online or deadline (refreshing environment lists when online) without altering Agent/Thread selections.
- **Kubernetes templates and diagnostics:** Kubernetes templates group connection, containers, resources, args, env/refs, storage, volumes, scheduling, and metadata, preserving unedited native fields and offering JSON editing; reclamation separates idle deletion, preparation deadline, and failed-instance retention (no stop/resume). Instance diagnostics and bounded container logs require explicit user action (`run` + Provider use), separating lifecycle stage, native observations, and Envd readiness without polling on focus/reconnect. A versioned finite debug hold requires `write`, postpones automatic cleanup, and never blocks explicit deletion.

## Skills

Skills lists built-in and workspace packages in one table with a shared Source filter (**Built-in**, **GitHub**, **ZIP**). Built-in packages appear on page 1 of unfiltered results and in Built-in-only results, with full-catalog client search and read-only file browser/download (unavailable version, usage count, and update time show a dash). ## Infrastructure Metrics

Environments → Metrics uses the durable dashboard model and authorization in [Environment monitoring](../a13n-service/13-environment-monitoring.md), sharing one panel renderer and editor across the built-in overview and custom dashboards. Builders edit names, panels (time-series or stat), units, legends, and desktop grid layout (with numeric keyboard positioning; narrow screens stack without rewriting desktop layout).

- **Drafts and queries:** Edits stay in workspace/dashboard-scoped session memory until Save (warned on reload, cleared on reload or auth change; Save/preset restore freezes controls under the opening ETag). Target selection is viewer-local. Typed queries target the selected Environment or Device; custom PromQL selects its own data source and runs only for workspace administrators, with syntax highlighting, local completion, and preview.
- **Charts:** Share time range and cursor, support legend toggles and drag zoom, and show missing samples as gaps. Absolute ranges and zoom pause live refresh until **Back to live**; hidden tabs pause refresh. Refresh keeps prior data with a stale indicator; identity changes never reuse another target's samples. Requests deduplicate, cap concurrency, cancel when unobserved, and display truncation notices when bounded.
- **Data sources and devices:** Separates collection, export, and historical query settings; administrators can keep, replace, or clear each credential independently. Connection testing probes the saved query endpoint. Environment creation defaults to no monitoring; details separate desired settings, provisioning receipts, manual external setup, and collector reload vs. scrape health. Device registration is separate from executable Environments, revealing attachment tokens once in component state.

## Sessions and Runs

Session UI uses the domain terms **Session**, **Thread**, and **Run** (会话、线程、运行 in Simplified Chinese).

### Session List and Ownership

- **Collection and sorting:** Session lists use the main content area with server-side sorting by Updated, Runs, and Cost (persisted in URL; unpriced requests marked; unavailable cost sorts last) and URL-persisted search/filters (title, source, label, text, exact Session/Thread ID, application, Agent, status, trigger, activity). Compact rows show the latest Run's Agent avatar, stable title (or untitled + ID), secondary Agent + label chips, plain-text source column (origin name + application caption, dash if absent), status (with localized trigger tooltip), run count, and update time. Clicking source applications or labels narrows the list. Row actions offer **Debug** plus **Inspect execution** and (for runners of Console-started Sessions) **Continue thread** (opening Chat on a unique `origin = new` root or offering a paginated root choice).
- **Console ownership:** Only Sessions started in Console (labeled `a13n.console=debug` with origin `{application: "a13n-console", name: "Console"}`) expose interaction controls. Other Sessions are observation-only in both Chat and Debug (read-only transcripts, pending requests, queued messages, mounts, Run details, and navigation remain available). Runners can edit a Console-started Session's title and origin under its ETag (origin edits replace the object; blank clears the field).
- **Opening and following:** Opening a Session reuses its collection summary and loads route code, target resolution, Run detail, newest message window, and anchored Run index in parallel. Opening a Thread follows its latest Run (automatic successors preserve transcript and unsent draft); explicit Run links and Debug navigator selections pin historical Runs until **Return to latest**.

### Chat, Debug, and Branching

- **Chat vs. Debug:** Chat and Debug switch in place, preserving the followed Run in the URL. Without a URL level, child Threads and non-Console Sessions open in Debug; other Threads open in Chat. Chat shows input, replies, tool activity, questions/approvals, and failures in observation order (omitting `display: false` input); Debug exposes Run/attempt boundaries, hidden/reminder inputs, model/tool calls, reasoning, usage, subagent correlation, and raw data. Failed model calls report provider HTTP status and error message or exception type. Pending/interrupted tools clear working indicators once sealed; a failed or cancelled Run stays in history for the next message, and re-running a stopped Run's input resubmits it with its original options and pinned revision.
- **Rich rendering and assets:** Chat replies render Markdown with inline/display KaTeX math (`$…$`, `$$…$$`, `\(…\)`, `\[…\]`; escape literal dollars as `\$`) and [static Mermaid previews](design-system.md#conversation-diagrams) with source view and copy. `publish_asset` tool outputs appear as downloadable attachments in Chat using Workspace asset metadata and permissions (marking retired/unavailable files).
- **Usage, context, and Run details:** Unknown usage/cost stays unknown (never zero); model and tool counts stay separate without double-counting nested calls. The Debug header reads model totals from [usage summary](../a13n-service/07-facts-and-delivery.md#usage-records) and opens **Session usage** (Spend, Tokens with cache hit rate, and the current Thread's last-call Context window estimate from [context usage query](../a13n-service/07-facts-and-delivery.md#usage-records), plus per-model and paginated per-Run breakdowns). Run headings and Run Details read the same recorded Run usage, followed by identifiers, configuration, frozen mounts (with file memories linking to Run-filtered History), attempts, lineage, raw record, and paginated [retained tool executions](../a13n-service/05-runs.md#retained-tool-executions) (read-only live/retained Shell output and versioned result fragments kept only in the open inspector).
- **Branching (Fork):** Sealed Runs offer **Create branch from here** (Chat) / **Create branch** (Debug) to users with `run` authority via the [fork command](../a13n-service/05-runs.md#waiting-interrupt-and-fork). The dialog pins the origin Run's Agent revision and options, requires a new message, explains waiting/failed/cancelled origin semantics and shared file-environment/memory writes, and offers **Use a new environment** (omitting original mounts, falling back to Agent default). Unchanged retries reuse the idempotency key; success navigates to the new Thread/Run in the current view level.

### Thread Navigation, Attribution, and Composer

- **Thread switcher and Run navigator:** The Session header switches between independent Threads using paginated reads loaded on open (using server-provided global origin positions and counts). The Debug Run navigator lists only the current Thread's Runs with server-side pagination, deep-link anchoring, and URL-persisted sorting by chronological order, cost, model calls, or duration (unknown values sort last; ties keep chronological order; Run numbers and previous/next controls remain chronological). Manually selecting another Run shows a skeleton until its detail and newest message window load, starting at the top of the viewport while keeping the navigator's scroll and focus intact. Delegation links resolve children via `GET /threads?origin=child&origin_run_id=...`.
- **Author attribution:** Ordinary messages show the author's avatar, current profile name (not submission-time snapshots), and submission time, adding localized **"You"** only when Principal ID matches the signed-in user. Service accounts show a distinct icon and label; duplicate names disambiguate via email (or short ID). A keyboard-accessible popover shows full name, email, account kind, and Principal ID with copy actions. Attribution uses `source_entry_id` (ordinary/queued inputs) and `metadata.source_id` (steering), batched and cached via [Session-scoped author lookup](../a13n-service/05-runs.md#reads).
- **Composer, options, and memory:** Starting a conversation exposes a session-memory toolbar control (**Follow agent** vs. **Custom** space/mount/access selection; immutable once the Session is created). New conversations and next-message composers share Run options (Model, thinking effort, optional instruction replacement, plus collapsed Execution policy and Advanced overrides/revision pin); a successful new-run submission clears overrides while failures retain them. Pending inbox entries live in a compact sticky dock above the composer (shown only when non-empty) and support ETag-checked edit, withdraw, and reorder. Command+Enter / Ctrl+Enter sends outside IME composition; Enter / Shift+Enter inserts a newline; with an empty composer and an interruptible Run, Send becomes Stop and Escape requests interruption.
- **Waits and AG-UI:** Question, approval, and client-tool cards bind exact waiting Run and tool-call IDs and submit one complete resume batch (including mixed waits; every pending approval and call requires an explicit result; continue-without-feedback submits denials and failed calls after confirmation). Stale cards cannot answer a newer wait. Waiting summaries follow `wait_reason` (approval, call results, or both). Console validates AG-UI 1.0 events with upstream schemas, isolates root and inline-child display scopes via `subagentRunId`, and nests child activity under its delegation without promoting child text to a root reply.

### Conversation Files

**Files** opens a resource panel for the current Thread alongside the transcript. It lists asset attachments and verified `publish_asset` results from the Thread's Run lineage. Older Runs are searched in batches on request. The panel marks the file list as potentially incomplete when Run display content is missing. Selecting a file in the list or a transcript file chip opens its preview in the same panel. The preview toolbar offers a return to the file list and a separate Download action. On phone-width screens, Files occupies the conversation workspace and closing it returns to the transcript at its existing scroll position. Switching to Browser or Desktop closes Files.

Console uses the existing workspace-scoped asset reads and prepares previews in the client. Text and code are read-only, Markdown offers rendered and source views, JSON is formatted, and CSV opens as a bounded table. HTML and SVG appear only as source. Raster images render from local Blob URLs; PDF uses the browser's native viewer and offers a new-tab action. Unsupported or oversized files retain Download without loading preview content. Console restricts preview media types independently of the Service [download protections](../a13n-service/10-api.md#representations) on the content endpoint.

### Display Recovery

Once authentication and Workspace are known, deep links load Session, Thread, selected Run, Run list, and newest display in parallel and subscribe to the [session stream](../a13n-service/07-facts-and-delivery.md#the-session-stream). `thread` frames update Thread, Run views, and loaded list metadata monotonically; membership changes refresh affected entry pages.

Active Runs render from stream `items` and subsequent deltas; sealed Runs read their committed display. Earlier content loads on demand in bounded windows (Debug loads one ancestor's newest window per Earlier Runs request; Chat loads bounded batches while scrolling up), preserving reading position before paint. After a `gap`, the Run marks output missing until the next `items`; reconnect replaces unfinished display from the fresh snapshot and rereads Runs that ended while disconnected. Output replaced by a newer attempt is discarded, `in_progress` items on sealed Runs render as interrupted, and Run status always comes from the Run record.

## Usage

Insights → Usage reads the Workspace [usage analysis API](../a13n-service/07-facts-and-delivery.md#workspace-usage-analysis) over 7- or 30-day presets or a custom range up to 366 days, bucketed in the browser timezone. Refresh reloads the view and advances a preset's end time.

- **Overview and trends:** Shows recorded USD spend (flagging unpriced requests as a known subtotal), started Runs, model requests, mean sealed Run duration, input/output tokens, cached input tokens (counted within input), and weighted cache rate. Daily charts toggle spend vs. total tokens, stacking the top five Agents or models plus a neutral Others series with interactive daily popovers. Chart and table Agent/model grouping stay synchronized (the admin-only member table keeps the chart grouped by Agent); window or grouping changes reset pagination.
- **Admin member breakdown:** Workspace administrators see a **By member** breakdown (with User / Service account labels and disabled status), a paginated page-level Member picker, and a **View usage** row action that filters the overview, trends, and Agent/Model breakdowns by `principal_id` (displaying a clearable scope banner). Readers without workspace `admin` neither see nor query member-filtered endpoints.
- **Agent Session sheet:** Activating an Agent opens a right-side sheet (full-width on narrow screens) listing that Agent's Sessions in the active window/member scope ordered by spend descending (unknown last), with server pagination and Debug links. Dismissing restores focus to the trigger. Browser history retains the selected Agent, window, member scope, chart controls, and pagination for Back navigation from a Session.

## Trace Inspection

Trace browsing follows the authorized [trace query contract](../a13n-service/07-facts-and-delivery.md#trace-query) and links from Runs/attempts. Telemetry availability and status are independent of Run outcome.

- **List and queries:** Lists show Trace ID, start time, duration (seconds), cost (USD), and bounded root plain-text previews (omitted in compact mode). Sorting supports start time, duration, or cost across the selected range with inclusive min/max duration and cost filters (edited in one popover and shown as removable chips). Default latest-first browsing uses native pagination; metric queries use whole-window Service search with keyset cursors (unknown values sort last; decimal costs compare without floating-point loss; backend limits/errors surface explicitly).
- **Details and observations:** Root detail and the parent-aware observation call tree load concurrently using payload-free overview fields; selecting a child loads its full detail on demand. Costs sum observation-local USD values once per identity (missing costs stay unknown; partially loaded traces show a loaded subtotal). Content offers safe preview and raw JSON with copy, continuous scroll loading for long sequences/values, offscreen virtualization preserving measured height, and bounded whole-payload syntax highlighting. HTML is never executed and remote media is never fetched automatically. Authorization or not-found errors hide cached trace content.

## Agent Composer

Agent Composer is an ordinary visible, duplicable built-in Agent ([resources](../a13n-service/04-resources.md#agent-composer)) whose conversations use standard Sessions, Threads, tool approvals, and caller authority.

- **Preparation:** Before the first submission of a new Console conversation with Composer or Finding, Console calls its preparation endpoint when the user has workspace `write` (skipping for explicit revision pins, non-writers, or 403 `forbidden` when a default revision exists). If a writer starts Composer without an enabled Model on an enabled Provider, Console opens inline model creation first and resumes on save. Completed preparation is reused across failed submission retries. New Composer conversations show the revision's default environment with a Run-only override chip (including **No primary environment**).
- **Entry points and private cards:** Usage, Webhook, and Credential pages expose **Ask Composer** to permitted runners, passing page/resource/filter navigation context. Console renders `configure_webhook` (requires `admin` + `run`) and `configure_egress_credential` (requires `write` + `run`) as native private cards validated against generated Composer schemas: proposed nonsecret fields stay fixed, existing-resource cards preserve the proposal's version, signing-key creation reveals the key once locally before resuming, input secrets clear on send, and only allowlisted statuses/IDs/versions return to batch resume. Saves never auto-retry; unsuccessful outcomes require reconciliation and a new proposal, while a mounted successful card retries only Run resumption.

## Findings

Insights → Findings provides **Findings** and **Analysis history** tabs (persisted in URL).

- **Findings list and review:** Lists workspace findings independently of trace backend availability, with pre-pagination filters for category (localized labels), severity, assessment, and open/closed state. ## Computer Use configuration and observations

The session actions menu opens **Environments and memory**, where `run` users on an interactive open thread configure per-mount Computer action ceilings (**Off**, **Observe**, **Interact**, or **Custom**; presets preserve non-Computer actions; edits apply to later Runs while Run Details displays each frozen mount ceiling).

Each mount displays Computer permissions and desktop status separately. Desktop status starts as **Not checked** and updates on explicit check (`run` authority), reporting unsupported, not running, observation-only, ready, or failed without starting the environment or capturing pixels. Tool entries with a retained image reference offer an authenticated screenshot preview (releasing object URLs on close).

### Desktop control

Interactive open root Threads with `run` authority show a **Desktop** icon beside **Browser** in the session header (mutually exclusive right-side panels; absent on child and externally controlled Threads). Desktop selects a mount with `desktop_enabled=true` and uses the [Computer-only control contract](../a13n-service/06a-environment-management.md#computer-only-desktop-control), persisting across successor Runs and closing on workspace/Thread change.

Opening Desktop connects a read-only viewer displaying automation, `draining`, human, or returning status, controller ownership, and lease expiry. **Take control** requests admission closure and connects input once authorized; **Renew control** extends the human lease explicitly; **Return control** requests cleanup without altering Run state; closing Desktop disconnects locally and clears credentials while keeping the lease. Input stays disabled until a valid control grant connects; metadata/renewal failure, generation/episode change, expiry, or disconnect disables input and disposes the connection.

### Dynamic subagent configuration

The Agent editor's Subagents section configures dynamic policy (`enabled`, additional allowed Models, default Model, and default thinking effort via the selected Model schema; the parent Model is always eligible, and enabling dynamic spawning in inline mode fails validation). Agent edits and Run overrides replace the whole policy. Run configuration views display task snapshots, actual Model/thinking, and source Agent; snapshot resubmission and retained forks preserve the snapshot source and frozen policy.
