# a13n Console

## Product Boundary

Console is the browser application for Service, consuming the public API through a private client generated from `proto/a13n-service/`. The Service's API-serving roles serve the production build and the API on one origin ([09](../a13n-service/09-runtime.md#console)); development uses a Vite proxy. The [design system](design-system.md) owns reusable UI components.

Service owns permissions, resource versions, execution, durable state and storage. Console owns navigation, forms, resource cache, localized presentation and interaction rendering. Closing a page or stream does not interrupt a run. Independent SDKs have no build or runtime role in Console.

## Navigation and Scope

A signed-out visitor sees sign-in. While the Service reports that it is not initialized, sign-in instead creates the first administrator through the public bootstrap route and signs them in ([bootstrap](../a13n-service/03-tenancy.md#bootstrap)).

Workspace pages use `/workspace/{workspaceId}/…`. The Console lists the workspaces the user can read in the Organization and selects the one with that ID ([tenancy](../a13n-service/03-tenancy.md)); an ID that matches none shows not found with workspace choices. Navigation and selector links use the workspace ID. Every business request carries the selected workspace's ID in `X-Workspace-ID` ([API](../a13n-service/10-api.md#paths-and-scope)), so avatars and downloads are fetched with it rather than loaded by URL. Agent, Skill and Memory details use the resource ID. Settings use `/settings/{section}` for personal settings, `/workspace/{workspaceId}/settings/{section}` and `/organization/settings/{section}`. OSS has one Organization and no Organization switcher. Deep links resolve their requested scope without silently selecting another Workspace. The root page can select the remembered accessible Workspace or the first accessible Workspace. Renaming a Workspace or Organization changes no link, and IDs remain cache identity.

The sidebar contains Agents, Sessions, Models, Skills, Memories, Environments, Connections, Usage and trace inspection. Providers live in Workspace settings, with Model, Web, Environment and Memory categories; Connections expose MCP or Composio setup. Each provider belongs to the selected Workspace, and editing one requires `write` there ([resources](../a13n-service/04-resources.md#provider-resources)). Provider configuration does not imply a successful connection test or available quota.

Workspace and User menus support pointer, click and keyboard activation. The Workspace menu offers its settings and always-visible workspace choices with the current Workspace marked. The User menu identifies the user, opens personal settings and signs out. Settings replace the primary sidebar with one searchable navigation for Personal, Workspace and authorized Organization groups and a return action. Desktop navigation offers an expanded sidebar and a persisted collapsed icon rail; narrow screens use an accessible drawer. Contextual and primary sidebars are not shown together.

Personal settings own profile, security and browser-local theme/language preferences. Workspace settings own profile, grants, invitations, workspace-confined user keys, service accounts and their keys, providers, and audit. Organization settings own profile, grants, invitations, Workspaces and audit. Visible controls follow viewer, runner, builder and admin projections from [tenancy](../a13n-service/03-tenancy.md); they never replace server authorization. Cache identity includes authentication session and scope. Sign-out clears sensitive state; Workspace switching cannot reuse another Workspace's resource data.

Every API-key form requires exactly one Workspace, with no global or Organization option. User keys belong to their signed-in owner; administrators may inspect authorized metadata and revoke them but cannot recover bearer values or create another user's personal key. Service-account keys use the account's home Workspace. Plaintext appears once and is never saved in browser persistence. Expiry choices include 1 day, 7 days, 30 days, 3 months, 1 year and no expiry; day presets are elapsed days, month/year presets use UTC calendar arithmetic with month-end clamping at submission. Organization administration uses a login session. Revoking a credential does not retract already accepted delegation; explicit interruption or changed principal/grant authority follows the Service contract.

## Resource Editing

Agent authoring uses a full-page form, without an embedded conversation panel. Its header identifies the Agent and selected revision, with metadata editing, version history and a trial link to a dedicated Session page. A sticky footer offers save/discard and save status. Trial requires saving executable changes. Management actions that would reload the form require saving or discarding first.

Model, instructions, skills, connections, default memory mounts, web tools, permissions, subagents and environment-template selection follow [AgentConfig](../a13n-service/04-resources.md#agents). The default template saves with the executable configuration; it has no independent automatic save. Thinking effort and output limits are visible near the Model selection; advanced configuration is disclosed on demand. Capability sections show selected resources and inline searchable additions. Skill/subagent revisions are explicitly pinned. Tool controls distinguish Allow, Ask and Deny and preserve settings not exposed by the current editor. Missing or inaccessible saved references remain visible with actionable errors; catalog failures never clear selections. Setup links open separately and refresh choices on return without altering local edits. Field validation expands the relevant section, identifies the field and preserves other input.

Saving configuration creates an immutable revision and selects it as default when requested. History shows number, note, creator, timestamp and default marker; Set as default selects an existing revision without copying it. Creating a revision from an earlier revision's content is a distinct operation. Metadata and revision operations retain the original strong ETag through background refreshes. A stale precondition preserves local edits and requires explicit review/reload; Console never silently overwrites newer data. Resource labels are edited on the owning resource. Archive, unarchive, duplicate and retirement use their actual lifecycle, preserving readable history.

Skill collections show name, default version and GitHub/ZIP source, with search/source filtering before pagination. Detail views provide Files, Versions and Used by agents. Selecting a revision opens its immutable package; `SKILL.md` is initially selected. The file browser supports directory navigation, Markdown preview and full source; binary or oversized files have an explicit download fallback. Imported content is never executed or allowed to fetch remote media automatically. ZIP/GitHub import and new-version forms validate before final publication and keep errors beside the input.

Memory collections show name, kind, type and update time, and a file memory's file count and stored size, with kind and type filtering before pagination. Creation chooses the kind of [memory](../a13n-service/11-memory.md) and takes name, description and guide. A file memory is a PostgreSQL memory and also takes always-loaded paths. A record memory names an enabled memory Provider the Workspace may use, linking to provider settings when there is none, and may adopt one of the provider's existing namespaces behind a disclosure that warns that deleting the memory deletes every record in that namespace. Detail views provide Files, History and Configuration for a file memory, and Records and Configuration for a record memory. Files show the tree with always-loaded files marked, open the first existing always-loaded file, and offer Markdown preview and source. People who may run agents create, edit, rename and delete files; an edit keeps the file ETag it started from, and a stale save keeps the text beside a choice to reload or to keep it for another save. History lists revisions newest first with operation, path, time and the Run (linked to its Debug view) or person behind each, filtered by file and by Run through the URL. A revision opens its diff; restoring confirms and names the file now at the path as its precondition. Purging one file's history needs configuration authority and states that content runs already read stays in their histories and traces. Records list a page in the provider's order or, for a search by meaning, the closest records with their scores. People who may run agents add, edit and delete records: an edit replaces the whole text without a precondition, the text counts characters up to the contract's bound, and a deletion is confirmed. A change the provider did not confirm reads as possibly applied and asks to reload before trying again; an unavailable or disabled provider is named as the cause. Configuration shows kind, type, provider and namespace read-only, edits name, description, guide and a file memory's always-loaded paths under the memory's ETag, and deletes the memory, stating that a record memory's records are deleted from its provider. The guide distinguishes inheriting the deployment's guide for the memory's kind, shown while the saved memory inherits, from no guide and a custom one. Always-loaded paths are chosen only by people who may configure the memory and may name files that do not exist yet. A stale configuration save carries only the draft's own changes onto the newer memory.

Model creation is one modal flow: select an enabled authorized Provider or create one, then choose discovery results or enter an upstream ID manually. Discovery failure does not block manual entry. Provider-owned schemas supply calling API labels and configuration. Upstream model identity is distinct from the local Model key. Native required settings precede collapsed advanced endpoint/header settings; secret fields never expose saved values. Switching schemas preserves local overrides and reports incompatible fields instead of dropping them. Exact saved null, false, zero and empty values survive editing. Optional tests run explicitly against saved configuration, with inline results; unsaved edits must be saved first, and successful saving is not a connectivity test.

Model Advanced edits native request defaults using a few common fields and a complete Settings JSON view of the same draft. Thinking effort and output limits remain optional; Responses additionally exposes reasoning summary and response storage, displaying the Service storage default as off. Calling-API schemas supply parameter vocabulary and validation, not a guarantee of a specific upstream model's reasoning support. Opening or saving the editor never applies a reasoning preset. Unrepresented native settings survive edits; existing flat request defaults are read and saved through `config.settings` with the same effective values. Temperature and Top P remain JSON-editable, without dedicated controls.

Model Advanced also edits `config.characteristics.image_input` in an Image input group: default-on preparation, GIF support, maximum image count and maximum per-image base64-encoded size in MiB (1,048,576 bytes). Turning preparation off saves explicit null and remains off when reopened. Numeric controls reject blank, negative, non-finite and fractional-count values without silently coercing them. Size conversion retains exact integer bytes, and editing exposed fields preserves hidden dimension/splitting controls and other characteristics. Catalog and Provider changes reset the group with their existing draft-seeding semantics; no model-name guessing selects GIF policy.

Provider editors use consistent type pickers, enabled controls and Cancel/Save actions. Types are immutable after creation. Credentials are write-only, cleared after success/dismissal, and never persisted by the browser. Name, configuration, credential replacement and enablement are staged and submitted atomically under the resource precondition. Failure leaves the saved resource unchanged. Lost create acknowledgements show an uncertain outcome and reconcile identity/uniqueness evidence before another create; there is no invented generic idempotency guarantee.

Web search and scrape select compatible providers independently; fetch/download require no provider. Saved unavailable references are not silently replaced. Tool configuration and permission controls preserve hidden settings, show effective access, and distinguish provider availability from authorization. Connection tool scopes use the selected MCP/Composio source catalog; absent saved tools and catalog errors remain visible.

## Agent Configuration Transfer

When creation is authorized, the Agent list and its empty state expose Create with AI as the primary action and Create manually as a separate split button whose menu offers Import YAML; readable saved Agent revisions offer Export. The Console owns the Agent file format; the Service only creates Agents and revisions ([resources](../a13n-service/04-resources.md#operations)). An Agent file is a YAML mapping with exactly `schema_version` (currently `1`), `name`, `description` and `config`, where `config` is an [AgentConfig](../a13n-service/04-resources.md#agents); any other `schema_version` is rejected. Files are at most 1 MB and use the YAML core schema with string keys, finite numbers, bounded nesting and no aliases or custom tags. Export identifies the selected saved revision, excludes credentials and dependent resource creation, and offers a readable overview, complete YAML, copy feedback and download. Unsaved form input is not exported.

Import accepts a file or pasted YAML. Preview preserves editable name/description, searchable replacement references and complete configuration inspection. Returning to YAML editing retains metadata and remapped references. Parsing, validation, loading and unavailable-reference errors stay beside the input. Nothing is created before the final Create agent action. In-flight creation blocks duplicate submission/dismissal; an uncertain result is reconciled before repetition. Success refreshes the collection and opens the created Agent. File text stays in the current form, never browser persistence.

## Connections and Environment Inspection

Connections present their configured source and their authorization state separately. MCP and Composio share a collection/editor, retaining source-specific configuration and tool scopes. Setup explains authentication and upstream prerequisites before creation, including the Service callback URL that a provider's OAuth app must allow exactly. OAuth uses the Service's returned action and one-use callback/state contract; Console does not reconstruct backend authorization state. Callback parameters are removed before rendering, secrets are never persisted, and lost completion acknowledgements lead to status inspection rather than blind reuse. Reauthorization preserves the Connection identity. Unavailable or revoked authorization remains distinguishable from disabled configuration. The [connection contract](../a13n-service/04-resources.md#connections) owns credential and uncertain-refresh behavior.

Environment pages distinguish Providers, Templates and actual instances. Forms use supported Provider schemas with ordinary controls, advanced disclosure and a complete JSON editor; switching types preserves local input. Only demonstrated supported managed backends are offered. Existing instance choices show name and ID. Details distinguish desired Thread mounts from frozen Run mounts, active use, retained policy, lifecycle operation, failure and external ownership. Pending stop/destroy stays pending until confirmed; uncertainty is not shown as success. Deleted instances remain tombstones; loss or replacement never implies file recovery or automatic recreation under the same identity.

HTTP envd registration is connect-only: endpoint, credential and working-directory binding, with bounded discovery where supported. Registered environments have no managed create/start/stop/destroy controls. The [Environment contract](../a13n-service/06-environments.md) owns safe lifecycle actions and authority; Console renders only actions that the selected backend/resource actually supports.

## Sessions and Runs

Sessions group Threads. The collection uses the main content area, not a transcript/composer; details open separately with a return link. Rows use authorized bounded summaries without fetching every Thread/Run, distinguish unavailable values from zero and link directly to their available conversation. Threads identify origin (new, fork or child), readable history, pending inbox and desired environment and memory mounts. Child views link to their origin. Desired mount changes affect future Runs; an active Run keeps its accepted snapshot. A memory mount names its memory, read or write access and, for a record memory, whether Runs recall from it. Access and recall change in place, while another memory removes the name and adds it again, each under the Thread precondition. Run details show the frozen memory mounts with their recall, each file memory linking to its History filtered by the Run. A new conversation's options may mount memories beside the Agent's defaults. Rows show the Agent, status and trigger of the Session's latest Run, the Session's run count and its activity time. Exact Session/Thread search and Agent/status/trigger/activity filters persist in the URL and reset pagination. A Thread search opens that exact Thread, including its explicit empty state. Collection and detail use the same backend preview without a per-row history fetch. Trigger labels are localized. Activity ordering is live and refreshable, not a snapshot across pages.

Chat and Debug switch in place and preserve the followed Run; the chosen level travels in the URL. Every Session the Console starts carries the label `a13n.console: debug`, and its header reads Debug session. Without a level in the URL, a child Thread or a Thread whose Session lacks that label (an application started it) opens in Debug, and any other Thread opens in Chat. Chat presents input, replies, tool activity, questions/approvals and failure in observation order without repetitive headings. Debug exposes Run/attempt boundaries and expands model/tool calls, reasoning, input/output, usage, subagent correlation and raw data. Unknown usage/cost remains unknown, never zero; model and tool counts remain separate and nested calls are not double-counted. Pending or interrupted tools cannot retain a false working indicator after sealing. A failed/cancelled Run never becomes a continuation head. Running a stopped Run's input again submits its message again, with that message's options and pinned revision. The Console offers neither fork nor Thread archive.

The composer submits ordinary messages with an Agent selection and an idempotency key retained across uncertain transport outcomes for that intent. Pending inbox entries can be edited, withdrawn or reordered with the Thread precondition; assigned entries are read-only. The inbox is shown within its Thread. Question, approval and client-tool cards bind exact waiting Run and tool-call IDs and submit one resume batch, including mixed waits. Question results carry structured answers or free text matching that pending call; they never become ordinary inbox messages. Ordinary messages remain queued while a head waits. Each approval makes an explicit Approve or Deny choice, with optional denial reason; client results are explicit. Every pending approval and call requires an explicit result; missing responses keep submission incomplete. Tool results distinguish returned JSON from an explicit failure message; intentionally skipping a question submits a failed call result. After confirmation, continue-without-feedback submits a complete batch of denials and failed calls before submitting any new message. Approvals retain their existing presentation and built-in questions retain their specialized controls; other calls display tool names and arguments. Waiting summaries follow `wait_reason`: waiting for approval, call results, or both; a call category alone never identifies a human or application as the responder. After a successor fails or is cancelled, the unchanged waiting head remains answerable from its own view and the latest Run view. Stale cards cannot answer a newer wait; conflicts preserve local input for review.

Interrupt names the exact Run. Closing a page or losing a stream never interrupts execution. The transcript follows live output while near the bottom; scrolling up preserves position and exposes Return to latest. The bottom composer keeps attachments and options in named dialogs. Enter sends only outside IME composition; Shift+Enter inserts a newline. With an empty composer and an interruptible Run, Send becomes Stop and Escape in the message field requests that Run's interruption. Completed replies offer copy feedback.

### Display Recovery

A Run renders from its committed display and the provisional output of the [thread stream](../a13n-service/07-facts-and-delivery.md#the-thread-stream). The Console reads the Run's committed items, continues them with stream deltas, re-reads the items on `reset` or `gap`, and re-reads the Thread on `changed`. Output that a newer attempt replaces is discarded, never concatenated into a successful answer, and an `in_progress` item of a sealed Run shows as interrupted. Items the display dropped or whose content it omitted stay marked as such. Recovery is bounded, so it never loops endlessly. Run status comes from the Run, never from the stream.

## Usage

Observe → Usage reads the Workspace's [usage analysis API](../a13n-service/07-facts-and-delivery.md#workspace-usage-analysis). The date selector offers the last 7 or 30 local calendar days through now and an explicitly applied custom range of at most 366 days. Daily buckets use the displayed browser timezone. Refresh reloads the current view and advances a preset's end time.

The overview shows recorded USD spend, started Run count, model request count, mean sealed Run duration, input/output tokens, cached input tokens and the weighted cache rate. Unpriced requests have a visible count and identify spend as a known subtotal. Unknown values remain unknown; cached tokens are not added to input again. Daily trends switch locally between spend and total input-plus-output tokens, allow pointer and keyboard inspection, and preserve empty days. Agent/model breakdowns page through the Service's ordering; only Agent rows show Run counts and duration. Changing the window or grouping resets pagination. Empty, loading and query-failure states remain distinct, with retry and refresh controls.

The page explains the separate ingestion-time and Run-start-time windows, USD costs and the inclusion of cached tokens in input. English and Simplified Chinese use the same metrics and query semantics.

## Trace Inspection

Trace browsing follows the authorized [trace query contract](../a13n-service/07-facts-and-delivery.md#trace-query) and links from the selected Run/attempt. Backend availability and telemetry capture are separate from Run outcome. Root input/output previews are bounded plain text from the root observation, not reconstructed child content; unknown content stays unknown. Durations use seconds. Known levels are localized while unfamiliar values remain inspectable.

Costs sum reported observation-local USD values once per observation identity; missing costs are not zero or estimates. Until all available pages load, details identify a loaded subtotal. Exhausted pagination does not prove complete capture, retention or billing. Trace lists identify Trace ID, start, duration and cost before content; compact mode omits content. Sorting applies only to the loaded page, keeps unknown values last, and compares decimal costs without floating-point loss.

Details separate Observations, root Input/output and Metadata. Observations default to a parent-aware call tree and timeline; missing parents remain identifiable. Inspection retains diagnostics, attributes, scope, events and links, with attempt/environment metadata only where explicitly supplied. Telemetry status never implies Run success. Model, tool, agent and service observations remain distinguishable. Content offers safe readable preview and unchanged raw JSON with copy, bounded scrolling and plain fallback. HTML is not executed, and remote media is not fetched automatically.

## Agent Composer

Agent Composer is an ordinary visible, duplicable builtin Agent under [resources](../a13n-service/04-resources.md#agent-composer). Its conversation uses normal Sessions/Threads and tool approvals; creation/revision tools run under the caller's authority and produce ordinary Agent revisions. Console shows the actual resulting resource links and execution evidence. The builtin definition is deployment-owned; setup links for missing permitted resources do not grant access.

## Experience and Accessibility

English is the default and fallback; Simplified Chinese is supported. Date/time pickers follow language and show the browser time zone while converting selections to UTC API timestamps. Relative timestamps retain exact date/time in their title; security/audit views show exact timestamps. Shared tokens, primitives, menus, forms and disclosure indicators keep presentation consistent. The brand SVG is bundled locally.

Collections emphasize names, descriptions and status. Search/filter controls retain visible borders and form a compact row; primary actions sit beside the title without duplicate shell headings. Models use flat rows showing name/key, Provider and status; authorized rows open editors by pointer or keyboard. Resource sections stack on narrow screens; settings navigation collapses behind an accessible control and closes after selection. Long content uses shared scrolling rules. Loading, empty, error, forbidden, unavailable and stale-data states are distinct.

Dialogs have accessible names, keyboard dismissal where safe, managed focus and restoration to their trigger. Validation identifies fields without discarding input. Raw payload dialogs fit narrow viewports. Copy actions show success briefly and offer retryable failure feedback. Password changes use a modal rather than resting-page fields; sensitive input clears on close. Supported profile/avatar image actions have keyboard access, progress, errors and a preview; unavailable image APIs do not receive simulated controls. Agent fallback initials/colors remain stable by ID and use sufficient contrast. A post-create image upload failure preserves the created Agent and offers retry without duplicate creation.

## Boundaries

The [API](../a13n-service/10-api.md) owns wire behavior, and the [Service boundaries](../a13n-service/00-overview.md#boundaries) name what the product does not provide. The Console identifies unavailable capabilities without simulated state.
