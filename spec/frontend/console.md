# a13n Console

## Product Boundary

`a13n-console` is the browser application for a13n Service. It consumes the public Native API through the TypeScript SDK and uses the shared [design system](design-system.md). Service remains API-only; production ingress serves Console assets and proxies `/api` on the same origin. Development uses a Vite proxy rather than permissive Service CORS.

Console owns navigation, forms, resource cache, localized presentation, and interaction rendering. Service owns authentication, permissions, resource versions, execution, durable state and object storage. Closing a page, stream, or SDK client never interrupts a Run.

## Navigation and Scope

Workspace pages use `/workspace/{workspaceKey}/…`; Agent detail uses `/workspace/{workspaceKey}/agents/{agentKey}` and Skill detail uses `/workspace/{workspaceKey}/skills/{skillKey}`. Organization settings use `/organization/settings`, and personal settings remain `/settings/profile`. The authenticated single Organization supplies organization scope; its key is not part of browser paths. Console generates Workspace and Agent paths from current resource keys, including links from Run history and resource references. Deep links match the exact keys without selecting a default Workspace or accepting ID aliases. The root page can select the remembered accessible Workspace or the first accessible Workspace.

Name and URL key are independent profile fields. Workspace and Agent key changes explain that existing links will stop working, refresh affected resource caches, and move the current page to the new canonical address. IDs remain the identity of cached resource data, permissions, revisions, and execution references; key-dependent lookups are invalidated after key changes.

The sidebar contains Agents, Sessions, resource management (Models, Skills, Environments), integrations (Bots, Application Accounts, Connections), and Traces. Provider management lives in Workspace and Organization settings under `section=providers`, with Model, Search, Environment, and Connector categories selected by the `category` query. The settings route determines ownership; there is no separate scope selector. Both settings surfaces reuse the same provider management components. The Providers heading description follows the selected category, with no description below the tabs. All categories use the same primary Add provider button with a plus icon. Organization administrators can manage shared providers without workspace membership. Workspace collections identify inherited organization providers and preserve their ownership and editing permissions. Models, Environments, and Connections retain contextual management links into the matching settings category. The standalone `/providers` route is removed. Environments retains Template and Instance child routes. Organization settings retain shared Models and Environment Templates. Usage and Schedules are absent from the primary navigation until available; their existing deep links display a Coming soon view without API calls or simulated data. Console exposes no Asset manager, Plugin editor, Secret management, or Webhook subscription editor.

Workspace and User menus open on pointer hover while retaining click and keyboard activation. The workspace name opens a same-width menu with Settings and an always-visible Switch workspace submenu. Workspace-menu Settings opens the current Workspace profile; User-menu Settings opens the Personal profile. The primary sidebar has no standalone Settings entry. The submenu includes the current workspace with a check mark, including when only one workspace is available. The User menu identifies the signed-in user, opens personal settings, and signs out. Language selection lives in personal Preferences. OSS has one Organization and no Organization switcher. Settings replace the primary sidebar with one searchable navigation containing Personal, Workspace, and authorized Organization groups, plus a return action. All authorized groups remain available across settings pages; primary and contextual sidebars are never shown together. Resource names within a scope do not repeat that scope in every link. The desktop sidebar stays expanded without collapse controls or shortcuts. Navigation uses compact rows and group spacing; narrow screens retain an accessible navigation drawer. Sidebar selection changes background and color while retaining the same font size and weight.

Personal settings contain profile, browser-local appearance and language preferences, email and password management, browser sessions and personal security activity. Workspace settings contain profile, members, invitations, Personal API Keys, Service Accounts and their keys, and security audit. Organization settings contain profile, members, invitations, Workspaces, shared configuration and security audit. Organization-shared configuration reuses the resource editor with an explicit scope.

Key creation offers 1 day, 7 days, 30 days, 3 months, 1 year, and no-expiration choices. Expiration is calculated when creation is submitted; day presets are elapsed 24-hour periods, while month and year presets use UTC calendar arithmetic with month-end clamping.

A Personal API Key belongs to its User and is bounded to one Workspace. Its creation and list live in that Workspace's settings. Administrators can inspect member-key metadata and revoke keys but cannot create another User's Personal API Key or recover its bearer value. Service Account keys live under their owning Workspace Service Account. Newly created bearer values appear once and are not persisted by Console.

## Bots

[Bots Integration](bots.md) owns the Slack/Feishu customer-owned application journey under Integrations, alongside Application Accounts and Connections. Bot pages reuse Application Account identity and credentials. [Bot Memory](bot-memory.md) owns the three-pane record browser, selected-content sharing, and continuing group-sharing settings. Memory has no separate primary sidebar item. Controls and routes that require unavailable Service capabilities remain unavailable with an explanation rather than presenting simulated working state.

## Connections

`/workspace/{workspaceKey}/connections` lists saved Connections together, including pending, ready, action-required, and disabled records. Row activation opens the owning connection editor. Both source kinds use one Connection resource, permission set, and lifecycle editor. Protocol-specific setup and tools remain in their source panels. Provider management stays in settings.

One New connection dialog searches applications from authorized, active Providers, the Service-owned Remote MCP server catalog, and a custom Streamable HTTP URL. Each application identifies its Provider instance; identical applications from different Providers remain distinct. Provider directories support cached search, pagination, and explicit refresh. MCP entries are deployment-resolved templates fetched through the authenticated Service API; Console contains no second catalog. Selecting a service reveals configuration, authorization requirements, setup documentation, and tool preview in the same dialog. Unsupported authorization explains its limitation before creation.

Remote MCP OAuth uses the application-owned `/connections/callback` route registered in the Service callback allowlist. Console retains the authorization ID and state in expiring tab-local storage, removes provider response parameters from browser history before authentication or rendering, and submits the code or provider error once through authenticated authorization completion. Connector browser handoff continues to require its explicit user confirmation and verifier; MCP OAuth does not use Connector receipts. Console requests the Service's typed OAuth setup action and renders that action directly instead of reconstructing setup state from separate client and discovery calls.

Connect performs local creation followed by authorization or an explicit check. Retries retain the created Connection. Composio-managed OAuth is the default where supported; named custom OAuth configurations are selected from Composio, with custom client credentials managed in its Dashboard. Both source kinds use the [application browser handoff](../a13n-service/40-connectivity/03-connectors-and-connections.md#browser-handoff). Console retains unpredictable state and a completion verifier in the initiating tab, sends only its SHA-256 challenge at creation, and removes callback query material before rendering or authentication requests. `/connections/callback` checks state and authorization identity, completes through the authenticated, CSRF-protected API, and returns to the saved Workspace Connection. The Service browser binding uses separate tab-storage material. Reauthorization preserves the Connection ID; an uncertain completion directs the user to current connection status.

MCP setup and repair support a pre-registered OAuth app with the discovered issuer, exact redirect URI, client ID, grant type, token authentication method, and write-only secret. Machine clients use noninteractive Authorization creation; other OAuth clients use the common handoff. Presets show provider setup requirements and documentation and may prefill non-secret static-header names. Public discovery or a documented token/header setup path is sufficient for catalog inclusion; missing issuer-response advertisements, paid plans, and account or administrator prerequisites are not exclusion criteria. Known unsupported integrations are omitted.

Brand icons share explicit canonical identities, exact aliases and endpoint hosts, then Provider-supplied logo and generic fallbacks. Theme variants follow Console appearance. Remote image requests omit referrers.

## Sessions and Runs

Sessions present Service Sessions directly. The Sessions collection retains the primary Workspace sidebar and displays the Session list in the main content area. It contains no conversation transcript or composer. New-session creation and Session detail open on separate routes; Session detail provides a return link to the collection. The collection is a table with a copyable Session ID, request summary, recent Agent, recent Run status, Run count, trigger source, and last-updated columns. Recent Run columns share the selected preview Run; counts include only readable Runs and unavailable values display a dash rather than zero. The collection has no new-session action; Agent trial remains an entry to creation. List labels and excerpts use the authorized, bounded preview returned with each Session; rendering a row does not fetch its Threads or Runs. A missing preview displays the empty label rather than searching older or inaccessible content. Session links open a Thread and its current or head Run without intermediate selection pages. The detail identifies the current request and its Agent before a Session-map action, semantic Items, the composer, pending actions and queued submissions. Triggering messages align to the right and use Input or Feedback labels. Each Run response starts with the Agent identity above its reasoning, tool calls, replies, fallback output, and run failure or structured output. Content retains observation order without repeating the Agent heading before every reply. Completed tools retain their state while another call waits; interrupted calls do not keep a working indicator. The Session map opens in a non-modal right-side panel alongside the transcript with collapsible Threads and their chronological Runs; branches appear beneath their originating Run when that origin is readable. The map uses single-line tree rows with readable Thread, Run and execution-step counts and Run status indicators. Consecutive Runs can collapse into a range while branch-point Runs and their child Threads remain visible. Run rows include a truncated request excerpt; the complete input and timestamp remain available in the Run preview. Hovering or keyboard-focusing a Run previews its input without navigating; selecting it updates the transcript while preserving the open map and its scroll position. Expanding a Run replays its available execution stream. Execution rows identify LLM calls, tool calls (including provider-native calls), human interaction, inline subagent delegation, CodeAct execution, context handoff, automatic compaction, and automatic memory recall from explicit observations. LLM rows omit model names. Model and tool calls count separately; replies, reasoning, arguments, and results are content of their originating action. Rows have no step numbers or expansion controls: hover and keyboard focus preview their content and state. Explicit parent-call and child-Run correlation nests subagent work and CodeAct inner calls without counting the outer tool twice. Asynchronous delegation can identify its child from the returned execution view; that row describes the dispatch call, not child completion. Human questions and approvals specialize their associated tool; external execution waits remain tool calls. Handoff summarizes and restores context rather than transferring to another Agent. Supporting recovery, retry, usage, context, state, file, shell, and custom observations remain available through a collapsed Other events group and are not counted as actions. Input and injected context are excluded. Request and operation identities are scoped by RunAttempt and Harness Run; matching terminal observations update action state. A sealed Run with an unresolved action does not fabricate that action's completion or failure. The total includes observed nested actions. Stream gaps are shown as unavailable or incomplete execution history, never a complete count inferred from retained message Items. Branch-point Runs carry an explicit label and a connector to their child Threads. The current Run is highlighted and closing the panel restores focus to its opener. Narrow layouts stack the map above the transcript without a backdrop. Request text used as a heading is a presentation of retained input, not a separately persisted Session title. Each Run is inspected inside that Session through a panel containing input/output, available configuration evidence, RunAttempts, lifecycle events and linked Trace details. Console provides no independent Run-list navigation. A Run deep link selects its Session, Thread and Run within the same layout.

The collection supports exact Session ID or Thread ID search, recent Agent, multiple Run statuses, multiple trigger sources, and last-updated bounds. Filters persist in the URL and reset pagination when changed. Run filters describe the same selected Run as the preview. The time popover always shows editable start and end fields in local time, with 24-hour, 7-day, and 30-day shortcuts that populate both fields before Apply; either bound may be omitted. Activating a row opens Session detail, while copying its ID leaves the list open. An exact Thread search opens that matched Thread. The request summary is retained Run input, not a Session title; absent text displays No request text.

Agent trial execution opens this same Session surface. Continue, historical Continue, Fork, Retry, Feedback, Steer, Interrupt and queue operations use the owning Native contracts and exact current version evidence. The UI distinguishes queue acceptance from Run acceptance and delivery receipt from command consumption. Waiting interactions expose their required feedback; Console never automatically executes arbitrary Client Tools.

Stream cursors advance only after events are applied. Replay gaps and explicit reconnection fetch current resource and Item snapshots even when cached values are fresh, with unavailable retained content shown explicitly. Views and recovery share resource reads; detaching one stream does not cancel another consumer's resource request. Lifecycle events, notifications and successful commands refresh the affected Session, Thread and Run resources. An observation gap refreshes the Workspace's cached interaction resources. Notifications are wake-ups, not durable history, and users without notification subscription permission retain Run streaming and recovery. Trace absence is not execution success, and unavailable cost or usage is not zero.

## Trace Inspection

Trace browsing consumes the thin [Trace Query API](../a13n-service/39-trace-query.md). The list shows bounded plain-text previews of root input and output from a full root projection; missing content is `-`, not reconstructed child output. Level and duration remain root-local; explicit telemetry status stays in observation diagnostics rather than the list or overview. All displayed durations use seconds. Known diagnostic levels have localized display names (`default` displays as Info, not success), while raw and unfamiliar levels remain inspectable. Displayed cost uses `$` and sums reported observation-local USD values once per observation ID, including the root only once. The list reads compact observation pages with bounded concurrency and pagination; failed or incomplete reads display `-`, never root-only cost. In details, until all observation pages load successfully, the label identifies a loaded subtotal rather than a trace total. Missing costs are never treated as reported zero or estimated from usage; an entirely unpriced trace displays `-`. Exhausted pagination does not prove complete capture, retention, or billing data.

The list places Trace identity, Started, Duration, and Cost before Input and Output. Compact view omits content columns and resets cursor pagination. Started, Duration, and aggregate Cost can be sorted within the current page; backend pagination remains newest-first. Unknown values remain last in either direction, equal values retain their loaded order, and decimal costs are compared without floating-point conversion. Root identity includes a copyable Trace ID and bounded metadata chips derived only from that observation's explicit attributes and resource environment, never inferred from children.

Details separate Observations, root Input and output, and Metadata. List content previews open the root content tab. Observations default to a parent-aware call tree with a seconds-based timeline; alternate time, duration, and observation-local cost orders apply only to loaded observations. A missing parent remains identifiable until loaded. Observation inspection pairs input and output and keeps diagnostics, attributes, resource attributes, scope, events, and links available. Environment, attempt, label, and custom metadata chips belong to the selected observation. Telemetry status describes the reported span status, not the Run outcome; unset or unavailable status does not imply success.

Chat/model calls, tools, agents, service phases, and other observations have distinct semantic icons while preserving the producer's open type and error indicators. Retained content has a readable preview and an unchanged raw JSON representation with copying. Preview recognizes message roles, text blocks, tool arguments and results, and JSON-encoded containers; unknown fields and content types remain inspectable. Markdown and code use the shared safe renderer and syntax highlighting, without executing HTML or automatically fetching remote media. Large payloads remain accessible with bounded scrolling and a plain rendering fallback.

## Resource Editing

Agent authoring uses a full-page form with aligned section descriptions and configuration controls, stacking each section on narrow screens. The header contains identity, version and management actions, and a link to trial execution on the dedicated Session page; there is no embedded conversation panel. A pencil action beside the name edits the name, description and resource key. The default environment is configured directly on the page and saves independently without clearing the executable configuration draft. Availability, archive and duplicate actions have a separate entry. Save or discard a configuration draft before opening management actions that could reload the form; trial execution requires saving the draft. Save status and pending-change actions stay in a sticky footer. Instructions support Markdown source and use the [shared field and scrolling rules](design-system.md#scrolling-and-long-content). Search, Skills, MCP connections, and Connectors are configured directly on the page. Capability sections show selected resources; adding resources opens a searchable inline selection. Each selected Skill or MCP connection exposes its version constraint or tool scope directly in its resource card; single-field configuration does not require an extra disclosure. Controls follow the [shared interaction affordances](design-system.md#control-meaning-and-configuration). Web Provider selection and parameters expand on demand. Configured references remain visible and editable even when their resources are no longer listed. Empty Skill, MCP, and Connector categories link to the corresponding resource setup in a new tab so the draft remains open; Web Provider management also opens in a new tab and refreshes choices on return without changing the draft. Model settings and advanced configuration remain collapsed by default. Validation expands the relevant section and identifies the field. Collapsing preserves the draft. Editing one field preserves other configuration, including Plugin and Secret requirements that Console does not expose. Saving executable configuration creates a Revision; restoring historical content creates a new Revision rather than moving the head backward.

Skill collections use two-column cards, stacking on narrow screens, and search names and keys through the paginated Service collection. Each card identifies the current revision source as GitHub or ZIP upload. An All, GitHub, or ZIP upload filter combines with search before pagination. Detail pages open the current version's file browser with `SKILL.md` selected. Files, Versions, and Used by agents are the detail views; selecting a version opens its own immutable package through an addressable revision query. The file browser presents a navigable directory outline and file contents, with Markdown preview and full source views. Binary and oversized files retain an explicit download fallback. Skill content is never executed, and preview does not automatically load remote media. A rename action beside the title edits the display name; deletion remains a confirmed action in the management menu. Import Skill and New version present ZIP and GitHub as source tabs; Publish version is the final revision action.

Provider types own the calling-API labels and parameter schemas returned by Service. A discovered candidate is not a saved Model. Adding a Model is one continuous modal flow: choose an enabled visible Provider or connect a new one inline, then select a discovered model or enter an upstream model ID manually. Model Provider setup shows the native credentials and required configuration first. Optional base URL overrides, extra headers, and OpenAI authentication options share one Advanced settings disclosure, collapsed by default even for saved overrides. Its summary indicates configured values. All extra header values are treated as secrets without a mode selector. Rows support addition, editing, and removal through a red trash-icon button on the right; saved values are never displayed and an empty saved value preserves it. Validation expands the section without discarding the draft. The single OpenAI type handles official and custom endpoints and offers both Responses and Chat Completions. A full Chat Completions or Responses URL offers an explicit correction to its base URL. Catalog failure never blocks manual entry. For the current provider, upstream ID, and calling API, the scoped model-catalog suggestion supplies the optional base identity and declaration defaults; stale suggestions do not overwrite the draft. Editing an existing Model preserves its exact saved base model and declarations, including explicit null, false, zero, and empty values. Names and keys are suggested and remain editable. Calling APIs use the Provider definition's concise labels. Parameters are collapsed by default, use the selected static API schema with an equivalent JSON editor, and preserve overrides when the API changes; incompatible values fail validation rather than being silently dropped. Successful creation brings the saved Model into the collection view. Model Provider rows open their configuration dialog on pointer or keyboard activation, with no separate Edit action. Optional connection checks display results inline in that dialog and test the saved configuration; unsaved changes must be saved before checking, and saving never requires a test. Model discovery is integrated into model selection with manual entry as a fallback, without a separate Provider discovery flow. Providers configured without authentication display that credentials are not required. Model inference tests remain explicit actions on saved Models. Skills retain immutable package revisions. Environments distinguish configured Providers, template recipes, and actual instances. Environment Template rows identify the current revision's Provider with its icon and open template details on pointer or keyboard activation, without an Actions column. Environment Provider type definitions supply a display_name for presentation while preserving their namespaced type identifiers; provider selectors search both names and identifiers and show matching provider or runtime icons. Integration authorization and credential ownership follow their Service contracts.

Environment recipes use Provider-owned, versioned schemas for ordinary fields, an advanced disclosure, and a full JSON editor. Switching Providers retains each draft. A single supported configuration version needs no version input. E2B asks for an existing upstream template name or ID; Console does not build or enumerate upstream templates, install software, or imply that template recipes change upstream CPU/RAM. Local Providers appear automatically when the OSS deployment enables them, with a read-only deployment source and no manual creation option. Instance creation accepts an optional name; lists and selectors show names with IDs, and authorized users can rename an instance under its ETag without altering its lifecycle.

Mutations retain exact ETags or expected versions. A conflict keeps the draft and offers an explicit reload; Console does not silently overwrite newer data. Permission projections guide visible controls but never replace server authorization. Cache identity includes the authentication session and resource scope; sign-out clears sensitive state, and Workspace switching does not reuse another Workspace's resource data.

## Search Setup

The Agent editor presents first-party search as an optional Web Provider selection with bounded per-Agent parameters. It lists currently visible Web Providers with their type and ownership under [Web Provider Management](../a13n-service/41-web-provider-management.md). Only enabled, credential-configured providers are offered for new selections; an existing unavailable reference remains visible with its configuration error and can be changed or cleared. Clearing search changes only the Agent selection. Provider creation and testing live exclusively in Providers, outside the Agent editor. The management link opens the Search category in a new tab with the current workspace, preserving the Agent draft. Returning to the draft refreshes available providers without automatically changing the selection.

The Search category supports provider creation, name/configuration editing, write-only credential rotation, enable/disable, tests, and authorized referencing-Agent navigation. The form reads the selected type's safe configuration and credential schemas from Service, asks only for required values, and links to its account/setup URL. Secret input is never prefilled from a resource read or stored in browser persistence. The create/update request holds it only for submission; the input clears after success or form dismissal. Provider save, explicit quota-consuming test, and Agent revision save show separate outcomes. A failed test leaves the saved provider available for correction. After a lost provider-create response, the form reconciles the visible provider collection and identifies the uncertain result rather than creating another name or claiming credential equality. Conflicts retain the draft and require an explicit refresh; tests are never automatically repeated.

Each provider category retains its Service API and type-specific configuration and actions, including model discovery and connector catalogs. Centralized management does not merge their domain models. The UI shows actual ownership and sends mutations through that scope. Workspace users can use permitted Organization providers while only Organization administrators can edit them. Enabled and credential-configured indicators do not imply a successful test, remaining quota, or current upstream availability. Provider selection does not require a Connector, Plugin editor, or separate Secret form. Web Provider management and testing are independent of Environment setup; running the selected Web tools requires an Environment and exposes search, fetch, and download together. Model-native search and custom external tools retain their separate labels and configuration. MCP Connections and Application Accounts remain separate resources.

## Agent Configuration Transfer

Agent lists offer a Create agent dropdown with New agent and Import from YAML under `agent.create`; readable Agent details offer Export agent for the saved configuration. The [Agent configuration file contract](../a13n-service/28-agent-management.md#agent-configuration-files) owns the format and dependency semantics.

Export provides a readable overview, complete raw YAML, clipboard copy with feedback, and a `.yaml` download. The dialog identifies the saved version and the exclusion of credentials and dependent resources. Unsaved edits remain outside the export.

Import accepts file upload or pasted YAML. Parsing leads to a preview with editable name and description, searchable dependency replacements, and complete configuration inspection. Returning to Edit YAML retains metadata and remapped references. Validation, loading, unavailable resources, and creation failures stay visible beside the draft. Import creates no resources before the final Create agent action; successful creation refreshes the collection and opens the new Agent. File text lives only in the current form, never browser persistence. In-flight creation prevents dismissal and repeated submission.

## Experience

English is default and fallback; Simplified Chinese is supported. Date and time pickers follow the Console language, display the browser time zone, and preserve conversion from local selections to API timestamps. Shared tokens, primitives, menus, settings compositions and keyboard interactions provide consistent presentation. Search fields and collection filters retain visible borders. Collection headers place primary actions beside the title. Resource pages have no duplicate shell title bar; narrow screens retain a navigation drawer button. Search and filters form a compact row above the collection; toolbar copy does not repeat the page description. On narrow screens, settings navigation collapses behind an expandable control and closes after selecting a section. Settings use the shared grouped sections and compact labeled rows for scalar fields, including theme, language, profile and security controls, and show profile save actions when the name changes. Related rows have fine inset dividers; section headings remain outside their surfaces. Model and environment configuration use shared sections and disclosures. Run tool calls and reasoning use the shared disclosure indicator, and long native content uses the shared scrollbar treatment. Password changes open from a settings action into a modal; password fields remain absent from the resting page and clear when the modal closes. Displayed settings identifiers provide a compact, muted copy icon that darkens on hover and keyboard focus. Successful copying briefly shows a check before restoring the copy icon; failures expose retryable feedback. Editable profile images open the file picker directly when clicked or activated from the keyboard, with a visible edit affordance on hover and focus. Resource collections emphasize names, descriptions and status; model collections use a flat table consistent with Agents, displaying model name and key, Provider logo, name and type, scope, and status. The editor labels the provider-facing identifier as Upstream model, distinct from the local Model key; upstream identity and calling API do not occupy separate list columns. Authorized users open the editor by activating a row with pointer or keyboard, without separate Edit or Test row actions. Inference tests run explicitly inside the editor against saved configuration, with inline results and disabled testing while edits are unsaved. An enabled Provider is not a verified connection. Model, Search, Environment, and Connector Provider lists use row activation instead of an Actions column. Their editors share the same icon-bearing Provider type picker, disabled while editing, modal sizing, Enabled settings rows, and a single Cancel/Save footer; credential replacement and supported enablement changes are staged until Save. Search references remain available inside the provider dialog under their existing permissions. Environment and Connector Provider saves apply name, credentials, and enablement in one atomic update under the current ETag or version; validation failure leaves the saved resource unchanged. Relative timestamps retain the full date and time in their title; security and audit views keep their exact timestamps. Run inspection opens in a named dialog with focus restoration and a layout that fits narrow viewports. Lists and forms provide loading, empty, error, forbidden and stale-data states. The supplied a13n brand SVG is bundled locally.

Session transcripts keep a readable content width and follow live output while the reader remains near the bottom. Scrolling up preserves the reading position and exposes an explicit return-to-latest action. The composer remains available at the bottom, with attachments and next-run options in named dialogs. Cmd/Ctrl+Enter sends outside IME composition; ordinary Enter inserts a newline. Completed assistant messages offer copy feedback. Approval decisions are explicit per-action choices before submitting the complete response set.

Agent avatars appear consistently in the Agent list and detail heading, with a saturated color background and the first letter or character of the Agent name when no image is available. The fallback color is deterministically selected from the Agent ID, stays stable across reloads and renames, and uses a contrasting white initial. Creation previews derive the color from the draft name until an ID exists. Edit Agent details provides upload and removal under `agent.update`; successful image mutations refresh those surfaces and the metadata ETag while preserving unsaved name and description fields. Avatar uploads use the shared profile image picker and display progress and errors in the details dialog. New Agent authoring offers the same picker with a local preview before creation. After the Agent is created, Console uploads the selected image using the returned Agent ETag; a failed upload preserves the created Agent and selected file, provides a retry without duplicate creation, and allows continuing without an avatar.
