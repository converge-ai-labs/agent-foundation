# a13n Console

## Product Boundary

Console is the browser application for Service, consuming the public API through a private client generated from `proto/a13n-service/`. The Service's API-serving roles serve the production build and the API on one origin ([09](../a13n-service/09-runtime.md#console)); development uses a Vite proxy. The [design system](design-system.md) owns reusable UI components.

Service owns permissions, resource versions, execution, durable state and storage. Console owns navigation, forms, resource cache, localized presentation and interaction rendering. Closing a page or stream does not interrupt a run. Independent SDKs have no build or runtime role in Console.

## Navigation and Scope

A signed-out visitor sees sign-in. While the Service reports that it is not initialized, sign-in instead creates the first administrator through the public bootstrap route and signs them in ([bootstrap](../a13n-service/03-tenancy.md#bootstrap)).

Workspace pages use `/workspace/{workspaceId}/…`. The Console lists the workspaces the user can read in the Organization and selects the one with that ID ([tenancy](../a13n-service/03-tenancy.md)); an ID that matches none shows not found with workspace choices. Navigation and selector links use the workspace ID. Every business request carries the selected workspace's ID in `X-Workspace-ID` ([API](../a13n-service/10-api.md#paths-and-scope)), so avatars and downloads are fetched with it rather than loaded by URL. Agent, Skill and Memory details use the resource ID. Settings use `/settings/{section}` for personal settings, `/workspace/{workspaceId}/settings/{section}` and `/organization/settings/{section}`. OSS has one Organization and no Organization switcher. Deep links resolve their requested scope without silently selecting another Workspace. The root page can select the remembered accessible Workspace or the first accessible Workspace. Renaming a Workspace or Organization changes no link, and IDs remain cache identity.

The sidebar starts with ungrouped Agents, Sessions and Schedules. Capabilities groups Models, Skills, Memories, Connections and Environments, in that order. Environments contains Templates, Instances and Metrics. Insights groups Usage, Traces and Findings. These groups organize navigation without changing resource ownership or permissions. Providers live in Workspace settings, with Model, Web, Environment, Connector and Memory categories; Connections expose MCP or Composio setup. Each provider belongs to the selected Workspace, and editing one requires `write` there ([resources](../a13n-service/04-resources.md#provider-resources)). All categories use Provider consistently in tables, counts, setup, deletion and template selection; Credentials and Configuration groups omit empty content. Provider configuration does not imply a successful connection test or available quota.

Workspace and User menus support pointer, click and keyboard activation. The Workspace menu offers always-visible workspace choices with the current Workspace marked. The User menu identifies the user and offers Settings, a Language link to `/settings/language` and sign-out; Profile and Preferences are reached inside Settings. Settings is the unified entry to all authorized settings scopes. API keys has a fixed entry at the bottom of the primary sidebar and opens `/workspace/{workspaceId}/api-keys` without replacing that sidebar. Settings replace the primary sidebar with one searchable navigation for Personal, Workspace and authorized Organization groups and a return action. These groups keep that fixed order when the selected scope changes. Desktop navigation offers an expanded sidebar and a persisted collapsed icon rail; narrow screens use an accessible drawer. Contextual and primary sidebars are not shown together.

Personal settings own profile, security and browser-local preferences. Preferences contains appearance settings; Language has its own page. Display language follows the browser's preferred languages by default, with English as the fallback when none is supported; an explicit English or Simplified Chinese choice overrides it. Returning to System resumes automatic selection. Workspace settings own profile, grants, invitations, member-key administration, service accounts and their keys, providers, Webhooks, and audit. Organization settings own profile, grants, invitations, Workspaces and audit. In both scopes, Members contains member and invitation tabs, with a direct Invite action; invitations have no separate sidebar entry. Visible controls follow viewer, runner, builder and admin projections from [tenancy](../a13n-service/03-tenancy.md); they never replace server authorization. Cache identity includes authentication session and scope. Sign-out clears sensitive state; Workspace switching cannot reuse another Workspace's resource data.

Agents with a default revision expose **Connect to app** in the list menu and detail header to users with Run authority. The dialog provides the `a13n.dev` application integration guide, the current Service origin, and copyable instructions for a coding assistant using the selected Agent ID and Workspace. The instructions refer to the installed SDK's owning documentation and server-side environment variables; they never include API-key values. The same dialog checks the user's keys for this Workspace, guides users without an active key to create one in place, and allows users with a saved key to reuse it or create another. Clicking **Create key** creates immediately without a form or confirmation, using a random `auto-app-` name that identifies it as automatically generated and no expiration. A new key appears once in the dialog, remains outside query and mutation caches and browser persistence, and is cleared on close. Closing is blocked while creation is pending so its one-time result is not lost. Archived Agents and Agents without a default revision cannot start this flow. Opening the dialog, reading docs, and copying instructions do not create credentials or execute the Agent.

Every API-key form requires exactly one Workspace, with no global or Organization option. User keys belong to their signed-in owner; administrators may inspect authorized metadata and revoke them but cannot recover bearer values or create another user's personal key. Service-account keys use the account's home Workspace. Plaintext appears once and is never saved in browser persistence. Expiry choices include 1 day, 7 days, 30 days, 3 months, 1 year and no expiry; day presets are elapsed days, month/year presets use UTC calendar arithmetic with month-end clamping at submission. Organization administration uses a login session. Revoking a credential does not retract already accepted delegation; explicit interruption or changed principal/grant authority follows the Service contract.

## Webhooks

Workspace administrators manage [subscriptions](../a13n-service/04-resources.md#subscriptions) in Settings → Webhooks. The paginated collection shows name, endpoint, event count, filter scope and enabled state. Each subscription opens a detail page with Deliveries and Configuration tabs. Non-administrators cannot open these settings or issue subscription and delivery reads through them.

Create and edit forms group Run, Attempt, Schedule and Occurrence lifecycle events, retain their wire names, and require at least one event. Common outcomes select waiting, completed, failed and cancelled Runs. Optional Agent, Session, Thread and Schedule filters combine with AND; empty filters match the Workspace. An unavailable Agent catalogue never clears a saved filter. The form explains the distinction between an Attempt ending and its Run ending, and between a Schedule ending scheduling and an Occurrence ending execution. Schedule outcomes select pauses, scheduling completion, archival and Occurrence completion/failure/skip/cancellation. A Schedule detail entry point preselects these events and its Schedule ID.

Schedule details keep Enable/Pause and Run once visible when authorized; Edit schedule, Add Webhook and Archive live in the More schedule actions menu. Timing, next trigger and unfinished work form one responsive summary without internal dividers; manual pause is conveyed by the header status, while exceptional pause reasons and completion context remain visible. Execution-permission guidance is expandable, and trigger history uses a compact empty state.

A creation response reveals the signing secret once in the open dialog, outside query caches and browser persistence. Closing the dialog or leaving the Workspace clears that state. An empty secret field generates a secret on creation and preserves the current secret on edit. An unconfirmed creation blocks another submission until the user reviews existing subscriptions. A stale edit preserves the draft and requires explicit loading of the current version; fields the user did not change adopt the newer values. Edit, enable, disable and delete use the observed subscription version. Disabling and deletion explain that already queued deliveries continue.

Delivery views follow [lifecycle webhooks](../a13n-service/07-facts-and-delivery.md#lifecycle-webhooks). They distinguish pending, delivered and stopped retries, and expose the saved endpoint, attempt count, timestamps, last error and event payload. Only dead deliveries with an available saved signing secret offer confirmed redelivery. Confirmation explains that the original ID, endpoint, payload and secret are reused and that receivers must deduplicate. Success means queued again, not delivered. A refused redelivery refreshes the list without claiming success. Console does not invent response bodies, per-attempt history or test-send operations absent from the API.

## Resource Editing

Its header identifies the Agent and selected revision, with metadata editing, version history and a trial link to a dedicated Session page. A sticky footer offers save/discard and save status. Trial requires saving executable changes. Management actions that would reload the form require saving or discarding first.

Model, instructions, skills, connections, default memory mounts, web tools, permissions, subagents and environment-template selection follow [AgentConfig](../a13n-service/04-resources.md#agents). The default environment template picker groups known runtimes into cloud and own infrastructure, shows the runtime provider beside each template name, and keeps unclassified runtimes separate. It offers one default or none; missing provider metadata does not clear a saved selection. The default template saves with the executable configuration; it has no independent automatic save. Thinking effort and output limits are visible near the Model selection; advanced configuration is disclosed on demand. Capability sections show selected resources and inline searchable additions. Skill/subagent revisions are explicitly pinned. Tool controls distinguish Allow, Ask, Automatic review and Deny, respecting the tool catalogue's supported permissions. Automatic review uses an Agent-level reviewer model and default risk policy. A dedicated settings panel edits the risk threshold, flagged action, custom instructions and per-tool rule overrides; shell instructions, failure handling, timeout and model settings remain under advanced settings. Rule selectors and unedited fields are preserved. Choosing review without a reviewer opens its settings, and saving requires a review model. Panel cancellation discards its edits; applying updates only the Agent draft. Read-only versions expose the same review settings without editing. Existing backend defaults and permission selections remain unchanged until edited. Missing or inaccessible saved references remain visible with actionable errors; catalog failures never clear selections. Model setup opens in place, preserves the Agent draft and selects the newly saved Model. Other resource setup links open separately and refresh choices on return without altering local edits. Field validation expands the relevant section, identifies the field and preserves other input.

The Plugins section follows the [installed Harness plugin catalog](../a13n-service/08-providers.md#installed-harness-plugins). It edits named instances in the Agent draft with scalar schema forms and JSON, preserves values across format switches, and updates tool-discovery memberships on rename or removal. It exposes saved unavailable instances for inspection and explicit removal, without treating catalog failures as proof of absence. Presets and historical revisions remain read-only.

Saving configuration creates an immutable revision and selects it as default when requested. History shows number, note, creator, timestamp and default marker; Set as default selects an existing revision without copying it. Creating a revision from an earlier revision's content is a distinct operation. Metadata and revision operations retain the original strong ETag through background refreshes. A stale precondition preserves local edits and requires explicit review/reload; Console never silently overwrites newer data. Resource labels are edited on the owning resource. Archive, unarchive, duplicate and retirement use their actual lifecycle, preserving readable history.

Composer and Finding reuse this editor for their model, supported model settings and supplemental instructions under [managed preset revision edits](../a13n-service/04-resources.md#managed-preset-revision-edits). The instruction input edits only the supplement; current official instructions appear in a read-only disclosure explicitly identified as deployment guidance, not a version snapshot. Other sections remain read-only. The editor keeps the selected default and original ETag for its draft. Version details show the saved supplement separately from current official guidance. Set as default also works for these presets. Preparing an existing preset preserves the selected default; protected configuration updates appear as candidates, while official instruction changes need no new revision. Run configuration explains that the actual official text comes from the Worker and can be inspected in the model request trace. Export combines current official guidance with the saved supplement into an independent custom configuration. There is no automatic-model option or separate reset action.

Skill collections show a separate read-only builtin catalog, including when the Workspace has no imported Skills. Builtin entries show name and description, support search and a builtin source filter, and have no resource detail or mutation actions. Workspace Skill collections show name, default version and GitHub/ZIP source, with search/source filtering before pagination. Detail views provide Files, Versions and Used by agents. Selecting a revision opens its immutable package; `SKILL.md` is initially selected. The file browser supports directory navigation, Markdown preview and full source; binary or oversized files have an explicit download fallback. Imported content is never executed or allowed to fetch remote media automatically. ZIP/GitHub import and new-version forms validate before final publication and keep errors beside the input.

Memory collections show name, kind, type and update time, and a file memory's file count and stored size, with kind and type filtering before pagination. Creation chooses the kind of [memory](../a13n-service/11-memory.md) and takes name, description and guide. A file memory is a PostgreSQL memory and also takes always-loaded paths. A record memory names an enabled memory Provider the Workspace may use, linking to provider settings when there is none, and may adopt one of the provider's existing namespaces behind a disclosure that warns that deleting the memory deletes every record in that namespace. Detail views provide Files, History and Configuration for a file memory, and Records and Configuration for a record memory. Files show the tree with always-loaded files marked, open the first existing always-loaded file, and offer Markdown preview and source. People who may run agents create, edit, rename and delete files; an edit keeps the file ETag it started from, and a stale save keeps the text beside a choice to reload or to keep it for another save. History lists revisions newest first with operation, path, time and the Run (linked to its Debug view) or person behind each, filtered by file and by Run through the URL. A revision opens its diff; restoring confirms and names the file now at the path as its precondition. Purging one file's history needs configuration authority and states that content runs already read stays in their histories and traces. Records list a page in the provider's order or, for a search by meaning, the closest records with their scores. People who may run agents add, edit and delete records: an edit replaces the whole text without a precondition, the text counts characters up to the contract's bound, and a deletion is confirmed. A change the provider did not confirm reads as possibly applied and asks to reload before trying again; an unavailable or disabled provider is named as the cause. Configuration shows kind, type, provider and namespace read-only, edits name, description, guide and a file memory's always-loaded paths under the memory's ETag, and deletes the memory, stating that a record memory's records are deleted from its provider. The guide distinguishes inheriting the deployment's guide for the memory's kind, shown while the saved memory inherits, from no guide and a custom one. Always-loaded paths are chosen only by people who may configure the memory and may name files that do not exist yet. A stale configuration save carries only the draft's own changes onto the newer memory.

Model creation is one modal flow: select an enabled authorized Provider or create one, then choose discovery results or enter an upstream ID manually. Selecting a catalog model seeds its known capabilities and context window, shown as a compact summary. The confirmation shows the chosen model once in its title, with Provider context and the model-selection action on a compact row. The confirmation requires only a name and any unresolved upstream ID; keys, metadata, capabilities, prices and request defaults remain available under advanced controls without requiring edits. Unknown capabilities are not inferred from a model's name. Agent-originated creation keeps the new Model enabled. Supported discovery displays the returned labels, unchanged IDs and server order, with search, loading, empty, retry and manual-entry states. Unsupported discovery retains the public catalog/manual flow. Discovery failure does not fall back to public metadata or block manual entry, and missing `run` authority does not block otherwise-authorized manual creation. Results are scoped by Workspace and Provider; starting reauthorization clears old choices, manual authorization completion refreshes them, and disconnect clears and disables them. Pending reauthorization with retained connected credentials is not a completed new login. Token expiry alone does not disable discovery because the Host can refresh it. Selecting a discovered model seeds its upstream ID, label and available characteristics, retains the Provider calling API, and clears stale catalog references and prices without inferring OpenAI API prices for a ChatGPT plan. Both public-catalog and account-discovery selection prefill media capabilities and context, except `document_understanding`: PDF stays off by default even when supported upstream. Users can enable PDF manually; saved declarations and explicit edits are not filtered or refreshed by metadata reads. Saved Model editing does not depend on successful discovery. Provider-owned schemas supply calling API labels and configuration. Upstream model identity is distinct from the local Model key. Native required settings precede collapsed advanced endpoint/header settings; secret fields never expose saved values. Switching schemas preserves local overrides and reports incompatible fields instead of dropping them. Exact saved null, false, zero and empty values survive editing. Optional tests run explicitly against saved configuration, with inline results; unsaved edits must be saved first, and successful saving is not a connectivity test. Credential schemas with multiple object alternatives expose an authentication-method choice. Only the selected alternative contributes fields and defaults; switching methods clears the previous secret draft.

Saved Model details place name and description first, with enablement on the left of the fixed action footer, opposite Cancel/Save. Creation uses the same placement unless the calling flow requires enablement. Provider selection and the upstream address form one connection group. Capabilities and context capacity use a compact control grid; pricing and advanced request/image controls disclose below. Narrow layouts stack identity fields and capability rows, and show labeled price fields without horizontal scrolling. Editing keeps one draft across sections and model selection, with fixed Cancel/Save actions.

Calling-API schemas supply parameter vocabulary and validation, not a guarantee of a specific upstream model's reasoning support. Opening or saving the editor never applies a reasoning preset. Unrepresented native settings survive edits; existing flat request defaults are read and saved through `config.settings` with the same effective values. Provider editors use consistent type pickers, enabled controls and Cancel/Save actions. Types are immutable after creation. Credentials are write-only, cleared after success/dismissal, and never persisted by the browser. Name, configuration, credential replacement and enablement are staged and submitted atomically under the resource precondition. Failure leaves the saved resource unchanged. Web search and scrape select compatible providers independently; fetch/download require no provider. Saved unavailable references are not silently replaced. ## Agent Configuration Transfer

When creation is authorized, the Agent list and its empty state expose one Create agent menu containing Create with AI when available, Create manually and Import YAML at every screen width; readable saved Agent revisions offer Export. The Console owns the Agent file format; the Service only creates Agents and revisions ([resources](../a13n-service/04-resources.md#operations)). An Agent file is a YAML mapping with exactly `schema_version` (currently `1`), `name`, `description` and `config`, where `config` is an [AgentConfig](../a13n-service/04-resources.md#agents); any other `schema_version` is rejected. Files are at most 1 MB and use the YAML core schema with string keys, finite numbers, bounded nesting and no aliases or custom tags. Export identifies the selected saved revision, excludes credentials and dependent resource creation, and offers a readable overview, complete YAML, copy feedback and download. Unsaved form input is not exported.

Import accepts a file or pasted YAML. Preview preserves editable name/description, searchable replacement references and complete configuration inspection. Returning to YAML editing retains metadata and remapped references. Parsing, validation, loading and unavailable-reference errors stay beside the input. Nothing is created before the final Create agent action. In-flight creation blocks duplicate submission/dismissal; an uncertain result is reconciled before repetition. Success refreshes the collection and opens the created Agent. File text stays in the current form, never browser persistence.

## Connections and Environment Inspection

Connections present their configured source and their authorization state separately. MCP and Composio share a collection/editor, retaining source-specific configuration and tool scopes. Setup explains authentication and upstream prerequisites before creation, including the Service callback URL that a provider's OAuth app must allow exactly. OAuth uses the Service's returned action and one-use callback/state contract; Console does not reconstruct backend authorization state. Callback parameters are removed before rendering, secrets are never persisted, and lost completion acknowledgements lead to status inspection rather than blind reuse. Reauthorization preserves the Connection identity. Unavailable or revoked authorization remains distinguishable from disabled configuration. The [connection contract](../a13n-service/04-resources.md#connections) owns credential and uncertain-refresh behavior.

Environment pages distinguish Providers, Templates and actual instances. Forms use supported Provider schemas with ordinary controls, advanced disclosure and a complete JSON editor; switching types preserves local input. Only demonstrated supported managed backends are offered. Existing instance choices show name and ID. Details distinguish desired Thread mounts from frozen Run mounts, active use, retained policy, lifecycle operation, failure and external ownership. Pending stop/destroy stays pending until confirmed; uncertainty is not shown as success. Deleted instances remain tombstones; loss or replacement never implies file recovery or automatic recreation under the same identity.

Template creation has a dedicated page combining runtime selection, Provider connection and environment configuration. Known runtimes are selected through mutually exclusive cloud sandbox service and own infrastructure tabs; only the active category is shown, and unclassified extensions remain separate. Switching tabs restores the last selected runtime in that category, or clears the active runtime until one is selected, so hidden configurations cannot be submitted. These are presentation groups, not new backend hosting modes. Only enabled Providers matching the selected runtime are selectable. Creating a Provider inline preserves the template draft and selects the returned Provider; its independent persistence is explained before submission. Dismissing the connection form discards its credential draft. Changing runtimes preserves each runtime's recipe input. Saving a template does not create an environment instance.

When reusing an existing managed instance or external target, new-conversation options and the add-mount form offer an optional working directory. Empty means the provider default; switching the selected instance clears the previous path. The field explains existing environment-local paths, Local's instance-root mapping and shared machine resources. Thread mount details display the selected instance and explicit directory. Selecting a template does not offer an existing-directory choice.

HTTP envd registration is connect-only: endpoint, credential and working-directory binding, with bounded discovery where supported. Registered environments have no managed create/start/stop/destroy controls. The [Environment contract](../a13n-service/06-environments.md) owns safe lifecycle actions and authority; Console renders only actions that the selected backend/resource actually supports.

Connection testing probes the saved query endpoint and does not assert export delivery. Missing collector deployment configuration disables new selection. Environment creation defaults to no monitoring and offers source selection before provisioning. Details distinguish desired native settings from the applied provisioning receipt, manual setup for external targets, and collector reload acceptance from scrape health. Missing saved references remain visible. Device registration is separate from executable Environments; attachment tokens appear once in transient component state and are not retained in query or mutation caches.

## Sessions and Runs

Only Sessions started directly in Console, identified by the `a13n.console=debug` label, expose interaction controls. Other Sessions are observation-only in both Chat and Debug, even for runners: no composer, guidance, retry, resume, approval feedback, desktop takeover, stop, fork, inbox mutation, desired mount or execution-policy changes, or Session metadata editing. Source loading or failure withholds those controls. Editable origin metadata does not establish Console ownership. Read-only transcripts, pending requests, queued messages, mounts, Run details and navigation remain available. Console Sessions retain Thread-level restrictions for delegated children and memory organization. This is a Console interaction policy; Service authorization remains unchanged.

Run Details uses consistent outlined bodies for expanded execution policy, mounts, tool executions, lineage and raw metadata, with headings outside the body and one content inset. Attempts use the same outlined list treatment. Nested disclosures do not add another frame; narrow layouts place record timestamps below names and status.

Starting a conversation shows session memory as a composer toolbar control. Its summary distinguishes following the first Agent's defaults, custom space selection, disabled memory and invalid settings. Opening the control exposes Follow agent and Custom modes; custom settings use the existing space selection, mount names and access controls without changing the Agent. Switching modes preserves the custom draft. Invalid settings block sending while keeping the message and configuration editable. Once the Session has been created, memory settings remain inspectable but cannot change while retrying the first Thread submission.

Retained tool executions are available in Run details filtered by Service Run ID, without a Session header entry. Inspectors use bounded paginated reads and refresh independently of Run versions. Open inspectors show read-only live or retained Shell output, process state and truncation evidence; unavailable observation remains distinct from completion. Active output refreshes while visible and stops when the inspector closes. Humans have no stdin, signal or execution-cancellation controls. Ownership, timestamps and raw metadata stay under disclosure. Full result retrieval is explicit, uses bounded versioned fragments, and replaces the previous fragment rather than accumulating payloads. Output and result text live only in the open inspector, outside transcript and query caches; closing or changing identity aborts pending reads. Expiry and owner loss remain visible. The [Service lifecycle](../a13n-service/05-runs.md#retained-tool-executions) owns cancellation, delivery acknowledgement and retention.
