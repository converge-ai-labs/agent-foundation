# Frontend Design System

## Design Position and Ownership

`frontend/packages/a13n-ui` provides shared React primitives, compositions, and design tokens for browser applications. The interface is quiet and precise: hierarchy comes from spacing, type weight, and soft surfaces rather than lines, boxes, and decoration. The product should feel like a mature SaaS console, where every screen follows one anatomy, every control explains itself before activation, and nothing on the page competes with the user's task.

Coss UI registry components provide the interaction foundation, using Base UI for focus, overlays, selection, and menu semantics and DayPicker for calendars. Tailwind CSS owns shared component styling and semantic theme utilities. CSS Modules own application layouts. The [repository model](../repository-model.md#frontend-workspace) owns workspace and packaging boundaries.

Product layouts, navigation, conversation rendering, protocol state, data fetching, persistence, and translations belong to applications. Shared components do not import applications or interpret domain states. Badge variants describe visual meaning; applications map domain states to variants and translated labels.

Recurring control behavior and styling are corrected in their shared owner rather than overridden per screen.

## Principles

1. **Quiet grouping.** Collections and secondary content use a soft 3–4% fill (`--a13n-surface`) or whitespace. Console configuration groups use a canvas background and one subtle outline, with their heading outside. Nested borders and resting shadows do not accumulate; tables, rails and dialogs keep their own surface treatment.
2. **One anatomy per screen type.** Every list page, detail page, editor, dialog, and settings page follows the shared anatomy below. A reader who has used one resource can use all of them.
3. **Names before identifiers.** People recognize resources by name, icon, and status. Identifiers are secondary, sans-serif, muted, and copyable; they never lead a row or a title.
4. **The primary action is obvious, once.** Each page has at most one filled primary button, aligned with its heading. Everything else is outline, ghost, or lives in a menu.
5. **State is explicit.** Drafts, saving, saved, failed, disabled, and pending states are visible where the change happens, in words, not only in color.
6. **Progressive disclosure.** Common settings stay visible; advanced or rare configuration lives in a quiet disclosure with a closed-state summary. Nothing important is hidden behind a hover.
7. **Density with air.** Rows are compact, but the space between sections is always larger than the space inside them.

Console uses cool neutrals; Harness UI's light theme uses a near-white canvas and a light neutral-gray sidebar and grouping surfaces. Each elevation step is a 1px hairline ring plus a softer, larger shadow, so layers separate without borders. Shared default radii, with Harness UI refinements below: 12px for grouping surfaces, dialogs, and empty states; 10px for popovers and menus; 8px for rows, tiles, inputs, and buttons; 6px for chips; 999px for pills. Dark mode uses the same roles with inverted alpha fills and raises elevated surfaces slightly above the canvas; every surface must read correctly in both themes. The document color scheme follows the selected theme, including native controls and syntax colors.

## Typography

Interface text uses the system sans-serif family. Console uses 13px interface text and 14px prose with 1.6 line height. Harness UI uses 13px sidebar navigation and 14px interface text, menu choices and supporting text, 14px conversation prose with 1.6 line height, and 12px code. Supporting information uses color and weight rather than another smaller size. Narrow touch editors use 16px input text to avoid browser focus zoom. The shared scale is 11, 12, 13, 14, 15, 17, and 24px (`--a13n-text-2xs` through `--a13n-text-2xl`), with Harness UI using 20px page and dialog titles, 16px content headings and no half-pixel sizes; hierarchy comes from these steps, weight, and color. Console uses weight 500 for page, dialog, and section titles, labels, names, header cells and emphasized content, and 400 for regular text. Emphasis stays one step above body text rather than using heavy bold. Titles tighten their tracking slightly. Harness UI uses regular body text and medium-weight interface titles and entry names; light-mode primary text is a soft charcoal (#333333), retaining strong contrast against its near-white canvas.

| Element                    | Size / weight | Color     |
| -------------------------- | ------------- | --------- |
| Page title                 | 24px / 500    | text      |
| Dialog title               | 17px / 500    | text      |
| Section title              | 15px / 500    | text      |
| Row name                   | 14px / 500    | text      |
| Field label                | 13px / 500    | text      |
| Body, table cells          | 13px / 400    | text      |
| Page and section summaries | 13px / 400    | secondary |
| Help text, metadata        | 12px / 400    | secondary |
| Table headers              | 12px / 500    | secondary |
| Rail and group headings    | 11px / 500    | secondary |
| Identifiers, keys, URLs    | 12px / 400    | secondary |

Monospace is reserved for code, JSON, commands, and Markdown code. Identifiers use the sans family; a copy affordance appears beside them. Numbers that are compared use tabular figures.

Labels, headings, badges and eyebrows use sentence case. Interface text is never set in all capitals or with widened letter spacing; emphasis comes from weight, color and size. Only literal values that must be read character by character, such as device codes, may use extra tracking.

Harness UI spacing uses 4, 8, 12, 16, 24, 32, 48 and 64px according to relationship: item internals, related fields, groups, and page edges. Optical offsets and control geometry are separate from that spacing scale. The same relationship keeps the same spacing across surfaces; grouping remains visible when borders are removed.

## Color and Status

Neutral surfaces carry the interface. The single filled accent is the primary button (near-black in light, near-white in dark). Indigo is a signal, not a brand fill: it marks focus, text selection, prose links, and the first chart series, and never fills buttons or decorates. Navigation and resource links inside the interface use text color with medium weight and an underline on hover. Console Markdown prose links use the signal color, medium weight and a persistent underline so they remain recognizable within generated answers and document previews; hover strengthens the underline and keyboard focus adds a visible ring. External navigation links carry a trailing arrow icon and open in a new tab only when leaving the product.

Status is a 6px dot and a 12px medium label. Settled states (success and neutral) stay untinted, so a column of healthy rows reads calm; states that ask for attention (warning, danger, and info) add a 10–12% tint of the same hue. Semantic hues are success (emerald), warning (amber), danger (red), info (blue), and neutral (gray). Color never carries meaning alone; the label always names the state.

## Page Anatomy

**List page.** Back link (only when nested) → title row (24px title, optional count) with the primary action at the right → one-line description → toolbar (search up to 300px with leading icon, narrowing before the filters wrap, then filter chips, then secondary actions at the right) → collection → footer (result count at left, pagination at right). Every collection has the toolbar, so moving between lists never shifts the collection. Content spans up to 1280px with 32px top padding and fluid 20–48px side padding, and the page reserves the scrollbar gutter so the content width is the same whether or not a page scrolls.

Console list, detail and settings pages share fluid side gutters. On narrow screens, titles and descriptions retain their reading width; actions wrap below when they cannot fit beside the title block. Page actions and collection toolbars, including Metrics and Usage filters, retain 32px controls and 13px labels, compact icons and preserved touch hit areas. Search fields, filters and trailing actions shrink within the available width and wrap naturally without forcing every control to full width. Loading skeletons follow the same gutters and stacked collection layout as loaded content.

Choose English casing for its context and keep peer controls consistent: status labels and filter options share their translated spelling; action labels and field headings generally use sentence case; inline phrases remain natural within their sentence. Preserve proper names, standard acronyms (API, ID, URL), and exact protocol identifiers.

**Pointer feedback.** Enabled click actions (links, buttons, menu/select options, tabs, toggles and disclosures) use `pointer`; text entry keeps the text cursor, and drag/resize controls keep their spatial cursors. Disabled controls do not advertise clickability. The shared base stylesheet owns semantic defaults, including portalled controls; components only specify cursors for specialized interactions or non-native clickable rows. Cursor styling complements keyboard semantics and visible hover/focus states rather than replacing them. This is our click-action convention, not a claim that every interactive control must use a hand: [CSS cursor semantics](https://www.w3.org/TR/css-ui-4/#cursor) distinguish interaction types, and [Radix cursor guidance](https://www.radix-ui.com/themes/docs/theme/cursors) illustrates design-system-level customization.

**Detail page.** Back link → identity header (44px avatar or brand tile, 24px name, status pill, edit affordance, key chip with copy, one-line description) with primary actions at the right → underline tabs → content up to 1280px, optionally with a 256px sticky summary rail at the right. Sections are titled at 15px with a 13px description and separated by 32px; a section that lists items uses surface rows; a section that edits values uses fields.

**Editor with drafts.** Edits accumulate in a draft. A floating save bar appears at the bottom center with a pulse dot, "Unsaved changes", a one-line consequence, an optional note field, Discard, and the primary Save. Autosaved settings show an inline status beside the control instead.

**Settings page.** A contextual layout with its own left navigation (Back to workspace, search, grouped entries). Content is one centered column up to 1040px. Headings, forms, groups and collections fill the same available width, so both edges stay aligned between sections: 24px title, then outlined configuration groups with rows (name and explanation at the left, control at the right, hairline between rows). Groups are separated by whitespace and titled outside the surface.

Harness UI carries this label/value rhythm into settings, resource editors, dialogs, and chat options. Its settings reading column is at most 760px and centered in the remaining workspace, with consistent title and content edges across pages. Page titles use 20px medium text. Group titles use 14px medium secondary text; rows use 14px regular names with same-size secondary explanations beneath, compact controls at the right, and no decorative icons before group or field names. A 32px gap separates groups and 8px separates a group title from its content. Groups use an 8px radius and 16px horizontal insets. Desktop rows use 8px vertical insets with a 48px minimum height; descriptions stay beneath the label in the left column, and the right control is vertically centered against that complete text block. Descriptions add only their required line height. Touch rows retain a 44px minimum height. Desktop buttons and single-line inputs use a 32px height and 6px radius, with flat surfaces and regular labels; primary actions use medium weight. Narrow and touch inputs use 44px height, and compact actions preserve 44px hit targets. Narrow layouts retain readable wrapping and larger touch targets. Short selectors show a right-aligned value and trailing chevron with a quiet hover surface. Short selectors keep a bounded content width; paths and other long values use a full-width control below their label. Long resource catalogs use searchable choices. Narrow screens preserve horizontal alignment where the control remains usable; prose and long-form editors keep their reading and writing space. Navigation, action and status icons retain their functional meaning. Resource collections keep identity at the left and supporting metadata and actions at the right; narrow layouts place metadata beneath identity before values become fragmented. Empty collections use compact explanatory rows and omit unusable search fields. Disclosure rows share the same text alignment and trailing caret. Settings groups use one quiet background surface and subtle row separators. Nested disclosures reuse that surface and inset without adding another frame. Inputs retain a visible boundary; collection rows use alignment, whitespace and necessary separators rather than an outer box. They reuse the summary’s title and description, with an 8px gap before their content; consecutive settings rows keep their normal height without an extra form gap. Embedded configuration editors keep a compact, bounded code area with its label and help text together above it.

Harness UI popovers use a 12px radius, layered shadows that separate them from the canvas, readable 14px choices, 32px desktop action and model-setting rows, and at least 44px option hit areas on narrow or touch layouts. Compact action menus use one 4px outer inset, one aligned icon column, single-line action names, full-row hover feedback, and consistent trailing states. Current values sit at the trailing edge. Supporting explanations appear where a choice is ambiguous or consequential, rather than beneath every action. Routine descriptions state one purpose or consequence in a short sentence. Longer setup instructions and technical accounting details use named disclosures or short steps; permission, deletion, conflict, and retry consequences remain beside the action they affect. Separators distinguish functional groups; small menus do not repeat a page-style title and close button. Share dialogs use compact unboxed option rows and place link management beside the primary action in one footer. Popup width remains inside the viewport independently of the trigger width. Nested choices retain one header and a Back action; inherited defaults and explicit choices have distinct selection states. Harness UI form dialogs use 480px for standard forms and 640px for complex ones, with a 20px medium title, 24px desktop insets and 16px narrow-screen insets; wide comparison reports retain their reading space. Long forms scroll within the dialog while keeping their actions accessible, with one footer inset. Form and confirmation footers provide Cancel beside the primary action; informational flows provide Close. Device connection steps use the same settings controls, secondary explanations, and trailing disclosures, with readable wrapping commands. Opening a dialog from a compact menu hides that menu throughout the dialog and its exit; closing returns to the workbench without flashing or reopening the menu.

Harness UI navigation keeps trailing additions, disclosures, status indicators and row menus on one aligned column. A hovered or selected row has one surface; nested overflow actions change emphasis without adding another filled rectangle.

Harness UI conversations use a centered 720px column shared by messages, the composer, and its quiet status row. The composer keeps a clear gap from the transcript and status controls, with a flat resting surface and a faint focus shadow. Status controls share compact hover fills; larger touch targets preserve that visual height. User input is a right-aligned soft neutral bubble that fits its content within a bounded width; long text and attachments wrap inside that boundary. Assistant prose uses the reading column with a small text inset. Message copy actions sit below the content: right-aligned with user bubbles and left-aligned with assistant responses. They remain available on hover, keyboard focus, and touch. The empty desktop composer fits on one compact line, with a caret matched to the text height. With input or at narrow widths, the editor spans the available width above one stable action row. It grows with the draft before scrolling internally. Mobile content has one balanced reading gutter rather than accumulating page and pane insets. Auxiliary reading pages share the centered layout; usage reporting may use a wider column for its chart and table.

Compact usage popovers lead with exact token and cost totals and an input/output distribution. Scope changes stay in place; token counters, model attribution and accounting explanations expand beneath the summary within one scroll region. Context gives occupancy and remaining capacity when the limit is known, and an explicit unavailable-limit explanation otherwise.

Disclosure panels and their carets use synchronized 150ms ease-out transitions and disable motion when reduced motion is requested.

**Dialog.** 520px for standard forms, 640px for complex ones and 880px for reports that compare many figures, such as usage tables; vertically stable across steps. Header: 17px title, 13px description. Creation flows start with a catalog (tiles or a searchable list) and continue with a step whose title carries the chosen brand. Fields use 16px gaps; advanced groups use a disclosure; the footer is sticky with Cancel and the primary action. Destructive confirmations name the resource and label the action with its verb. All Console modals, including forms and confirmations, dismiss when the user clicks outside the topmost modal; a backdrop click never activates the obscured page or submits a form. Pending work does not block dismissal or get canceled by it. Dialogs and modal sheets share a 120ms ease-out opacity transition for entry and exit, without scale or slide motion, and disable transitions for reduced-motion preferences. Conditionally mounted editors remain present until the exit completes; closing does not remount or clear their visible content mid-transition.

**Provider editors.** Adding a provider is a catalog step followed by a setup step with Basic information, Credentials and Configuration groups. Credentials include a link to where they are issued; configuration contains non-secret settings, with optional settings disclosed in place. Empty groups are omitted, including for credential-free providers. Editing uses the same grouping below a brand-marked title. The credential row states what is stored (Saved, Not configured) and only reveals inputs on Replace or Add; backing out keeps the saved key. Check connection has its own feedback row above the footer. Enabled sits at the lower left, opposite the red Delete action, Cancel and Save. Delete opens a confirmation for every provider kind; referenced providers show an actionable refusal, and environment providers include a bounded reference preview. OAuth authorization remains distinct from saved configuration and retains its own progress and recovery actions.

**Empty state.** Centered on a surface: a 40px icon tile, 15px title, 13px explanation, and the primary action. When the empty state offers that action, the page header does not repeat it; the screen still offers it exactly once. Search results with no matches use a shorter inline message and keep the toolbar.

**Loading.** Skeletons preserve the destination's layout and density; spinners are reserved for gates and explicit actions. Existing content stays visible during background refreshes.

## Collections

One `ResourceTable` serves every resource list. The list is part of the page: the page scrolls, the table never scrolls inside a fixed-height box. The table has a thin rounded outer border and a light neutral header fill; the search toolbar and pagination stay outside the frame. Header cells are 40px tall with 12px medium sentence-case secondary text. Rows are 52–60px with a hairline divider, a 3–4% hover fill, and a pointer cursor when the row opens something. The first column is the identity: a 32px icon tile or avatar, the name at 14px medium, and one line of secondary text (key, source, or summary). Supporting columns use 13px text; timestamps and identifiers use 12px secondary text; status uses a pill. Columns that are compared as numbers align right with tabular figures; timestamps stay left with their own inset. A search field carries its accessible name, and a placeholder when the field accepts something more specific than the name says. Row actions live in an overflow menu at the right that stays visible on touch devices. Long lists load in pages with a footer count and Previous/Next; search and filters query the server, or read the whole collection and match in the browser when the Service cannot filter it, never only the current page.

Selection lists inside pickers use the same row anatomy with a checkbox in place of the tile, sorted with selected items first.

## Forms and Fields

Console configuration follows the decisions a person makes: identity, connection or storage, behavior, then optional advanced controls. A group has a 15px medium-to-semibold heading outside one 12px-radius outline, 16px field spacing and insets, and 24px between peer groups. Narrow screens use 14px insets and stack controls that cannot retain readable labels. Short forms with one or two related inputs do not require an extra group title. Row-based settings and field-based editors share this treatment; nested groups do not add another frame. Save and Cancel stay together at the right, with staged Enabled at the left when present. Connection checks and their results sit above that outcome row. Opening a group does not change the draft.

Labels sit above controls at 13px medium; descriptions sit below the control at 12px secondary; validation replaces the description in the danger color and names the fix. Optional fields say "(optional)" in the label; required fields carry no asterisk. Inputs are 32px tall (36px below the `sm` breakpoint) with an 8px radius and a hairline border. Controls that share a row share a height: page header and toolbar controls are 32px, section actions and footer controls 28px, and extra-small icon buttons 24px. Textareas for long content (instructions, prompts, JSON) use a soft surface with no border, grow to a bounded height, and scroll internally. Console boolean, choice and short numeric settings place the label and description together on the left and the control at the far right. Switches remain beside their text at narrow widths. Dropdown triggers size to the selected content within a readable minimum and the available space, rather than stretching across a form column; long names truncate in the trigger. Menus may be wider than their trigger so options and search remain readable, and stay within the viewport. Compact filters omit the visible label column. Selects and pickers show the current value with one trailing chevron. Read-only values use `ReadOnlyField`; long-form text retains the soft surface and padding, while short values have no box. A read-only model reads as its picker option: brand mark, name and key.

Buttons: primary (filled), outline (secondary), ghost (tertiary and inline), and destructive (only inside confirmations and menus). Icon-only buttons always have an accessible name. Tooltips explain unfamiliar actions or add useful context; familiar controls such as overflow menus do not repeat their accessible name in a tooltip. Loading preserves size and disables activation. Menu items pair an icon with a label; destructive items sit last after a separator. A form whose submit is not the screen's primary action uses the outline button for it, so the one filled primary per screen still holds.

A segmented control switches an in-place view or mode: a track on the soft surface, the active segment lifted onto the elevated surface, medium labels, and no outline. The small control is 28px tall with 12px labels, matching section actions; the default is 32px with 13px labels, matching toolbars. It never navigates and never replaces tabs; an unavailable segment is disabled rather than hidden. Fields generated from a schema are named by the property that holds them; a schema's own type name is never a field label.

## Conversation Rendering

The session view keeps a compact header (agent identity, status pill, view switch, and actions, with the session identifier copied from the actions menu) and, in Chat, a centered 760px transcript; on narrow screens the identity and actions menu keep the first line and the view controls take the second. In Chat, the user's message is a right-aligned soft bubble and the agent's answer is full-width prose under a small avatar and name line; the name line names the run's model with its brand mark and the count of the run's overrides, and opens the run's agent configuration; its work line, prose, notices, and actions all start at the avatar's left edge. One quiet line summarizes the tool calls and opens into compact rows. While a run works, the animated a13n mark and "Working…" stand where the next step will appear, and the name line carries no status; a completed run's name line adds its duration. A finished answer closes with quiet secondary actions: copy the reply and Create branch from here; a run waiting for the person offers only its answer. Debug reads a session as an executor's log, not a conversation: it has no avatars, bubbles or reply prose. Each run is a card with a soft border and a 12px radius, and cards stand 12px apart. The card's header holds the caret and the 14px semibold run name, a status pill and the run's quiet secondary actions: Resubmit on a stopped latest run, Create branch, Configuration and Details as dialogs. They keep only their glyphs on narrow screens. Under the name each figure is named: the start time to the second, duration, model calls, tokens, cache share and cost, with values in the monospace face and the run identifier last. A closed card is its header alone, with one line of input and the duration. The body is the run's log. A 64px time gutter on a faint tint, like line numbers, gives each line's offset from the run's start, and a column head names the steps and the fixed figure columns: cache, tokens and duration. The log opens on an Agent line that spans the figure columns: the agent's name, its version in monospace, the model with its brand mark and the count of the run's overrides; it opens the same configuration, and below 560px it keeps the model and the count. Input and Output are lines of the log that hold their content beneath them and fold back to their line; a long input or output stops at a fixed height with a fade and Show all. Output renders Markdown with Raw and copy actions, or shows the structured value. Each step is one line: a 13px glyph per entry kind, the name at 13px medium (monospace only for a tool's own name), the subject as secondary prose, and monospace figures in their columns. An exception (failed, working, waiting or interrupted) takes the glyph's place; a completed step shows no mark. Model requests are the skeleton; what they emitted, replies included, indents beneath them with a 1px guide per depth under the parent's glyph, and top-level lines are separated by faint hairlines. A lifecycle fact names its outcome in its tone and its reason in secondary text, and a finished run ends on a Run completed line. Opening a line selects it and shows its record in a band under it, level with its name: 11px medium section labels, code blocks on the elevated surface, patches with additions and removals tinted success and danger, and a folded request summary; raw payloads open in a named dialog. Below 560px the log keeps the time, the step and its duration. Chat's compact rows carry the same names, glyphs and subjects at the same level of detail. A run's configuration dialog is the agent editor read-only: the agent, version and overridden fields above its sections, and an Overridden badge on each section a run override changes. In Chat, sections are separated by more space than the rows inside them, and nested content never accumulates borders. Failures are a quiet danger-tinted notice with a title, a plain-language explanation, and an "Error details" disclosure, the glyph hanging in its own column; a run someone stopped uses the same notice on the neutral surface. In Chat, an earlier run that stopped short keeps its notice, and only the thread's latest run offers Resubmit. In Debug, the thread's inbox and an answer to a wait are cards beside the runs, on the same edges, and the composer asks for the input of the next run. The run navigator appears once a thread has more than one run. Where the page is at least 1000px wide, Debug is a tool page up to 1440px: the run index is a 240px sticky column beside the runs, with a Runs head and two-line rows. A status dot, the run name and an input excerpt lead; recorded cost, model calls and duration align in three monospace columns below. The sticky column headings sort those metrics in either direction, and Order restores chronological order. The scrollbar shows only under the pointer. A narrower page pins a pill with the previous run, the next run and the list. Run-list pagination uses quiet full-width rows with upward or downward chevrons and Earlier runs / Later runs labels; the narrow menu uses the same labels and compact typography. The composer floats at the bottom as an elevated surface: a borderless text area, attachment and option chips at the left, and a round primary send button at the right; Command+Enter or Control+Enter sends; Enter and Shift+Enter insert a newline. Its Run options dialog uses a single column, primary model fields and an instruction switch above quiet collapsed disclosures. Expanded groups keep their heading outside a thin rounded outline, with consistent field insets and flush row separators, matching Agent details. The instruction editor appears only when enabled. A small dot marks changed options on the composer; the dialog keeps Restore defaults at the left and Cancel/Apply at the right, with its body scrolling independently at narrow widths.

Run Details leads with a soft overview surface for the agent, duration and timestamps. Identifiers and trace links sit behind References. Execution policy, mounts, tool executions, lineage and raw metadata use quiet disclosures; attempts stay visible. Spacing, alignment and secondary label colors separate the sections without repeated divider lines. Read-only environment variables are static name/value pairs, with explicit empty states and no editing controls.

## Documentation Pages

The documentation site is a reading surface, so its pages set type for sustained reading rather than interface density. Prose is 16px with a 1.7 line height in supporting text (`--a13n-text-supporting`), so headings, bold text, links, and code stand out in text color. Page titles are 30px, section headings 22px, and subsection headings 18px, all at weight 600, which prose also uses for bold text; a hairline above each section heading divides the page. The description beneath the title is 18px secondary text. The reading column is at most 800px wide, centered between the navigation and the table of contents. The navigation sits on the canvas without a tint: rows keep the 32px height and 8px radius but use text color, and group labels are 13px at weight 600 in text color. The copy and open page actions follow the table of contents when it is shown and otherwise sit beside the title.

Hue appears in page content only where it carries meaning. Links keep the text color at weight 500 over a signal underline that strengthens on hover. Inline code in running text is a chip on the surface with a 6px radius and an input-border outline; in headings and controls it is bare monospace. Table headers sit on a rounded surface band in 12px secondary text at weight 600. Code blocks have a hairline frame on the surface and a title bar naming the file, or the language when no file is given; plain text and output keep a bare frame. Code tokens use one vivid palette in both themes: keywords pink, functions and commands violet, types teal, keys red, strings green, and literals orange, with comments and punctuation gray. Callouts are surfaces tinted with their kind's hue: note info, tip success, important violet, warning amber, and caution red.

Diagrams sit on a surface panel with a dot grid that fades toward its edges. Nodes, states, and sequence participants are cards with a hairline ring and a soft shadow; groups and sequence frames are hairline outlines with their titles at the top-left, edges are thin with small arrowheads, and edge labels are masked by the panel. Wrapped labels break into lines of even length. ## Accessibility and Motion

Every interactive element keeps a visible focus ring at both densities. Titled regions name themselves through their heading, so assistive technology can address them. Fields and icon-only actions have accessible names; tooltips complement, never replace, them. A resource without an image presents initials from the first and last word of its name on a hue derived from its identifier, so similar names stay distinguishable. Base UI controls keep keyboard interaction and disabled semantics. Motion is short (100–200ms), animates only color, opacity and transform, is used for hover fills, press feedback, disclosures, and overlays, and respects reduced-motion preferences. Console buttons confirm a press with a slight scale (0.97) on top of their pressed fill; reduced motion keeps the fill only. Harness UI keeps button geometry fixed on hover and press, using fill and color feedback without scaling. Its transcript disclosures omit leading category icons and use a 12px trailing chevron, revealed on hover or keyboard focus and always visible for touch, without a hover surface, and the latest-work summary labels the toggle without tool totals or a repeated Work log label. That label remains present when expanded so expansion cannot resize its hit area.
