# App plugins: installation, policy and execution

## Design position

An App plugin is trusted installed Python code that extends the Service with organization-scoped business APIs, bounded background work, owned Harness factories and a packaged Console frontend. Installation is deployment-wide; desired enablement belongs to an organization. The Service owns admission before entering tenant business code. [Harness plugins](../a13n-harness/05-plugin-system.md) own execution middleware and Capabilities inside the accepted graph.

| Fact                                                         | Owner                                                                  |
| ------------------------------------------------------------ | ---------------------------------------------------------------------- |
| Installed package identity, registrations, process resources | Service assembly, stable until restart                                 |
| Desired enablement                                           | `Organization.settings.app_plugins`, under organization administration |
| Accepted activation                                          | Immutable `Run.app_activation`                                         |
| Agent-local instances and effective graph                    | Harness source selection and binding                                   |
| Business database identity, metadata and migration history   | App package, migrated by deployment startup or operator                |
| Browser contribution identity and composition                | [Console](../frontend/console.md)                                      |

## Installation and registration

Assembly explicitly discovers `a13n_service.app_plugins` entry points once per application build, before loading extension settings. Each entry is a zero-argument function returning an `AppDefinition` with an `app_id` equal to its entry-point name. Package distribution and version come from installed metadata. IDs consist of lowercase alphanumeric segments separated by `.`, `_` or `-`, beginning with a letter.

An App definition declares its name, owned Harness factory keys, business routers, settings sections, organization sweeps, Run seal subscriptions, optional process startup callback, optional frontend and optional `AppDatabase`. Service migrations own internal records; each App database owns an independent migration history and business metadata under the persistence contract below. Installation and upgrade require a coordinated restart of serving and executing processes; there is no runtime installer or historical package archive.

Duplicate App IDs, factory ownership, settings sections and HTTP operations fail startup. Each business route uses the host's `app_router(app_id)` and remains under the literal `/api/v1/apps/{app_id}/` namespace. A route cannot impersonate another App or replace a core endpoint. Replacements require a concrete subsystem-owned seam.

The detached installed catalog contains metadata only. Tenancy and execution consume that catalog without importing registration callbacks. Assembly alone opens callbacks and registrations over the existing real Runtime, `Tasks`, `Sweep` scheduler and `AsyncExitStack`. Process startup and imports may execute installed code while its tenant policy is disabled; organization business callbacks require host admission. Startup resources register shutdown on the host exit stack.

Apps reuse the host's process-wide OpenTelemetry provider and private metrics listener through the standard metrics API. The [observability contract](12-observability.md#app-plugin-metrics) owns initialization, instrument namespaces, bounded labels, publication and cached collection; no separate metrics registration is part of an App definition.

## App persistence

An optional `AppDatabase` has the same `app_id` as its definition, ordinary independent SQLAlchemy metadata, a package-relative migration resource (`package:directory`) and an optional prefix label. App rows use the existing Runtime Storage and canonical short-session/transaction scopes. Native ORM rows can participate in the same queries and joins. Explicit native table references support foreign-key resolution without granting the App generator ownership of native DDL. Apps enforce their business authorization and tenant scoping; table prefixes isolate migration ownership, not database privileges.

All tables live in PostgreSQL `public`. The reserved family `app__` belongs to App persistence. The default prefix is `app__{slug}_{digest}__`: up to 11 readable App-ID characters with separators normalized to underscores and trailing underscores removed, followed by the first 12 hexadecimal characters of SHA-256 over the full exact App ID. This selection is deterministic and installation-order-independent, including for long IDs and IDs differing only in separators. An explicit label is lowercase snake case, begins with a letter and fits 24 bytes. The optional override is resolved from the App's deployment configuration before declaring models; serving, migration and worker processes use the same value. Duplicate App IDs and duplicate physical prefixes fail assembly; conflicts never allocate a runtime suffix or merge identities. Table names and named shared-schema objects use the resolved prefix; the version table is `{prefix}alembic_version`. Native Distribution metadata cannot claim the reserved family.

Core's `app_databases` registry retains a unique binding from App ID to physical prefix. The first App upgrade claims an empty namespace under the same deployment-wide advisory lock used by Core migrations. A conflicting retained binding or an occupied namespace without a binding fails before App DDL. Binding survives organization disablement, package removal and failures leaving committed namespace objects. A failed first upgrade releases its new binding only when rollback leaves the namespace empty, under the same lock. Changing a configured prefix selects another physical namespace; it does not rename tables or move data. An initialized database refuses a different binding. Moving existing data requires a separately reviewed operator migration.

Each App package ships one independent Alembic graph with at most one head and its own version table. Core and App graphs never merge. Core autogeneration ignores the entire reserved table family, including uninstalled Apps. An App generator compares every reflected table in its exact prefix, including tables removed from current models, while excluding native tables, other Apps and version bookkeeping. Native unknown unprefixed tables remain visible to Core drift checks. App histories must use prefix-portable identifiers: generated table, key, index and foreign-key names resolve through `migration_name` at application time. Data literals remain literal. App authors review raw SQL, expression text, data changes and other objects explicitly, naming owned objects through the same helper. Installing another App or replaying a second App's base revision does not recreate Core shared functions.

`apps db init` creates only the declared source migration directory. `apps db revision` replays Core and the selected App history in a newly created disposable database before drafting a source revision; `apps db check` repeats that replay and verifies metadata parity. These authoring/CI operations connect to a maintenance database on the selected PostgreSQL server and never prepare the configured business database. The selected development/CI role needs permission to create and drop its temporary databases. The disposable database scope is also reusable in App tests. Source generation requires a filesystem source package; applying/checking installed histories reads packaged resources.

`apps db status` reports retained identity, applied revisions, installed head and compatibility without DDL. `apps db upgrade` requires Core at the build's head and explicitly applies one installed App history. Plain `migrate` applies Core first, then every installed App history in discovery order; `--no-apps` excludes Apps. `migrate --check` checks live Core and App metadata parity without DDL or temporary-database privileges; the App authoring check retains its disposable replay. Histories cannot depend on another App's installation order or own its DDL. Revision generation, checks and runtime compatibility consume the same declaration and selected prefix.

Before any App startup callback runs, every process role validates all installed App database bindings and exact heads, including organization-disabled Apps. A missing, behind or unknown revision fails startup with an explicit upgrade instruction. Assembly resolves installed heads once; readiness repeats only the read-only database check against those heads. On `all` and `control`, `database.auto_migrate` enables startup migration of Core and, by default, all installed App databases. `database.auto_migrate_apps=false` opts out of App startup migration; `database.auto_migrate=false` disables all startup migration. These settings do not change explicit operator commands. Migration inventory is installation-wide and independent of organization enablement. Workers, organization enablement and readiness never perform App DDL. Uninstalling an App retains its tables, version table and binding.

## Organization policy and management

The settings namespace is a typed JSON object `{"enabled": ["acme.reports"]}`. Missing entries default to disabled, including newly installed Apps. Unknown retained policy IDs confer no authority. An administrator can remove a retained ID with a disabling policy update after its package is uninstalled; enabling requires an installed App. Unrelated organization settings survive policy updates.

The operator can set `plugins.bootstrap_enabled_apps` to a list of installed App IDs (empty by default). [Bootstrap](03-tenancy.md#bootstrap) validates the IDs against the installed catalog and writes that initial policy in the transaction that creates the first organization. A missing App aborts bootstrap without creating the organization; HTTP returns `unavailable` and the CLI reports a configuration error. The setting is consumed only when creating the organization. Restarts, configuration changes and repeated bootstrap attempts leave existing policy unchanged.

`GET /api/v1/organizations/{organization_id}/app-plugins` requires ordinary organization read access. Its uncached response contains organization `id`, `version`, `permissions` and installed `items`. Each item exposes App ID/name, distribution/version, owned factory keys, desired `enabled`, and compatible frontend entry/style URLs only when enabled. It contains no configuration values, credentials or import paths. This is the serving process's inventory, not a fleet-health assertion.

`PUT /api/v1/organizations/{organization_id}/app-plugins/{app_id}` accepts `{"enabled": true|false}`. It requires organization `admin` and the ordinary strong organization ETag in `If-Match`. Existing organization locking and in-transaction authority rechecks serialize administrative changes. A real change increments the organization version and records `app_plugin.update` with App ID and enabled flag in the same transaction; a no-op leaves version and audit unchanged. Missing/stale preconditions use the existing 428/412 responses. Both endpoints are tenant administration and intentionally excluded from MCP admission.

## Dispatch boundary

A business HTTP route authenticates with the existing authenticator and CSRF/Origin rules, resolves the selected workspace and checks read authority, then reads its organization's policy. Only after admission does FastAPI resolve App dependencies and invoke its handler. App handlers retain responsibility for the business action's additional verbs and resource checks. Disabled work receives 422 `disabled` with `app_id` and executes no App dependency or handler.

Organization sweeps use a host-owned bounded keyset scan of enabled organizations, with a cursor per sweep for fairness. Each callback is a separate admission with a fresh committed-policy read. SQL sessions close before invoking the callback, which receives the real Runtime and organization ID. The callback owns any durable claims/fencing needed across replicas. Each organization callback has the declared timeout. Ordinary admission or callback failures and callback timeouts are collected while remaining organizations in the batch continue, then fail the pass through the existing scheduler's logging and counters. The enclosing pass deadline includes the bounded callback count and database admission budgets; external cancellation propagates immediately through shutdown. App sweeps run only on API/control-owning roles.

A Run seal subscription receives a detached hint only after the seal commits. Its default `app` scope selects Runs whose `app_id` equals the subscribing App. `organization` scope selects all Runs in an enabled organization. Hints include the Run’s `app_id`, `app_context` and `trigger_app_id`. It defaults to completed, failed and cancelled; waiting is opt-in. A hint contains the organization, workspace, session, thread, run and principal IDs, sealed status and immutable acceptance-time options labels. The worker and control roles communicate over a bounded Redis Stream; no subscription means no publication. A shared consumer group distributes each retained hint to one control replica with NOACK. Entries published before group creation, trimmed entries and entries lost after a consumer receives them are not retried; sweeps remain the recovery backstop. Hints are best-effort and may be lost or duplicated. Publication and per-App callback concurrency and timeouts are bounded; capacity drops increment `a13n_app_run_seal_dropped_total` and `a13n_run_seal_publish_dropped_total`. The seal transaction never awaits App code or hint delivery. Each control-role callback checks current organization enablement immediately before admission, closes the policy session and invokes the App outside SQL. Subscribers must reconcile durable state via their own organization sweeps and tolerate duplicates; a post-interruption burst can exceed the per-App callback cap. A waiting Run remains a sealed historical record; resume creates a successor with a new Run ID, so an App checks the Thread's current wait before acting. Hints confer no authority over a Run or its resources. Shutdown cancels outstanding callbacks.

A request/job already admitted can finish and clean up. Disabling changes subsequent admissions; emergency revocation remains with existing credential and authority owners.

## App provenance

The native Session, Thread, Run, Schedule, Occurrence, Environment and MemorySpace carry immutable `app_id` and optional `app_context`. A context is a flat map with at most 16 entries, keys of 1–64 characters and values of up to 256 characters; it requires an owner. Inbox Entries carry an immutable `app_id` for the submitting App. `EgressCredential.app_id` governs the App's exclusive secret management. A null owner identifies an unattributed resource. Existing labels and Session Origin remain editable metadata and do not establish attribution.

Only trusted in-process App SDK admission can establish new provenance, after checking that the App is installed and enabled for the organization. HTTP and MCP cannot supply provenance. Detailed, list, and compact read views expose `app_id` and, for Runs, `trigger_app_id`. Resource APIs do not expose `app_context`. Native descendants inherit provenance from the owning resource. App SDK ownership checks apply to existing resources, including unattributed rows. When reusing an owned Session or Thread, omitting `app_context` preserves the stored context. An explicit context must match, treating an empty map and a null stored context equivalently. Console read, cancellation and Resume remain available under the ordinary authority rules.

## Environment callbacks

An installed App declares `environment_hooks`, `environment_run_hooks` and `environment_events` on its `AppDefinition`. Default `scope="app"` matches the owner of the Environment for instance hooks and events, and the owner of the Run for Run hooks. `scope="organization"` includes every target in that organization. Instance hooks and event delivery require organization enablement; Run hooks use the Run's immutable activation snapshot, including for external mounts.

Each hook or subscription has a positive timeout of at most 30 seconds and runs outside database scopes. Timeouts and ordinary exceptions produce safe structured diagnostics and a failure metric, then allow progress. `EnvironmentHookAbort(code, message, permanent=True)` is an explicit assertion with a public message. During `after_create`/`after_start` it refuses readiness but preserves the allocation. During `before_stop` it prevents the stop; during Run `on_enter` it fails the current Run. In `before_delete`, `on_exit` and event delivery it is diagnostic only. A nonpermanent instance abort can be retried by maintenance.

An `EnvironmentLifecycleHook` selects one phase. The App receives an `EnvironmentHookContext` with its own ID, the phase, tenant and Environment IDs, owning App and context, predecessor ID if present, operation ID and generation, working directory and an open `EnvironmentExecution`. The scope closes at callback exit. [Managed lifecycle](06-environments.md#lifecycle-execution-scopes) defines the phase boundaries and lease authority. Run `on_enter` and `on_exit` use the Harness Environment extension context and surround foreground execution, with exit occurring before the Environment closes.

An `EnvironmentEventSubscription` receives detached transition hints from a bounded stream after commit. `ready` records `create`, `start` or `register` origin. `deleted` records `explicit`, `idle`, `preparation_failed` or `replaced`. `lost` records confirmed `environment_lost`; `recreated` identifies the new reservation and predecessor. Each event carries tenant and Environment IDs, kind, event, provenance and any predecessor ID. Control dispatch uses the same bounded best-effort delivery and sweep reconciliation as Run seals.

## App objects

`app_sdk.objects.AppObjects` provides `put`, `get`, `read`, `keys` and `delete` in `apps/{app_id}/{organization_id}/{workspace_id}/`. Each call checks installed and enabled App access before storage I/O. `put` writes a new immutable object and returns an `ObjectRef`; `read` checks that reference against stored bytes. `keys` accepts a relative prefix and a full-key cursor within that prefix. Keys outside the namespace and traversal components are rejected.

## Accepted Run activation

Every new durable Run captures one detached schema-versioned snapshot in `Run.app_activation` during [acceptance](05-runs.md). It records the organization version observed with policy in one ordinary committed row read, and each installed App's ID, distribution, package version, sorted owned factory keys and enabled flag. Acceptance projects already loaded metadata and performs no App callback or external I/O for this capture. This observation does not serialize acceptance commit order with a concurrent administrative change.

The snapshot is an immutable accepted field protected by the existing Run guard. Public Run options, steering digests and Harness checkpoint compatibility stay independent. Older rows default to an empty snapshot and never hydrate from current policy.

| Boundary                                                            | Activation                                                            |
| ------------------------------------------------------------------- | --------------------------------------------------------------------- |
| Turns, retry, checkpoint restore or worker takeover of the same Run | Original accepted snapshot                                            |
| Inline child                                                        | Same accepted availability ceiling, child's own instance declarations |
| New durable child, fork, resume or result/handback successor        | Current policy captured at its own acceptance                         |
| Restored plugin state and historical tool results                   | Continuation data, never enablement authority                         |

Before opening execution resources, after closing its planning SQL session, a worker verifies every enabled App's exact installed distribution/version and factory ownership against the snapshot. Mismatch fails deterministically with `conflict`, reason `app_inventory_mismatch`, before factory construction/model execution. This check covers every enabled App in the accepted snapshot, including Apps with no authored instance in that Run; package upgrades require coordinating and draining accepted work across the organization. Disabled ownership remains authoritative even if the worker no longer advertises that App. A newly installed App-owned key absent from the accepted snapshot stays disabled. Unowned standalone Harness factories retain their existing authored behavior.

Composition passes enabled flags into Harness sources before construction, binding and contributions. Each inline node retains local instance IDs and selections. A required dependency on an unavailable contribution fails through the Harness graph contract; no automatic activation occurs.

An installed Harness factory can export named native output handlers. A Run exposes one only when its [output contract](04-resources.md#run-output) explicitly selects the enabled, configured plugin instance and exported key. Missing or disabled references fail rather than falling back to a different output. The handler is trusted installed code; a request cannot supply code or select an arbitrary function.

A new resume successor can encounter an unfinished target from an App now disabled. Harness validates the restored exact deferred target against its current dispatcher before effects and reports `deferred_surface_mismatch`; Service preserves that failure code. Disabling never re-enables a historical target or erases recorded results.

## Worker post-run hooks

An App can capture terminal environment data in `wrap_run`, then generate and publish an artifact in the same run-bound plugin's [post-run hook](../a13n-harness/05-plugin-system.md#post-run-hooks-and-forked-inference). The Worker hands off the session only after its own seal transaction commits. Foreground Run resources are released before the hook starts. Resources retained by detached tools close on their own schedule; the hook does not wait for them. The model clients stay open through the handoff, so replay can reuse the connection pool and Thread affinity header. The detached hook owns neither the Attempt slot nor the Thread lease; it may finish after a successor starts.

The process bounds concurrent sessions with `worker.post_run_concurrency` and elapsed hook time with `worker.post_run_seconds`. Excess sessions are dropped and counted. Shutdown cancels outstanding work. The hook is best effort, has no recovery or retry, and cannot change the sealed result. Apps own publication and any reconciliation required for their business records. Use a Run seal subscription when a separate control-role consumer needs a hint without in-process plugin state.

Each forked request rechecks the original principal's execution authority, the Workspace, pending cancellation, the selected Model and Provider, and any configured paid-dispatch policy. SQL closes before provider I/O. The request does not reserve `Run.max_usage.requests`, write native Run or Session usage records, or participate in sealed Run totals.

## App SDK

Trusted installed Apps use `a13n_service.app_sdk` as Service's supported in-process integration boundary. The SDK exposes native value models and delegates to Service's existing lifecycles; ORM tables, runtime internals and private helpers are not part of the compatibility contract. There is no new HTTP surface. Apps pin a compatible Service version and keep authority for their own product resources at their entry points.

Writes check the installed App inventory and current organization enablement under the organization lock before taking App or resource locks. Every target is confined to the selected workspace. Thread admission and other execution operations use a current workspace Service Account with `run`; native management operations retain their own resource permissions. Read projections without an App or principal parameter consume IDs already authorized by the App and constrain their queries to the workspace. The SDK is a compatibility and data-authority boundary for trusted code, not a Python sandbox.

| Facade      | Contract                                                                                                                                                                                                                                                                             |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `egress`    | Own the lifecycle of [App-managed credentials](04-resources.md#egress-credentials). An active principal in the target organization supplies attribution, without workspace `write`. The App may never read or mutate another App's or an operator's credentials through this facade. |
| `threads`   | Admit a workspace Service Account before App state locks; create a Thread with its first accepted Run or submit to its native Inbox inside the caller transaction. Read activity and page native child Threads.                                                                      |
| `projects`  | Reserve native managed Environments, create Memory Spaces and check native Environment and Browser selections.                                                                                                                                                                       |
| `agents`    | Read an Agent's default revision or derive an immutable revision from it without changing the default. An unchanged configuration returns the existing default.                                                                                                                      |
| `schedules` | Ensure a conversation Session and create, page or count native fresh-Thread Schedules by their App label and optional instance labels. Labels are filters, not authorization.                                                                                                        |
| `usage`     | Read native model usage for resources already authorized by the App.                                                                                                                                                                                                                 |

Transaction-taking commands participate in the outer Service transaction, never commit it, and require the caller to roll it back on failure. Thread admission is valid only in the transaction that issued it. Inbox receipts are durable only after commit; retry with the same request key and body using the native idempotency contract.

Desired primary Environment or Session configuration changes lock the root and its shared-Environment descendants (named shared edges and dynamic children) in parent-first breadth-first order. A current Run, waiting Run or pending Inbox entry prevents the change. Independent child and fork selections are unchanged. Browser-only updates affect the root without imposing Environment quiescence. Historical Runs keep their frozen bindings; later Runs admit the new desired configuration through normal Session versioning. A template queues creation of the replacement Environment and records its create audit event in the caller transaction. `update_thread_resources` returns the root’s resolved desired Environment and Browser IDs, including preserved bindings.

Schedule list cursors are bound to the App and instance labels. The active Schedule count includes enabled or paused Schedules and Schedules with a pending occurrence, even if the Schedule is archived.

The `egress` facade accepts the caller's Service transaction through `create_app_credential_in_transaction`, `rotate_app_credential_in_transaction` and `revoke_app_credential_in_transaction`. The credential change and its audit event commit with the App's own state. Rotation and revocation keep the native notification after commit; rollback sends no notification. The standalone helpers wrap these operations in a Service transaction.

`threads.update_app_egress_secrets` uses the same shared subtree and quiescence rules as other desired primary configuration changes. It checks the selected Environments and binding idleness, then applies `set_secrets` and `remove_envs` by variable name to each existing desired primary binding in the caller's transaction. Setting a reference requires a root primary and an active credential owned by the calling App in the workspace. A patch that would replace or remove another owner's reference fails for the whole subtree; removing a missing name is a no-op. Each Thread retains its own unrelated configuration and other references. When both egress fields are unset, a nonempty `set_secrets` requires explicit `initial_destinations` and initializes controlled egress with exactly those destinations. Otherwise additions require an existing controlled mode and destination policy; `initial_destinations` cannot replace either field. Every injection host must satisfy the resulting policy under the native [Session credential rules](06-environments.md#session-credentials). Empty additions and removal-only patches never initialize egress. Removal retains the mode and destinations even after removing the last reference. Removing a desired reference does not revoke a credential in a live Session; use credential revocation for that.

## Packaged browser assets

An App frontend names an importable Python package, package-relative asset directory, ESM entry, style paths and supported bridge version (currently `1`). Assembly resolves the complete resource directory with `importlib.resources` and keeps any extracted directory alive on the host exit stack. Missing declared entry/styles or unsupported bridge versions fail startup.

API-serving roles serve files at `/api/v1/app-plugins/{app_id}/assets/{package_version}/{path}` with `public, max-age=31536000, immutable` and `X-Content-Type-Options: nosniff`. Package versions identify immutable asset trees; publishers must change the version when bytes change. Relative chunks, CSS and fonts resolve within that tree. Unknown versions, missing files and paths escaping the root return real 404 responses, never Console SPA HTML. Packaged code follows core Console public asset policy; its business APIs remain authorized separately. The organization catalog is `no-store`, so refresh obtains current enablement and entry URLs.

The loopback App development host can serve a selected App's local build output at the same asset URLs with `no-store`. Other Apps keep their packaged asset roots and immutable cache policy. Discovery, application startup and organization enablement retain their ordinary Service behavior.
