# a13n Service

## Design Position

This directory defines `a13n-service`, the optional durable Host that embeds `a13n-harness`. It is a modular service with independently selectable control, worker, and connectivity process roles, not another Agent loop and not a collection of independently versioned microservices.

Service owns managed Secrets, Model Providers and Models, resource authorization, serializable Agent authoring resources, immutable AgentRevisions, Workspace Skill resources and immutable package revisions, immutable Workspace Assets, trusted Harness plugin artifacts and Runtime locks, durable Threads, editable queued submissions, Runs, and RunAttempts, scheduling, the durable Thread inbox, waiting pending summaries and exact Run-state requests, Organization- or Workspace-owned Environment Providers, template revisions, actual Environment records, fixed Run selections, coordinated preparation and stop/delete retention, lifecycle events, Connectivity resources and safe external references, in-process external-tool composition, raw usage records, generic OpenTelemetry tracing, an authorized provider-neutral Trace Query API, and the public management API. Telemetry is not durable domain authority. The control surface also owns the a13n Service Protocol Gateway, which maps Native, Hosted AG-UI, and A2A callers into the same application authority.

It does not redefine the code-first Harness `AgentDefinition`, Pydantic Agent loop, Harness result and state semantics, Agent Stream Protocol conversion, Environment provider lifecycle types, EIP, or provider-native state. Platform-owned data and APIs follow [Platform Data Conventions](../data-conventions.md) and [Platform API Conventions](../api-conventions.md).

## Accepted Identity Model

The shared [Platform Interaction Model](../interaction-model.md) owns the public concepts `Session`, `Thread`, `Run`, and `Item`. Service uses Run and RunAttempt directly as its durable scheduling identities:

```text
Session -> Thread -> Run -> RunAttempt -> Harness Run -> ModelAttempt
```

Every Service-managed Agent invocation accepts a Run belonging to exactly one Session and Thread and persisting exactly one User or Service Account authority Principal. Interactive requests, schedules, webhooks, service requests, queued continuations, retries, and asynchronous children use the same Worker scan, RunAttempt, current-Principal reauthorization, and recovery contract; a Worker, queue consumer, responder, or internal system actor never becomes the execution Principal implicitly.

Each hosted Thread is an independent versioned relational resource. It owns Session membership, origin, the current Run (the most recently accepted Run), the selected continuation head, and optimistic concurrency for accepted advancement; Run rows remain the durable work and state DAG. Whether the current Run is active derives from its status.

A non-terminal Run can span several process-local Harness Runs when Worker takeover creates another RunAttempt. Under [Agent Control: Input and Continuation](18-agent-control-input-and-continuation.md), a waiting Run is sealed; authenticated Feedback or explicit waiting Continue accepts a new Run whose `parent_run_id` names that waiting Run. The new Run receives fresh state and, when claimed, its own RunAttempt, fresh `RunBindings`, a fresh ready or lazy operation object for its fixed logical Environment, and a Harness Run. Environment use is acquired at eager/lazy preparation, and [Environment retention](29-environment-management.md#retention-policy) aggregates active use across all sharing Runs; approval waiting uses the template's ordinary idle stop/delete policy when no Run remains active. Steer can bind to a current accepted Run before that claim; the first Attempt reconciles it after initial Run input and before the first provider request, except where the waiting-successor gate intentionally defers inbox delivery. Waiting Continue delivers default deferred results and new input in the same first model request; waiting-bound steer and async results remain pending until the Service-owned awaited Capability reaches the following complete safe boundary. One `RunAttempt` starts at most one Harness Run; internal Harness `ModelAttempt` values are not durable worker generations. Neither `run_attempt_id` nor `harness_run_id` replaces `run_id` or `thread_id`.

Asynchronous child delivery is gated by the spawning Run's outcome. If that Run fails or is cancelled before its child result is consumed, Service retains the result as `suppressed` but neither injects it into another active Run nor accepts an automatic successor for it. Retry copies the terminal Run's accepted intent and eligible parent state, not its child relationships or suppressed results.

## Implementation Orientation

The current package establishes these service-wide roots:

| Path                                                       | Architectural role                                                                |
| ---------------------------------------------------------- | --------------------------------------------------------------------------------- |
| `packages/a13n-service/a13n_service/settings.py`           | Maps process environment into typed provider and migration configuration          |
| `packages/a13n-service/a13n_service/app.py`                | Owns FastAPI lifespan, constructs one storage resource set, and exposes readiness |
| `packages/a13n-service/a13n_service/storage/`              | Generic backend configuration, construction, lifecycle, and capability semantics  |
| `packages/a13n-service/a13n_service/database/metadata.py`  | Explicit common registry selected by the OSS distribution descriptor              |
| `packages/a13n-service/a13n_service/database/migration.py` | Programmatic Alembic runner and bounded migration coordination                    |
| `packages/a13n-service/a13n_service/database/migrations/`  | OSS distribution revision location assembled into its final graph                 |
| `packages/a13n-service/a13n_service/cli.py`                | Stable `a13n-service serve` and `a13n-service db ...` executable interface        |

These roots are boundaries, not a requirement that every capability become a subpackage. Small capabilities remain focused modules; a capability gains a subdirectory only when it owns several cohesive implementations or contracts. Runnable configuration and migration usage live in the [a13n Service package guide](../../packages/a13n-service/README.md).

## Authority Rules

- The control role accepts resources and commands and commits exact revisions and complete `EffectiveAgentConfig` snapshots. Durable Run lifecycle authority remains in the relational Run and Thread rows.
- Each Worker uses the deployment's persisted Plugin Runtime mode. An on-demand `WorkerExecutionLoop` preflights exact Plugin locks before claim; a runner Supervisor starts lock-scoped children containing equivalent loops. The loop reserves bounded local capacity and transactionally claims or replaces a fenced `RunAttempt`; every winner starts one process-local `RunAttemptExecutor` root task with `LeaseMonitor` and `ControlWatcher` children, one non-task `RunAttemptControl`, and one root-task `HarnessDriver` for preparation, Harness execution, control, and cleanup. It exposes no additional product API and never runs migrations.
- Each Control process can load explicitly registered ConnectorProvider client adapters for management operations. Connectivity processes load inbound Ingress adapters and receive provider events. Executing Workers or Runners load outbound native-action and Connector adapters, construct in-process a13n MCP groups, and directly connect selected Remote MCP servers. These roles use shared application operations and stores without a private cross-pod Service API; Connectivity owns no Agent Thread, Run, RunAttempt, or parallel inbox lifecycle and never executes an Agent.
- PostgreSQL is authoritative for accepted lifecycle state and fencing. Real Redis is required for distributed data flow and coordination; each owning domain defines its Redis retention and replay semantics, and Redis delivery alone never proves a relational transition.
- Queued input remains a separate editable relational resource until one short consumption transaction accepts its Run. Queue rows own no Worker lease, retry, or outcome state.
- The artifact's distribution descriptor explicitly composes the complete configuration, routers, role components, authorization contributions, metadata, and migration graph; installed packages never change the service implicitly.
- Service records contain only Service-owned serializable data. They contain no Python class, plugin instance, native Model, Toolset, Capability, callable, client, credential, Environment adapter, entered facade, opaque `mount_id`, or other live runtime object.
- The worker verifies exact locks and uses trusted installed adapters to reconstruct a process-local Harness `AgentDefinition` and fresh `RunBindings`.
- In the default on-demand profile, Agent authoring selects exact PluginVersions. In runner mode, authoring selects active Plugin keys. Revision creation freezes exact PluginVersions and one Runtime lock into every AgentRevision in either profile; a typed runner Run override resolves and freezes its own exact lock at acceptance.
- A managed Skill becomes usable only through a stable Skill binding frozen by AgentRevision creation or a typed Run override. A binding can pin one integer version or resolve current when a new Run is accepted; that Run then freezes the exact Skill Revision lock. The selected Attempt executor verifies its immutable object and supplies run-local materialization through the fresh primary Environment before model exposure; GitHub and upload sources are never runtime inputs.
- Connectivity adapter package presence grants no trust. Every Run fixes external-resource selections and tool scopes rather than discovered schemas. Every RunAttempt revalidates current authority through bound in-process a13n MCP handlers and Remote MCP client guards without receiving third-party account credentials held by an external integration service.
- Native event ingress deduplicates one source occurrence before using the common Agent Thread, Run, and Steer contracts. It does not bypass Agent, IAM, scheduling, or Run authority.
- Service manages Environment templates and actual Environment records, fixes Run selections, and supplies ready or lazy operation objects from the shared Provider contract. Service owns preparation and retention policy; Provider implementations own connections and target operations; Harness owns local operation scope.
- A stale RunAttempt cannot mutate Thread current/head selection, Run lifecycle or state, pending work, retained Items, child delivery, or terminal outcome. A late immutable `UsageRecord` can still be ingested under its original RunAttempt when record identity and content validate, but it cannot mutate lifecycle.
- During graceful drain, active RunAttempts keep heartbeat and lease renewal until a safe checkpoint and `yielded` transaction, another authoritative outcome, or the drain deadline. Planned handoff keeps the Run and stream running, then creates a fresh RunAttempt and Harness Run from the same latest complete `state.json`.
- Service performs no generic PostgreSQL write solely because an Agent tool call is about to be dispatched. Tool execution becomes recoverable only after a complete `state.json` checkpoint incorporates it. A replacement Attempt resumes from the latest such checkpoint; tools that require cross-crash duplicate suppression or outcome reconciliation own an idempotency key or a tool-specific durable task protocol.
- Every distinct Asset upload or Agent publication creates a new immutable `asset_id`; exact idempotent replay returns the original publication. Run input, output, and Items retain Asset references in their existing values, while `state.json` owns no Asset publication state and Service defines no Run-to-Asset link table.
- Harness completion, durable Run sealing, Item projection, event delivery, external delivery, usage ingestion, and any external settlement are separate facts.
- Native, Hosted AG-UI, and A2A adapters call the same Service application authority; their external identifiers and deliveries never replace current IAM, Run, or Thread authority.

## Specification Conventions

- Python-like schemas are conceptual unless explicitly declared as API or storage formats.
- An `AgentRevision` is immutable; changing materialized Agent content, selected Model key, concrete Harness model characteristics, Agent-authored model settings, or another managed-resource reference creates another Revision. Each Model owns its single calling API and request defaults. Editing a Model affects the next accepted Run that selects it; an already accepted Run retains its Model execution snapshot and effective settings. Editing a Model Provider affects the next outbound request under the live Provider-resolution contract.
- `Ref` values identify entities or revisions and grant no authority.
- Process-local objects are reconstructed and never become durable payloads.
- Domain schemas, repositories, queue messages, and events live in their owning domain rather than the generic storage substrate.
