# Environment Management Providers

## Outbound execution connection

The [managed outbound contract](06-environments.md#managed-outbound-execution) defines `envd_ws` for Docker, E2B, Daytona, Modal, Sprites and Vercel. Their Envd prerequisites and native lifecycle remain the same as `envd_http`; bootstrap selects reverse WebSocket with a private environment-bound credential instead of an HTTP listener. Docker publishes no Envd port, Modal/Vercel expose no Envd HTTP port, and E2B/Daytona/Sprites skip HTTP/TCP readiness probes in this mode. Service waits for Control admission and EIP initialization instead. Existing native and HTTP defaults and saved fingerprints remain compatible. Sprites accepts both headless and desktop Envd recipes.

## Design Position

Service owns built-in Environment management definitions and vendor implementations. Each managed infrastructure vendor implements its own `EnvironmentProvider` subclass for resource lifecycle and connection preparation, independently of the selected execution path. They perform explicit operations on one target; [Environments](06-environments.md) owns durable instances, lifecycle operations, coordination, renewal scheduling, and retirement policy. Harness owns [Environment Execution](../a13n-harness/08a-environment-execution.md): shared state, execution definitions, fixed-target connectors, and native/EIP operations. Service composes those execution definitions rather than maintaining a second implementation of execution.

The [execution backend boundary](../a13n-harness/08b-environment-providers.md#execution-backend-boundary) governs which Harness execution route Service composes. For Envd-backed targets, vendor integration owns lifecycle, daemon installation/bootstrap and connection setup; Agent operations use the shared EIP implementation. Bounded vendor commands used to prepare a target do not create a vendor-native Agent execution path. Human desktop access remains a separate management responsibility.

This boundary separates database-backed orchestration from vendor I/O inside Service as well. Management drivers receive plain validated account settings, current credentials, recipes, portable state, and stable operation identity. They never read business tables or receive database sessions, ORM objects, or principals. Management status, lifecycle capability flags, operation results, and lifecycle error categories are Service contracts; shared identity, state codecs, and execution types remain Harness contracts.

## Definitions and Inputs

An immutable `EnvironmentManagementDefinition` composes one Harness `EnvironmentProviderDefinition` with an allocation recipe schema, management factory, and explicit managed/stop/destroy/renewal capabilities. It reuses execution-side account, credential, identity, and state schemas; management-only inputs stay in Service. Its recipe can include both shared target-compatible inputs and allocation settings, with no duplicate codec or validator for the same fact. Definition construction performs no external I/O and imports no optional vendor SDK.

This separation does not rewrite accepted account configuration, frozen recipes, or state payloads. Service validates the complete recipe and projects the inputs needed for Harness execution. Shared target-compatibility checks preserve existing fingerprints, including provisioning characteristics needed to verify an existing target; carrying those values grants no allocation authority.

Service's registry and deployment qualifications follow [Providers](08-providers.md#registry). Execution and management definitions must agree on Provider type, backend and native target identity, state codec, and shared input meaning. Assembly rejects mismatches and capability flags unsupported by their factories. Connect-only registrations construct Harness connectors directly and need no fictitious allocation lifecycle or management definition. A custom Host can supply its own management and `EnvironmentSource`; the Harness catalog never imports Service management implementations.

The following is a conceptual Python API, not a wire schema:

```python
class EnvironmentManagementDefinition:
    execution: EnvironmentProviderDefinition  # Harness-owned execution metadata
    async def open_provider(self, configuration, credential) -> EnvironmentProvider: ...


class EnvironmentProvider:
    async def create(self, recipe, *, environment_id, operation_id) -> EnvironmentState | None: ...
    async def start(self, state, *, operation_id) -> EnvironmentState | None: ...
    async def inspect(self, target) -> EnvironmentStatus: ...
    async def stop(self, state, *, operation_id): ...
    async def destroy(self, state, *, operation_id): ...
    async def keepalive(self, state, *, deadline, operation_id): ...
    async def close(self): ...
```

Lifecycle calls may return typed `Pending(state, retry_after_seconds, settled)` or `Completed(state)` results. Pending is ordinary asynchronous progress, not an error; it carries the partial native state required to reconcile the same operation. A provider marks it settled only when no outstanding request can allocate further resources and cleanup can identify all resources from that state. Completed confirms the requested transition, including required cleanup for destruction. Existing providers returning state or `None` retain synchronous-completion semantics. The Host owns persistence, pacing and replacement under [one outstanding external operation](06-environments.md#one-outstanding-external-operation).

Creation additionally accepts optional private sampler and exporter launch settings on supported Docker/E2B Envd paths. Each management definition declares this capability for its validated recipe; lifecycle orchestration consults the registry before freezing launch inputs. These settings are independent of the recipe and its compatibility fingerprint; unsupported paths refuse them before allocation. The Host freezes and encrypts their retry input and records the application receipt under [Environment monitoring](13-environment-monitoring.md#managed-launch-and-applied-state). Start and resume retain the target's existing daemon settings.

Supported Docker/E2B Envd providers additionally expose session-free `observe_device` for the existing target's cached descriptor and metrics. It reuses fixed-target HTTP connection preparation, preserves ownership and endpoint checks, and grants no lifecycle or Agent execution authority. [Environment monitoring](13-environment-monitoring.md#proxy-collection-and-temporary-history) owns polling, admission and temporary collection ownership.

Management providers hold account-scoped clients and close them independently from execution clients. Connector construction uses the composed Harness execution definition with authoritative state and current credentials, allocating no live execution client and performing no target I/O. Management can perform initialization and readiness probes without constructing a Harness execution scope. No factory returns an object carrying both roles.

### Default Command Environment

All eight built-in managed providers accept `recipe.environment`, a string-to-string map defaulting to empty. These are ordinary readable template values, not secret storage. Names use `[A-Za-z_][A-Za-z0-9_]*`; values must not contain NUL. Recipe validation rejects platform-owned `A13N_ENVD_*`, `EIP_*`, `A13N_DESKTOP*`, `OTEL_*`, `DISPLAY` and `XAUTHORITY` variables before allocation.

The first create claim freezes these defaults with the rest of the recipe. Retries, execution attachment, stop/start and snapshot resume retain them; later template edits apply only to instances whose recipe has not yet been frozen. Providers with a native creation environment receive the defaults during allocation. All managed execution paths also apply them when dispatching Agent shell/process requests, including EIP paths where the daemon need not inherit its launch environment. This does not mutate the Service process environment or a shared sandbox's global environment during a Run.

Explicit command values take precedence. A command unset removes a default where the execution provider supports unset; existing unsupported-operation errors remain unchanged. Ordinary child processes inherit the resulting command environment. Local defaults must satisfy `allowed_environment_keys`; command authorization and Envd bound-secret protections remain authoritative. Agent, Thread and Run defaults overlay the frozen recipe at command dispatch under the [Run execution policy](05-runs.md#execution-policy); they do not reconfigure or recreate the instance.

### Desktop Access Enforcement

E2B, Docker, Daytona, Modal, Vercel and Sprites management adapters support an optional, internal desktop-access endpoint on an existing running target. The endpoint is distinct from Agent Computer execution and environment lifecycle credentials. Service owns its public control-plane authorization. Custom desktop recipes require explicit human-access opt-in; Service automatic E2B, Modal, Daytona, Vercel and Sprites desktop recipes default that opt-in to true. Discovery reports unsupported unless the prepared target supplies the endpoint; access calls never install dependencies, create a target, restart its display, resume it or extend its sandbox lifetime.

The Host owns human authorization and exclusive admission to the managed Computer channel. The scope is the native desktop target across Environment aliases and Threads. Files, Shell, processes, scripts, model generation and other desktops continue. Provider grants do not exclude independently connected SDK clients, arbitrary guest processes or administrators; those remain outside this Computer-channel guarantee.

The internal endpoint accepts discovery, grant, inspect, renew, revoke and held-input cleanup under desktop-access protocol version 2, separate from EIP. Requests and discovery carry the version; incompatible versions fail before dispatch. Grants bind the endpoint generation, a Host-chosen identity, mode (`view` or `control`), positive epoch and absolute expiry. A generation change invalidates prior commands. Retrying an identity with different mode or epoch conflicts. Revoked or expired grants cannot be resurrected. Discovery must advertise `revocation_fences_grants`; revoking an unknown identity records a tombstone that fences delayed grant requests.

Each grant supplies an authenticated WebSocket-to-RFB connection. Read-only enforcement belongs to the endpoint, including for raw malicious input. Clipboard synchronization is disabled. Revocation removes reconnection authority, terminates existing connections and releases held keys/buttons with X-server confirmation. Unconfirmed cleanup prevents returning to automation. This confirms the managed input channel, not OS-wide quiescence or rollback of application effects.

Guest grants last at most 60 seconds and are renewed only within the accepted absolute expiry. A live control grant can renew with the same token, password and RFB connection beyond 15 minutes while its human lease remains valid. Wall and monotonic clocks bound expiry. Endpoint death terminates its direct input backends; restart changes generation and requires reconciliation. Reconciliation ends the old control grant instead of renewing it across generations. Handback revokes the old grant identity on the current endpoint generation and confirms held-input cleanup there before reopening Computer admission under the still-current target, claim and control episode. Missing endpoint evidence is an unknown cleanup outcome. The supervisor bounds active grants to 16 and remembered identities to 4,096 per generation; read-only viewing remains independent of the controller.

The management socket is root-private. The browser connects directly to the provider-local endpoint on port 6081 using WSS, except loopback development WS. Operators provide reachable routing and prevent bypass; Service does not publish Docker viewer ports or proxy frames. Docker's `desktop_viewer_url` contains `{container_id}`. Daytona uses short-lived port-scoped signed routes rather than sandbox-wide credentials. Route expiry is independent of endpoint grant enforcement. Browser credentials contain no cloud, Engine or Envd credentials and remain outside ordinary state, tool results, logs and page URLs.

## Computer-only desktop control

An authorized user controls an existing desktop through its Environment. The recipe retains `desktop_assistance=true` as the human-access opt-in; it does not install an Agent tool. Service provides no built-in `request_desktop_assistance` tool or dedicated pending-request card. Applications may define their own request workflow independently of desktop control.

One durable control record represents a native target, shared by every alias. Its primary `version` supplies the strong ETag. `generation` fences target invalidation; `episode` increments on takeover and fences stale control requests and observations. It identifies the takeover that produced a handback event. Run identities are provenance for blocked calls, not the control lifecycle owner.

| Route                                                          | Contract                                                                                                                                         |
| -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `GET /environments/{environment_id}/desktop-control`           | Current metadata with strong ETag and `Cache-Control: no-store`; no viewer credentials.                                                          |
| `POST /environments/{environment_id}/desktop-control/takeover` | Require `If-Match` and an open `thread_id` currently mounting the Environment; accept a bounded optional `lease_seconds`.                        |
| `POST /environments/{environment_id}/desktop-control/renew`    | Require the controller principal and exact `generation`/`episode`; extend a still-valid lease within configured bounds.                          |
| `POST /environments/{environment_id}/desktop-control/handback` | Require `If-Match`; begin revocation and return the resulting control state.                                                                     |
| `POST /environments/{environment_id}/desktop-viewer`           | Issue independent read-only access (`mode=view`) or expose the current controller grant (`mode=control`); return sensitive uncached credentials. |

Routes require workspace `run` and current Environment/provider authority. Control renewal and reconciliation revalidate the controller, originating Thread binding and native identity. Desktop binding checks include the current Run's explicit Run-only primary (or the last Run's while the Thread is idle), replacing only that name in the desired mounts. Cancellation invalidates this temporary binding; a newer Run supersedes it. Handback checks the same effective binding without writing it into the Thread's desired mounts. A control viewer additionally requires the controller principal, a live human lease and explicit request `generation`/`episode` matching the initiating control state. Read-only responses include a `viewer_id`; supplying it renews that same live grant after checking the original principal, Environment, target and guest generation. Renewal retains its guest epoch and credentials, consumes no additional reader slot, and cannot resurrect an expired or revoked grant. Execution/control routes are intentionally excluded from the management MCP catalog.

The control states are `automation → draining → human → returning → automation`. The wire value `draining` denotes pending human viewer authorization. Takeover closes Computer admission when its intent transaction commits and proceeds directly to viewer authorization. Calls admitted before that commit may finish, including sending input while human control is active; takeover neither waits for them nor retracts dispatched input. Service keeps no per-Computer-call settlement ledger. Failed, cancelled or abandoned calls do not block a later takeover or retain the Environment beyond its ordinary Run and tool-execution lifecycle. The same gate covers built-in tools and Computer calls inside CodeAct. Files, Shell, process input and initialization scripts remain independent. Browser control retains its own subsystem contract.

A new Computer call during draining, human control or returning is rejected before dispatch with `desktop_human_control`. Its guidance says the call did not execute, registers handback for the actual caller, and directs the Agent to continue other work or finish without polling. A Run keeps its ordinary lifecycle; takeover never seals a desktop wait, suspends the task tree, interrupts an unrelated tool or fabricates a deferred tool result. Roots, active children and independent Threads sharing the native target obey the same Computer gate.

Human control has a configurable lease: `control.desktop_control_seconds` defaults to 300 seconds, bounded by `desktop_control_min_seconds` (60) and `desktop_control_max_seconds` (3,600). Explicit renewal extends that deadline. Short guest-grant renewal is separate and cannot extend the human lease. Closing the viewer only closes that connection. Handback, expiry, lost authority or invalidated bindings revoke input and confirm cleanup before reopening automation. Cancellation before a grant was dispatched reopens admission directly; both paths complete the takeover and produce its registered handback notices. Unconfirmed transitions retain blocked authority for reconciliation; no force-release API is provided. Control reservations also protect the native target from retirement across aliases. Authoritative lifecycle confirmation that a native target is permanently lost advances its control generation, fences pending publications, expires its viewer reservations and suppresses handback notices. The target remains tombstoned across aliases and cannot regain Computer or viewer authority. Network failures and absence under changed provider credentials do not establish target loss and retain reconciliation obligations.

Grant, controller-authority and viewer failures remain visible after verified cleanup until the next explicit takeover. Cleanup retries preserve that initiating failure; transient target-access and revocation failures clear when cleanup succeeds. Ordinary handback and human-lease expiry do not create failures.

### Model-visible admission

Each normal model request projects current Computer admission for known native targets in that invocation's Environment mounts: `open`, `human_control` (including pending authorization and returning), or `unavailable` for a permanently lost target. Entries identify the mount alias and, when a control record exists, its control state, generation and episode. Admission is distinct from mount permissions and provider readiness. Unknown native targets are omitted; the Harness Environment context continues to describe their capability and preparation state.

Projection is read-only: it does not prepare, probe or renew an Environment, create control records, acquire control, or register notifications. During human control its guidance points to `computer_notify`; after handback it requires a fresh observation and subsequent model decision. It includes no controller identity, native target identifier or viewer credentials.

### Handback and fresh observation

A blocked Computer call or explicit `computer_notify(alias)` registers its actual caller for handback, deduplicated by target generation, episode and Thread. The explicit tool belongs to the Agent's Computer toolset and uses its normal per-tool permission. It requires a current frozen Run mount with Computer permission, current execution authority and a usable matching native target. Registration covers the current takeover only; if admission is already open, it returns `already_available` without subscribing to future episodes. Successful registration returns `registered` and directs the Agent to continue other work or finish without polling. Ending the takeover sends one typed `desktop_handback` through the existing inbox and outbox, including cancellation before grant dispatch. The notice preserves the registering Run's original principal, execution authority and frozen mount; it grants no new authority. Delivery and consumption revalidate the current binding, native identity and generation, original authority and current permissions. Cancellation, archival, changed mounts, lost targets and settled child Threads suppress stale notices. A later takeover preserves an already-produced event: its episode records provenance, not current Computer admission. Registration does not migrate to that later episode; a caller may explicitly register again after reading current state. Active children may consume a notice at their next checkpoint; a notice never resurrects a settled child.

The ordinary inbox supplies sequencing, checkpoint consumption, idle-root continuation and backpressure. A full inbox defers delivery rather than dropping or bypassing capacity. `control.desktop_notice_seconds` bounds notification eligibility (default one day). The notice reports that the registered takeover ended and asks the caller to check current Computer admission. It may arrive during another takeover, giving the model another decision without promising current availability. It is neither a tool replay nor a completion answer. Waiting approvals and external calls retain their exact full-batch resume contract.

After a control episode, each Agent invocation must obtain a fresh successful Computer screenshot observation of the current generation/episode and reach the following model decision before issuing physical input, clipboard mutation, or native accessibility mutation. The seven accessibility read actions can reassess semantic state after handback, but trees, text, native readback, and screenshot-coordinate projections do not create screenshot freshness. All accessibility reads and mutations still obey the same prospective Computer gate during human control. The model must receive that observation; observing and acting in the same CodeAct block or parallel tool batch does not satisfy the gate. Persisted pre-takeover observations and gestures provide no authority. Other tools remain usable throughout this freshness gate.

### Compatibility

Desktop-access protocol v2 and the Environment-scoped control schema replace the Run-scoped assistance/pause contract. Old routes and desktop-only wait fields are absent. Existing immutable Run history remains readable. Migration refuses live legacy reservations, unresolved assistance and resumable legacy desktop waits. Operators must drain old replicas and reconcile these contexts with the old release before upgrading; mixed-version rolling operation is unsupported. Prepared desktop guests must provide v2 before new control can be granted. Downgrade refuses new control or handback history that the old release cannot represent; forward repair preserves those facts.

## Management Operations

| Operation   | Observable contract                                                                                                                                                                                                        |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `create`    | Allocate under the supplied stable Environment and operation identities, or recover the result of that same allocation after an ambiguous response. Preserve observed state even if later readiness fails.                 |
| `start`     | Start the represented existing environment under its declared stop/resume guarantees; never silently replace a lost target. Snapshot-backed providers report any resulting native incarnation change explicitly.           |
| `inspect`   | Observe a saved target or find an interrupted allocation by stable ownership correlation, without creating, starting, renewing, or deleting it. Distinguish running, stopped, confirmed absence, and unavailable evidence. |
| `stop`      | Stop or pause the exact validated target and preserve its declared resume state. Repeated calls reconcile actual state without waking it.                                                                                  |
| `destroy`   | Remove the exact owned target. Confirmed absence is an idempotent result; uncertainty retains state for reconciliation. Host-supplied directories, bind sources, and unrelated volumes are never removed.                  |
| `keepalive` | Extend a running target's supported lifetime and report expiry evidence. Never start a stopped target; disclose hard limits and uncertain outcomes.                                                                        |
| `close`     | Release owned management clients, without stopping or destroying the target.                                                                                                                                               |

A stopped target remains distinct from a lost one. A provider whose explicit stop retains a native snapshot can resume from that retained state under its declared contract; a missing target without such evidence is not permission to create a replacement. Replacement is a new Host-authorized allocation and state publication.

Provider metadata declares renewal requirements and supported bounds; the Host owns scheduling, retry policy, idle stop/delete decisions, and active-use protection. Local synchronization protects clients and operations, not cross-process ownership. The Host reconciles outstanding mutations before issuing conflicting ones; an expired database lease cannot cancel an already dispatched vendor request. Provider I/O occurs outside Host database transactions.

## Service and Harness Collaboration

Service workers embed Harness in the same process. The boundary remains `EnvironmentSource.ensure_ready() -> EnvironmentConnector`, followed by `EnvironmentConnector.open() -> EnvironmentExecution`; it introduces no RPC or new remote service.

```mermaid
sequenceDiagram
    participant Service as Service source and lifecycle coordinator
    participant Driver as Service management provider
    participant Harness as Harness Run
    participant Connector as Harness connector
    participant Execution as Harness execution
    Service->>Harness: Authorized source with frozen mount policy
    Harness->>Service: ensure_ready() on first dependent use
    Service->>Service: Read current authority and state; end transaction
    opt Target requires management
        Service->>Service: Claim operation in a short transaction
        Service->>Driver: Inspect / create / start outside transaction
        Driver-->>Service: State and outcome evidence
        Service->>Service: Publish under current claim in a short transaction
    end
    Service-->>Harness: Fixed-target connector using authoritative state
    Harness->>Connector: open()
    Connector-->>Harness: Ready execution
    Harness->>Execution: Execute permitted operations
    Harness->>Execution: close()
    Note over Service,Driver: Renewal and target retirement remain Service-owned
```

The Agent's `lazy_environment` option keeps its [existing readiness semantics](06-environments.md#execution): default true defers managed preparation until first dependent use; false prepares selected managed instances before Harness execution. Connection and Session acquisition remain lazy in either mode. Source metadata is inert. Host sources may perform database reads and lifecycle coordination internally, but every transaction ends before vendor I/O, readiness waits, Harness execution, or cleanup; no live session is retained by a source between calls.

Harness never claims a lifecycle operation, writes current state, extends a target lease, or decides to replace a target. Source failure and cancellation keep Service's classification and durable operation identity. A cancelled wait does not undo a dispatched vendor operation or erase published state. Service reconciles uncertain effects under the same operation, while Harness releases only its acquired execution resources. Current mount authorization, active-use protection, publication fencing, and lazy/eager failure handling remain owned by [Environments](06-environments.md).

## Failures and Publication

Management errors retain a typed category, dispatch/outcome certainty, stable operation identity, and any observed target state. A timeout after possible dispatch is unknown, not a safe-to-repeat rejection. The Host queries or reconciles before retrying management; provider idempotency and native correlation remain backend-specific. A failed readiness check after successful creation must not discard the known target ID.

Management results and partial failures carry the Harness-owned `EnvironmentState` envelope to the Service coordinator for fenced publication. Only that coordinator decides which observation is authoritative. Management drivers themselves own no persistence. State remains credential-free and contains no lease, claim, principal, session, or transaction; [the state contract](../a13n-harness/08a-environment-execution.md#state-envelope) owns its format. No state is discarded until deletion or absence is confirmed under the backend's guarantees.

## Built-in Management Guarantees

The registry selects supported deployments and narrower account/recipe choices. The following guarantees cover the native management drivers; [Harness Providers](../a13n-harness/08b-environment-providers.md) owns execution and connect-only behavior.

### Docker

The recipe includes the `image` and `pull_policy` (`if_missing` by default, or `never`). The selected Engine uses a local image when present; `if_missing` pulls an absent image, while `never` fails with `environment_image_missing` and build/load guidance without contacting a registry. Acquisition policy is excluded from the configuration fingerprint because it does not change an existing container. The other recipe fields include `environment` and an optional `init_script` executed only on a newly created container; optional `cpus`, `memory_gb` (decimal GB, minimum 6,291,456 bytes), and `pids_limit`; `disable_network`, default false, whose true value selects Docker's `none` network for initialization and commands alike with no published ports; `mounts` with an existing absolute host `source`, an absolute container `target`, and `read_only` defaulting to true; and advanced user, shell, Python, stop grace, request timeout, file and query limits, output preview and capture limits, and concurrent observation limit. Named volumes are not a recipe option, and external mounts cannot replace `/workspace`, the root filesystem, or the Provider's private `/tmp/a13n` command metadata directory.

`/workspace` belongs to the container writable layer, and each Environment owns a separate container. Explicit external host directories are shared only when recipes name the same source; Docker resolves source paths in the Engine's filesystem namespace, which may differ from the process hosting the Harness. Destruction never removes an external source. The default image is `ghcr.io/converge-ai-labs/a13n-sandbox:dev`; a custom Native image supplies Linux, Python 3.10 or later, the configured shell, and a user able to write `/workspace` and `/tmp/a13n`, with Git additionally required for Git-ignore queries. With `execution="native"` (the default), the Provider replaces the image's ENTRYPOINT and CMD, enables Docker init, and runs a Python waiting process. The container user is the explicit recipe `user`, otherwise the image label `ai.a13n.environment.user`, otherwise the image default USER. The sandbox image labels its native execution user as `sandbox` (UID/GID 1000) while retaining root for standalone Envd startup. Native Docker does not start the bundled daemon. There is no guest operation server: file operations use bounded one-shot Python standard-library commands through Docker exec, and file semantics share the native helper.

Creation uses a deterministic name plus ownership and configuration labels; interrupted creation discovers that target and validates its labels without starting it. Foreign or incompatible targets are never adopted or destroyed. `create()` recovers its allocation, and `start()` starts the retained container; confirmed loss is not permission to recreate. Initialization must finish before readiness is published: a marker records completion, and a retained container without it fails preparation rather than replaying a partial script. `stop()` preserves the writable filesystem. `destroy()` removes only the validated container and its private filesystem, never external sources; confirmed absence succeeds idempotently. Changing an image tag does not replace an existing target. Execution attachment and close follow the [Docker execution contract](../a13n-harness/08b-environment-providers.md#docker).

With `execution="envd_http"`, Service preserves the image's entrypoint and command, sets the allocation device ID and envd HTTP bootstrap settings, and publishes container port 8888 on the account's configured bind interface with a Docker-assigned host port. The image must start envd as root with Session execution under its own provisioned identity, honor `A13N_ENVD_HTTP_CREDENTIAL_FILE`, and atomically create a protected random per-instance credential if absent. The supplied images implement this in their common entrypoint. Headless Envd accepts the official slim image or an explicitly authored compatible wrapper image. The wrapper owns daemon installation, root startup, Session identity and restart behavior in its Dockerfile; selecting it does not authorize Service to replace its entrypoint or install packages into an arbitrary base. Management initialization, marker checks and bounded credential reads use POSIX shell/core utilities without guest Python or jq. Custom compatible images need no official image label or particular window manager. Recipe user and envd/display variable overrides are rejected. Native defaults and saved native fingerprints remain compatible; unpublished experimental relay targets must be recreated with the explicit execution configuration.

Console offers Standard environment, Desktop environment and Custom image. The Docker definition publishes the two built-in recipe tuples in `x-environment-presets`, following Service's sandbox image policy and the desktop variant's `-desktop` tag suffix. Standard fixes the standard image, native execution and no desktop requirement; Desktop fixes the desktop image, HTTP EIP execution and the desktop requirement. Only Custom exposes editable image, execution, desktop and advanced/JSON configuration. Existing nonmatching images or advanced overrides open as Custom without rewriting them. Explicitly choosing a built-in preset restores advanced defaults and keeps CPU, memory and mounts; no preset identifier is persisted. Connection routing and Agent permissions remain independently configured. Publishing a Service release that offers the desktop preset requires publishing its matching sandbox desktop tag first.

`desktop=true` additionally requires an observable, input-ready desktop before create/start succeeds. The supplied desktop image owns Xvfb/Openbox/envd supervision. EIP without this requirement only needs the ordinary execution protocol. Readiness failure retains the allocation for inspection and explicit retry; it never authorizes a replacement. Agent tools and Run-frozen mount permissions remain separate authorization layers.

With `execution="envd_http"`, the forward HTTP route is separate from `docker_host`: Service/Workers must reach the explicitly configured host and the published per-instance port. Remote Engine access alone is insufficient. Published plaintext HTTP is intended for loopback or an explicitly trusted private link, never an unprotected public route; deployment endpoint policy still applies. `disable_network=true` is incompatible and rejected. There is no Docker exec HTTP proxy. All execution operations on this route reuse Harness HTTP EIP, which verifies the expected device identity. `max_file_bytes`, output limits and concurrent-process limits configure envd; native `max_query_entries` does not change EIP traversal semantics.

Credentials stay in each container's protected writable layer and survive stop/start. Destroying that container removes its credential. Revocation stops/destroys the container; in-place rotation requires stopping it, replacing its credential file through authorized operator access, and restarting it. New attachments read the replacement; already-open sessions must be closed before rotation. No shared provider token or plaintext database credential is introduced. Closing execution leaves the desktop running; stop/start retains files but recreates GUI/session/observation state. Reverse WebSocket Service enrollment, ingress and cross-Worker ownership are a separate integration.

### Guest Startup and Crash Recovery

Prepared headless and desktop runtimes select one restart owner. External service managers, including Sprites services, start `a13n-envd daemon` and own activation and replacement. Supplied images and automatic Modal, Daytona, E2B and Vercel assets without an external manager start `a13n-envd supervise`. Its native parent owns bounded crash replacement and explicit version-selected restart under [Envd lifecycle](../a13n-envd/01-daemon-lifecycle-and-configuration.md#launch-and-restart-ownership). Desktop preparation keeps the existing display/access launcher outside daemon supervision, so native daemon replacement preserves those processes. Display or access-endpoint failure retains the launcher's fail-closed cleanup. Custom preinstalled images retain their authored boot contract.

Process supervision detects exit, not EIP responsiveness. Authenticated EIP readiness remains the capability check; a failed probe cannot kill a live runtime or replay a command. Execution attachment and human-access grants remain check-only. Restart reuses the existing installation, Device identity and private credential; it never allocates a target, reinstalls packages or replays Session work. Stdio execution retains its caller-owned peer lifetime and is not restarted transparently.

### Managed Envd Versions

Docker, E2B, Modal, Daytona, Vercel and Sprites recipes accept `envd_management: managed | preinstalled`, independently of `execution: envd_http | envd_ws`, except that preinstalled Sprites requires `envd_http`: its private outbound credential currently requires Service-owned launcher bootstrap. Native execution rejects `managed`. Automatic Envd preparation and official Docker Envd images default to `managed`; explicit custom images, templates and snapshots default to `preinstalled`. The selected policy freezes with the recipe. Automatic asset selectors require `managed`; `preinstalled` rejects automatic assets and explicit headless installation. This Service-only policy is excluded from execution compatibility fingerprints. Kubernetes retains operator-authored Pod/init-container installation and boot.

`managed` gives Service ownership of the instance's Envd binary version. Service selects its release-pinned version, acquires and verifies the release through the standalone installer, atomically replaces the executable, and requests native version-selected restart or the external manager's restart. It never polls `latest`. Standard root-owned install/runtime paths and GNU/Linux installer prerequisites are required; opting a custom runtime in does not replace its authored entrypoint or provision missing desktop components. Automatic artifact/base preparation remains the recipe's separate provisioning contract. `preinstalled` gives the operator installation and startup ownership. Service never installs Envd or replaces its authored startup, and readiness remains check-only. E2B requires a compatible custom template with `preparation=preinstalled`; Modal requires a custom image and explicit `startup_command` argv used unchanged on allocation and snapshot resume. Daytona requires a custom snapshot whose boot contract starts Envd. Vercel requires a custom snapshot and explicit `startup_command` argv: management executes it as root with the instance bootstrap environment on create and native session resume. One frozen startup job per native session records completion; management reentry rejoins it after a lost allocation, resume or command reply instead of replaying the authored command. A confirmed failed job requires an explicit new lifecycle operation to retry. The command starts the runtime in the background and returns; snapshots preserve files, not processes. Sprites retains its operator-configured service without registering or changing a launcher. Docker retains image-authored boot. The operator owns later binary changes or instance replacement.

Create and start/resume apply the frozen target version before publishing readiness. The first authorized execution preparation of an already-ready managed instance also requests an update when its recorded applied version is older than the Service pin, using the existing fenced `starting` lifecycle. [Environments](06-environments.md#one-outstanding-external-operation) owns version freezing, claiming and publication. Existing human desktop reservations, viewers and pending handback defer this first-use update. Maintenance continues a claimed update; it does not start updates on otherwise idle ready instances. Execution connectors, ordinary readiness probes and human grants remain non-mutating.

The guest retains one bounded installation job and its outcome per target version. Reentry joins that job; a failed attempt needs a new explicit lifecycle retry. The existing `retry-creation` API also retries a settled failed managed `starting` operation under workspace write/run authority and the instance ETag. It retains the native target and frozen version, advances the operation identity and generation, and refuses active, unknown or in-use attempts. Console exposes this as Retry preparation. Installation failure retains the previous executable. An interrupted external-manager restart retains its restart-needed marker. Native version-selected restart is idempotent after a lost receipt. Readiness requires a fresh authenticated EIP/Session probe or outbound admission after the restart, rather than installer completion or process launch alone.

An update retires existing Envd Sessions, process/output handles and in-flight work. Files remain subject to the provider's ordinary persistence contract. Session recovery may open a new Session, but never reconstructs old work or replays Agent commands. Unknown command and lifecycle outcomes retain their existing reconciliation semantics.

Managed creation is recoverable through deterministic native names or ownership metadata, including after an interrupted allocation, and native metadata is revalidated before adopting a recovered target. Unknown existence, transient errors, and ambiguous control-plane states fail closed. Reconciliation does not allocate, start, stop, or delete. HTTP deletion waits for authoritative absence or the provider's terminal state before state is discarded, and timeout or polling failure retains state and uncertainty. Execution cancellation, dispatch evidence, and command completion belong to the Harness execution contract.

Native lookup names and backing identities are distinct: Sprites state retains its native ID and Vercel state retains name plus creation timestamp, and `target_identity()` exposes that evidence to Host persistence. Reconnecting preserves Host generation; confirmed replacement advances it even when the lookup name is unchanged.

#### E2B

The allocation recipe selects the template (default `base`), sandbox-wide internet access, and sandbox TTL (`timeout_seconds`, default 3600), alongside the Harness-owned execution inputs. Compatible backends can require their own templates and may lack lifecycle operations. Lifecycle calls use the explicit account API URL or `https://api.<domain>` and never inherit an ambient API URL. Ownership metadata contains the stable Environment identity and configuration fingerprint. Interrupted creation can search allocation metadata; multiple matches and incompatible metadata are conflicts. Search is not atomic create-if-absent, so Service lifecycle coordination remains necessary.

Service accepts `desktop=true` without a template or execution setting: it defaults to `template="auto"`, `execution="envd_http"` and `desktop_assistance=true`. Console selects these together. [Automatic preparation](06-environments.md#automatic-e2b-desktop-builds) resolves a durable credential-scoped private build before calling the management driver. The driver rejects unresolved `auto`; Harness execution never builds templates. Explicit custom templates preserve their previous opt-in semantics.

Headless Envd supports `preparation="headless"` on the selected template's actual sandbox. Service selects it for the stock `base` Envd recipe; custom templates explicitly opt in, while existing custom recipes retain `preparation="preinstalled"`. Preparation requires GNU/Linux x86_64 with glibc >= 2.39, apt-get and util-linux; Debian 13 and Ubuntu 24.04+ satisfy the userspace contract. Incompatible stock Bookworm fails with actionable template guidance instead of upgrading libc. Allocation metadata freezes the installer revision before dispatch. A bounded root-private installation job retains the first script, operation identity, child-held lock and terminal status. Reentry returns `Pending` against the same sandbox; only a new explicit retry can rerun a failed attempt. Installation adds no Python, desktop assets or replacement for E2B's SDK daemon. Native allocation and existing preinstalled-template fingerprints remain compatible.

For `execution="envd_http"` with `preparation="preinstalled"`, the template preinstalls Envd, the shared sandbox entrypoint and (when selected) desktop and viewer components. Creation remembers the allocation before starting those components, generates a private HTTP token per instance, and binds the daemon's device identity to the allocation. No reusable template snapshot contains a generated token or live daemon. The execution account is UID/GID 1001 with `/workspace`; credentials and daemon state are root-owned. Creation and explicit start require authenticated EIP readiness, including Computer methods when `desktop=true`. Recovered preinstalled-template creation checks readiness without rerunning bootstrap; headless preparation rejoins installation and starts the runtime under its existing startup lock before publishing ready. Execution attachment remains check-only. Missing or incompatible prerequisites fail explicitly while retaining the allocated target identity. Native pause/resume preserves the daemon and desktop in memory. `desktop_assistance=true` additionally starts the preinstalled revocable viewer supervisor; grants never install or repair components.

Template selection grants neither Agent tools nor mount permissions. Native E2B keeps the base asynchronous SDK, the `base` default, its configuration fingerprints and lifecycle behavior for Files & Shell. Computer operations require the explicit Envd route; neither resource preparation nor Agent execution uses the Desktop SDK.

`stop()` pauses the validated sandbox with memory preservation; `destroy()` kills only that sandbox. Neither prepares or resumes it. Keepalive rejects paused or missing targets, never shortens an existing deadline, and reports observed expiry. [Execution attachment](../a13n-harness/08b-environment-providers.md#e2b) never performs those operations.

#### Daytona, Modal, Vercel Sandbox, Sprites, and Runloop

Daytona, Modal, Sprites and Vercel with `execution="envd_http"` prepare a compatible Envd runtime and an authorized connection on the selected target. Native Vercel, Sprites, Runloop and boxd retain Files & Shell without Envd or desktop access. Images and snapshots can preinstall Envd; provider bootstrap reuses the [shared executable distribution and installation contract](../a13n-envd/08-protocol-source-client-and-generation.md#executable-distribution-and-installation). Management verifies the required EIP capabilities before publishing readiness. Vendor-specific connection routes do not substitute vendor file, command or Computer APIs for Agent operations.

Daytona recipes default to `snapshot="auto"` for both headless and desktop Envd. Preparation selects the profile from `desktop`; headless snapshots install the daemon and boot assets without Python, X11 or browser dependencies. Automatic desktops enable human assistance unless explicitly overridden. An explicit custom snapshot supplies preinstalled compatible Envd and owns its boot entrypoint; Service does not install into or rewrite that snapshot. An omitted connection `organization_id` is resolved from the current API key; an explicit value constrains snapshot preparation to that account. Creation supplies a stable allocation Device identity and boot configuration; the snapshot starts the preinstalled daemon on creation and after native stop/start, with a private per-sandbox HTTP credential retained on disk. Snapshot construction does not start services or bake credentials into the image. Headless and desktop execution share `/workspace` and the same EIP connection. With Daytona `desktop=true`, the snapshot also supplies compatible desktop packages; management create/start checks the EIP Computer readiness of the recorded target. A startup failure retains the observed target identity for reconciliation and cleanup. Execution attachment does not start or repair desktop processes. With `desktop_assistance=true`, management also confirms the resolved snapshot's preinstalled endpoint. The snapshot starts the supervisor at boot; access calls never bootstrap it. Automatic preparation requires Snapshot read/write/delete authority in addition to sandbox permissions; operators can instead provide a custom snapshot with a runtime-only key.

For Modal `image="auto"` and Daytona `snapshot="auto"`, optional `base_image` explicitly selects a digest-pinned registry base for managed headless or desktop preparation. The base supplies GNU/Linux x86_64, glibc >= 2.39, apt-get, a root build user, and an unused `sandbox` name and UID/GID 1000. Debian 13 and suitably authored Ubuntu 24.04+ bases satisfy this contract. A build preflight rejects incompatible userspace or identities before package mutation. Managed preparation installs its launch assets and replaces the base entrypoint; existing custom image/snapshot selectors remain preinstalled contracts and reject `base_image`. The selected digest participates in the frozen manifest and reusable artifact scope. Once the built native identity is pinned, the allocation recipe drops the build-only base selector. This input does not alter existing execution fingerprints.

Daytona automatic preparation has a durable snapshot ledger scoped by Workspace, Provider, normalized backend, credential version and public manifest revision. The manifest pins the base image, Envd release and checksums of downloaded boot/access components; builds contain no account credentials or guest tokens. Service records a unique name and submission state before cloud I/O, polls the native asynchronous build, and pins the immutable snapshot ID only under the current environment operation and lease. Workers never hold a database session during cloud I/O. Reuse still validates the current account, exact snapshot identity, private ownership, Dockerfile and active state. Credential changes cannot reuse another credential scope.

Ambiguous submission is reconciled by the recorded unique name without resubmitting. Failed or timed-out builds with a confirmed identity are deleted only after identity and manifest validation, and deletion must be confirmed before replacement. Unresolved submission or conflicting identity fails closed and retains its record. Ready snapshots are reusable account assets: stopping or deleting an instance does not delete its snapshot. Deleting an instance before allocation does not allocate a sandbox. A cancelled worker leaves its durable submission and bounded lease for later reconciliation. Console exposes preparation/build/start stages and server elapsed time, continues creation in the background, supports explicit retry of confirmed failures, and provides a read-only desktop snapshot after readiness.

Daytona native stop and start preserve files only with confirmed disabled auto-deletion, so stop fails before dispatch otherwise; delete acknowledgement is fire-and-forget, so destruction polls until `destroyed` or absence.

Modal rejects stop for external registrations because snapshot-based resume would require allocation. A managed stop caches its snapshot selector before terminating the sandbox, resume retains that selector until readiness succeeds, and deletion retains pending snapshot cleanup state until cleanup succeeds. Native ownership tags must agree before deleting snapshot images. Modal execution and custom-image management use an existing App; automatic desktop preparation may create the configured App. Execution creates no Apps and deletes no Host-supplied base image. If an upstream snapshot response is lost before its image ID is known, the provider cannot enumerate that orphan image; this is an upstream limitation, not permission to infer completion.

For Service Modal recipes, omitted `image` means `auto`. The first explicit creation prepares a pinned headless or desktop image according to `desktop`; later creations reuse the matching profile. Headless images install Envd and its launcher without desktop, browser or guest Python dependencies. Credentials alone select the account: `workspace` is an optional descriptive label, `app_name` defaults to `a13n-sandboxes`, and `environment_name` defaults to `main`. Only preparation may create that App if absent. Custom images retain the explicit compatible-image requirement. Automatic desktops default to human assistance enabled, 2 CPUs, 4096 MiB and a 3600-second lifetime; explicit overrides remain authoritative.

Modal preparation owns a durable image ledger scoped by Service workspace, Provider, normalized backend and SDK endpoint, credential version and immutable manifest revision. The manifest pins the base digest, public Envd release and launch/access script checksums; it includes no account or guest credentials and starts no daemons. An account-scoped final layer separates image identities while public dependency layers may use Modal's content cache. Each claim rechecks account and credential identity, commits a bounded lease before cloud I/O, and publishes only with that lease. Public SDK content-addressed builds may be rejoined after cancellation or restart with the same frozen manifest; forced/ignore-cache builds are refused. A 20-minute preparation deadline bounds retries. Ready ledger entries are resolved with current credentials before their exact `im-...` identity is pinned into the environment recipe, under its generation/operation fence. Sandbox allocation begins on the next claim with a fresh operation deadline.

A definitive build rejection remains failed until explicit retry or a new instance binds a new preparation; unresolved builds keep their frozen inputs. Builds allocate no ephemeral Sandbox. Clients close under bounded shielding on success, failure and cancellation. Content-addressed layers and the shared App remain intentional reusable account assets; they are not deleted as speculative cleanup. Once allocation begins, existing native ownership, EIP/desktop readiness, snapshot cleanup and lost-target checks apply unchanged. This is a Modal-specific preparation capability, separate from E2B template provisioning.

Modal desktop authorization shares one Client and one validated Sandbox across discovery, optional renewal and grant. Handback shares them across all grant revocations and final input settlement; every revocation must be confirmed before settlement, and settlement must confirm input cleanup before publishing readiness to resume. Each request pins the saved native target, validates current ownership tags and liveness before commands, and retains per-command generation/epoch checks and final durable authorization checks.

Service owns a bounded process-local cache of Modal transports across requests and execution attachment. Reuse is isolated by Provider identity, configuration version, credential version, backend locator, logical environment, recipe fingerprint and exact Sandbox ID. Each borrow repeats target validation; cached transports confer no authority, retain no desktop grants or Envd Session hints, and never replace current credentials or endpoint policy. SDK access to one cached Sandbox is serialized; Envd execution releases that SDK lease before yielding its independent EIP Session. Separate control and worker processes have independent caches.

Failures, cancellation, ownership mismatch and terminal targets retire the affected transport without replaying commands or discovering a replacement. Create/start/stop/destroy invalidate the saved target's cached transport before lifecycle work. Idle expiry, maximum age, capacity eviction and process shutdown close local Sandbox/Client resources; an active borrower releases its retired resources after bounded cleanup. Returning a successful request releases its borrow before the final database transaction, while the local transport may remain cached. Other providers retain their existing lifetimes.

Vercel retains native Files & Shell and its existing configuration fingerprint by default. Explicit Envd execution selects automatic final-target preparation when `snapshot` is omitted or `auto`, or a compatible preinstalled custom snapshot when an exact ID is supplied. `desktop=true` adds desktop prerequisites, and Service `desktop_assistance=true` enables the access supervisor. Management creation and start reconcile components on the recorded native session, including recovery after lost replies. Preinstalled custom snapshots supply an explicit `startup_command`; its bounded per-session guest job retains a confirmed result across reentry, and only an explicit preparation retry starts a new attempt after failure. Execution attachment and grants never repair or resume a target. Startup failure retains allocation evidence for cleanup. Each EIP attachment validates ownership and pins the native session, checks the discovered TLS route against Host policy before reading the root-private guest token, and negotiates the expected Device and capabilities. Account credentials stay on the vendor control API; guest credentials stay on EIP; the browser receives only per-grant desktop credentials. Desktop commands within one management request share a validated session while retaining guest generation/epoch and durable authorization checks. Stop/resume preserves disk, recreates processes, and invalidates old observations and grants.

For Service Vercel recipes, `desktop=true` defaults to `execution="envd_http"`, `snapshot="auto"` and human assistance enabled. Automatic recipes default to a 2700-second lifetime compatible with Hobby accounts; explicit values remain authoritative. Explicit custom snapshots and the native default remain supported. Console accepts a token and lists its accessible teams and projects through a bounded, write-authorized discovery request. Draft credentials are not persisted by discovery or placed in query caches. Selecting another credential clears the earlier choices. The selected team and project are saved in the Provider connection.

Vercel automatic preparation installs directly on the final persistent Ubuntu target. Before installation, Service publishes its native identity as settled `Pending` state; subsequent claims rejoin that target. A frozen headless or desktop manifest pins the public Envd release and launch scripts. Headless preparation adds no Python, jq, browser or display dependencies. The vendor Ubuntu image and, for desktops, Ubuntu/Chrome repositories supply system dependencies; those package versions are not content-pinned. A bounded root-private installation job records its revision, operation identity, child-held lock and terminal result. Reentry retains the original attempt instead of replaying partial installation. Only an explicit retry may restart a confirmed failed attempt. Readiness requires an authenticated EIP connection to the recorded native session.

Historical Vercel snapshot-ledger waiters continue their frozen build and pin the exact resulting snapshot under the environment operation and generation fence. New automatic creates never bind that ledger. An explicit retry clears a confirmed failed legacy reference only while no native target exists, so the next claim uses final-target preparation. Unknown allocation and snapshot outcomes retain their reference: unique name/tags and exact source session reconcile them without a second submission. Credential and full backend identity are checked before cloud I/O, outside database sessions.

Control maintenance also advances a bounded batch of unfinished legacy ledger entries with no creating dependents, using cancellation-only steps and the existing lease and native ownership checks. Dependencies and active leases are rechecked before claiming. Disabled Providers permit cleanup; changed credentials or account identity retain a diagnosable record. Blocked entries rotate behind other candidates. Failed temporary builders and unfinished snapshots require provenance checks and confirmed deletion; expiry alone never proves absence. Ready ledger entries and successful snapshots remain reusable account assets, including for explicit custom snapshot inputs. The ledger and saved-handle readers remain compatible. Console reports the frozen preparation profile, stage and elapsed time, continues creation after navigation, supports explicit retry after confirmed failure, and offers a read-only desktop preview after readiness.

Vercel Sandbox destruction verifies target absence and requests native orphan-snapshot deletion, which the provider performs asynchronously without deleting snapshots still used elsewhere.

Fly.io Sprites automatic native sleep and wake retain disk. There is no supported explicit stop operation, and the capability declaration prevents a Host from presenting one. Destruction verifies absence of the exact named backing target.

Runloop suspend and resume preserve disk. Keepalive uses the returned target idle policy rather than an assumed recipe interval, and shutdown is complete only after confirmed native shutdown or absence.

boxd creates one isolated machine per Environment under a deterministic name with ownership labels, and recovers an interrupted allocation by those labels. Ordinary creation passes the recipe's environment defaults to the new machine; a snapshot restore takes none, and commands receive the defaults either way. An acknowledged create records the machine ID before any further read, and ownership labels are validated whenever the machine is read back, so a failed read after allocation stays retryable and keeps the machine. Stop hibernates the recorded machine with disk and memory; start wakes a hibernated machine, starts a stopped one, or resumes one in standby, then waits for command readiness within the recipe's request timeout. A create that meets its own deterministic name adopts that machine only after its ownership labels match. Start also applies the recipe's idle hibernation timeout, which defaults to off, so an idle ready instance does not become stopped on its own. Idle standby is reported as running because the next command resumes it. Destruction deletes the exact recorded machine ID and completes only after confirmed absence. The SDK client uses a fixed API endpoint and the account's region with SDK request retries disabled, so a mutation with an uncertain outcome is reconciled instead of resent. The SDK reruns a command only when the machine never received it.

These management drivers refuse destruction of externally owned targets. Service's managed `local` driver and its directory lifetime remain defined by [Environments](06-environments.md); it is distinct from Harness `direct_local`, which operates an existing Host directory and has no management lifecycle.

### Automatic Sprites desktops

A Service Sprites recipe with `execution="envd_http"` or `execution="envd_ws"` installs Envd on the actual target. Headless preparation installs the pinned daemon and verified shell launcher without Python, browser or display dependencies. Selecting `desktop=true` defaults to Envd execution and desktop assistance and adds desktop assets and packages. There is no template, image, checkpoint clone or cross-Sprite installation cache. A retained Sprite keeps installed files across vendor-managed sleep and wake. The account token must permit ownership labels and desktop route configuration; restricted tokens that cannot set labels fail rather than bypassing ownership validation.

Allocation uses the existing deterministic name, ownership/configuration labels and immutable native ID. The frozen handle records installation revision and phase; short background claims publish installation progress without treating a pending installation as ready or as a diagnostic failure. A root-private lock and terminal status reconcile a lost launch response. Installation has a bounded deadline. A failed or interrupted installer is retried only by an explicit new creation operation on the same validated target; a changed installation revision is rejected. Deletion validates ownership and confirms target absence, including when installation is incomplete.

Readiness requires authenticated EIP capabilities for the selected profile; desktop readiness additionally requires observable, input-ready Computer targets. Credential loading and readiness probes require no guest Python. The provider-owned service supervises restart after automatic wake. Envd remains loopback-only behind the private vendor TCP proxy. For opted-in human access, the browser-reachable HTTPS route serves only the desktop supervisor on port 6081; its independent short-lived grant token and VNC password enforce access. Cloud credentials never enter the browser, target state or guest files. Desktop access retains the generation, epoch, expiry, revocation and held-input cleanup checks above and cannot repair or provision a desktop.

Console explains the per-new-Sprite installation delay before creation, displays the persisted stage and server-based elapsed time, and allows navigation while background work continues. Confirmed failures expose an ETag-fenced retry. Ready instances expose the existing authorized, uncached read-only desktop preview when their saved execution mode supports standalone preview; `envd_ws` keeps that action disabled.

## Kubernetes

The Kubernetes management provider creates a directly managed Pod and composes Harness EIP execution. A recipe contains a native PodTemplateSpec, an explicit execution-container binding, storage bindings and an optional instance NetworkPolicy. Deterministic names, ownership labels, recipe fingerprint, bootstrap volume and execution bindings are platform-owned; conflicting recipe fields are rejected. Deployment and StatefulSet adoption is outside this provider.

Operator-configured cluster profiles select refreshable in-cluster or explicit kubeconfig/context authentication, allowed namespaces, the ownership ID and sandbox ServiceAccount. Sandbox Pods disable automatic ServiceAccount-token mounting. Native Pod authoring remains privileged configuration subject to cluster admission; namespace access alone is not tenant isolation.

Each instance freezes its recipe and native resource inventory before allocation. Resource references carry exact UIDs and delete, retain or borrowed disposition. Per-instance PVCs are created before the consumer Pod without waiting for binding, allowing WaitForFirstConsumer. Borrowed resources and shared-PVC directories survive retirement; retained resource references remain in the instance retirement receipt. Destruction removes the Pod first, uses UID preconditions, and completes after required resources disappear. It does not strip third-party finalizers or delete same-name successors.

Creation publishes paced pending progress for native scheduling and Envd preparation. The execution container uses a ready Envd image or an explicitly authored bootstrap command. An authored initContainer may publish the compatible binary and startup assets into a shared volume mounted by the execution container; its package installation cannot modify the execution container's separate root filesystem. The recipe owns image userspace compatibility, command, shared mounts and native restart policy. Rendering preserves those choices and injects only platform-owned bindings, without a hidden package installer or entrypoint replacement. Running alone is not readiness: publication requires authenticated EIP attachment to the expected device. HTTP uses direct Pod reachability or an explicitly enabled, process-owned port-forward; ordinary Agent operations use EIP. The instance-private bootstrap credential is supplied outside portable state and reused across retries. Fixed native identity and bootstrap are independent of the transient tunnel endpoint. Pod loss refuses new execution rather than allocating a replacement under the old identity. Kubernetes supports creation, inspection and destruction, with instance idle-delete rather than stop/resume.

### Inspection and preflight

The saved Provider's nonallocating test verifies trusted profile selection, the required HTTP transport opt-in, cluster authentication and namespace Pod-list access. A denied HTTP policy returns an operator-actionable configuration failure before native requests. Its result explicitly identifies creation permission, admission, scheduling, storage and Envd readiness as requiring an explicit smoke Environment. It creates no native resources or EIP Session.

`GET /environments/{id}/kubernetes/diagnostics` returns the instance lifecycle snapshot and a timestamped native observation: exact identities, resource disposition, presence versus unavailable inspection, Pod/PVC status, readiness and restart details, finalizers, bounded UID-selected events, a redacted rendered configuration and native kubectl guidance. Envd readiness is labeled as the previous published observation, not a new execution grant. Missing and denied observations remain distinct. The rendered configuration omits literal environment values, command arguments, annotations and secret data.

`GET /environments/{id}/kubernetes/logs` reads one named container, including previous-container logs on explicit request, with at most 1,000 tail lines and a 65,536-byte upstream limit. The target UID is checked before and after the name-addressed logs request. Both queries require workspace run and Provider use authority, perform native I/O outside database sessions, and leave the idle clock and debug hold unchanged. Platform bootstrap credentials are redacted from diagnostic messages and logs; guest logs remain potentially sensitive content under that authorization.

## Invariants

1. Service owns vendor management and durable lifecycle decisions; drivers perform no database operations.
2. Shared execution schemas and codecs have one Harness owner and are reused by Service.
3. Vendor I/O and waits occur outside database transactions.
4. Only management dispatches explicit target allocation, start, stop, destruction, or renewal; declared native automatic sleep/wake remains a backend behavior.
5. Connector construction is inert; execution cleanup cannot retire a target.
6. Unknown dispatch retains operation identity and observed state for reconciliation.
7. Every infrastructure vendor retains an Environment Provider subclass for its resource management. Native Agent execution is limited to Local, Docker, E2B, Vercel Sandbox, Sprites, and Runloop Files & Shell; general execution and advanced operations use Envd/EIP without native fallback.
