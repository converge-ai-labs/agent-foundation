# Environments: mounts and external lifecycle

## Design position

A thread chooses environments; a run uses the mount set frozen for it at acceptance. Several threads may share one instance, so lifecycle coordination is a property of the **instance and all its active users**, never of one thread or worker. Every external lifecycle call belongs to a durable, fenced operation. A confirmed-lost instance refuses new use with `environment_lost`. A session can authorize a new primary instance for a later run.

A `reserved` managed instance has a durable identity and selected template/provider but no native target, operation, claim, failure, or renewal schedule. Reservation is not a queued create. A **managed** instance has a template and its provider. An **external HTTP target** has neither, nor a handle or provider identity, and holds the `device_id`, `endpoint` and `token` of the envd daemon it reaches ([external targets](#external-targets)). A **client environment** also has no provider or template; its registered device connects outbound to Control and its separate settings hold a connection-token hash ([client environments](#client-environments)). A target belongs to the principal that registered it (`owner_principal_id`); managed instances have no owner. The instance references its provider by `(workspace_id, provider_id)`, so the database refuses a provider of another workspace ([04](04-resources.md#provider-resources)), and identity columns never change.

- `handle` is `{recipe, state, credential_version, outbound?, e2b_desktop_template?}`: the recipe a managed instance was built from, the provider's portable state for reaching it, and the version of the provider credential that last reached it, which is its encryption envelope's nonce and changes whenever the credential is written.
- `provider_identity` is `{type, backend}`, the provider type and non-secret backend locator the handle is meaningful in. It is frozen when a managed instance's create operation is first claimed; NULL means the create was never claimed.
- `token` is an external HTTP target's credential, encrypted for its own row and column; the tombstone drops it.
- `envd_bootstrap` is an instance-private managed Envd credential, encrypted for its own row and column before native allocation. Kubernetes creation retries and fixed-target attachment reuse it. It is separate from readable recipes and portable state, and is erased only after confirmed deletion.
- `retirement_state` retains the provider's secret-free final deletion receipt independently of the cleared live handle. Kubernetes receipts keep exact retained storage and borrowed resource references; retaining a receipt grants no execution or deletion authority.
- `failure` is `{code, message, certainty, permanent, operation_id, at}`: the last error of the outstanding operation or, on a ready instance, of its last [renewal](#renewal), whose `operation_id` is NULL. `certainty` is `not_dispatched`, `known` or `unknown` (the call may have taken effect); `permanent` failures refuse new use until the cause is fixed or the instance is deleted. An unknown outcome is never permanent. A provider error's `message` is its category's safe message with the provider and error code, such as `Environment provider operation was denied (e2b, provider_denied).`; when the provider's schema refuses the recipe, it adds up to five fields with the schema's reasons. It never contains input values or upstream text.
- `renew_at` is when the next [renewal](#renewal) of a ready sandbox whose type ends sandboxes unless renewed is due, and `expires_at` the expiry its provider last reported. Changes confined to them keep the version, so renewing leaves the ETag unchanged.
- The view shows everything except `replaces_environment_id`, `retired_for_idle`, `handle`, `provider_identity`, `token`, `envd_bootstrap`, `generation`, `operation_deadline`, `next_operation_at`, `operation_unsettled`, `renew_at`, `expires_at` and the lease columns.

Mount names match `^[a-z][a-z0-9-]{0,62}$`; `workspace` is the primary mount. A `working_directory` is a canonical absolute path of at most 1024 characters, without empty, `.` or `..` segments. Inserting, updating or deleting a thread's mounts bumps the thread version.

## Templates and instances

Operator-selected Local and Docker defaults are prepared by [workspace provisioning](09-runtime.md#workspace-provisioning). A Docker recipe accepts `pull_policy: never | if_missing` (default `if_missing`). `never` uses only an image already in the configured Engine; a missing image fails with `environment_image_missing` and build/load guidance. Image acquisition policy is not part of the native container identity.

A template is live configuration ([04](04-resources.md#environment-templates)). Its effect on instances:

- **The recipe is frozen per instance.** The first claim of an instance's create operation validates the template's current recipe, materializes its effective provider defaults into `handle.recipe`, and freezes `provider_identity` before any external call. A reservation does not freeze the recipe: edits before its first create claim apply to it. Later template edits and changes to provider defaults apply only to instances whose first create claim is still pending; after that claim the instance never changes its image, resources or storage. Explicit template values remain explicit even when equal to the current default. A legacy Docker handle without `image` retains `ghcr.io/converge-ai-labs/a13n-docker-environment:dev`, including a create whose response was lost before portable state was saved; reconnect, retry, stop and delete never reinterpret that omission as the current release.
- **Automatic E2B desktop preparation is pinned before allocation.** A recipe with `template="auto"` binds a durable `e2b_desktop_template` reference at first claim. That record freezes the build manifest and credential scope. Once its private native template and sole build are validated, a fenced transaction resolves `handle.recipe.template` to that native template ID before sandbox allocation. This resolution does not change the selected manifest. Restarts reuse the pinned reference; later releases and credential changes never rewrite existing instances. Preparation pending is a normal `creating` outcome, polled by maintenance without holding a database transaction.
- **Reclamation is instance-scoped.** An explicit template `reclamation` is copied at reservation. Later edits apply to new instances. Without it, maintenance reads the template's current `stop_after_seconds` and `delete_after_seconds` ([idle policy](#idle-policy)).
- **Disabling refuses new instances.** A disabled template refuses reservation, and a reserved instance whose create was never claimed fails its first claim with the permanent failure `environment_template_disabled`. Instances already created keep working.

### Desktop release assets

Service desktop recipes for E2B, Daytona, Modal, Vercel and Sprites share an explicit Envd release version and target. Recipe rendering performs no network I/O: the frozen manifest or installation script includes the complete installer and release selection. During the cloud build or installation, the installer downloads the archive and `SHA256SUMS` from that exact official Release, verifies the archive checksum and executable version, and then replaces the destination binary. A failed download, checksum, extraction or executable check leaves an existing binary unchanged. The published Release owns the archive digest; Service does not maintain separate per-provider archive hashes or select `latest`.

Changing the release selection or installer changes each provider's recipe revision. Existing frozen manifests and ready cloud artifacts retain their original inputs and identities; retry does not rewrite them to the current recipe. Launcher and desktop-access sources retain their independent source-revision and checksum pins.

### Automatic E2B desktop builds

`e2b_desktop_templates` retains the provider/workspace, backend domain, credential envelope version, manifest, random private alias, native template/build IDs, phase, bounded claim and 20-minute preparation deadline. Its unique scope hashes the workspace, provider identity, domain, credential version and manifest revision. An advisory lock deduplicates first binding; short row claims coordinate build phases across workers. No API key, guest credential or upstream build log is stored in this record.

Service persists reserve/submit intent before network dispatch and IDs before the next mutation. An expired claim reconciles the private alias or exact build status; it never blindly repeats an ambiguous reserve or submit. A missing alias after an ambiguous reserve remains unresolved and never authorizes another allocation. Reuse verifies private ownership, alias and sole build identity through the current credential. Changing credentials refuses an outstanding old preparation; new instances use a new scope.

The E2B builder downloads a pinned official Envd archive and checksum-verified startup sources into a digest-pinned base image, installs desktop packages, and verifies that no guest token or running access socket is baked in. Each sandbox separately initializes credentials, verifies authenticated Envd identity and Computer readiness, and owns its access grants. Custom templates retain their existing explicit configuration.

A failed or timed-out build is deleted only after its private alias and build ownership checks. Ambiguous deletion retains cleanup intent for the next dispatch. Confirmed failure remains attached to its original instances; a new instance can start a fresh preparation after that failure is recorded. Successful private templates intentionally remain reusable account assets when individual sandboxes are deleted. With no remaining waiter, unfinished records remain available for reconciliation on the next use; Service does not run a separate template garbage collector. Unresolved identities and mismatches are retained for operator inspection, never silently replaced or deleted. Existing sandbox allocation failures retain their native target for ordinary lifecycle cleanup.

## Mounts

A thread's **desired mounts** are the environments later runs will use. `POST …/threads/{thread}/environments` adds one (`{name, environment_id, working_directory?, permission_ceiling?}`) and `DELETE …/threads/{thread}/environments/{name}` removes one; both need `run` and the thread `If-Match`, answer with the new thread ETag, and are audited as `thread_environment.create` and `.delete`. Adding needs an open thread. To replace a mount manually, remove the name and add it again. A duplicate name is `already_exists` (kind `mount`); an environment already mounted on the thread is `conflict` (`already_mounted`). A thread holds at most 32 desired mounts: a path that would add more is `conflict` (`mount_limit`, details `limit`), and a request naming more than 32 is `invalid_argument`. Acceptance's primary reservation below may add one beyond them, and a `shared` child adopts all of its parent run's frozen mounts. `GET` lists the mounts with the thread ETag.

Mount representations include read-only `desktop_enabled`, derived from the instance's frozen `desktop` and `desktop_assistance` recipe settings. It is false before a recipe is frozen. This flag lets clients select human-desktop candidates independently of Agent Computer permissions and later template edits. It does not probe readiness or grant access; desktop operations retain their current authority and lifecycle checks. Mount creation/update inputs and frozen Run mounts contain no such projection.

Every new use checks the instance under its row lock:

- an external HTTP target of another principal is `forbidden`; client environments are shared with principals holding workspace `run`;
- a `deleting` or `deleted` instance is `conflict` (`environment_{status}`). Selecting a superseded instance ID for a mount continues to report `environment_lost` after retirement;
- an instance with a permanent failure is `conflict` with the failure's code.

Mounts share-lock their instances in ID order: new use excludes a concurrent stop, delete or lifecycle step, never other new use. The same checks apply to every path that adds mounts:

- **New threads and forks** may name up to 32 initial `environments`, added in the transaction that accepts the first run. A fork also shares the origin thread's desired mounts unless `fresh_environments` is set, and its shared and named mounts together count against the 32; shared and named mounts are checked and locked in one ID-ordered pass, so an unusable shared mount refuses the fork (`forbidden` or `conflict`).
- **Child threads** take their mounts from the delegating edge ([05](05-runs.md#child-runs)): `shared` adopts the parent run's frozen mounts, `dedicated` reserves an instance from the edge's template, `none` mounts nothing.
- **Acceptance** freezes the thread's desired mounts into `runs.environment_mounts` ([05](05-runs.md#source-selection)), checking each instance for the run's principal. If the thread has no `workspace` mount, acceptance first gives it one from its primary source. A new or forked thread uses its agent's `default_environment_id` when configured: acceptance mounts that existing instance as `workspace`, with ordinary mount validation and permissions. Otherwise its source is `default_environment_template_id`: acceptance reserves a managed instance from it and mounts it as `workspace`. These defaults are mutually exclusive. An existing thread primary always wins; changing the Agent default never replaces it or a run's frozen mounts. A child thread never uses its agent's default environment or template. Its source is the edge that spawned it, as its parent run resolved it ([05](05-runs.md#child-runs)): a `dedicated` edge's template, used the same way, or for a `shared` edge the parent thread's current `workspace` mount, mounted with the same working directory and permission ceiling. A shared child whose parent has no `workspace` mounts none until the parent's own acceptance gets one.

### Confirmed loss of the primary environment

The session boolean `auto_recreate_lost_environment` defaults to true, including for existing sessions. When accepting a run that uses the thread's desired `workspace` mount, Service checks the instance's recorded failure. A settled, permanent `environment_lost` with certainty `known` allows recovery. Under the workspace reservation lock, acceptance follows the successor links to the latest instance. If that instance is also confirmed lost, acceptance reserves its replacement from the same template with the usual template, provider and authorization checks. A new row records its predecessor in `replaces_environment_id`, unique within the database. Concurrent recoveries therefore share one replacement. A thread returning after several losses follows the links through retired instances. If idle policy has deleted the latest replacement, the next eligible run reserves a new successor against the current quota. Both threads already bound to the retired replacement and threads still on an ancestor follow the same chain. A deletion in progress, an explicitly deleted latest instance, or another permanent failure refuses recovery.

Only the accepting thread updates its desired mount. Rebinding, reservation if needed, the audit event `thread_environment.recreate` with both IDs, and acceptance commit together. The mount keeps its working directory and permission ceiling. A named child can replace its dedicated environment. Shared children, explicit run-only selections and desktop handback retain their exact targets. Other mount names and external targets follow their ordinary usability checks. Disabling the setting preserves the original binding and the `environment_lost` refusal even if a different session has recovered. Each accepted run keeps its frozen mount set across attempts, including when its own first use discovers the loss.

The replacement starts with the template's fresh filesystem. The usual [preparation policy](#execution) determines when its native sandbox is created. A later run sees the mount change through the [turn reminder](05-runs.md#turn-reminder).

### Run-only primary selection

`RunOptions.environment` optionally selects the primary `workspace` mount for one accepted Run:

- `{mode: "fresh", template_id}` reserves a new instance from that template at acceptance.
- `{mode: "existing", environment_id}` selects that exact usable instance.
- Omission or null uses the Thread's desired mounts and normal primary reservation above.

An explicit selection replaces only the Run's primary mount; other desired mounts remain. Both modes accept the usual optional `working_directory` and `permission_ceiling`, defaulting to no directory override and the standard file/execution ceiling. It never inserts, removes or rewrites a desired Thread mount. The same instance cannot appear again under another mount name. Reservation and exact-instance selection use the ordinary workspace authorization, capacity, ownership and usability checks. An explicitly selected missing, deleting, deleted or permanently failed instance refuses acceptance; it never falls back to an Agent default.

Acceptance stores the resolved instance in `runs.environment_mounts` in the same transaction as the Run. Idempotent command replay, attempt retry and Worker takeover reuse it. A new message requesting `fresh` reserves again; resume and inherited result continuations keep their originating Run's resolved primary and refuse it if no longer usable. A later ordinary message without this option uses the unchanged Thread selection. Omitted values preserve historical request and options digests.

An instance is **in active use** while an accepted or running run's frozen `environment_mounts` names it, while a nonterminal [retained tool execution](05-runs.md#retained-tool-executions) holds that frozen mount set (including cancellation cleanup), or while a desktop control record holds the reservation of its native sandbox or container ([06a](06a-environment-management.md#computer-only-desktop-control)). The frozen mounts are durable evidence across worker loss, handoff and backoff; a GIN index answers "which active runs use this instance". A target reservation covers every instance whose handle names the same native target, across registered aliases. Removing a desired mount never hides active use.

**Reservation** creates a managed instance in `reserved` without an operation, from an enabled template of an enabled provider the principal may `run`. Each managed instance occupies a workspace quota slot until deletion or replacement. Replacing a confirmed loss transfers its slot, including when the limit is one. A successor after idle deletion needs a free slot because deletion already released the previous one. Creating another independent environment beyond `environments.managed_count` is `conflict` (`environment_limit`, details `limit`). The workspace reservation lock serializes new reservations and successor selection, and no transaction that locks an instance exclusively reserves, so acceptance may reserve before or after share-locking the instances it mounts ([05](05-runs.md#lock-discipline)). Acceptance and dedicated-child reservations remain `reserved` until an authorized use requests readiness. Control maintenance never begins creation for `reserved` instances. A run that never uses its mount can finish without any target allocation.

`POST …/environments {template_id, name?}` explicitly requests creation: it reserves the identity and begins `creating` in the same transaction (`run`; 201; audited as `environment.create`); the name defaults to the template's name. This retains the explicit create API's eager behavior. Service may also prepare a run's source ahead of first use by calling the same readiness path; there is no separate lifecycle implementation or Harness mode.

Existing instances retain their status and outstanding operation when `reserved` is introduced; an existing `creating` instance is never downgraded to a reservation. API representations and status filters include `reserved` as a non-ready state. Clients must not infer native allocation from the presence of an environment ID.

Each mount carries an exact Harness `EnvironmentPermissionSet` as `permission_ceiling`. Omission, including on historical frozen Run mounts, preserves the file/execution action set and grants no `environment.computer.*` actions. `PATCH …/threads/{thread}/environments/{name}` replaces this ceiling with `{permission_ceiling}` under `run`, an open thread and the thread `If-Match`; it rechecks authority over the target, returns the new thread ETag and audits `thread_environment.update`. The primary `workspace` mount is editable through the same route. Accepted Runs freeze the ceiling with the mount; changing desired permissions never mutates an accepted Run. Forks sharing desired mounts and children sharing frozen mounts preserve those ceilings.

Computer Use requires both the Agent's enabled `computer` toolset and explicit Computer actions in a mount ceiling. Harness intersects this authority with the provider's supported actions and current readiness at execution. Enabling it does not provision a desktop or add one to an existing headless image. These permissions govern Computer operations only; file, shell and other separately authorized operations retain their own authority. Static Computer permissions alone do not establish exclusive ownership; opted-in desktop access additionally follows the [Service handoff contract](06a-environment-management.md#user-requested-desktop-control).

`POST …/environments/{id}/computer/check` requires workspace `run` and the same private-target ownership as execution. It probes only a ready instance using a bounded temporary execution after closing the authorization read session. It neither starts an instance, captures pixels nor sends input. The result distinguishes `not_ready`, `unsupported` and `checked`, reporting observation/input readiness, display count and exact Computer actions. Provider errors remain failures, not unsupported results. The probe releases its execution on completion, failure and cancellation; its result is a point-in-time capability observation, not a permission grant or a guarantee for a later Run.

## One outstanding external operation

The status names the instance's outstanding operation: `creating`, `starting`, `stopping` or `deleting`. No other status carries one, and an error stays on the phase with the same operation.

1. **Begin.** Under the environment row lock, set the phase, increment `generation`, allocate a new `envoper_` `operation_id`, clear any claim and failure, and commit. A different operation replaces an outstanding one only when the outstanding one is **settled**: nobody holds or silently lost its claim, no pending provider request can still allocate additional resources, and its last call did not end with an unknown outcome.
2. **Claim.** A dispatcher locks the row, finds the claim free or expired and `next_operation_at` absent or due, records a fresh token, a call deadline of `environments.operation_seconds` and a claim that outlives the deadline by 10 seconds, and commits. The claim first refuses, as permanent failures without dispatching: a provider whose backend identity cannot be resolved (`environment_provider_unavailable`), a disabled provider for `creating` or `starting` (`environment_provider_disabled`), a disabled template at the create's first claim (`environment_template_disabled`), a template whose provider changed since the reservation, also at that claim (`environment_template_moved`), and a provider that now points at another account or endpoint (`provider_identity_changed`). Stop and delete still proceed on a disabled provider.
3. **Perform.** With no database session held, one bounded call: `creating` calls provider `create()`; `starting` calls `inspect()`, fails with the permanent, known `environment_lost` if it no longer exists (or with `provider_credential_changed`, which is not permanent, when the provider's credential changed since it last reached the instance, as for [renewal](#renewal)), and otherwise calls `start()`; `stopping` calls `stop()`; `deleting` calls `destroy()`.
4. **Publish.** Lock the row and record the outcome only if generation, operation ID and claim token still match; a superseded dispatcher changes nothing. Success clears the operation and failure, reaches `ready`, `stopped` or `deleted`, stores the new handle state and the version of the credential that reached it (a deleted instance keeps no handle), sets `last_used_at` on `ready` and schedules its first renewal when its type requires one, and audits `environment.{ready | stopped | deleted}` with no actor. A failure clears the claim, keeps any state the provider reported, and records the failure on the same phase. A failure before dispatch after an earlier unresolved dispatch is recorded as unknown. A dispatcher interrupted mid-call publishes the unknown failure `environment_operation_interrupted`.

A normal pending result persists partial state, clears the claim without recording a failure, and schedules `next_operation_at` using the provider's positive delay (at most 300 seconds). Both Worker first-use preparation and Control maintenance honor that timestamp. The phase, generation and operation ID stay unchanged. Pending work blocks replacement unless the provider confirms no request can allocate further resources and the recorded state identifies everything cleanup must reconcile. Native preparation of already identified resources may continue while cleanup replaces a settled create. A later local refusal cannot erase an unsettled request's uncertainty. Completion clears both progress fields; late progress is fenced like any other result.

Managed Envd instances keep an applied binary version and an optional in-flight target version in their private handle. Beginning create/start freezes the Service pin, floored by any newer applied version; continued claims retain that target across Service deployments. Successful fenced readiness publication records the applied version and clears the target. Pending, failed and superseded results cannot advance it. The first authorized preparation of a ready instance whose managed version is older than the Service pin begins `starting` under the same row/Run locks before returning an execution target. A second caller joins the existing operation. Other active Runs or retained tools, human desktop reservations, viewers and pending handback postpone that update while the current ready runtime remains usable. The caller's own Run and current tool do not block its first-use update. Native allocation/start precedes the guest update, and authenticated readiness follows it, so an unavailable old daemon cannot prevent upgrade reconciliation. A failed update on a previously ready instance retains that instance for explicit retry; it does not start failed-initial-preparation reclamation. Ordinary connection/readiness checks do not begin an update. [Management providers](06a-environment-management.md#managed-envd-versions) own installation and restart behavior.

An expired claim lets the next dispatcher continue the **same** operation. Shared provider management reconciles the selected instance by stable Environment and operation identity even when no state was recorded: create recovers an earlier allocation, while stop and destroy observe actual state without allocating. So continuing never issues conflicting work, and a timeout never mints a new operation ID.

| Status     | Next action                                                                                    |
| ---------- | ---------------------------------------------------------------------------------------------- |
| `reserved` | Wait for authorized first use or explicit preparation; no maintenance create or renewal        |
| `creating` | Prepare the instance from the frozen recipe; a continued create finds the instance first made  |
| `ready`    | Renew when required; first authorized preparation starts a pending managed Envd version update |
| `stopping` | Continue the same stop until it is known                                                       |
| `stopped`  | An attempt requiring readiness begins `starting`                                               |
| `starting` | Resume the same handle; a lost instance fails permanently and is never recreated               |
| `deleting` | Continue destruction; new mounts and starts are refused                                        |
| `deleted`  | Terminal tombstone; the ID is never reused                                                     |

**Maintenance.** The `maintain_environments` sweep ([09](09-runtime.md#sweeps)) runs every `environments.scan_seconds`. Reserved instances are excluded from lifecycle dispatch; after readiness begins `creating`, maintenance can continue that operation even if the requesting attempt ends. Each pass begins idle deletes, then idle stops, then dispatches, concurrently, up to `environments.batch` outstanding operations whose claim is free or expired and whose pending delay has elapsed, oldest change first. A start with confirmed target loss ends preparation for that instance. Other retryable failures are revisited at the fixed interval with the same operation ID. A dispatch that fails unexpectedly is logged and retried by a later pass. A pass is bounded by twice `environments.operation_seconds` plus 30 seconds. The pass also advances at most `environments.batch` orphaned historical Vercel builds through cancellation-only steps, each bounded by `environments.operation_seconds`, under the [legacy preparation contract](06a-environment-management.md#daytona-modal-vercel-sandbox-sprites-and-runloop). Renewals have their own sweep, so a slow lifecycle call never delays one ([renewal](#renewal)).

### Idle policy

Idle time counts from `last_used_at`, or `created_at` when the instance was never used. `last_used_at` is set when an instance becomes ready, when an attempt finds it ready and when an attempt stops using it. Instances in `creating` use the preparation deadline and failed-retention policy below instead of the idle timer.

- **Idle stop.** A ready managed instance whose type supports stop, idle past its template's `stop_after_seconds`, not in active use and without a permanent failure begins `stopping`. Stopping would clear a failure, such as `environment_lost`, that refuses its use.
- **Idle delete.** A `reserved` instance not in active use becomes `deleted` without a provider call after `delete_after_seconds`; its idle time starts at reservation. A ready or stopped managed instance whose type supports destroy, idle past `delete_after_seconds` and not in active use begins `deleting`. Idle deletion records `retired_for_idle` and removes thread mounts in the same transaction, except desired `workspace` mounts of replacement instances. These keep the shared recovery chain while the retired instance occupies no slot once deleted. The threads precede the instance in the lock order, and neither lock waits: an instance that a thread locked elsewhere mounts is left to a later pass. A thread that loses its `workspace` mount gets one from its primary source at its next acceptance ([mounts](#mounts)), and that run's model is told which mounts changed ([05](05-runs.md#turn-reminder)).
- **Confirmed loss.** Maintenance preserves a lost instance while any thread mounts it, including before the first recovery and past an idle deadline. Once it has a successor and its last mount, active use and debug hold are gone, maintenance can retire it through the usual settled, destroy-capable lifecycle with audit reason `replaced`, regardless of its idle policy. Its row and successor link remain available for exact selections and later recovery.

Idle stop and delete recheck active use with a fresh statement under the row lock, an idle delete also the threads that mount the instance, and audit `environment.stop` or `environment.delete` with no actor and reason `idle`.

### Instance reclamation and debug holds

An explicit `reclamation` contains `idle_delete_seconds` (default 1800; null disables idle deletion), `preparation_seconds` (default 600) and `failed_retention_seconds` (default 3600). Reservation copies it onto the instance. Kubernetes templates always use this policy; other destroy-capable providers can opt in. It replaces the live template stop/delete timers for these instances. Idle deletion uses the same active-use checks and mount-removal transaction as above; it never calls stop. Active use includes accepted/running Runs, unfinished retained tool executions, and desktop reservations, viewers and pending handback delivery.

Beginning creation or start fixes `preparation_deadline`. Expiry refuses readiness publication and, once the operation is settled, records permanent `environment_preparation_timeout`. Known permanent initial preparation failures also set `preparation_failed_at` once. A previously ready instance, identified by its retained `last_used_at`, keeps its workspace after failed start or upgrade under either managed or preinstalled ownership. These instances retain their phase, frozen input and observed resources for diagnosis, and no longer dispatch creation. Maintenance begins deletion after the failed retention interval, once no active user or debug hold remains. A failure before native dispatch retires without a provider call. Retention expiry authorizes cleanup to begin; provider failures or native finalizers can delay its completion.

An unknown operation or expired claim continues reconciliation under its original operation ID even after the preparation deadline. A timeout is not evidence that native work has stopped. A later confirmed result is saved for cleanup, but cannot publish readiness after the deadline. Deletion still requires settled prior work and keeps the existing generation/claim fences.

`PUT /environments/{id}/debug-hold` (`write`, `If-Match`) accepts `{seconds}` from 60 through 86400 or null to clear the hold, and returns the updated instance. The server fixes `debug_hold_until`; the mutation is audited. A live hold delays automatic stop/delete and failed-instance cleanup only. It does not extend preparation, block explicit deletion, pause a Pod, or protect against cluster eviction. Deleted/deleting and external instances reject the mutation. Reads of the instance, diagnostics or logs never update last-use or the hold.

The instance view exposes reclamation settings, preparation deadline, first preparation-failure time and hold expiry. Existing instances without a policy retain the live-template behavior.

### Renewal

Some hosted types end a running sandbox at a deadline unless it is renewed; their definition sets `requires_keepalive` ([08](08-providers.md#environment-providers)). The `renew_environments` sweep ([09](09-runtime.md#sweeps)) keeps a ready instance of such a type alive for as long as it stays ready, so the template's idle policy, not the vendor's timeout, decides when it stops. Every `environments.scan_seconds` it renews, concurrently, up to `environments.batch` instances whose `renew_at` has come, earliest first; a pass is bounded by `environments.renewal_seconds` plus 40 seconds.

- **Schedule.** Becoming `ready` makes a renewal due at once. Each renewal asks the provider, within `environments.renewal_seconds` and with no database session held, to keep the sandbox for at least the adapter's keepalive horizon, records the expiry the provider reports in `expires_at`, and falls due again halfway to it. The horizon is at least 300 seconds, which the Service's E2B timeout floor keeps ([08](08-providers.md#registry)), and settings keep `environments.scan_seconds` plus twice `environments.renewal_seconds` plus the 10-second publication margin below half of it ([09](09-runtime.md#operational-limits)): a due renewal that a pass just missed finishes before the expiry even when that pass takes its full bound. Beginning any operation clears `renew_at` and `expires_at`, so a stopping, stopped or deleted instance is never renewed; nor is an external target or an instance of another type.
- **Claim.** A renewal only extends a deadline; it never creates, starts or stops a sandbox, and it carries only explicit renewal authority. So the claim is the lightest one that excludes a second dispatcher: under the row lock, a due renewal moves `renew_at` past its call deadline plus the publication margin. Its outcome is recorded only while `renew_at` still holds that claim, which an operation that began or a later claim replaces. An interrupted renewal records nothing; its claim expires and a later pass renews. A provider whose backend identity changed or cannot be resolved is not called until it is restored, as for runs.
- **Outcome.** A success clears `failure` and records in `handle.credential_version` the credential that reached the sandbox. A provider that no longer has the sandbox makes the instance permanently `environment_lost` (certainty `known`) and ends renewal, unless the provider's credential changed since it last reached the sandbox: the new credential may belong to another account that cannot see it, so that failure is `provider_credential_changed`, which is not permanent, and renewal goes on. A provider that reports the sandbox stopped, at its own time limit say, leaves the instance `stopped`, clears the failure and audits `environment.stopped` with reason `provider`; the next run starts it as after any stop. One that cannot keep the sandbox that long, near a vendor's hard lifetime (`provider_keepalive_limit`), is expected: nothing is recorded, and the next renewal waits for the reported expiry, when the sandbox is found gone or stopped. Any other failure is recorded, permanent by its category as for [operations](#provider-contract), so an unfixable one refuses new use; a repeated failure with the same code keeps its first record.
- **Retry.** A failure that is not permanent is retried halfway to the reported expiry while one remains. Otherwise the retry waits as long as the same failure has lasted, at most ten minutes.

## Automatic Envd creation feedback

`GET /environments/{id}/creation` (`read`) returns automatic E2B, Modal, Daytona, Vercel or Sprites creation progress, or null for other instances. Its `profile` is `headless` or `desktop`, derived from the instance's frozen recipe. It reads durable preparation and environment state without cloud I/O. The stages are `preparing`, `building`, `starting` (sandbox startup and authenticated EIP verification for the selected profile), `ready`, `failed`, and `inactive`. `started_at` identifies the current creation attempt while it is pending; `observed_at` supplies the server clock so browser clock skew cannot distort the timer. `ended_at` freezes elapsed time on failure. The separately polled response is not cached and does not change the Environment ETag. It exposes no cloud build logs, account credentials, or reusable access credentials.

Console explains the initial preparation delay before creation, shows the actual stage and elapsed time, and allows leaving and reopening the environment while background maintenance continues. Saving a template alone never starts a build. Estimates are guidance, not a completion guarantee or simulated progress percentage.

`POST /environments/{id}/retry-creation` (`write` and `run`, `If-Match`, 202) retries only a failed automatic Envd creation whose prior environment operation has a confirmed outcome and no active claim or run. It rechecks provider identity and credential access. A definitively failed preparation preserves its original error until explicit retry and can bind a new credential-scoped build; unresolved builds retain their identity for reconciliation and cleanup. A resolved native target retains its recipe and state. A new fenced operation prevents stale completion from publishing, and concurrent retries cannot dispatch duplicate allocations.

`GET /environments/{id}/desktop-preview` (`run`) captures one read-only snapshot of a ready E2B, Modal or Daytona desktop, without creating a Run, starting a sandbox, or issuing an input grant. Provider identity, current authority, observation permission and readiness are checked; the target is revalidated before returning pixels. Calls are bounded and execution resources close on failure and cancellation. The image response is `no-store` and is excluded from MCP as binary live output. Console can refresh this snapshot and releases it when the inspector closes. Interactive control remains in the existing conversation takeover flow.

## Stop, start and delete

Stop and delete arbitrate with use under the environment row lock and only begin an operation; provider calls happen in the fenced lifecycle, never in the request. Acceptance share-locks the same row before installing new active use, so whichever commits first wins: a stop that wins is observed by the run, which starts the instance again; an acceptance that wins makes the stop decline.

- `POST …/environments/{id}/stop` (`write`, `If-Match`, 202) needs a ready managed instance without a permanent failure, whose type supports stop, not in active use. Otherwise it is `conflict` with `connect_only`, `environment_{status}`, the permanent failure's code (stopping would clear it), `stop_unsupported` or `in_use`.
- `DELETE …/environments/{id}` (`write`, `If-Match`, 202) returns a `deleting` or `deleted` instance unchanged. It refuses an instance a thread mounts (`mounted`), one in active use (`in_use`) or whose outstanding operation is not settled (`operation_unresolved`). An instance with a permanent failure, such as a lost one, is not refused for its mounts: it leaves the threads that mount it, which it locks first in ID order as the lock order requires, so their next run can use another; a thread that loses its `workspace` mount gets one from its primary source at its next acceptance. An external target, or a reservation whose create was never dispatched, becomes `deleted` at once without a provider call. A managed instance whose type cannot destroy is `conflict` (`destroy_unsupported`); any other begins `deleting`.
- `PATCH …/environments/{id}` (`write`, `If-Match`) renames an instance and points an external target at a new endpoint or token ([external targets](#external-targets)).
- Starting is never a request: an attempt requiring readiness begins it ([execution](#execution)).

An external target is managed by its owner, or by a workspace administrator; anyone else is `forbidden`. Stop, delete and update are audited as `environment.stop`, `.delete` and `.update`. `GET …/environments` lists a workspace's instances; `status` filters by one status, and without it tombstones are left out.

Archiving a thread removes its desired mounts ([05](05-runs.md#waiting-interrupt-and-fork)); an active run's frozen use delays deletion until the run seals.

## Execution

The attempt constructs one Host-owned [Environment source](../a13n-harness/08-environment-integration.md#run-inputs) per frozen mount. Construction validates selection and inert metadata without waiting for native readiness. `AgentConfig.lazy_environment` defaults to `true`: execution prepares each mount only on its first dependent use, which may be input placement or Skill materialization before inference. When `false`, before entering Harness each attempt creates or starts the instances of all its frozen mounts and waits for their published ready state. Service performs this management work directly, without constructing or opening execution connectors or requesting Harness operation readiness. No mounts means no preparation. The source's `ensure_ready()` is an in-process call into Service, with the environment ID, attempt authority, and Service dependencies already bound; Harness neither calls an HTTP endpoint nor writes PostgreSQL.

`options.overrides.lazy_environment` replaces the revision's value for one Run; omission or `null` inherits it. The accepted revision and overrides keep this policy stable across retries and successor Runs. Async children use their own selected Agent configuration; inline children share the parent's already owned environment. This policy does not change explicit Environment creation or mount acceptance. Both modes leave execution connection opening to Harness on first dependent use. The source rechecks current authority and instance readiness before returning the fixed-target connector; an already ready instance does not repeat creation or startup. Operation readiness and explicit working-directory checks occur at that first execution use, not during Service instance preparation.

Each readiness request waits at most `environments.wait_seconds`, measured from that request rather than run entry. Its checks use short transactions that prove the attempt's current lease and lock the instance:

- The instance must remain usable by the run's principal, and its provider must resolve under the run's authority. An external target then updates `last_used_at` and returns its connector inputs.
- `reserved` begins `creating` and takes its initial claim in one short transaction. The requesting Worker performs and publishes that operation directly after commit, then checks readiness immediately. Concurrent attempts converge on that one operation; none allocates outside the operation claim.
- A `ready` instance whose provider identity changed is refused as `provider_identity_changed` without recording a failure; otherwise the check sets `last_used_at` and returns its target.
- `stopped` begins `starting` for the same instance.
- An outstanding operation without failure, other than `stopping`, may be dispatched once by this attempt. If another dispatcher holds its claim, this readiness request waits for fenced publication, bounded by the same request deadline; losing a claim never returns an unready connector. After a failed call the attempt waits while maintenance owns retries.

Both preparation before the run and first-use preparation reuse the same begin, claim, perform, and publish lifecycle. Management I/O and waiting hold no database session or transaction. The source returns a fixed-target connector only after required lifecycle success and fenced state publication, with current authorized credentials. Library connection opening and reconnection never create, start, resume, replace, or renew an instance. Harness opens and owns the resulting execution. `workspace` appears at `/workspace` and is the default; other mounts appear at `/mnt/{name}`.

Client connectivity failures at a tool boundary follow the recoverable behavior below. Other mounts that can no longer be used fail their dependent execution with `environment_unavailable`. A readiness timeout is `unavailable` (reason `environment_not_ready`): the attempt fails and the run recovers within `max_attempts`. These Service failures retain their cause through Harness and reach worker classification even when raised during input, Skill materialization, or a tool; they are not converted into a model retry that bypasses attempt policy ([05](05-runs.md#failure-semantics)). Cancellation stops the attempt's wait at once; drain yields a handoff without charging the attempt. A dispatched operation retains its durable identity and known or unknown outcome for recovery. Cancelling a wait never reverts an instance to `reserved` or deletes it.

`working_directory` selects the mount's default directory and route root; omission preserves the provider default. On first activation, the opened Environment execution checks an explicit directory outside a database transaction: it must exist, be a directory, and be listable. It is never created or replaced with a default. Failure identifies the environment, mount, path, and safe underlying reason, closes the acquired Environment execution, and fails preparation without recording an instance lifecycle failure or preventing other Threads from using valid directories. Providers without file operations reject explicit selection; later filesystem changes can still make operations fail.

For managed Local, `/projects/app` means `{recipe.root.path}/{environment_id}/projects/app`, not an arbitrary host path. Relative file paths, `/workspace/...` (or the named mount route) and a command's omitted cwd resolve to the selected directory. Different directories organize files but do not isolate processes, ports, software or OS permissions. Removing a mount does not remove its directory.

Service includes Harness `FileContextCapability` for every agent, including inline children. It best-effort loads the default user mount's working-directory `AGENTS.md` and the shared [project-local guidance entrypoint hints](../a13n-harness/09-context-and-memory.md#runtime-context-workspace-outline-file-context-and-handoff) before the first model request. Child guidance and local Skill directories contribute paths, not their contents or additional selected Skills. Discovery uses the current Environment permissions and no worker-host filesystem fallback; without a default mount it contributes nothing. The primary `workspace` mount is the default when present; otherwise a sole user mount is the default. Multiple named user mounts without `workspace` have no default. This file-context preparation is a dependent Environment use and can activate the default mount even when the model never calls a file or terminal tool. Other mounts remain lazy. Selected Skill materialization and synchronization remain unchanged.

Harness opens and closes Environment execution scopes, including on binding failure, cancellation, and replacement. Service marks activated instances used on completion; merely registering an unused mount does not update `last_used_at`. Frozen mounts retain active-use protection even before activation. Closing an Environment execution preserves the backing instance while applying the provider's declared Session/process cleanup; it does not select stop or delete.

For Envd-backed execution, a logical Session binding is identified by Thread, Environment instance and binding name. Directory views selecting the same binding share one Session; separate binding names select independent Sessions on the same Device. Model, prompt, route name and view working directory do not partition Session identity. Forks and async child Threads have independent bindings. External HTTP, client reverse-WebSocket and managed Envd routes use the same recovery contract. Native execution produces no Session state.

Each binding owns its desired startup configuration and one private admitted Session head, independently of Run checkpoints. A desired edit changes the binding configuration and Thread ETag; admission freezes the selected configuration and Session version into every directory view atomically. Changed startup configuration advances the Session version only when no admitted Run or unfinished retained tool uses that binding. Busy replacement fails with `environment_busy`. A captured positive version must still be current; it cannot roll the head backward. Returning from configuration A through B to A advances the version again and never revives the retired A Session.

The binding retains its monotonic version and exact Session recovery descriptor when its last directory view is removed. Its head is stored and updated independently: admission and Session checkpoints read only the selected bindings, without loading or rewriting the Thread's historical binding collection. The first borrower of a new version durably retires the previous Session before opening its successor. An uncertain close preserves that retiring descriptor for retry. Endpoint and credential edits keep the registered Device identity and do not create a new logical binding.

The Thread execution context's worker ownership generation fences state publication. Existing attempt and retained-tool leases keep overlapping work colocated; idle contexts need no heartbeat. A live source or borrower owns the process-local shared connection. Releasing the final borrower detaches that connection while preserving the recoverable Session. A replacement worker attaches with the durable Session descriptor and advances the Envd owner epoch; stale owners cannot perform operations or close it. Context state remains outside portable `EnvironmentState` and Harness checkpoints.

Ordinary new work may open a fresh Session when the saved Session is definitively unavailable; authentication, transport and protocol failures remain failures. Recovery of an already admitted [native Shell](05-runs.md#native-shell-recovery) requires its exact original Session and process and never substitutes fresh work. Session attachment alone does not restore standalone Run-local process references. Providers use the shared [transport-neutral Session acquisition contract](../a13n-harness/08b-environment-providers.md#envd-session-continuity). Client environments use EIP Sessions through the Control-owned carrier and Service routing described below.

### Session-binding schema cutover

The Session-binding migration requires a coordinated stop. All admitted environment work must settle before migration: Runs with environment mounts must leave `accepted`, `running` and `waiting`, and retained environment or Shell tool executions must finish. Worker drain or handoff alone does not satisfy this condition. Old Controls and Workers stop before migration, and only the new version restarts afterward.

Migration creates named binding configuration without importing legacy Session hints as admitted heads, clears obsolete recovery hints and advances context ownership generation. Environment registrations, provider state, files, historical Run captures and completed results remain intact. The first new admission creates a fresh Session. Mixed-version execution across this cutover is unsupported.

## External targets

An external target is an envd daemon someone else operates, reached over HTTP(S) at its own endpoint with its own token. It is no provider resource: the Harness `http_envd` Environment connector reaches it, built by `providers/envd.py` from the row's values. Each executing worker connects directly to the endpoint, which must be reachable from every process that uses it.

`POST …/environments {endpoint, token, name?}` registers one (`write`; 201; audited as `environment.register`). The endpoint is an HTTP(S) origin of at most 2048 characters, plain HTTP only for a loopback address, and the token at most 4096 characters; a malformed one is `invalid_argument` on the field. Outside any transaction and within `providers.operation_seconds`, the Service checks the endpoint against the [endpoint policy](08-providers.md#outbound-endpoint-policy), asks the daemon which device it is, then opens and closes one session expecting that device. A refusal that repeating cannot overcome (an invalid, unsupported, missing, denied or conflicting outcome, such as `provider_endpoint_denied`) is `conflict` with details `{field: "endpoint", reason}`, the provider's error code as reason; any other failure is `unavailable` (dependency `environment:http_envd`) with that code, or `environment_timeout` for a timeout, as reason. A daemon refusing the token cannot be told from one that cannot be reached, so it is `unavailable` with `provider_connection_failed`. It then records a `ready` target owned by the caller with only the daemon's `device_id`, the endpoint and the token, encrypted for the row; the name defaults to the `device_id`. The view shows the endpoint and `device_id`, never the token.

Every later connection, whether a run's or a verification's, builds its Environment connector from the row's endpoint, device and revealed token, checks the endpoint policy before dialing and expects the stored device. A daemon that is another device refuses to initialize, which the adapter reports as the permanent `provider_device_mismatch`. `PATCH …/environments/{id}` with a `token`, and a new `endpoint` if it moves (a new endpoint always comes with its token), repeats the verification with the stored device outside any transaction, then stores both, and a new name if one is given, under the same `If-Match` precondition. A daemon that is another device is `conflict` (`provider_device_mismatch`); any other refusal is `conflict` on the environment or `unavailable`, as for registration. A token without a new endpoint replaces the token only. An endpoint without a token is `invalid_argument` on `token`; for a managed instance, a new endpoint is `invalid_argument` on `endpoint` and a token alone on `token`; for a deleted target either is `conflict` (`environment_deleted`).

The Service never creates, starts, stops or destroys a target, and maintenance never touches it. `ready` means selectable, not currently reachable: an unreachable target fails preparation of the runs that mount it. Deleting a target only removes the Service's access; the tombstone keeps the `device_id` and endpoint and drops the token. A timeout or broken connection after dispatch does not authorize replaying an unknown command; the EIP Session and operation-identity checks of the shared client apply.

Environment instance records and selection eligibility are shared resource-layer inputs for Agent defaults and Run mounts. The execution layer owns lifecycle transitions, Thread mounts and connection/session preparation. Configuration validation does not import execution orchestration.

## Managed outbound execution

Managed Docker, E2B, Daytona, Modal, Sprites and Vercel recipes accept `execution="envd_ws"`, alongside their existing execution modes. This selects the execution connection only: the existing Provider still creates, starts, stops and destroys the sandbox. The instance remains `kind="managed"`, retains its provider state and native target identity, and creates no client registration or client settings row. Run selection and provider access rules remain unchanged.

Before provisioning I/O, Service freezes a dedicated random connection credential, expected Device identity (the environment ID) and Control URL in the private `handle.outbound` binding. The credential is encrypted with the environment's organization and ID as associated context; its hash authenticates reconnects. Ordinary Environment views, recipes and provider configuration never expose this binding. Retried provisioning and stop/start reuse it. Sandbox bootstrap supplies the credential through protected launch inputs, writes a root-private credential file and removes the bootstrap token from the daemon environment. Custom images/templates must implement the same bootstrap contract as the supplied sandbox entrypoint.

The sandbox connects to `WSS /api/v1/environments/{environment_id}/connect` using that dedicated bearer credential and `eip.v1`. This route never enrolls a device or accepts an ordinary API token in place of the connection credential. Control checks the current environment, active workspace, enabled and unchanged Provider identity and expected Device ID. Connection admission is allowed while creating, starting or ready; tool dispatch additionally requires ready state, current run ownership, its accepted authority and frozen mount permissions. Stop/delete invalidates connection admission; stopped or stopping instances return a retryable rejection so a preserved daemon can reconnect on start. Provider-native cleanup remains available independently of this execution connection.

Execution selection uses the shared connection-mode capabilities (`native`, `envd_http`, `envd_ws`). Provider implementations retain provisioning and their concrete backend construction; Service routes Host-owned connections through its client transport. Standalone preview capability is exposed on each Environment view as `desktop_preview`, derived from the instance's saved handle and provider identity, never its mutable template. Outbound mode returns `connection_unsupported`; the preview API rejects it before opening a connector.

For managed execution, one pure resolver chooses the explicit frozen mount directory, otherwise the Provider descriptor's default for the instance's saved `Handle.recipe`. Worker preparation and Control authorization use that same result. This reads no additional database rows and does not consult the current template. Reserved instances resolve their directory after provisioning has published a handle.

Creation/start waits within the existing bounded lifecycle operation for the initialized carrier and request subscription to become discoverable. A WebSocket upgrade alone does not complete readiness. Connection failure retains allocation evidence for retry or cleanup. Once native create/start has succeeded, a failure or deadline while waiting for outbound readiness is a known, retryable `envd_ws_not_ready` failure; the saved target remains eligible for normal deletion. A timeout during the native mutation itself retains unknown-outcome fencing. Explicit cancellation remains cancellation and preserves the observed state and completed-phase evidence. Session capabilities and Computer readiness are checked when a run opens its execution scope. Standalone Computer preflight and desktop snapshot preview outside a run are unsupported for outbound targets. Reconnection, request Pub/Sub, request timeouts and binary relay use the same transport rules as client environments below, including failure without automatic command replay. Native provider state continues to identify managed Computer reservations; outbound transport does not replace it.

`server.public_url` must be an HTTPS origin reachable from the sandbox, with WebSocket forwarding enabled. Explicit loopback development policy permits local HTTP only. Workers still need provider management access for lifecycle operations, but need no inbound Envd HTTP route to the sandbox. Human desktop viewing and metrics have their own routes and capabilities; choosing outbound execution does not provide either automatically. Built-in Harness execution connectors require Service to supply the managed outbound connection and reject standalone `envd_ws` attachment explicitly.

## Client environments

A `external` environment identifies one registered installation owned by a principal in one workspace. Registration and connection are independent: a client environment can be registered, selected and mounted while offline. Its `status` is `ready`, `disabled` or `deleted`; `ready` means eligible for use, never proof of connectivity. It has no provider lifecycle operation. Connecting never creates an environment, changes a run's selected mounts or grants new operations.

The migration classifies existing managed and HTTP environments without changing their resource versions. New writes must supply `kind`; no trigger supports old writers. Old Controls and Workers must drain and stop before this schema migration. A client registration, including a deleted one, prevents downgrade because the old schema cannot preserve its execution authority.

### Console pairing

Console can enroll a local Envd without exposing an API key or device credential to the browser. A signed-in user with workspace `write` creates a ten-minute pairing request, scoped to that principal and workspace. Creation is limited to ten requests per principal per ten minutes. Its unpredictable `pair_` ID and launcher URL identify the request; they do not authorize execution. Redis retains the request with its original expiry; no new database table is required.

The browser endpoints under `/api/v1/client-environments/pairings` are `POST /` (create), `GET /{id}` (observe), `POST /{id}/approve` (submit `verification_code`) and `POST /{id}/cancel`. They require a login session and current workspace write authority; reads and decisions are restricted to the creating principal and workspace. These routes and the native claim endpoint are excluded from MCP.

Native Envd generates and saves a device credential before its first `POST /{id}/claim`. The claim uses `X-A13N-Device-Credential: Bearer …`, not ordinary API authentication, and supplies device ID, name, default working directory, optional existing environment ID, and local Shell/desktop settings. The endpoint rejects browser Origin headers, query parameters, ordinary Authorization headers and insecure remote transport. Explicit loopback development mode permits local HTTP. The first claim fixes the credential digest and metadata; different credentials or changed metadata are refused. Redis stores only the digest. A pending reply supplies a six-digit verification code for the native app or terminal.

The owner reviews the machine and permissions and enters that verification code in Console. The state sequence is `waiting → claimed → approving → approved`; cancellation is allowed only before `approving`. Compare-and-set transitions preserve expiry and prevent a concurrent cancellation from revoking an already accepted approval. Approval uses the existing client registration rules: immutable owner/workspace/device binding, no automatic rotation, replacement, re-enable or revival. An existing registration additionally requires the same saved credential. New registrations receive file and execution permissions, plus Computer operations only when the native claim enables desktop use. Local execution policy remains authoritative. Registration metadata and ceilings of existing registrations remain unchanged.

Approval may be retried after an interrupted response with the same claim and credential. If Redis expires after registration commits, a new pairing with the retained credential resolves that registration; the old request cannot be recreated by a late update. Lost local credentials require explicit credential recovery. An approved native claim rechecks the registration's current credential and returns only environment ID and WebSocket path. Envd then connects through the existing reverse-WebSocket transport. Approval does not prove online readiness, mount the environment, or start a Run.

A native `POST /{id}/recognize` proves an existing external registration using its dedicated device credential, environment ID and device ID. It uses the same native-only credential transport restrictions as claim and is excluded from MCP. The registration must remain active, credential-valid and in the request's workspace. A waiting request becomes `approved` with `reused: true`, without a verification code, enrollment, permission changes, credential rotation or a new carrier. Identical recognition retries are idempotent and recheck credentials; cancelled, expired or conflicting requests fail. Browser observation still requires the request creator's login and current workspace authority. Recognition is independent of online readiness; Console reads connectivity from the existing environment. Old requests omit `reused` and default to false; request expiry is unchanged.

### Identity and credentials

The client generates a random installation `device_id` once and persists it locally. Server registration creates the `env_` identity and binds it to that device, workspace and owner. These bindings and `kind` are immutable. A launcher selects a separate environment ID and credential file for each Service origin, owner and workspace. Switching accounts keeps the installation ID and changes the registration used for the connection. A self-reported device ID is an expected identity, not cryptographic proof of a physical computer: copying the device ID and its dedicated credential copies the installation's access. Ordinary reconnects reuse both identifiers; deleting local identity and registering again creates a new installation. EIP `generation` distinguishes daemon incarnations independently of the persistent device ID.

`client_environment_settings` has exactly one row per client environment. It holds the dedicated token's hash, positive `credential_version`, default working directory, operation permission ceiling, optional declared capabilities and optional description. Raw tokens are returned only when created or explicitly rotated, never from reads or repeated registration. Credential version advances on rotation, revocation and status transitions, including disable followed immediately by enable. An old carrier cannot retain authority across these transitions. Deletion removes the hash and keeps the tombstone's device binding.

| `POST /client-environments?workspace_id=…`                        | `write`; registers `{device_id, name, default_working_directory, permission_ceiling?, declared_capabilities?, description?}` without connecting. Concurrent requests converge on one record.                                                                                                            |

| `POST /client-environments/{id}/rotate-credential?workspace_id=…` | Same management authority and precondition; issues a new credential and invalidates old carriers.                                                                                                                                                                                                                                                                                                                                                                                 |

Registration and credential responses are `no-store`. Administrative credential and status operations are excluded from MCP; the read operation is admitted. Renaming and deletion use the ordinary Environment APIs. Any user or service account with current `run` authority in the same workspace may select and execute the environment. Execution requires neither ownership nor workspace `write`. The owner binding controls registration and management, not execution. This policy applies to existing and new client registrations without a schema migration or data rewrite. Update all Controls and Workers together so selection and dispatch enforce the same policy. External HTTP targets remain owner-restricted.

First-connection enrollment is an HTTP request before the dedicated-token WebSocket upgrade. A successful response is not online presence and attaches no run. Concurrent enrollment and explicit registration serialize on the workspace/owner/device binding. A supplied unknown environment returns not-found; a device mismatch returns `conflict` with reason `device_id_mismatch`. Inactive bindings return reasons `client_environment_disabled`, `client_environment_deleted` or `client_credential_revoked`. Explicit offline registration remains the operation that can create a replacement after deletion.

Enrollment stores no recoverable raw credential on the server. If delivery or local persistence fails after creation, a repeated request discovers the existing environment without returning the credential. The caller uses the existing explicit rotation endpoint with ordinary API authority and the current ETag, then installs the new device credential. Startup never rotates automatically. Device credentials cannot authenticate enrollment; ordinary API tokens cannot authenticate the WebSocket.

### Connection ownership

Control authenticates in a short database scope, then claims an expiring Redis connection owner before accepting the WebSocket. A valid owner rejects a second connection, including one presenting the same credential and device ID. Disconnect or lease expiration permits a new claim with a new connection epoch. Cleanup, presence publication and renewal compare that epoch; an old handler cannot overwrite or delete its successor's presence.

Control initiates EIP `initialize` over the accepted socket, with the registered device ID as its expectation. It validates device identity, generation and limits. This does not run commands or open a Session. Online presence is published only after successful initialization. Initialization failure releases the connection; a WebSocket upgrade alone is not readiness. Heartbeats renew ownership and recheck current registration, credential version and active workspace, independently of tool requests. Authority or coordination uncertainty retires the carrier. Redis presence expires and is not a durable Environment status. Workspace list and detail reads include a timestamped connection observation for client instances: offline, connecting, online or unknown if coordination is unavailable. The read opens no Session.

### Execution and recovery

Run acceptance freezes the selected client environments, resolves an omitted mount directory from registration settings, and intersects mount permissions with the registration ceiling and any explicitly declared capabilities. Declarations narrow the offered actions and do not grant authority or prove native support. First dependent use acquires a fixed-target Service connector through the owning Control; it borrows the Thread's matching EIP Session context, checks readiness and validates the frozen directory. Run-local routing scopes carry each caller's authority independently; ending one scope releases only its borrow and transfers. Harness receives normal Environment operation interfaces and has no PostgreSQL or Redis dependency. Initialization and reconnect never widen the run's frozen authority.

Control rechecks run or retained-execution ownership, the executing principal’s current workspace `run` authority within its captured execution authority, the frozen mount, current registration permissions, connection epoch and Session ownership before each native dispatch. The device carrier authenticates independently of the registering principal’s current role; changing that role does not revoke the device credential. Disable the registration or revoke its credential to disconnect it. Authorization facts are reused only within that operation. Each renewal round reads callers, runs, attempts/retained executions, principals, environments and providers in sets of at most 64 checks. Active transfers join that round with their own caller and operation permissions instead of running independent database timers. At most four Session authorization reads run concurrently per Control process. Each caller receives an independent result; one caller losing authority does not revoke a valid sibling. Unavailable database evidence fails closed. Database sessions end before Redis or native I/O. Existing monitoring registrations and carriers confer no execution authority. An unrelated client's connection changes have no effect on a run that did not select it.

A scope retired or replaced during authorization cannot dispatch or close its replacement. Scope acquisition and retirement for the same Thread and environment are serialized through transfer retirement and release of the native borrower. Reusing a Session selector on one carrier waits for the previous requester's pending control replies and transfer RESET acknowledgments. An unconfirmed transfer retirement closes the carrier before reuse; it does not deliberately close the native Session. A Session cleanup failure is logged and isolated from other Sessions and connection admission. A failed request subscription ends its pending dispatches and retires only that connection; the client may reconnect and establish a new subscription. If shared Session renewal fails unexpectedly, Control stops admitting connections during recovery, retires old carriers and scopes, and restarts renewal. Both previously connected and new installations can then connect. Recovery never replays interrupted requests; an unconfirmed dispatched operation retains an unknown outcome.

Disconnect alone does not add model context. A dependent tool invocation reports a connection failure as a tool result and records that this run observed the failure. Only a run with such a pending failure receives one recovery notice, on its next natural root model-request boundary after current presence is verified. Ordinary command failures and confirmed operation timeouts do not create pending connection failures. A later successful tool result supersedes an unconsumed recovery notice. Healthy successes remain transient until model projection consumes them; they do not write recovery state. A pending recovery cycle or a connection loss promotes the current batch observations into checkpointed state, preserving canonical tool-result ordering even when parallel calls complete in another order. Online events never start a new model request, wake a completed run or replay a command.

At that boundary, after the previous tool batch completes, a mount whose initial activation failed solely because the client was offline may be replaced by an inert mount with the same environment, device, directory and permissions, once cleanup is complete. This discards the cached failed activation task. Replacement does not open a Session; the next dependent access does. One connection epoch does not repeatedly replace the same failed mount. Permission, identity, protocol and incomplete-cleanup failures do not qualify. A notice reports restored connectivity and an opportunity to retry, not proven execution readiness.

Connection loss, Session loss and revoked authority are distinct. Control checks native Session usability during operation admission and periodic renewal, independently of Device connectivity. A Session that closes itself, including after a keepalive timeout, retires its scope and transfers instead of having its binding renewed. If a Control scope has disappeared or its Session has closed, Control first rechecks current run, device and mount authority. Valid authority produces a pre-dispatch `environment_unavailable` response with `session_failed=true`; denied authority remains `environment_denied`. The Worker records the failed scope independently of connection epoch. After that failure reaches the model as a tool result, the next safe model-request boundary can replace the stale mount even when the device connection is unchanged. It discards that Session's recovery hint, detaches its local binding and permits a fresh Session on the next dependent use. Recovery emits one notice per observed failure, not per online event, and does not claim tool readiness. No operation is retried automatically, including operations with unknown results. Retained handles from the retired Session are not transferred to the fresh one.

Recovery and cancellation cleanup of a retained native Shell remain authorized by its original execution lease after Run completion or principal revocation. Control restricts that authority to discovery of its saved start operation and exact Session/process identity, process kill/wait/release, release of that process's outputs, and scope detach. Current device credentials, workspace/provider binding and frozen operation ceilings still apply; cleanup cannot start work or close a shared Session.

Already activated mounts follow Session continuity checks. Reconnection may attach only the same authorized device generation and Session; expired Sessions or restarted daemons cannot lend their old handles to a fresh Session. No unfinished transfer or command is replayed. Background processes survive only within the native Session's lifetime and a valid run or retained execution scope. Session keepalive is independent of individual request waits, but ends when that execution ownership is lost.

### Routed requests and long commands

Worker and Control address Redis Pub/Sub channels by environment ID: `a13n:client-environment:requests:{environment_id}` and `a13n:client-environment:replies:{environment_id}`. Neither role discovers the other's process address. After claiming the connection, Control subscribes to its environment's request channel and receives the subscription acknowledgment before publishing online presence. The subscription ends with the connection. New and retiring Controls can briefly subscribe to the same channel; each silently ignores requests for another environment or connection epoch. Redis ownership checks remain required before native dispatch.

Worker shares one reply subscription per environment across its local Sessions and outstanding calls, releasing it when the last user leaves. It confirms subscription before publishing and rejects a known stale connection before sending. All Workers using the environment can receive replies; each accepts only its outstanding request ID with the expected environment, epoch and execution scope. Subscription loss fails outstanding waits without replay; subsequent calls may acquire a fresh subscription. Timeout and cancellation remove only the affected wait, and late or unrelated replies are ignored.

Each request binds a unique request ID, environment, connection epoch, caller run/attempt/worker, execution scope, operation, parameters and deadline. Proxy request IDs remain distinct from real EIP operation IDs. Control validates supported operations and their parameters; this is not an unrestricted EIP forwarding endpoint. Requests and results may be lost; mutations are sent once and are never automatically replayed.

Queueing consumes the request deadline. Native operation deadlines leave time for cleanup and forwarding; Control's response wait ends before Worker's outer deadline. Both roles bound concurrent work, message sizes and waits. Cancellation and close retain admission when ordinary operation capacity is full. No database session is held during transport, command execution or waiting. A late response can only satisfy its original outstanding request.

| Evidence                                           | Meaning and handling                                                                                                                                                                                                                             |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Confirmed offline or rejection before dispatch     | No operation was dispatched; return a recoverable tool failure.                                                                                                                                                                                  |
| Explicit `process.wait` timeout from envd          | This wait ended without observing completion. Retain the process handle; do not kill, restart or declare the device offline. A current running-state claim requires an inspection result.                                                        |
| Worker or Control response wait times out          | Outcome unknown; end this reply wait without claiming the command stopped. Do not replay a mutation.                                                                                                                                             |
| `process.start` reply lost                         | Preserve the original EIP operation ID; a separate bounded `receipt.get` in the same Session/generation may recover execution stage and outcome. A receipt alone does not return a process handle. Missing evidence does not prove nonexecution. |
| `shell.exec` reaches its native operation deadline | Preserve native termination and cleanup semantics; never silently convert it into a background task.                                                                                                                                             |

Long commands use explicit process start and bounded wait/inspect calls. On a process-capable mount a single agent `shell_exec` starts the command and waits for the Host-configured foreground interval. A retained execution tracks completion after returning an execution reference. The agent may choose `shell_info` or `shell_wait` for a subsequent observation; routing does not extend one request indefinitely. Command wall time, individual wait duration, transport response deadline and Session lifetime remain independent limits.

Large files and screenshots use Redis Streams between Worker and Control, and the existing EIP binary WebSocket between Control and envd. Workers need no network route to a Control replica for binary traffic. A `transfer.attach` request over the existing Pub/Sub route authorizes the current run/execution owner and its previously opened Session, handle, direction and permissions. Attachment is one-shot. Control returns a fresh random `transfer_id` and the transfer deadline; device credentials and arbitrary Redis keys are not accepted as selectors. Frame handling and periodic checks retain connection-epoch and live execution authority.

Each admitted transfer owns exactly two streams:

```text
a13n:client-environment:{environment_id}:transfer:{epoch}:{transfer_id}:w2c
a13n:client-environment:{environment_id}:transfer:{epoch}:{transfer_id}:c2w
```

`w2c` carries Worker-to-Control EIP frames; `c2w` carries Control-to-Worker frames. Both include data and the corresponding EIP attachment, credit, end or reset frames. Values are raw encoded binary frames, not JSON/base64 file bodies. Each direction has one reader with an explicit `XREAD` cursor; there are no consumer groups. Admission creates both empty streams atomically under the current connection owner. Each stream holds at most eight unconsumed frames, each bounded by the negotiated EIP frame limit; a full stream makes its producer wait rather than trimming data. EIP credit limits remain in force independently. Consumption deletes that message. Writes and acknowledgments atomically check that both keys still exist and the epoch is current, and refresh a five-minute TTL. Neither a late frame nor cleanup may recreate expired streams or affect another transfer.

The configured `client_environments.transfer_seconds` bounds the whole attachment (120 seconds by default), including waits for capacity or data. Terminal data stays available for the reader, and the empty pair remains open for final reader credit until explicit close/commit/abort or the deadline. Cancellation, Session/connection retirement and transfer failure cancel the relay, retire an incomplete native body and delete both keys; Redis failure leaves TTL cleanup as a fallback. Stream operations use a Redis client without automatic mutation retries. A lost response, expired key or changed connection fails the transfer; streams do not resume a whole file or replay a command after reconnect. Native file commit is still a separate authorized control request and a lost commit response remains an unknown outcome.

The previous binary WebSocket relay route, per-scope transfer token and `client_environments.transfer_origin` setting are removed. Workers and Controls must run the same transport version; drain active work before replacing both roles. Full file bodies never enter Pub/Sub control envelopes.

## Provider contract

Service owns [Environment management definitions and vendor lifecycle implementations](06a-environment-management.md), composing the Harness [execution contract](../a13n-harness/08a-environment-execution.md) for fixed-target connectors, operation clients, and portable state. Service orchestration adapts plain account inputs, current credentials, frozen recipes, `EnvironmentState`, and operation identity to those interfaces. Neither management drivers nor Harness execution code receive a database session, ORM object, or principal; Service alone accesses the database and ends transactions before vendor I/O, waits, or execution.

Lifecycle dispatch uses explicit management methods and releases its management clients after the bounded call. Results and partial-failure evidence preserve observed state for fenced publication. Harness receives a Host-owned source whose readiness method returns the authorized instance's fixed-target connector. The connector has no `allow_create` mode or management methods; Service alone owns the management and persistence performed by its source. The Service management definition declares stop, destroy, and renewal support; the composed Harness definition declares execution capabilities only. Service's narrower recipe/account choices remain owned by [Provider Integration](08-providers.md#registry).

A provider error carries a category and a certainty. Invalid, unsupported, missing, denied and conflicting outcomes are permanent unless their outcome is unknown; transport errors, timeouts and unknown outcomes are retried on the same operation.

## Failure semantics

| Situation                                                                                       | Observable outcome                                                       | Recovery                                          |
| ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ | ------------------------------------------------- |
| Provider call times out or fails transiently                                                    | `failure` on the same phase, certainty `unknown` when it was dispatched  | Maintenance continues the same operation          |
| Dispatcher dies mid-call                                                                        | Claim expires; `environment_operation_interrupted` when it could publish | The next dispatcher reconciles the same operation |
| Permanent refusal (disabled provider or template, identity changed, invalid recipe)             | Permanent `failure`; new mounts and acceptance refused with its code     | Fix the cause, or delete the instance             |
| Template moved to another provider before the create was claimed (`environment_template_moved`) | Permanent `failure`                                                      | Reserve a new environment                         |
| Instance lost while stopped                                                                     | `starting` fails permanently with `environment_lost`                     | Next eligible run reserves a fresh primary        |
| Provider no longer has a ready sandbox that it should keep                                      | The renewal records the permanent `environment_lost`; renewal ends       | Next eligible run reserves a fresh primary        |
| Provider's changed credential no longer sees a ready sandbox                                    | `provider_credential_changed`, not permanent; renewal goes on            | Restore a credential of the sandbox's account     |
| Provider stopped a ready sandbox itself                                                         | The renewal leaves the instance `stopped`                                | The next run starts it                            |
| Provider cannot keep a ready sandbox any longer (`provider_keepalive_limit`)                    | Nothing recorded; the next renewal waits for the expiry                  | The renewal then finds it gone or stopped         |
| Renewal fails otherwise                                                                         | A failure on the ready instance, permanent by its category               | Retried with backoff; a success clears it         |
| Mount unusable when readiness is requested                                                      | The run fails with `environment_unavailable`                             | None for that run                                 |
| Instance not ready within `environments.wait_seconds`                                           | The attempt fails; the run recovers                                      | Within `max_attempts`                             |
| Delete requested during an unresolved operation                                                 | `conflict` (`operation_unresolved`)                                      | Retry once the operation settles                  |

## Trade-offs

- **Shared environments share mutable files.** Threads, forks and children that mount one instance see each other's changes and can run tools concurrently. Checkpoints neither snapshot nor roll back files; a caller that needs isolation mounts fresh environments.
- **Frozen recipes.** Each newly reserved instance uses the template recipe in effect at its first create claim.
- **Fixed-interval recovery.** A failed operation waits for the next maintenance pass instead of a per-instance schedule, in exchange for one simple rule: an operation is only ever continued, never duplicated.

## Invariants

- A `reserved` instance has no outstanding operation or native target; Control never starts it merely because it exists.
- An instance has at most one outstanding operation, and a completion is recorded only by the dispatcher whose generation, operation ID and claim token still match.
- A different operation begins only after the previous one is settled.
- Stop and delete never begin while an accepted or running run's frozen mounts name the instance. An idle delete, or a delete of an instance a permanent failure makes unusable, removes the threads' mounts of the instance in the same transaction; any other delete requires that no thread mounts it.
- Opening or reconnecting execution never creates, starts, replaces, or renews an instance; explicit renewal never creates, starts, or replaces it.
- Only a ready instance is renewed, and a renewal's outcome is recorded only while its claim still holds.
- A managed instance's recipe and provider identity never change after its create is first claimed.
- The Service never calls a lifecycle operation on an external target, and every connection to one expects its registered device.
