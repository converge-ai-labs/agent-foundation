# Control Background Tasks

## Design Position

Control background tasks deliver committed intents, advance eligible domain work, recover interrupted operations, and reclaim data whose retention dependencies have ended. Periodic scans make this work independent of request traffic, a surviving process-local wakeup, or a particular control replica.

This contract owns the control task catalogue, execution obligations, and common recovery and collection rules. Each domain continues to own its identities, transitions, authorization, delivery semantics, and retention dependencies. A task iteration is a process-local activity, not another durable product resource. The catalogue requires no public Job API, user-authored schedule, generic task table, or global scheduler leader. Several logical tasks can share a bounded loop without merging their authorities or completion boundaries.

## Task Catalogue

Every control-capable deployment operates the tasks applicable to its enabled domain. Lack of current candidates does not disable a task's recovery scan. A disabled protocol contributes no publisher; retained authority is never discarded merely because its protocol is disabled.

A scan cannot revive a suppressed result, bypass an earlier eligible inbox entry, consume a queue blocked by a selected waiting head, or substitute a control identity for the persisted authority Principal. Recovery uses the same application operations and final locked revalidation as the corresponding ordinary path.

## Execution and Recovery

### Scheduling and Bounded Work

Each task has a positive finite scan interval and bounded candidate count, concurrent work, and per-operation execution time. A collection task also has a bounded deletion batch. Tasks can share effective configuration values; neither their parameters nor their cadence create domain authority. Required values are validated during startup through the runtime configuration boundary.

An enabled task begins scanning within one configured interval of component startup and continues independently of incoming requests. Wakeups can reduce latency but never replace the periodic scan. The next candidate set is recoverable from owning durable state after process loss. A durable intent or cursor is used only where its domain needs one; restarting a stateless scan is sufficient when the existing records are the complete recovery authority.

Candidate selection is deterministic and makes progress beyond busy, deferred, or failing entries. Repeatedly reading the same first page must not indefinitely starve other eligible work or another Organization. A failed item does not consume an unbounded iteration or prevent unrelated task classes from running. Under healthy dependencies and sufficient compatible capacity, continuously eligible work receives processing attempts without requiring an API request or manual wakeup. Backlog and dependency outages can delay completion and are observable; an interval is not a promise that arbitrary external work finishes within that interval.

### Replicas, Transactions, and Authorization

Every task remains safe when several control or all-in-one processes scan the same candidates, including rolling overlap. A scan result is only a candidate observation. The domain's short mutation transaction rechecks current identity, lifecycle, version, authorization, and retention conditions before accepting work or committing a result.

Tasks use existing locks, compare-and-set transitions, unique identities, and leased claims as their domain requires. External work executes after the claim/read session closes. Completion uses a fresh short transaction and the same valid claim generation or domain fence. Claim expiry permits the owning recovery path; it never authorizes a stale process to publish. A task with atomic relational selection, such as queue drain, needs no lease merely because it runs periodically.

Skip-locked selection is appropriate only where skipped rows are independent. It cannot break an ordered inbox, queue, or lifecycle retention prefix. When an operation must preserve a contiguous retained boundary, competing replicas serialize or defer that boundary instead of deleting around a locked predecessor.

Background execution grants no product Principal. Automatic Run acceptance reauthorizes the persisted authority required by the domain; maintenance can perform only the internal transition justified by its durable source. Every query and effect retains Organization and Workspace ownership checks. Revalidation preserves the domain's distinction between live eligibility and immutable accepted references, including after configuration changes or source deletion.

## Retention and Collection

### Eligibility and Required Progress

Logical expiry, public absence, physical reclamation, and audit expiry are separate facts. Eligibility ends at the domain deadline or invalidation commit even if a sweeper is delayed. Conversely, a tombstone, expired credential, sealed Run, or expired subscription does not by itself release every retained reference.

Control must periodically discover and process records that satisfy all applicable collection conditions. Reclamation is an execution obligation once the owning retention policy permits it; it cannot depend solely on later reads opportunistically deleting expired rows. Each scan processes a bounded batch and leaves deferred or interrupted work discoverable for another iteration or replica.

Retention horizons come from the owning contract and bounded deployment policy, not one global age cutoff. A dependency can outlive the candidate's own horizon. If a domain establishes no expiry or hard-delete permission, its authoritative records remain retained. This contract does not add a Run expiry, shorten historical Revision availability, or make security audit expire with a credential. A configured hold keeps otherwise eligible data retained without restoring public eligibility.

Collection checks both outgoing work and incoming references. It preserves evidence needed by accepted operations, replay, retained successors, reconstructible locks, pending delivery, authorized redrive, or required audit. An unfinished operation's sole durable progress record is not audit-only history. Dependency cycles or unknown ownership keep the affected data retained and observable; they are not resolved by guessing that the oldest object is unused.

### Evidence and Lifecycle Retention

The sweep also clears expired public-steer idempotency metadata in bounded inbox batches using row locks with `SKIP LOCKED`. It never acquires Thread locks or removes accepted input; [Steer Idempotency Storage](19-agent-control-active-execution.md#steer-idempotency-storage) owns the replay window and lazy replacement rules.

The HTTP evidence sweep covers the shared command evidence independently of protocol bindings, execution identities, and security audit. Expired evidence never proves that an earlier external operation did not happen.

Outbox retention evaluates each source and destination under its own delivery-audit, duplicate-suppression, redrive, and progress requirements. Pending or claimed work is not deleted by a terminal-history sweep. Releasing an Outbox dependency does not automatically delete its source or destination; their remaining dependencies are evaluated separately.

Lifecycle retention removes only settled, eligible event ranges and preserves the lowest retained organization and resource sequence semantics. It cannot delete around an event still pinned by unfinished Hook dispatch, delivery, or projection, nor manufacture a gap inside a retained prefix. Hook dispatch, publication, projection, and retention remain independent completion boundaries.

### HookSubscription Collection

The collector evaluates the head and immutable Revisions against the full [Hook retention contract](26-hook-notifications.md#hook_subscriptions-and-hook_subscription_revisions). It preserves an inline head and Revision v1 while its owning Run remains an eligible Feedback, waiting-Continue, or Retry source, even after automatic expiry or manual deletion. It also checks unfinished dispatch for the owning Run and its RunAttempts, retained command evidence, delivery/redrive, audit, and relational references.

After all dependencies end, periodic collection removes the eligible head and Revisions in a referentially valid order. Deleting a Revision cannot leave a retained head's current Revision or an Outbox destination dangling. Collecting a historical Revision does not change a managed subscription's current version, and collection never reuses a subscription or Revision identity. The collector does not replace missing configuration with an empty Hook or reconstruct it from Run input or state.

### Objects and Upload Evidence

An expired upload receipt and its package object have separate eligibility. Receipt cleanup preserves any still-required command replay evidence; package cleanup proves that no retained publication, unexpired candidate, or accepted Run/Revision lock requires the same object. A consumed receipt's expiry cannot delete its published Skill Revision.

Object listings, timestamps, digest equality, and a missing response can locate candidates but never prove absence of ownership. An orphan scan covers service-owned object namespaces and checks authoritative selections, including publication that may have committed with a lost acknowledgement. Temporary files local to another process are not inferred to be abandoned from age alone.

Collection and publication serialize authority for the exact object: before destructive I/O, the collector establishes that no committed reference owns it and prevents a concurrent publisher from selecting bytes being removed. A publisher that loses that race must recreate or verify durable content under the owning publication boundary before accepting a reference. A grace period alone cannot provide this guarantee. The exclusion uses short owning transactions and fenced state where needed; it never holds a database transaction across object deletion.

Deletion targets the exact selected key and, when the object store supports replacement, the exact object generation. A missing object counts as successful idempotent cleanup; an unknown deletion outcome remains reconcilable. Relational progress needed to identify and retry the effect survives until the owning completion boundary commits. A retained reference whose object is missing produces the domain's explicit content-unavailable failure and an operational diagnostic, not a fabricated successful collection.

### Object Publication Authority

`object_publications` coordinates service-owned immutable object publication and reclamation. It is internal per-key exclusion, not a work queue or resource API. Its primary key is the exact logical object key (up to 1024 characters). Each row records a fresh kind-prefixed `generation`, `phase` (`publishing`, `ready`, `collecting`, or `collected`), nullable provider `object_version`, nullable `lease_expires_at`, and UTC `created_at` and `updated_at`. Only the two active phases have a lease. An index on `(updated_at, key)` supports recovery inspection.

A publisher establishes a fresh publishing generation in a short transaction, writes outside the database under a finite timeout, and marks ready only while that exact generation and lease remain valid. The transaction accepting the Asset, Skill upload or Revision, or new Run locks its exact publication keys and requires ready state before committing the reference. Existing verified objects without a registry row are registered under that same lock. Updating an already accepted Run's checkpoint retains its owning Run writer CAS and permanent namespace pin.

Collection locks the same key, checks every retained owner, and commits a collecting generation before deleting the observed provider version outside the transaction. The completion transaction requires the same unexpired generation. Expired publishing and collecting claims are independently scanned, including when a lost delete acknowledgement has removed the object from listings. A publisher reusing bytes after a collection race republishes the stored content with a fresh provider version before committing readiness; the losing caller's conflicting bytes are never substituted. Thus a delayed former deletion cannot remove the republished version. Collected fence rows remain retained to reject stale final reference commits.

Known namespaces include Asset content, Skill packages, native Run state/display/replay/payloads, and hosted AG-UI replay. A retained Run pins its state, display, replay, and payload namespace, including payloads referenced inside checkpoints. Skill Revisions continue to pin their packages. Unknown namespaces remain retained. The first deployment of this fence requires all object-writing processes to use the new boundary before collection starts; migration alone does not make old writers safe.

### Effective Collection Policies

Hook history and Asset tombstones have separate default minimum ages of 30 days. Required security audit and unexpired command receipts continue to pin them beyond those ages. Asset tombstones also wait for retained cleanup Outbox records and source RunAttempt reconstruction; published cleanup receipts use the configured published-delivery horizon, while unfinished cleanup dead letters remain durable progress. Skill upload receipts expire at their own deadline, subject to unexpired HTTP replay evidence. Object orphan discovery uses a default 24-hour minimum age in addition to publication fencing.

Owner cleanup rotates bounded batches of Service Accounts, live RoleBindings, and Assets beneath deleted Workspaces; Secret erasure has its own bounded scan. Asset cleanup uses the same atomic tombstone, audit, and Outbox transition as explicit deletion. Reversible User or Service Account disablement does not authorize erasure. The implementation establishes no hard-delete horizon for retained Runs, finalized inbox/queue history, Secret metadata, IAM tombstones, or security audit; those authorities remain retained until their owners establish such a policy.

## Failure and Shutdown Semantics

| Failure or race                                                                   | Required behavior                                                                                                                                               |
| --------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Process exits before mutation or claim commits                                    | The candidate remains discoverable; another iteration uses the same owning facts                                                                                |
| External effect may have occurred before acknowledgement is recorded              | Reconcile by the existing identity or retry only an idempotent effect; never mark success from timeout or missing evidence                                      |
| Lease expires or a competing transition changes eligibility                       | Discard stale completion; the next owner revalidates and follows the domain recovery path                                                                       |
| Temporary dependency failure or capacity exhaustion                               | Preserve authority, use bounded backoff, and continue or resume unrelated eligible work without a tight retry loop                                              |
| Permanent per-item failure                                                        | Apply the owning failed/dead-letter/action-required outcome and emit a safe diagnostic; absence of such a transition does not authorize deleting the item       |
| Collection dependency appears or ownership cannot be proved                       | Defer collection and retain data; destructive I/O cannot race accepted ownership                                                                                |
| One ordered predecessor remains retained or locked                                | Defer the affected prefix and continue independent work without creating a retention hole                                                                       |
| Critical task returns unexpectedly or fails outside its handled recovery boundary | Follow runtime supervision: become unready and terminate after bounded cleanup                                                                                  |
| Service drains during work                                                        | Stop new scans, claims, and external dispatch; finish or relinquish in-flight authority within the drain deadline without reporting unfinished work as complete |

Cancellation propagates after bounded cleanup. Drain does not extend a lease indefinitely, clear durable intent, release retention dependencies prematurely, or force an uncertain external operation to repeat. A successor process resumes from the owning durable state under the ordinary fence and idempotency rules.

## Operational Evidence

Every task exposes a stable bounded task label, last iteration outcome, iteration duration, candidates examined, committed progress, deferred/failed counts, and age of eligible backlog or equivalent lag evidence. Collection distinguishes records examined from records and bytes successfully reclaimed. Measurements of bytes reclaimed are reported only when known. Dead letters, repeated failures, blocked retention dependencies, and growing lag remain observable even if other task classes are healthy.

Diagnostics include the owning role and safe correlation identifiers needed to inspect affected durable records. Metrics use bounded labels; Organization, Workspace, Run, and object identifiers do not become unbounded metric dimensions. Logs and traces do not contain callback credentials, OAuth material, Secret ciphertext or plaintext, uploaded content, or Run payloads. [Observability](38-observability.md) owns export and data-policy controls; diagnostics never replace durable progress evidence or decide task completion.

## Invariants

01. Every catalogue task has one role owner; `all` includes each enabled component once.
02. Losing requests, wakeups, or a control process cannot permanently strand continuously eligible work while compatible capacity and dependencies remain available.
03. Concurrent scans and expired claims cannot accept duplicate domain transitions or publish stale completion.
04. No task holds a database session across external I/O, a wait, or another background iteration.
05. Background acceptance preserves the owning Principal, current authorization, Thread selection, FIFO, and waiting barriers.
06. Logical expiry and access revocation do not depend on physical cleanup; physical cleanup waits for every required retention dependency.
07. Eligible collection is periodically attempted, while data with unknown ownership or an active publication race is preserved.
08. Collection cannot destroy a retained continuation source, replay dependency, or required audit record.
09. Per-item failure and shutdown preserve enough durable authority to recover without inventing an effect outcome.
10. This catalogue adds no control-owned RunAttempt executor, Environment maintainer, ingress consumer, credential refresh scanner, or telemetry archive.
