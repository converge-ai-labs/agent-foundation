# Browser Use Capability

## Design Position

`BrowserUseCapability` supplies native browser tools over an embedding Host's explicitly supplied browser backend. Harness owns tool definitions, instructions, managed permission metadata, observation rendering and compact element references. The Host owns browser process creation, profiles, endpoint selection, access and human takeover. Harness provides the CDP connection and page-operation adapter; the Host bounds that connection lifetime. The Capability neither launches browsers nor implements a remote desktop or a provider platform.

The native operation layer uses cdp-use as a regular Harness dependency. It follows the observation/reference, action and condition-wait patterns of [browser-use](https://github.com/browser-use/browser-use) and [agent-browser](https://github.com/vercel-labs/agent-browser), without importing their Agent orchestration or requiring an external CLI/daemon. This keeps the existing Harness model loop, permissions and Host ownership boundaries while concentrating CDP routing and cleanup in one adapter. Chromium/CDP is the supported browser family; no Playwright fallback is retained.

## CDP Adapter

Use the regular Harness installation to access `a13n_harness.capabilities.browser.cdp`. `CdpBrowserBackend.connect(cdp_url)` is an async context manager accepting a trusted HTTP(S) CDP base URL or WS(S) browser debugger URL. HTTP(S) discovery reads `/json/version`; the endpoint remains Host-only connection input and is never an Agent tool argument or continuation state. The adapter supports Chromium-compatible browsers through cdp-use and does not launch or install a browser.

The context creates one dedicated page and yields a `BrowserBackend` usable by `BrowserUseCapability`. The backend owns that page and tabs explicitly created through its tab API. Its operation lock serializes selection with actions in this scope. On exit, including failure or cancellation, the context closes its created tabs and disconnects its CDP client. It does not close the supplied browser process or other pages. The Host keeps this context alive for every Run that borrows its backend. The standalone backend has no human-control owner; applications that provide takeover wrap the same operations with their current authority checks.

`Chromium.connect(cdp_url)` exposes the shared connection for Hosts such as Harness UI that manage several page targets. Harness owns observation, frame/session routing, element actions, keyboard dispatch, navigation, screenshots, scrolling, JavaScript dialogs and Host-path file operations. Harness UI supplies native window sizing, VNC viewing/input, Thread ownership and takeover. Disconnecting the adapter never implicitly sends `Browser.close`; only the browser process owner invokes that explicit operation. There is no CDP image-streaming viewer in this implementation.

## Observation and Actions

Navigation, observation, screenshots, click, ordinary text fill, supported keys, tab management, scrolling, condition-based waiting, JavaScript dialogs and file operations use the existing native FunctionToolset and Harness approval path. Website content is untrusted external data. Mutations have no automatic replay guarantee; read-only observations and bounded output use canonical tool metadata.

Navigation passes the requested URL to Chromium, which determines supported schemes and reports navigation errors. Browser-internal pages such as `chrome://settings` and Host-local `file:` documents use the same tool as ordinary websites. Access to these locations has the browser Host's authority.

Each Run has fresh Capability reference state. An observation returns a bounded page description, backend observation revision and element identities. Harness exposes compact references such as `e1`; those references resolve only through that Run's latest observation. Navigation clears references. The backend validates the revision and actual element identity before dispatch, rejecting stale or detached targets instead of inferring a replacement from an index or label.

The backend rechecks current Host authority for every call. During human control all model-facing browser operations are unavailable, including page observations and screenshots. A browser tool requested during human control waits for explicit handback without collecting page content or polling the model. On release it returns an instruction to observe afresh; the pending operation is not replayed. Other explicit browser failures become tool results without being treated as successful actions. After handback, the Host requires a fresh observation before another mutation and invalidates prior element identities.

A restrictive `RunConfiguration.allowed_hosts` is rejected before browser tools become available. The browser owns opaque subresource, redirect and background traffic and cannot enforce that per-request policy. Hosts use Environment or deployment network isolation for the browser; an unrestricted Run does not itself grant access to a backend.

The Capability borrows its backend and never closes the Host browser when a Run ends. [Harness UI Host Browser](../a13n-harness-ui/11-browser.md) owns the built-in headed Chromium runtime and VNC viewer contract.

## Tabs and Frames

`BrowserBackend.tabs` lists or mutates only its Host-assigned tab scope and returns `BrowserTab` values with target, title, URL and selected state. `browser_tabs` exposes Run-local `t1` references for list/new/select/close, and clears element references on tab changes. Consecutive tab-management operations do not require an intervening page observation. The Host rechecks ownership on every operation; a tab reference never grants access to another Thread. In Harness UI, a Thread owns a native window and its tabs, including explicitly assigned popups. New tabs are created from an owned page and their native window identity is checked. Explicit selection may activate that Thread's window. Ordinary element operations address explicit page targets without an explicit window-activation step. Chromium may still change native focus when dispatching input; separate windows do not isolate native focus, browser dialogs or profile state.

Observations collect up to 32 owned frames and 1200 accessibility nodes. Same-process frames use their page session; out-of-process iframe sessions are admitted only through that page's frame ancestry, not by enumerating arbitrary global targets. Element references retain frame, session and backend-node identity. Click coordinates are translated through iframe owners, checking visibility and occlusion at each boundary. Rotated/unsupported frame geometry fails explicitly rather than guessing a target. Frame navigation or detachment invalidates references; a frame change during observation requires another observation. Shadow DOM hit testing follows the composed element ancestry.

`browser_scroll` scrolls the document or an observed scroll-container reference by bounded horizontal/vertical CSS pixels and returns before/after positions. `browser_wait` waits up to ten seconds for text in an owned frame or an observed element's visible/hidden/enabled condition. Neither operation introduces a global cross-Thread task queue.

## Dialogs, Credentials and Host Files

`browser_dialog` inspects, accepts or dismisses a pending JavaScript alert/confirm/prompt. Observation reports dialog state without querying paused page scripts; screenshots and ordinary actions return an explicit pending-dialog result. A click whose reply is paused by a modal returns a dispatched/pending outcome, not a completion claim or an automatic retry. CDP completion and node-handle cleanup may finish after the dialog closes. After handback or selection, page-content mutations require a fresh observation; dialog inspection alone does not override that requirement. OS authentication prompts and other native browser UI require human takeover.

Text fill supports password inputs as well as ordinary editable fields. File inputs use `browser_upload`. Saved-password autofill can be triggered using browser clicks and supported keys; the tools do not extract saved passwords or render input values in observations. Explicitly supplied fill text passes through normal tool arguments and conversation history; users who want credentials to bypass the Agent use native takeover or saved-password autofill. Password-store and OS authentication behavior remains browser/platform dependent.

`browser_upload` selects 1–16 absolute regular-file paths on the browser Host for a referenced file input, without opening an OS chooser. Multiple-file inputs must support the requested count; directory upload is not provided. Harness UI verifies local file existence after authorization. A standalone remote-CDP Host supplies paths meaningful to the remote browser filesystem. This operation transfers website data with the Host's authority; it does not upload files from the WebUI client or an Agent Environment.

The browser process owner optionally configures native download tracking. Harness UI uses `<data_root>/browsers/downloads`, preserving files across runtime shutdown. Files use browser-generated GUID names rather than website-supplied paths. `browser_downloads` reports at most 100 observed download records, status and completed Host paths; Harness UI filters them by originating Thread, including closed owned tabs. Unknown frame origins are not adopted. Records are process-local and do not reconstruct completed downloads after restart; stored files are not automatically removed or transferred to the client. In-progress downloads have no completed-path claim.
