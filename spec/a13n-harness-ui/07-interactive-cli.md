# Interactive CLI

## Design Position

Harness UI is a full-terminal client of `HarnessUiApp`. The App remains the sole owner of configuration acceptance, agent execution, continuation selection, decisions, agent cancellation, and agent observations. Explicit user-owned local shell commands are terminal operations, not agent executions. Terminal code does not construct Harness Runs, Environment mounts, or database transactions. The WebUI adapter reuses the same App boundary through the explicit `a13n-harness-ui webui` subcommand. Interactive mode does not start a server, daemon, or subprocess terminal. The CLI uses native prompt-toolkit interaction on Windows, macOS, and Linux: startup update confirmation, setup, and conversation in one full-terminal Application. These stages never compete for terminal input.

The terminal owns one current conversation and an editable draft. Durable Thread and Project identities remain internal application concepts. Removing their management UI does not delete or migrate historical execution data.

## Startup and Terminal Ownership

`a13n-harness-ui` without a subcommand starts interactive mode in the invocation's current directory. Input and output must both be terminals; automation uses `a13n-harness-ui run <prompt>`. CLI help, version, and command parsing do not import the App, Harness, database, provider libraries, or terminal renderer.

Startup mounts the landing TUI before heavy imports and App initialization. Loading, questions, account actions, and previews replace the current view in one alternate-screen Application, not append terminal scrollback. Conversation replaces the startup view in that same Application without leaving and re-entering the alternate screen. The composer preserves drafts but does not admit execution until the selected session is ready. It does not issue a model request, authenticate an account, launch an Environment, or connect configured MCP servers merely to inspect configuration. Ctrl+C exits preparation. A usable selected Agent and Model configuration enters the conversation directly; an unconfigured launch first opens the standalone setup workflow. Broken configuration produces repair guidance rather than overwriting the source. Startup failures return to the terminal without mounting chat. One task owns the same App context through setup, conversation, and cleanup; setup does not start a second App or an execution Run.

One process owns input and terminal rendering for its lifetime and restores the terminal on exit. A scrollable Markdown viewport retains a bounded semantic display cache, not a second conversation database. Blocks reflow on resize and theme changes. Eviction and truncation are visible; Ctrl+T opens the retained-history browser through the App. Streaming updates are coalesced, and completed blocks are not reparsed on each delta. Large active messages use cached plain-text chunks until final Markdown reflow. Rendered rows are paged through disposable local caches, not deleted merely to satisfy a viewport budget. Semantic retention remains separately bounded and eviction is explicit. Interleaved root and child messages remain distinct. Finalization and cancellation flush pending text. Scrolling away from the latest output freezes the view until explicitly returning to the latest output. Best-effort event loss is distinguished from a complete live transcript; the committed final answer remains authoritative.

The composer, pending interaction, status, and transcript share one layout. Narrow or short terminals preserve usable input. Dark, light, and passive automatic themes are available; auto preserves the terminal default foreground/background and semantic ANSI palette. Terminal detection never consumes keyboard input. Theme colors apply consistently to transcript, composer, selections, and status. The bounded multiline composer has a distinct surface and contextual action hints; short terminals collapse decoration before sacrificing editable input. Footer shortcuts reflow between complete labels into at most two rows as width allows, prioritizing the retained-history entry during conversation and keeping `/notes` discoverable in both normal and narrow layouts. Submission guidance stays in the composer header rather than repeating in the footer; interaction and history views show their own relevant controls. In narrow conversation layouts the composer header identifies the current Scroll or Select mode, while the footer names the Esc switching action. Scroll mode captures mouse events by default: the transcript, selector, and composer handle their own region. Selector wheel motion browses options without changing an answer; clicking highlights and Enter confirms. Ctrl+Space switches selector/composer keyboard focus; arrow keys edit the composer when it owns focus. Esc dismisses an interaction or completion before toggling scroll/select mode. Select mode leaves mouse selection/copy to the terminal, so application-local wheel routing is unavailable; PageUp/PageDown and Ctrl+End remain usable. Returning to the bottom resumes following output. Clipboard images are read only on an explicit paste action, with file attachment as a portable fallback. Multiline text paste never triggers image reads or submission.

Enter sends a new prompt while idle and sends text guidance to the active root operation while it accepts steering. During a pending decision or selector it answers that interaction instead. The composer identifies whether Enter sends a prompt, adds guidance, or confirms a selection. Alt+Enter inserts a newline; bracketed multiline paste remains a draft until explicit submission. Ctrl+C requests active cancellation with immediate feedback; cancellation and cleanup finish before another operation starts. While idle, the first press clears the draft and shows an exit reminder; a second press within two seconds exits. Editing the draft disarms that exit reminder. Ctrl+D on an empty draft exits. Rejected commands and unavailable submissions preserve input. Slash input is a command only when its complete leading name matches the command catalog or an alias. A successfully parsed command produces an explicit acceptance notice before dispatch. Unmatched slash input produces a plain-text fallback notice and follows ordinary input handling without removing or rewriting the slash: it starts a prompt while idle, steers the exact captured active receipt when allowed, or answers the current interaction. Known commands with invalid arguments or unavailable state remain rejected commands, never model input. Fallback does not bypass readiness, attachment, interaction, or active-operation constraints.

Unexpected terminal exceptions produce a private temporary diagnostic report with exception chains, frame locations, version, and recovery context, without copying execution state, locals, source lines, or transcript contents. Reports are never uploaded automatically; users are warned to inspect exception messages for sensitive content before reporting an issue. Recovery refers only to already selected saved continuations, not unsent drafts or in-flight work. Report-write failure does not replace the original error. Event-loop reports also retain bounded task identity, coroutine location, suspended frame locations, and creation frame locations when available, without serializing task representations or arbitrary loop context. The specific asyncio notification that a pending Task was destroyed, without an accompanying exception, produces a visible warning and private report but does not terminate the terminal. This does not restore the lost task, declare an operation successful, select a continuation, or retry work; execution status remains App-owned. Other unhandled terminal event-loop failures still terminate the terminal with recovery guidance. Completion and newly required human decisions emit a terminal bell; terminal sound policy remains terminal-owned.

During an eligible model interruption, the terminal renders the Harness `model_retry_scheduled` recovery observation as a short system notice that the model request is being retried. It does not display exception payloads, stack traces, continuation instructions, or per-attempt terminal errors. Root notices appear in both display modes; child notices follow the detailed child-visibility rule and include child identity. Only exhausted recovery displays the terminal failure with the total attempt count and continuation guidance; the text surfaces omit the redundant raw `new_run` retry hint while structured failures retain it. Recovery notices never change Run status or authorize tool replay.

Interactive logging writes JSON diagnostics to `<data-root>/logs/terminal.log`, with 5 MiB rotation and three backups, rather than either terminal screen. Repeated unchanged plugin diagnostics produce one actionable terminal notice per process; details remain in the log. Noninteractive and WebUI logging are unchanged.

Interactive launch and explicit setup check the public package index before configuration readiness and setup questions when `process.terminal_update_check` is true (the default). `--no-update-check` disables both cache lookup and network detection for one invocation; `make a13n-harness-ui` always supplies this flag. Development versions (`0.0.0` and PEP 440 development releases), help, version, and noninteractive commands never check. A daily metadata cache lives under the data root; the check has a three-second total timeout, a bounded response, no model credentials, and silent offline failure. Only stable PEP 440 versions newer than the installed distribution trigger a prompt.

The update prompt and subsequent setup redraw the same landing TUI. For a recognized uv-tool installation it shows the command and installation directory, with **Update now** and **Not now** choices; Not now is the default. Escape or Ctrl+C at the update question skips updating. Skipping is not remembered as installation consent or version suppression: a still-newer cached version prompts again on the next enabled launch. Unknown installation methods show manual package-manager guidance and cannot launch an installer.

Startup detection never installs anything. Only an explicit Update now answer returns an installer command to the executable. The App and terminal fully close before `uv tool upgrade a13n-harness-ui` inherits the ordinary terminal, using the running installation's uv tool directory. Success asks the user to restart; failure reports the installer exit status without retry. Neither path continues setup or chat in the old process, and no startup or exit task installs in the background. Exit does not repeat update notices.

`a13n-harness-ui update` explicitly authorizes an immediate foreground update of the running uv-tool installation without a second confirmation. It uses the same installer handoff, installation-directory selection, success guidance, and failure exit behavior as Update now, but starts neither the App nor a TUI. It bypasses startup metadata detection and its daily cache; `--no-update-check` and `process.terminal_update_check` do not disable this explicit command. uv owns package resolution and network access. An unrecognized installation or missing uv executable fails with manual package-manager guidance rather than guessing an installer. Interruption exits with status 130 and asks the user to inspect the installation before retrying; no path retries automatically.

After terminal restoration and App cleanup, an existing saved root session produces a shell-quoted `a13n-harness-ui --resume <thread-id>` hint with configuration/data-root overrides and the required workspace directory. Setup-only, failed startup, and sessions without a created thread have no resume hint. The hint does not assert that an unfinished Run published a continuation.

## Commands and Presentation

One command catalog owns syntax, aliases, help, completion, and availability during active work. Duplicate names or aliases are rejected. Commands that would change subsequent execution configuration are unavailable while work is active. `/mode`, `/status`, `/help`, `/steer`, `/cancel`, and `/quit` remain available. Command arguments preserve native backslashes; paths containing whitespace use surrounding quotes. Typing `/` opens command completions; `$` opens available Skill names and short descriptions. Both support filtering and completion without requiring Tab. Whitespace-delimited `$name` references may appear anywhere in an ordinary prompt; repeated names carry one reference. Explicitly selected completions are accepted before submission; a fully typed command remains directly executable. Skills never appear in the slash namespace; the same name may independently identify a command and a Skill. Skill shortcuts carry the App's catalog references and are validated against the selected or active catalog, rather than creating an independent Skill registry. Pending approvals and external tool results use the typed decision interface, not raw approval/result slash commands. Login is exclusively outside the TUI through `a13n-harness-ui login <provider>`.

- **Concise** is the default: assistant text, heading-free provider-exposed reasoning, decisions, errors, and compact tool rows. Each tool updates one correlated block from running to result; retained details expand together. Tool rows do not insert blank spacer rows. Shell calls use one correlated borderless summary row with an explicit running/waiting state or observed exit code followed by the command. Concise mode does not preview stdout or stderr; Ctrl+O reveals retained arguments, literal output, and full native diagnostics. Empty or redirected streams never create placeholder bodies or imply failure. Merged output such as `2>&1` remains literal stdout in expanded details. Failure, timeout, output-coverage, omission, and disclosure facts appear inline ahead of the command so narrow terminals prioritize outcome visibility. Process handles remain in expanded details rather than separate lifecycle panels. `shell_wait` resolves a command only from a retained observation for the same Run and process reference; missing observations remain explicitly unavailable. An API-level `ok: true` does not imply exit code zero, and a nonzero exit remains visibly unsuccessful. Expanded arguments are formatted JSON. Reasoning deltas update a stable block without repeating a Thinking heading. Thinking blocks have no synthetic blank separator before adjacent thinking or tool blocks, including Shell and edit panels; model-authored paragraphs, block identities, and separation before answers remain intact in both display modes. Shortcut reminders appear once in the footer, not after every folded block. User messages use a prompt marker rather than a role-name prefix.
- Native Shell status events do not append running/exited/exit-code panels or fall through to generic event JSON. A later background completion can produce one compact, command-first notification when its completion was not already observed in a tool result. Notifications correlate within a Run using bounded retained display state, expose raw diagnostic fields on expansion, and obey child-output visibility rules. Unknown event types retain the generic fallback. These presentation choices do not change native event emission, execution semantics, or user-owned `!command` panels.
- `edit` and `multi_edit` replace the correlated pending invocation with a panel containing the file path, added/removed line counts, and an eight-line diff preview; Ctrl+O expands retained content. Panel titles omit raw call IDs. Diffs derive only from the successful native `a13n.filesystem.edit_applied` event's actual before/after text. The panel body contains diff context and added/removed lines without repeated file headers or hunk line-number headers; separated hunks retain an explicit gap marker. All replaced occurrences and trailing-newline differences derive from the actual result. Failed batches and semantic no-ops produce no applied panel. Comparisons above a combined 131,072 characters or 2,000 newline boundaries use explicitly labeled actual before/after text instead of potentially quadratic diff matching; ordinary transcript retention bounds still apply. Specialized edit, summary, and compaction presentation does not duplicate raw invocation arguments. Failed tools remain visible and do not imply a successful effect.
- `summarize` shows the persisted summary and file reminders from `a13n.context.handoff_summary`, not a projection of its arguments. Handoff and compaction lifecycle blocks show every exposed field, including operation identity and failure phase. Preparation and application are distinct. Compaction summary content arrives through the public native Capability event, correlated by operation ID, and is displayed in a separate expanded panel. Expanded Shell details, edit, information, notes, handoff, and compaction panels share a subdued frame with a bold left-aligned title and literal, width-aware bodies (rounded corners where supported, with Rich's safe legacy-console fallback); edit additions and removals use semantic colors. This common structure distinguishes panels from ordinary assistant Markdown without giving each capability a competing accent. The CLI never infers it from unrelated or previously selected history.
- **Detailed** expands retained ordinary tool blocks and additionally shows subsequent child output. Tool results identify their call and elapsed observation time; child output identifies its execution or Run. Neither mode invents reasoning or exposes hidden model state.
- `/mode concise|detailed` and Ctrl+O fold or expand retained tool details without deleting their sources. `/history` explicitly reads saved details independent of presentation mode. Upstream omissions and retention bounds remain visible, not represented as recoverable full content.

Display mode never changes tool access, shell review, model reasoning effort, or approval behavior. The compact status bar prioritizes state, a Fast indicator when the effective requested `service_tier` is `priority`, cumulative observed root Thread tokens (input plus output), latest root request context tokens and occupancy, cache rate, and model cost, followed by model and elapsed time as width permits. Cumulative counts use uppercase K/M units with one decimal place at every width, or integers below 1K. Narrow layouts shorten the label to `tok` before omitting lower-priority fields; `/usage details` retains exact totals. `tokens` is cumulative request usage, while `ctx` is the latest request footprint, not a cumulative value. `/status` uses one aligned settings panel with Agent, Model, reasoning, requested service tier, context footprint, Environment, workspace, session, and display mode. Recorded counters are available separately through `/usage details`. Cache rate is cache-read tokens divided by input plus output tokens, matching the terminal metric rather than a prompt-only hit rate; cache subsets are never added to token totals. Context and cost fields remain visible with unknown placeholders before observations arrive. Each native model-request usage report refreshes the bar while the root operation remains active, without waiting for operation completion or transcript output. This is provider-reported request-boundary usage, not invented per-token metering. Fragmented custom reports are reassembled before usage projection. The status bar's observed root Thread cost excludes child and non-model costs and is distinct from subscription billing. The [observed usage ledger](03-local-storage-and-recovery.md#observed-thread-usage) restores the root Thread baseline on resume and before admission. Live reports add the current operation's usage, deduplicated by native record identity. After the operation settles, retained ledger totals replace the live projection, including failed or cancelled requests and observations missed by the live subscription, without counting reports twice. Cache rate uses summed counters, not an average of per-Run percentages. Starting another Run preserves the Thread totals; switching Threads replaces them, and `/new` clears them. Unknown costs remain unknown, not zero; any root request with unknown cost makes the status total unknown. History without ledger coverage remains unavailable rather than being reconstructed from messages. Occupancy uses the last root request footprint divided by the configured working budget, not provider capacity. Unknown usage is shown as `--`, real zero as `0%`. Narrow widths discard secondary fields before the current state. `/status` retains exact context tokens, model, environment, and session details without repeating the bar or a usage report. Request footprint is not cumulative Thread usage and does not estimate the next prompt. Child and auxiliary request usage are not added to root context occupancy.

Active-run Enter captures the exact root receipt before asynchronous dispatch and sends literal text through the App's existing steering operation. `/steer <message>` remains an optional explicit entry point, not a prerequisite for guidance. Acceptance means the Harness accepted the input for a model boundary, not that the model consumed it or that a durable checkpoint exists. Acceptance produces a brief sent notice without echoing the guidance body or receipt JSON. Queue and delivery observations do not repeat that notice or its body; the actual model-input event displays the guidance only when applied. Preparation, cancellation, non-agent work, completed receipts, and absent receipts do not accept ordinary steering input. A draft containing images is preserved in full rather than silently sending only its text. A rejected or unconfirmed submission restores its draft or exposes `/recover` without overwriting a newer draft. A race with Run completion never converts guidance into a new prompt or retargets a replacement receipt. The CLI adds no next-Run queue, message reordering, or automatic retry; native Harness enqueue order and consumption boundaries remain authoritative.

Ordinary input is displayed locally before asynchronous admission. Its explicit source identity correlates the later model-input event, avoiding duplicate display without comparing text. Repeated equal prompts remain distinct. Admission failure remains visible and retains the existing draft-recovery behavior; a local echo is not a saved continuation. Restoration summaries and internal reminders use presentation metadata rather than being shown as new user submissions. Harness lifecycle notices carrying `a13n.steering-source` content metadata (`background_process` or `async_subagent`) render as subdued Activity text without the user prompt marker; message wording never determines provenance. Native history part content and order are not rewritten for terminal presentation.

Host-generated feedback uses a consistent System marker and theme-aware accent/muted styling, distinct from user and assistant messages. The marker is presentation only and never inserted into retained source text. Markdown help retains its formatting, and structured informational panels retain their own labeled layout.

File-tool summaries and applied-edit panel titles display absolute descendants of the invocation directory as relative paths. Outside paths, already-relative paths, foreign filesystem paths, and parent-traversal paths remain unchanged. This is lexical presentation only: it does not resolve symlinks, change operation arguments, or rewrite raw results, expanded payloads, command text, or file contents.

The task pane is separated from the transcript by a full-width rule, including when collapsed. It is populated from selected-continuation task snapshots and typed native task changes, never from tool-result text. It starts expanded with at most five rows, prioritizing active and pending tasks, with at most two completed rows. F2 toggles the list; counts, task IDs, and unresolved dependency hints remain bounded. An accented heading distinguishes the task pane without extra border rows; active subjects and textual state labels carry semantic emphasis, while identities and completed subjects are subdued. Width-aware headings retain the F2 control before lower-priority counts, and task rows truncate at terminal-cell boundaries with an ellipsis. Task and state versions reject stale observations without dropping different task updates at the same state version. Snapshot reloads after operation completion or session changes restore the selected durable state. Unavailable provider-backed snapshots are labeled unavailable, not reported as empty completed work.

### Observed Thread Usage

Bare `/usage` is read-only, works with every model, and remains available during active work. It uses the [observed usage ledger](03-local-storage-and-recovery.md#observed-thread-usage), not retained messages or the status bar's in-flight projection. The default view is a compact panel of combined input/output tokens, response counts split into root and children, cache reads, known model cost with unknown-cost counts when present, and separate provider-currency subtotals. Zero-valued audio and receipt rows and repeated Run breakdowns are omitted from the default view. `/usage details` retains root-agent, descendant, and combined totals, model breakdowns, and the latest 32 observed Runs with native Run/agent identity. Older Run contributions remain in the totals. Known model cost and provider currency subtotals retain separate unknown counts. Missing coverage, subset counters, and first-observation receipt attribution are explicit. Context occupancy remains a separate current-context field.

`/usage subscription` shows read-only Codex limits while idle. `/usage reset` is the only usage command that opens credit redemption, retaining the explicit account-bound confirmation and same-ID recovery contract. Opening status, Thread usage, or subscription limits never opens a redemption prompt.

### Activity Inspection

A compact activity line above the status bar, separated from the transcript by a rule and outside the input area, displays the selected conversation's total saved child-execution count with `/subagents`, and observed running background-process counts with `/ps`. Empty categories are hidden. The child count includes completed executions and is periodically refreshed through the App, independently of transcript rendering; failed reads show unavailable rather than zero, and late reads cannot overwrite a newer conversation's display or pagination state. `/subagents` reads one App page of at most 20 child executions, `/subagents next` advances one page, and `/subagents <execution-id>` opens the App's existing bounded child review. Persisted running state without local execution authority is explicitly distinguished from active work. The `/subagents` list and detail header emphasize textual state and Agent name with the same theme-aware activity palette as `/ps`; identifiers, timestamps, and other metadata are subdued. Narrow layouts fold content without hiding local-authority caveats, pagination, or incomplete-preview warnings. Inspection remains available during active work and does not select a different Agent or start execution.

`/ps` reads bounded, Run-scoped live observations rather than a host process list or a new execution registry. Only returned running Shell handles count as background work; in-flight foreground calls do not. Child Shell observations are collected in both display modes. Terminal status removes the observed running count; a Run boundary marks that Run's remaining running observations unavailable, not successfully exited. Closing the live subscription invalidates all remaining running observations, including children that may outlive the parent. Counts disclose live gaps or retention omissions, and inspection shows last observed status, command, process handle, and Run identity for at most 16 retained background processes. The inspection panel emphasizes textual state labels and commands, with subdued process/Run identities and theme-aware state colors; nonzero observed exit codes remain failures rather than successful exits. Width changes reflow content without dropping identities or observation warnings. Output remains in expanded tool details. The display retains at most 128 Shell observations and does not claim complete process inventory or reconstruct processes from saved transcripts. New or resumed conversations discard prior process observations. Neither inspection command controls or cancels work.

### User-owned Local Shell

`!command` is reserved before steering and interaction dispatch. On an idle POSIX host it runs noninteractively in the CLI invocation directory with the inherited host environment. It is explicitly outside the model's selected Environment or Sandbox; the panel labels it **Local shell**. It does not create a Harness Run, invoke the model, inject output into model context, or consume attached images. Model shell tools continue through the selected Harness Environment.

Active work, preparation, and pending interactions reject the command while preserving its draft. Bare `!` shows usage. One foreground job owns process creation, both pipe readers, deadline, cancellation, and process-group cleanup. Native terminal operation events carry started, stdout/stderr output, and finished observations with phase, exit code, elapsed time, and truncation. Rendering consumes only these events. Output is bounded to a combined 256 KiB while excess bytes are drained; stdin is closed and the deadline is 120 seconds. Cancellation, timeout, and terminal exit kill the owned process group and await cleanup, including cancellation during creation. Commands cannot serve as detached terminal jobs. Windows rejects `!command` until equivalent lifetime cleanup is supported; this limitation does not disable the normal Windows CLI or model shell tools.

Working State notes and their native bounded context injection are enabled by default for UI-composed Agents. Explicit `notes_enabled: false` or capability disablement is respected. Saved notes are read through the App from the selected continuation after resume and operation completion, not inferred from invocation arguments. Changed snapshots use a single concise row with the saved count, explicit omission count when applicable, a Ctrl+O hint, and note keys. Ctrl+O expands the saved values; an explicit `/notes` request shows them directly in a subdued panel with an accented title. Both retain complete values within 256 entries and 256 KiB of UTF-8 content; omissions are counted explicitly. The shared subagent/background activity row also shows the saved note total and `/notes` entry after a snapshot is loaded, including zero and entries omitted from the value preview. This count belongs to the selected Thread; late snapshots from a previous Thread do not update it. On narrow screens the activity row keeps counts before command hints and explicitly truncates when necessary. Note tool previews identify the key (or all notes) and observed result state rather than raw JSON fields. Repeated unchanged snapshots are not appended again. Display budgets never mutate saved notes.

CLI-composed Agents inherit Harness's default `ColdStartFilterConfiguration`, including its 3600-second idle threshold, without duplicating a terminal-specific policy. Cold compression and model-context compaction are independent from display eviction and retained-history navigation.

## Project Selection and Resume

The CLI is an entry point into the ordinary [Project model](04-projects-threads-and-environments.md#projects), not a separate Workspace resource. On the first submission, the App matches the canonical invocation directory against Project first roots. A unique exact match is reused with its entire ordered root list; additional roots do not make it ineligible. Without a match, the App publishes a deterministic directory-derived single-root Project through normal validated configuration mutation. Multiple exact matches require explicit session resume or a Project configuration edit, rather than silently choosing an ID or creating a duplicate. It does not adopt a containing ancestor or match a secondary root as an entry point.

CLI creation and resume use the same App-owned exact-first-root query. The CLI never rewrites or narrows Project roots. Setup also reuses a unique matching Project and preserves its resource instead of publishing a duplicate single-root starter; ambiguous matches require configuration repair before setup publication. Adding roots through configuration or another surface therefore preserves CLI Project identity and resumability from the first root. The first root remains the default working directory and subsequent Runs capture all configured roots; admitted Runs retain their existing capture. Concurrent creation can reuse a verified identical resource; collisions or unrelated configuration changes fail without overwriting user files.

Launch resume cannot be combined with Agent, Environment, or title overrides; the CLI rejects the combination before startup rather than silently discarding a requested permission boundary.

`/new` clears the current selection and starts a new conversation on the next submission, preserving all history. `/resume` lists saved root sessions from Projects whose first root equals the invocation directory, including multi-root Projects; `/resume <id>` and `--resume <id>` reject archived, child, active, and nonmatching-Project sessions. Resume uses the durable selected continuation, not discarded partial output. Before switching, the terminal reads one recent transcript page of at most 50 messages from the App. It replaces the previous display with a chronological tail of at most 100 visible parts and 256 KiB of content, with a 32 KiB per-part bound. Hidden guidance and system prompts do not appear. Older, omitted, and oversized content is explicitly marked; Ctrl+T opens the independent retained-history browser. The page is consumed once, not rehydrated after every turn. Failed navigation preserves attached images and command text. Asynchronous command failures never overwrite a newer draft; explicit recovery remains available. Successful navigation discards only the unchanged prior attachment draft. `/history` is an alias for Ctrl+T, not a cursor-printing command. The browser remains inside the same Application, preserves the live transcript, draft and pending decisions, and closes with Ctrl+T, q, Escape or Ctrl+C. PageUp/Up at the loaded top reads an older App page; PageDown/Down at the bottom reads a newer page. Home selects the loaded page top and End reloads latest; neither exhaustively hydrates history. It retains one bounded display page and at most 128 navigation cursors, with one load in flight and explicit continuation-conflict/reload feedback. Closing discards late responses. The selected continuation can already exclude pre-compaction messages; the browser promises retained messages, not a complete event archive.

## Agent Selection and Reasoning

`/agent` lists configured Agents by display name and model route; `/agent <agent-id>` selects the complete Agent for subsequent operations, including instructions, capabilities, shell-review policy, and model. Auxiliary Model resources are not Agents and do not appear in this picker. `/model` independently lists configured Model resources; `/model <model-id>` overrides only the model for subsequent operations in the current TUI session. It never selects or mutates an Agent, writes configuration files or defaults, or changes a Thread's sticky configuration. `/model default` clears the override and uses the selected Agent's configured model. The temporary choice survives `/new`, `/resume`, and `/agent` within the same TUI lifetime but is not restored by a later TUI invocation. Switching models clears model-specific reasoning and service-tier overrides and previous context occupancy. Selection is unavailable during active work; unknown IDs preserve the previous choice. `/agent default` selects the configured default Agent.

Before a Thread exists, Agent selection stays in the session draft. For an existing Thread, Agent selection uses the App's expected-version Thread configuration mutation and preserves its history, Project, Environment, and other sticky axes. Selection is unavailable during active work or pending interactions. Failure preserves the previous selection. No YAML or global default is rewritten. Switching clears reasoning and service-tier overrides and previous context occupancy, while preserving an explicit session Model override. A subsequent `/new` retains the selected Agent.

`/thinking` changes reasoning effort independently from display mode through detached `RunModelOverrides`; `default` clears that override. The root coordinator copies options before scheduling execution. Composition capture validates effective settings and records the complete recipe before native construction. Inheriting Markdown children receive the effective parent model; explicit child and auxiliary selections remain independent. Invalid selections fail without fallback. Previous immutable compositions remain unchanged.

`/fast` toggles a detached per-operation `service_tier` override: `on` requests `priority`, `off` explicitly requests `default`, and `reset` clears the override to inherit the selected Model's settings. These are generic Pydantic AI service-tier settings, not a Codex-only model switch or a change to reasoning effort. The temporary override survives `/new` and `/resume` within the TUI lifetime, but is never restored from historical usage by a new TUI process. `/thinking` and `/fast` preserve each other's overrides; switching Agent or Model clears both. Active work or pending decisions reject `/fast` and preserve the draft. Fast feedback distinguishes requested priority from guaranteed provider support, latency, pricing, or entitlement. The Fast indicator represents effective requested settings, not observed service fulfillment. Commands never silently retry at a different tier after rejection. Permanent choices belong in the Model's `settings.service_tier`; no `/fast` command rewrites configuration.

Resume restores the Thread's selected Agent. When there is no explicit session Model override, it restores saved reasoning only when the last continuation's Model ID still matches that Agent's configured Model; a previous Agent's saved model cannot undo a later explicit Agent switch. Current accepted resources resolve the selection, never stale credential bytes or deleted resources.

## Setup and Context Management

When the selected Agent has no Model configuration, the CLI opens setup in its own alternate-screen view before creating a conversation composer. The Codex subscription path asks four primary questions: connection, model, Fast or Standard service, and execution permissions. Fast is preselected and saves `service_tier: priority`; Standard saves explicit `default`. The choice explains that priority may consume more quota or cost more and does not guarantee speed. The same choice is offered when adding a new Codex Model or an Agent with a new Codex Model. Reusing an existing Model does not offer it or change that Model. Grok keeps the three-question subscription path. Existing configurations and programmatic setup selections that omit a service tier are not migrated or silently opted into priority. The final answer authorizes validated publication without a redundant confirmation screen. API-key connections instead collect provider/protocol, base URL, a hidden key or credential reference, model ID, settings preset, and working context budget. The final Environment or name question displays the resulting connection and explicit settings. Switching providers discards incompatible endpoint, credential, model, and preset drafts; changing the model reselects its preset and context defaults. The landing screen states that the final choice saves configuration. Existing compatible subscription accounts, including refreshable expired credentials, are reused without another login prompt. Missing accounts show the external login command and offer rediscovery or configuration without login; unsupported or malformed stores offer repair guidance without replacing the store. Discovery never authenticates or refreshes credentials. Explicit `setup --advanced` offers context/reasoning, shell-review, built-in subagent inclusion, and additional-instruction customization. The normal path includes the three built-in subagents without a separate question. Subagent migration is separate through `/import`, not a required setup step.

Selectable steps accept arrow keys, numeric choices, or exact values; text fields retain explicit defaults. Setup selectors use available terminal height and wrapped content width rather than a fixed option count, keep the focused choice visible, and reflow when resized. API Model ID choices are release-owned provider-specific suggestions, not a live inventory; operators can enter a custom case-sensitive ID and revisit it without losing the value. Suggestions do not query account entitlement. Esc revisits selections and Ctrl+C/Ctrl+D cancel the wizard. Cancelling an initial wizard returns to the command shell rather than opening unconfigured chat. Successful first-use setup enters chat; explicit `a13n-harness-ui setup` exits after completion or cancellation. Chat has no `/setup` command. Cancellation before publication writes no selected resource files and never undoes completed credential operations. Existing edits, stale previews, and partial publication follow the shared setup contract. Configuration values remain explicit editable fields, not opaque preset references.

API setup always offers an editable positive context budget. It recommends 350,000 tokens, reduced to the model's context window when the bundled Harness catalog supplies a smaller value. An unknown model still defaults to 350,000, explicitly labeled as a local working default rather than a known provider limit. Catalog lookup is local and does not fetch remote data. Changing the provider, endpoint, or model invalidates the previous context recommendation. Generated API Models save this value in `model_characteristics` with the same 65% summary reminder and 90% compaction thresholds as Codex; generated Agents use native default summary prompts. Existing Models selected for reuse keep their context policy unchanged.

## Multimodal Drafts

The CLI uses the [App's shared composer input contract](05-runtime-subagents-and-surfaces.md#process-local-operations). It sends expanded authored text and byte uploads; the App stages and retains attachments, then creates native Harness input. Images are actual `BinaryContent`, never a local path disguised as image content. Image-only and file-only inputs are supported without inventing authored text. Ordinary files retain their original display names and become model-readable Environment references.

Bracketed text paste stays in the draft and never reads the image clipboard or submits automatically. Pasted text over 1000 characters is represented by a distinct compact marker while editing; multiple blocks remain distinct. Submission and input history contain the complete expanded text, not the markers or temporary text-file references. Alt+E expands folded text for editing; moving the cursor into a marker also expands it before editing. Backspace/Delete next to an intact marker removes that entire block. Removing a block does not send its hidden content. Existing draft save/restore behavior also preserves pending paste content across interactions and rejected submissions.

The composer retains at most eight file/image attachments, at most 10 MiB each and 20 MiB in aggregate. PNG, JPEG, WebP, and GIF images are accepted after decoding validation and a 32-megapixel bound. `/attach <path>` accepts a regular file; clipboard-image actions can also acquire clipboard file lists. Oversized or invalid acquisitions do not alter the draft. Chips identify each pending file and support `/remove <index>` or `/remove all`. Clipboard acquisition runs off the input loop, is fenced to its originating draft, and never inserts a late file into a submitted, cleared, or replaced draft. A failed pre-admission submission preserves text and attachments for explicit retry; once admitted, receipt recovery governs the outcome and the CLI does not automatically resend input. Local draft removal does not delete previously submitted attachments.

Explicit image-paste failures distinguish an unavailable clipboard from an empty image/file result. In detected SSH sessions, failure guidance explains that native clipboard access targets the remote host, not the connecting computer, and directs users to upload files before attaching a remote path. Local Linux unavailability distinguishes missing display-session hints, a missing session-appropriate helper, and a failed read despite an installed helper. Environment hints explain failures only: they never preempt a successful clipboard read, including through a forwarded display. Help documents this boundary without probing the clipboard or displaying startup warnings. All such guidance keeps terminal text paste separate from image acquisition and preserves the existing draft.

## Decisions, Cancellation, and Recovery

Pending approvals and external results are presented using App-owned deferred request types. Individual terminal answers are local drafts until every request in the exact continuation batch has a response. Unknown IDs, mismatched kinds, invalid JSON, or stale continuations are rejected. Cancelling, exiting, or leaving setup never implies approval. Structured question results remain subject to the same App/Harness validation as other adapters. Structured questions omit generic running-tool rows, call IDs and duplicate decision headings in concise display. Approval requests retain explicit review and authorization context in a dedicated panel. Shell review risk and reason appear as styled sections before a syntax-highlighted command and subdued working directory; raw policy and resource metadata stay behind retained-details inspection rather than filling the shell approval panel, and the compact selector owns the approval choices without repeating them in the panel; reviewer failure without an assessment is explicit, never presented as a risk judgment. Environment overrides show names rather than values in the compact approval preview. Bounded previews disclose omissions and offer inspection of retained request details. No approval choice is preselected. An observed Harness invocation denial with `reason_code: shell_review_timeout` produces a visible timeout panel stating that AI review timed out and the command was automatically denied before execution. This is an observed backend outcome, not a terminal timer; human approval has no automatic waiting deadline. Complete numbered option labels and descriptions remain in the scrollable transcript even when the compact selector clips them.

Each newly displayed structured question receives the configured `tools.user_input_timeout_seconds` waiting interval. The terminal captures that setting when opening the interaction and starts a new interval after each accepted answer. Expiry rejects the entire unanswered question call, discards its partial answers, and supplies an explicit native failed external-tool result saying that no user answer or approval was received. Other requests in a mixed batch still require their own responses; only a complete batch resumes the Run. Approval requests and ordinary external results never expire into approvals. Cancelling or closing the terminal stops local waiting without submitting a timeout; reopening a pending interaction starts a fresh interval. This is terminal presentation policy, not a durable Harness deadline or a server-side timer.

Cancellation goes through the root receipt and waits for execution/environment cleanup. Exit cancels active work before closing the App in its owning task. Login cancellation uses the existing credential-store transaction boundary; a completed store write is not reported as rolled back. No cancellation retries a potentially side-effecting operation automatically.
