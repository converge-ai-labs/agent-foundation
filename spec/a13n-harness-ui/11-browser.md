# Host Browser and Remote Desktop

## Design Position

Harness UI optionally owns a headed Chromium browser on its Linux Host, shown through VNC in the WebUI Browser drawer. The Agent operates that same browser through the native [Browser Use Capability](../a13n-harness/23-browser-use.md). Users on different devices can view the same Host browser. Human input bypasses the model and tool history.

This facility requires WebUI computer sharing, explicit enablement in an idle root Full Control conversation, and separately prepared browser/display dependencies. It uses Host networking and filesystem access, outside Agent Environment isolation. CLI, child and Memory Threads do not receive the browser. Service, client extensions, macOS and Windows are outside this milestone.

The remote desktop consists of Chromium, a dedicated resizeable TigerVNC X display, and a window manager on the Linux Host. The display's TCP RFB listener is disabled. All viewers use its native RFB endpoint through an owner-only Unix socket and the authenticated WebUI bridge. TigerVNC's native VncAuth distinguishes view-only access from control access; view-only authentication permits display updates and rejects keyboard, pointer, clipboard and resize operations. It does not provision a virtual machine, container or full desktop environment. Chromium exposes its normal tabs, address bar, menus and settings; its window can be closed normally.

## Ownership and Lifetime

Harness owns tools, instructions, observation and compact Run-local references. Harness UI owns browser enablement, Chromium, its profile and graphical session, remote display, input authority and cleanup. No third-party MCP server or MCP Apps sandbox is required for this built-in pixel viewer.

## Host Preparation

Browser support is optional. The Browser drawer queries Host preparation before offering Enable or Start. The authenticated preparation query requires the same computer-sharing, root Thread and Full Control authority as browser operations and rechecks authority after inspection. It reports the Host platform and Linux distribution, desktop support, compatible browser discovery, installed requirements, installation availability and manual installation steps. Inspection creates no browser binding, browser process, graphical session or package installation. It may briefly initialize the installed Playwright driver to discover its browser executable.

Install browser support explicitly starts a background installation using the inspected, server-owned plan. The request accepts no command or package input. Automatic system installation requires an apt-based Linux Host and an already privileged server account; it never invokes sudo or prompts for credentials. Without the required privileges or package manager, the drawer explains the limitation and retains manual guidance. Missing Python automation uses an available uv or pip in the current application environment. Existing compatible browsers omit the browser download. Known unsupported Linux baselines, including Ubuntu before 22.04 and Debian before 12, report unsupported and offer no installation action; distribution vendor maintenance alone does not imply browser runtime compatibility.

The App owns one process-local installation task shared across its Threads. Concurrent install requests return the existing task; they never start competing package operations. Installation has idle, installing, succeeded and failed states, a current step, bounded output of at most 16384 characters, and an explicit failure cause. Authority is checked at admission and between steps. The drawer polls while installing, shows progress and failures, and rechecks preparation after completion. Success requires a fresh readiness check. Installation creates no browser binding and never silently starts a browser or Agent Run. Enable and Start remain explicit operations. A failed installation is retryable from a fresh missing-component plan.

Viewer closure and Thread switching leave installation running. Server shutdown cancels the task and terminates its subprocess group. Each installation step has a twenty-minute bound. Interrupting package installation does not roll back already installed components; package-manager repair can be required. Installation status and output are transient, while installed packages follow Host/container lifetime. A replacement container needs the dependencies installed again or included in its image. No container engine, elevated helper or separate installation daemon is required.

Linux readiness requires Playwright, a compatible browser, TigerVNC with its password tool, Openbox, xrandr and xauth. An installed Playwright Chromium is preferred; otherwise an existing Chrome, Chromium or Edge executable is reused with a dedicated profile. Missing Python automation and desktop tools remain independent requirements. Guidance targets the running Harness UI Python environment and the Host package manager. Check again performs a fresh inspection after manual installation. Readiness describes detected components, not a successful browser launch; missing shared libraries or incompatible browser versions can still produce explicit startup failures. Enable and launch enforce preparation on the server, independently of WebUI state.

macOS and Windows have separate compatible-browser discovery paths. Their result distinguishes installed browsers from unsupported remote desktop operation, never claims readiness and does not offer Linux installation commands. Adding desktop support for another platform requires its own runtime and preparation implementation.

## Browser Bindings

Each enabled root Thread has one process-local browser binding. Enablement creates no operating-system process. Explicit Start or the first admitted navigation starts the dedicated graphical session and headed browser. A Run captures its browser binding at admission; later enablement cannot add browser tools to that Run. Every operation rechecks current root and Full Control authority. Retired bindings cannot address replacements.

Run completion, Thread switching and viewer closure keep the browser alive. Explicit Stop and WebUI shutdown close the created browser, display and VNC resources. Stop leaves the drawer in the stopped state with a Start browser action; it does not require enabling again. Dedicated profiles live under `browsers/<thread_id>` in the selected configuration's data root and remain after Stop or shutdown. They never import a personal profile. Separate live browser processes cannot share a profile. Restart restores neither live memory nor input authority and never replays uncertain actions. Enablement and live bindings are process-local. There are at most four enabled or running browsers and eight connected viewers per browser. Stopped browsers release runtime capacity.

Closing a tab preserves remaining tabs and invalidates references to the closed page. Closing the last page, exiting Chromium, a page crash, or termination of a required display, window-manager or VNC process has the same stopped state and Start browser action as explicit Stop. Abnormal exits additionally report the cause. Detection does not depend on an open viewer or state polling. The Host immediately revokes access and wakes waiting tools with a retired-binding failure, then cleans up the runtime after its in-flight operation settles. Explicit Start waits for cleanup and creates a new binding with the retained profile. Old Agent navigation never starts a stopped binding automatically. Startup failures remain explicit and retryable through Start browser.

Reset browser closes the current runtime and immediately starts a replacement with the same profile. Its initial browser window is visible within the virtual desktop, recovering misplaced or minimized windows. Reset is distinct from viewer reconnection, which preserves the running browser. Starting a replacement after Stop, exit or Reset begins read-only and requires a fresh Agent observation. Old Run bindings, viewer tickets and human input authority cannot address the replacement. Profile retention does not guarantee recovery of unsaved page contents or unflushed data after a crash.

## Viewing and Human Control

The default viewer is read-only. The server connects it to a VNC endpoint that rejects input; frontend `viewOnly` is supplementary. Access uses authenticated HTTP admission and a bounded, short-lived, single-use viewer ticket. Tickets select a specific binding, access mode and control generation. Admission also returns an ephemeral native VNC credential for that access mode; only the current controller token can request the control credential. These credentials travel in authenticated HTTP responses and the VNC authentication exchange, never URLs, conversation history or persistent settings. Tickets contain no API key. Display and CDP listeners are never published as unauthenticated network endpoints.

Browser preparation, installation and desktop access require instance-owner authority. Scoped guest sharing does not expose these endpoints or grant desktop viewing or input control, including for a guest with prompt permission. Prompt guests retain access to the Thread's existing Agent tools through conversation, under the separate scoped-sharing contract.

Take control first blocks new Agent operations, then settles the in-flight browser operation before granting human input. Observation, waiting and screenshots are also blocked during human control. A newly requested native browser tool waits outside the operation lane for handback, then returns a fresh-observation requirement without executing its original action. Stopping the browser wakes these waiters with a retired-binding failure. Only the controller's opaque input authority can acquire a writable connection; other devices remain read-only. Human input, including passwords, is not converted into tool arguments or saved as conversation content. Existing Agent history is not retroactively erased.

Human-control transitions revoke outstanding tickets and close established VNC connections. Native VNC credentials rotate atomically with the control generation, so prior credentials cannot authenticate through a newly admitted connection. The Host's native password file lives in the owner-only runtime directory and is removed with the runtime. The VNC server releases the disconnected controller's pressed keys before Agent access resumes. Old element references are invalidated. An Agent must obtain a fresh observation before another browser mutation. Control transport loss revokes human input while preserving the Agent pause; an explicit handback is required. Closing a viewer never silently resumes Agent collection. An authenticated user can hand back a browser whose controlling device has disconnected. Permission changes reauthenticate the VNC connection against the same desktop; the viewer retains its last frame until the replacement connection paints. Retained frames remain transient in the mounted viewer and never grant input authority.

The viewer does not execute or reconstruct website DOM. Browser chrome, frames, Canvas and browser-level dialogs are rendered in the real graphical session. Plain-text clipboard synchronization is automatic for the current controller while its browser desktop has focus in a visible, focused WebUI document. It transfers Unicode text of at most 65536 characters through noVNC's native clipboard API and TigerVNC's extended clipboard protocol on the admitted controller connection. No separate clipboard HTTP endpoint or selection-owner subprocess is used. Clipboard contents never appear in URLs, persistent stores or model messages. Local OS clipboard polling stops outside that focus scope; handback, disconnect and viewer disposal stop synchronization and discard permission-delayed reads. A browser clipboard write already issued before handback can still finish because the browser Clipboard API has no cancellation primitive. Clipboard access requires a secure browser context and browser permission; denial is reported without repeated background permission requests. Paste shortcuts update the Host clipboard before forwarding paste, and macOS Command modifiers map to Linux Ctrl before noVNC handles other keys. Mapped modifiers are released when the desktop loses focus, the document is hidden, or the connection is disposed. Automatic client/Host file transfer is not provided; browser file dialogs address Host files. Clipboard image, rich-text and file transfer are not supported. Clipboard synchronization does not grant Agent clipboard tools.

## Page Viewport Sizes

The Browser drawer offers predefined CSS viewport sizes: Desktop (1280 × 800), Laptop (1366 × 768), Desktop HD (1920 × 1080), Tablet (768 × 1024), Tablet landscape (1024 × 768), Phone (390 × 844), and Phone landscape (844 × 390). These resize the actual page viewport and reflow responsive content. They do not emulate a mobile user agent, device pixel ratio, touch hardware or operating system. Full browser chrome remains available; Chromium's minimum window width and toolbar height can make the remote desktop larger than the page viewport.

Changing size requires current Full Control authority and the controlling viewer's opaque input token, including while another device is viewing the same browser. It settles the operation lane, invalidates existing element references and requires a fresh Agent observation after handback. Existing pages and new tabs use the selected viewport. The virtual desktop fits the browser windows rather than cropping their pixels, and established VNC connections receive framebuffer size changes without acquiring new input authority. Resizing does not reload pages, restart Chromium, change the binding or discard in-memory login state. Partial failure ends the runtime with an explicit error instead of leaving input mapped to uncertain geometry.

The selected size is shared by all viewers of that browser. Stop/Start and Reset retain it within the WebUI process; server restart returns to the default Desktop preset. The profile's saved settings remain distinct from this process-local choice.

## Failures and Invariants

- Display preparation is optional. Ordinary Files, Shell and chat do not import Playwright or start a display. Installed use requires no separately installed Node.js.
- Missing Linux dependencies and unsupported platforms produce an explicit preparation error; there is no DOM/screenshot viewer fallback.
- Current authority is checked during established desktop connections as well as admission. Stop and control changes actively revoke sockets even if they are idle.
- Disconnection never implies an action was rolled back. Reconnection obtains fresh access and never resends input automatically.
- A stopped or replaced browser rejects queued operations through its retired binding. Profile persistence is distinct from live-session recovery.
- Browser operations and human-control transitions do not retain database sessions or transactions across external I/O or waits.
