# Host Browser and Remote Desktop

## Design Position

Harness UI optionally owns one globally shared headed Chromium browser and persistent profile on its Linux Host, shown through VNC in the WebUI Browser drawer. The Agent operates that same browser through the native [Browser Use Capability](../a13n-harness/23-browser-use.md). Users on different devices can view the same Host browser. Human input bypasses the model and tool history.

This facility requires WebUI computer sharing, explicit enablement in an idle root Full Control conversation, and separately prepared browser/display dependencies. It uses Host networking and filesystem access, outside Agent Environment isolation. CLI, child and Memory Threads do not receive the browser. Service, client extensions, macOS and Windows are outside this milestone.

The remote desktop consists of Chromium and a dedicated graphical session on the Linux Host. Supported server adapters are TigerVNC Xvnc, x11vnc with Xvfb, and WayVNC with headless Sway. TCP RFB listeners are disabled. All viewers use owner-only Unix sockets through the authenticated WebUI bridge. TigerVNC and x11vnc use native VncAuth passwords to distinguish view-only access from control access. WayVNC uses separate control and native input-disabled servers attached to the same private compositor; admission chooses the endpoint, and exposes no native password. View-only connections cannot inject keyboard, pointer, clipboard or desktop-resize operations. It does not provision a virtual machine, container or full desktop environment. Chromium exposes its normal tabs, address bar, menus and settings; its window can be closed normally.

## Ownership and Lifetime

Harness owns tools, instructions, observation and compact Run-local references. Harness UI owns browser enablement, Chromium, its profile and graphical session, remote display, input authority and cleanup. No third-party MCP server or MCP Apps sandbox is required for this built-in pixel viewer.

## Host Preparation

Browser support is optional. The Browser drawer inspects the prepared Host before offering Enable or Start. Inspection requires the same computer-sharing, root Thread and Full Control authority as browser operations and rechecks authority afterwards. It reports the platform, discovered executable paths, missing components and manual installation guidance. Bounded help/version probes create no browser window or graphical session. Discovery can briefly initialize an installed Playwright driver to locate an already downloaded Chromium. It never installs Python packages, invokes a package manager or downloads browsers. There is no installation API or background installation task.

The global root `browser` configuration binds `executable` and `vnc_executable` to absolute Host paths. Omitted or null paths leave the component unconfigured and prevent Enable or Start. Scanning only provides candidates; the user selects and saves both executable bindings. An invalid saved path is reported and never silently replaced. The settings editor exposes these fields under General, alongside `profile_root`, an optional absolute directory for the shared profile. Opening the Host browser settings section automatically invokes the owner-only `POST /api/browser/scan` to enumerate compatible installed browser and VNC executables, deduplicated by resolved path. Other collapsed settings do not trigger discovery; the Scan button also allows a manual refresh or retry. Both selectors remain disabled until a successful scan. Their final Other option reveals an absolute-path input; saved paths absent from the results remain visible as Other. Scanning never rewrites configuration. Reopening the section or returning to its settings refreshes the candidates; window focus and network reconnection alone do not trigger discovery. Runtime preparation still validates the selected paths independently. They are captured when the App starts; saving requires a Harness UI restart. Changing profile storage does not move, merge or delete existing data. The [configuration contract](01-configuration-and-resource-catalog.md) owns source validation and publication.

Browser scanning lists installed Chrome, Chromium and Edge executables, as well as an already downloaded Playwright Chromium. It never selects one for runtime startup. A bounded version probe checks that the executable identifies a supported Chromium browser. Linux VNC scanning recognizes `Xtigervnc`, `Xvnc`, `x11vnc` and `wayvnc`, and verifies the private transport and authority options required by their respective adapters. x11vnc requires an installed Xvfb executable; WayVNC requires Sway and Unix-socket and input-disable support. WayVNC versions without a desktop-resize disable option are accepted only on the older releases through version 0.7, which has no client desktop resizing. Unknown newer variants fail preparation rather than allowing viewers to mutate desktop geometry. Sway runs headless with software rendering, without Xwayland or the user's compositor configuration; Harness UI must run as a non-root user for this adapter. Detected display helpers are resolved to executable paths during preparation. An arbitrary VNC program or an existing remote-desktop URL is not a substitute for these capabilities. Harness UI launches its own graphical session using the resolved executable paths; it does not attach to or stop an existing user desktop.

Linux readiness requires the configured browser, compatible VNC server, its display component, and Python automation dependency. X11 display cookies and native VNC password files are generated inside Harness UI, atomically published with owner-only file permissions. TigerVNC uses its two-record password format; x11vnc uses its reloadable control/view-only password file. Rapid credential rotations publish strictly increasing integer modification times so x11vnc cannot retain an earlier generation. X11 displays have an authentication cookie before their server starts; unauthenticated local X11 clients are rejected. The Wayland adapter uses a private owner-only runtime directory and two Unix VNC endpoints without native VNC authentication; the authenticated bridge and endpoint selection own access, and the read-only server disables native input and clipboard access. Neither `xauth` nor a `vncpasswd` executable is required.

Window management and desktop resizing are optional capabilities and do not block Enable or Start. Discovery can reuse Openbox, Fluxbox, IceWM or twm, without requiring Openbox specifically; absence launches the browser without a separate window manager. For TigerVNC, an available `xrandr` utility enables dynamic desktop sizing after a successful display probe. The x11vnc and WayVNC adapters currently use the fixed desktop and report resizing as unavailable. If absent or its initial probe fails, the browser uses a fixed 1366 × 1024 display with the default 1280 × 800 page viewport, resetting any retained unsupported viewport choice to Desktop. The state reports `resize_available=false`, the viewer disables size selection with an explanation, and viewport-change requests fail before mutating the page. Optional capabilities are reported separately from missing required components. A started window manager remains a monitored runtime resource; an unexpected exit still requires explicit restart.

Users prepare missing required dependencies using the WebUI instructions and choose Check again. Detection establishes component availability, not guaranteed startup: missing shared libraries, incompatible browser versions or display permissions can still produce explicit launch errors. Linux distribution age alone does not override a detected compatible runtime. Enable and Start enforce preparation independently of WebUI state.

macOS and Windows have separate browser discovery paths. Their result distinguishes installed browsers from unsupported remote-desktop startup, never claims readiness and does not offer Linux installation commands. Adding another platform requires its own preparation and runtime implementation.

## Browser Bindings

Each enabled root Thread owns an independent window binding in the App-owned Chromium instance. All windows share its graphical session and persistent profile. Enablement creates no operating-system process. Explicit Start or the first admitted navigation starts the runtime if needed and creates a separate native browser window for that Thread. Each binding has its own generation, active Agent page, observation revisions and element references. Tabs created in an owned window inherit that window's Thread; popups inherit their opener's Thread, including when another Thread is active. Manually opened additional windows belong to the Thread holding human control. A backend never adopts another Thread's page merely because it is foreground. Tools from concurrent Runs use their own windows through a shared operation lane; desktop sizing and human input authority remain global. Window ownership prevents accidental tool redirection and does not isolate website storage or restrict the instance owner's desktop access.

A Run captures its Thread's window binding at admission; later enablement cannot add browser tools to that Run. Every operation rechecks current root and Full Control authority. Stopped and replaced bindings cannot address a reopened window. Starting another Thread opens another window in the existing Chromium instance; it does not copy the profile or start a second browser instance. Cookies, local storage, saved browser passwords, extensions and browser preferences are shared across Threads and Projects through that one persistent context.

Run completion, Thread switching and viewer closure keep conversation windows alive. Stop closes only the requesting Thread's windows, tabs and popups, revokes that binding's tickets and established viewer connections, and retires its queued Agent work. Other Thread bindings, pages, observations and viewer connections remain valid. If the stopped Thread holds human control, the Host first revokes that global input authority and safely hands back to Agent control; other Threads' VNC connections then reconnect under the normal global control-generation rules. Stopping another Thread's window does not release or transfer the current controller's authority. Reset closes only the requesting Thread's owned pages and immediately creates a replacement window at a visible position, retaining the shared profile and runtime. Reset cannot interrupt another Thread's active human controller; explicit handback is required first. Stop and Reset revoke the target binding before waiting for an in-flight operation to settle. Neither operation closes the shared Chromium instance, display or VNC service, even when it is the last conversation window.

The Host retains an internal browser window, minimized or hidden by its compositor, to keep Chromium alive when no conversation window remains. Agent tools never adopt it, and viewport changes do not resize or restore it. Harness UI shutdown closes this internal window, Chromium and all graphical-session resources. The profile lives directly at `profile_root`, defaulting to `<data_root>/browsers/profile`, and remains after window Stop or shutdown. It never imports a personal browser profile. Chromium's profile lock prevents a second process from opening the same directory; Harness UI does not remove that lock or fall back to another profile. Restart restores neither live Thread/window ownership nor input authority and never replays uncertain actions. Enablement and live bindings are process-local. The shared desktop admits at most eight connected viewers. Old per-Thread profile directories are retained without automatic migration or merging; an existing profile can be reused by explicitly selecting its directory while its previous browser is stopped.

Closing a tab preserves remaining pages owned by that Thread and invalidates its references. Closing the Thread's last owned page has the same local stopped state and Start browser action as Stop. The user must explicitly reopen that window; an old Run cannot navigate it back into existence. A page crash retires the affected page and its Thread's binding if it has no remaining page; it does not close other Threads' windows. Exiting the entire Chromium instance, closing the internal runtime window, or termination of a required display, window-manager or VNC process stops the shared runtime and revokes every Thread binding. Abnormal runtime exits report the cause. Detection does not depend on an open viewer or state polling. The Host immediately revokes access and wakes waiting tools before cleanup waits for the in-flight operation. After a shared runtime failure, explicit Start prepares a new shared runtime and opens the requesting Thread's window; other stopped Threads require their own explicit Start.

Reopening after Stop, manual window closure or Reset creates a new binding and requires a fresh Agent observation. Only the affected Thread's old Run bindings and viewer tickets are retired; other Thread bindings remain valid. Reset is distinct from viewer reconnection, which preserves windows. The VNC viewer still shows one shared desktop, so other windows can be visible and the human controller can operate them. Admitting a viewer or taking control focuses the requesting Thread's window when doing so cannot interrupt another human controller. The WayVNC adapter uses the private Sway control socket to focus a native window by its compositor identity because CDP tab activation alone does not reliably raise Wayland windows. No separate swaymsg executable is required. This is window lifecycle ownership, not window-level pixel or input isolation. Profile retention does not guarantee recovery of unsaved page contents or unflushed data after a crash.

## Viewing and Human Control

The default viewer is read-only. The server connects it to a VNC endpoint that rejects input; frontend `viewOnly` is supplementary. Access uses authenticated HTTP admission and a bounded, short-lived, single-use viewer ticket. Tickets select a specific binding, access mode and control generation. For password-authenticated adapters, admission also returns an ephemeral native VNC credential for that access mode; only the current controller token can request the control credential. These credentials travel in authenticated HTTP responses and the VNC authentication exchange, never URLs, conversation history or persistent settings. Tickets contain no API key. Display and CDP listeners are never published as unauthenticated network endpoints.

Browser preparation and desktop access require instance-owner authority. Scoped guest sharing does not expose these endpoints or grant desktop viewing or input control, including for a guest with prompt permission. Prompt guests retain access to the Thread's existing Agent tools through conversation, under the separate scoped-sharing contract.

Take control in any Thread first blocks new Agent operations across all Threads, then settles the in-flight browser operation before granting human input. Observation, waiting and screenshots are also blocked during human control. A newly requested native browser tool waits outside the operation lane for handback, then returns a fresh-observation requirement without executing its original action. Stopping a Thread window wakes that Thread's waiters with a retired-binding failure, even while another Thread remains under human control. Shared runtime failure wakes all waiters. Only the controller's opaque input authority can acquire a writable connection; other devices remain read-only. Human input, including passwords, is not converted into tool arguments or saved as conversation content. Existing Agent history is not retroactively erased.

Human-control transitions revoke outstanding tickets and close established VNC connections. Where native passwords are used, credentials rotate atomically with the control generation, so prior credentials cannot authenticate through a newly admitted connection. The WayVNC adapter instead selects separate private sockets after the same ticket and control-generation checks. The Host's native password file lives in the owner-only runtime directory and is removed with the runtime. Before Agent access resumes, native VNC client cleanup releases held keys; the x11vnc adapter additionally uses its synchronous native key-reset command because that server retains global X11 key state on disconnect. WayVNC transitions wait for native client cleanup through its private control socket before admitting another controller, avoiding overlapping virtual-keyboard lifetimes. Old element references in every Thread are invalidated. An Agent must obtain a fresh observation before another browser mutation. Control transport loss revokes human input while preserving the Agent pause; an explicit handback is required. Closing a viewer never silently resumes Agent collection. An authenticated user can hand back a browser whose controlling device has disconnected. Permission changes reauthenticate the VNC connection against the same desktop; the viewer retains its last frame until the replacement connection paints. Retained frames remain transient in the mounted viewer and never grant input authority.

The viewer does not execute or reconstruct website DOM. Browser chrome, frames, Canvas and browser-level dialogs are rendered in the real graphical session. Plain-text clipboard synchronization is automatic for the current controller while its browser desktop has focus in a visible, focused WebUI document. It transfers Unicode text of at most 65536 characters through noVNC's native clipboard API on the admitted controller connection. Unicode interoperability depends on the server's clipboard extensions; older servers can be limited to Latin-1. No separate clipboard HTTP endpoint or selection-owner subprocess is used. Clipboard contents never appear in URLs, persistent stores or model messages. Local OS clipboard polling stops outside that focus scope; handback, disconnect and viewer disposal stop synchronization and discard permission-delayed reads. A browser clipboard write already issued before handback can still finish because the browser Clipboard API has no cancellation primitive. Clipboard access requires a secure browser context and browser permission; denial is reported without repeated background permission requests. Paste shortcuts update the Host clipboard before forwarding paste, and macOS Command modifiers map to Linux Ctrl before noVNC handles other keys. Mapped modifiers are released when the desktop loses focus, the document is hidden, or the connection is disposed. Automatic client/Host file transfer is not provided; browser file dialogs address Host files. Clipboard image, rich-text and file transfer are not supported. Clipboard synchronization does not grant Agent clipboard tools.

## Page Viewport Sizes

The Browser drawer offers predefined CSS viewport sizes: Desktop (1280 × 800), Laptop (1366 × 768), Desktop HD (1920 × 1080), Tablet (768 × 1024), Tablet landscape (1024 × 768), Phone (390 × 844), and Phone landscape (844 × 390). These resize the actual page viewport and reflow responsive content. They do not emulate a mobile user agent, device pixel ratio, touch hardware or operating system. Full browser chrome remains available; Chromium's minimum window width and toolbar height can make the remote desktop larger than the page viewport.

Changing size requires available desktop resizing support, current Full Control authority and the controlling viewer's opaque input token, including while another device is viewing the same browser. It settles the operation lane, invalidates existing element references and requires a fresh Agent observation after handback. Existing pages and new tabs use the selected viewport. The virtual desktop fits the browser windows rather than cropping their pixels, and established VNC connections receive framebuffer size changes without acquiring new input authority. Resizing does not reload pages, restart Chromium, change the binding or discard in-memory login state. Partial failure ends the runtime with an explicit error instead of leaving input mapped to uncertain geometry.

The selected size is shared by all viewers of that browser. Stop/Start and Reset retain it within the WebUI process; server restart returns to the default Desktop preset. The profile's saved settings remain distinct from this process-local choice.

## Failures and Invariants

- Display preparation is optional. Ordinary Files, Shell and chat do not import Playwright or start a display. Installed use requires no separately installed Node.js.
- Missing required Linux dependencies and unsupported platforms produce an explicit preparation error; there is no DOM/screenshot viewer fallback.
- Current authority is checked during established desktop connections as well as admission. Stop and control changes actively revoke sockets even if they are idle.
- Disconnection never implies an action was rolled back. Reconnection obtains fresh access and never resends input automatically.
- A stopped or replaced browser rejects queued operations through its retired binding. Profile persistence is distinct from live-session recovery.
- Browser operations and human-control transitions do not retain database sessions or transactions across external I/O or waits.
