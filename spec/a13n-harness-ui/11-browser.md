# Host Browser and Native Viewer

## Design Position

Harness UI owns one headed Chromium process and one persistent profile. Linux uses a private graphical session; macOS launches native windows in the logged-in user's graphical session. Each admitted root Thread owns its browser windows and tabs. The WebUI displays the private desktop through VNC/noVNC on Linux and an exact owned native window through ScreenCaptureKit on macOS. Both show Chromium's real address bar and browser chrome. Harness owns the [Browser Use Capability and cdp-use operation layer](../a13n-harness/23-browser-use.md); Harness UI owns startup, Thread ownership, human takeover, viewer admission and cleanup. No Playwright driver or additional Agent loop is used.

This optional Host facility requires WebUI computer sharing. Browser filesystem and network authority remain outside Agent Environment isolation. Native Host startup supports Linux and macOS. Windows supports browser discovery but not graphical startup. Scoped guest links expose neither preparation nor desktop APIs.

Model-facing Host browser tools require the Run's captured Full Control profile (`environment-native`). A Run-only Sandbox override omits those tools even when the Thread default remains Full Control and its browser binding stays enabled. Eligibility is captured at Run admission; subsequent default changes neither grant nor revoke Host browser access for that Run. A Run-only Full Control override can capture a ready binding on a Sandbox-default Thread. Owner viewer and lifecycle controls use instance authority rather than the next Run's Environment defaults. Thread availability, binding lifetime and human takeover remain dynamic checks.

## Host Preparation

Global `browser.mode` is `auto` by default or `disabled`. Auto prepares one shared runtime at WebUI startup when computer sharing is enabled; disabled starts no runtime and injects no browser tools. This startup policy and executable bindings require an App restart after saving. Browser preparation never gates ordinary Run admission. A starting, failed, disabled or unavailable runtime leaves ordinary Runs available without browser tools and with explicit model-visible availability context.

Global `browser.executable` and `browser.vnc_executable` settings optionally bind absolute executable paths. Omitted or null paths select automatic discovery of compatible installed programs during preparation and startup, without rewriting configuration. Discovery uses its stable browser order and, on Linux, prefers a complete VNC adapter (TigerVNC, then x11vnc with Xvfb, then WayVNC with Sway and a non-root account). If no adapter is complete, preparation retains the first compatible candidate's missing-component diagnostics. Users can override either path in Settings → Environments → Browser or return it to Automatic. Invalid explicit bindings never fall back to another program. The browser profile is stored at `<data_root>/browsers/profile`, shared across Threads and Projects, with no separate profile-location setting. Saving executable bindings requires restarting Harness UI. Personal profiles are never imported. The [configuration contract](01-configuration-and-resource-catalog.md) owns source validation and publication.

Settings → Environments → Browser owns Host runtime status, diagnostics, explicit retry and configuration. Owner-only `GET /api/browser` reads status (`disabled`, `starting`, `ready` or `failed`), effective App-start configuration, platform, sharing availability and error without preparation or Thread allocation. Owner-only `POST /api/browser/prepare` retries shared runtime preparation using that effective configuration, without allocating a Thread binding or page. Status remains readable with computer sharing off; preparation and component probes retain the sharing gate. Retry never applies saved configuration that requires an App restart. The page distinguishes effective configuration, saved changes awaiting restart and unsaved edits, using the existing root source draft and save path.

The settings panel checks the current browser/VNC selection, including unsaved custom paths, without publishing configuration or starting a graphical session. It lists each component's purpose, detected path or missing-component guidance, and required or optional status. The same preparation rules own settings previews and Thread startup. TigerVNC includes its X display and optionally uses xrandr for viewport changes and an X11 window manager for window controls. Selecting x11vnc requires detecting Xvfb and keeps X11 window management optional. Selecting WayVNC requires detecting Sway and a non-root Host account; fixed-size adapters do not request xrandr. The panel lists components users prepare on the Host. Bundled Harness/WebUI libraries and TigerVNC’s integrated display server do not appear as separate installation requirements. Discovery success does not certify shared libraries, display permissions or successful runtime startup.

On Linux, the managed Chromium process uses basic password storage so profile initialization does not depend on unlocking the Host's desktop keyring. Saved passwords and cookies have no OS-keyring protection at rest; access to the profile and its backups grants access to this data. Harness UI preserves the profile and leaves the system keyring unchanged. Existing keyring-encrypted data can require signing in again after switching storage. macOS retains Chromium's native credential-storage behavior.

Chromium's sandbox is enabled by default, including when the Host runs as root. The startup flag `webui --browser-no-sandbox` or `A13N_HARNESS_UI_BROWSER_NO_SANDBOX=1` explicitly disables it; `--browser-sandbox` overrides that environment setting. Preparation and startup reject a root Host account without that explicit opt-out and explain both remedies: run as non-root or explicitly disable the sandbox. Harness UI never disables the sandbox automatically after a startup failure.

cdp-use is a regular Harness dependency. Harness UI detects prepared components, provides manual installation guidance and rechecking, and launches the configured programs. It never executes installation commands or downloads browsers. Component inspection uses bounded executable version/help probes and does not create a graphical session. Linux distribution age alone does not override detected runtime capabilities; missing shared libraries or permissions can still fail startup.

Supported Linux display adapters are TigerVNC Xvnc, x11vnc with Xvfb, and WayVNC with a private headless Sway compositor. VNC uses owner-only Unix sockets, without public RFB listeners. X11 authentication cookies and native VNC credentials are generated inside Harness UI, without requiring xauth or vncpasswd executables. Window management is optional for X11. TigerVNC can resize with optional RandR utilities; x11vnc and WayVNC use a fixed desktop. Sway requires a non-root account. WayVNC variants must disable viewer-requested resizing or be recognized older versions without that facility. Arbitrary VNC URLs are not accepted.

On macOS, Chromium is the only required browser component. Optional read-only window preview requires macOS 14 or later and Screen Recording permission for the application running Harness UI. The owner can open Screen Recording settings; this action neither grants permission nor changes system settings. Missing permission, unavailable capture dependencies or preview failure do not block CDP startup and automation. The Host runs in the logged-in user's graphical session and keeps the physical display resolution unchanged. `browser.vnc_executable` is unused. Screen Sharing, VNC credentials, native remote input and native clipboard access are not part of the macOS browser facility.

## Browser and Thread Lifecycle

App startup prepares the shared Chromium process and profile without conversation pages. Run admission synchronously captures a process-local binding and empty scope only when the runtime is ready and the Thread binding is not retiring (never awaiting browser I/O; unavailable runtimes leave other capabilities running with the reason recorded). The first navigation or new-tab call creates the Thread's native window.

- **Isolation and tools:** Harness's `CdpBrowserBackend` owns per-Thread target scopes, selection locks, and per-page locks, forwarding all 11 Browser Use tools through Harness UI's auth and human-control boundary. Popups inherit their opener's Thread; targets created during takeover are admitted to the controlling Thread on handback.
- **Close, Stop, and Reset:** **Close conversation tabs** closes only the requesting Thread's targets, revokes its viewers, and releases human control while keeping its binding usable. **Stop** (archive/reset) retires the binding and closes all owned targets; **Reset** closes them and opens a fresh window/binding. Control-transport drops attempt bounded reconnection to the same browser (invalidating page refs without replaying uncertain ops).
- **Shutdown:** An internal hidden window keeps Chromium alive when no conversation window is open; WebUI shutdown settles viewers, requests normal Chromium exit, flushes the profile, and stops graphical resources.

## Viewing and Human Control

- **Human control lease:** Five-minute Host-owned monotonic lease starting on takeover/transfer (renewed by trusted Linux viewer input only; automatic handback on expiry even if the viewer disconnects). Handback revokes input, rotates Linux VNC credentials, invalidates page refs, synchronizes selected tabs, and releases the global automation pause (carrying the non-secret `control_episode` to fence stale requests).
- **Viewer transport and limits:** Read-only by default (instance-owner only; max 8 viewers; short-lived single-use ticket tied to Thread, generation, and input authority; API keys/socket paths never enter URLs). Linux uses `vnc` (noVNC + TigerVNC/x11vnc/WayVNC native read-only enforcement); macOS uses `jpeg` (isolated ScreenCaptureKit worker bound to exact PID + newly created window ID; rejects client input).
- **Automation pause:** Linux **Take control** and macOS **Pause automation** block all Agent browser page ops globally. Blocked tools return immediate non-error guidance and register the calling Thread for a handback notice (`browser_notify_on_handback` registers explicitly). On Linux, explicit **Take control** transfers control between viewers while keeping Agent automation paused.

### Availability Context and Handback Registration

Each ordinary root Run includes a short trusted `<browser-context>` block describing browser availability and the next useful action. An unbound Run states its captured unavailable reason and that browser tools are absent for this Run; it offers no handback registration tool and directs the Agent to continue independent work. With a captured eligible binding, each model request projects current availability. Projection checks current authority and binding without preparing a runtime, accessing pages or registering a recipient. An empty ready scope remains usable. Runtime failure, retired binding and lost authorization are unavailable states, not successful handback.

`browser_notify_on_handback` registers one reminder without a page operation or waiting. It remains callable during takeover and rechecks the current Run's binding and authority. Gate inspection and registration are synchronous after authorization, so handback cannot occur between them. If automation is already available, it returns `already_available`, directs fresh observation after handback and creates no future subscription or redundant asynchronous notice. Explicit requests and blocked calls coalesce under the same process-local lifecycle. The context is advisory; every page operation retains live admission because takeover can start after projection.

### Handback Notices

After native input is revoked, all ready scopes are synchronized and references invalidated, and the global gate is released, the Host delivers one coalesced notice to each registered Thread. Active execution receives native steering; an idle eligible Thread receives an ordinary normal-mode submission. Delivery never replays browser actions or restores a previous Goal policy or budget. The Agent observes afresh and continues only still-relevant work.

Normal Run completion preserves registration. Explicit Stop, archive, and context clearing suppress pending delivery; ordinary user input preserves a useful notice. Pending approval or another deferred decision postpones delivery until normal execution lifecycle events make the Thread eligible. Repeated calls and rapid takeovers coalesce, and admission rechecks notice validity after asynchronous capture. There is no timer-based polling, proactive broadcast, or dependency on Coordinator/worker relationships. Registration and delivery authority are process-local; shutdown or browser-runtime failure discards them, and restart does not replay notices.

## Viewer Controls

The empty drawer offers Open browser. Successful live native navigation or tab creation/selection in the foreground Thread reveals the drawer once per Thread on wide screens without moving keyboard focus. A collapsed supporting panel opens for this first reveal; visible resource views, full-width tab layouts and narrow screens receive a View browser prompt instead. The viewer remembers that it has handled this reveal in browser-local preferences, including when the Browser was already visible or the user satisfied the prompt through any Browser entry. Closing the viewer then suppresses automatic reveals across later Runs and returns to that Thread. Background Threads, retained history, refresh and replay do not reveal it. The compact viewer toolbar contains a labeled Take control / Hand back button on Linux or Pause automation / Resume automation on macOS, an icon button for Reset, and an options menu. It has no additional address bar because Chromium's native address bar is visible. Reset and Close conversation tabs affect only the current Thread's windows; labels and descriptions explain their scope. A Linux read-only click shows a temporary takeover hint; pointer movement alone does not show it. macOS explains local operation and remains read-only.

The viewer distinguishes waiting for current browser operations, connecting the transport, waiting for its first frame, watching and active human control. Retained pixels stay visibly pending during replacement. Input becomes available only after the current connection has authority and a painted frame; a successful takeover response does not itself mean the viewer is ready. State polling cannot delay successful command completion or overwrite it with an older in-flight result. Admission, handshake and initial-frame waiting share a bounded connection deadline. Failure keeps input disabled and exposes an explicit retry. Linux Reconnect control renews authority without handing back first. A viewer without local authority during human control offers Take control here and a separate Hand back action. Handback remains available while the controller connection is pending or failed and when the current Thread has no open pages.

The menu owns Close conversation tabs, local display zoom and viewport presets. Fit centers the desktop without viewer scrollbars; numeric 50–200 percent zoom allows scrolling oversized desktop pixels without changing input authority. noVNC owns Linux rendering and keyboard/pointer translation. Client Command shortcuts map to Linux Control shortcuts. Modifiers are released on focus loss, document hiding and viewer disposal. macOS offers local display zoom without keyboard, pointer or clipboard forwarding.

During Linux human control, local input methods compose in a client text entry target. Only committed text is pasted through the clipboard bridge; preedit keys remain local. This requires native Unicode clipboard support and an application that accepts paste. Committing does not write the client clipboard; the next successful focused clipboard sync restores its contents on the Host. Suitable Host fonts are needed to display committed characters. Handback and disconnection remove the text entry target.

The Linux plain-text clipboard bridge runs only for the focused controller in a visible, focused WebUI. It uses noVNC's native clipboard API, bounds transfers to 65536 characters, stops on handback/disconnection and reports permission failures without blocking the viewer. Linux Unicode interoperability depends on server clipboard extensions. Clipboard text remains outside model tools and conversation history. Rich clipboard and automatic file transfer are not provided; native file dialogs address Host files. Permission-delayed reads are discarded after revocation, while an already issued browser clipboard write cannot be cancelled.

Remote viewport changes require current human authority and desktop resizing support. Presets include desktop, laptop, tablet and phone orientations with fixed width and height. Presets request browser content dimensions, subject to native minimum window sizes; browser chrome remains visible. Desktop windows start maximized when an X11 window manager is available; fixed-size desktops place the browser at the origin and size it to fill the desktop. Other presets verify actual content dimensions after native window restoration, correct delayed decoration changes within a bounded wait, and report an error if the requested size cannot be reached. The shared desktop stays large enough for other owned windows. Unsupported adapters disable remote resizing while retaining local zoom. The preset belongs to the Thread binding and survives Stop/Reset within the WebUI process. It does not emulate mobile hardware or a mobile user agent.

## Local Screenshot Annotation

The viewer's capture action freezes the current rendered desktop or native-window preview in the client, including native browser chrome. It is available in read-only and controlling views after a frame arrives. Capture neither acquires human control nor pauses Agent operations; the captured frame stays fixed while the live browser continues. It uses no backend capture endpoint or CDP screenshot.

A local editor provides crop, arrows, rectangles, ellipses, freehand strokes, multiline text, mosaic and opaque redaction. Creating marks and crop regions requires a pointer. Marks can be selected, moved, resized and deleted. Undo/redo records completed edits, not pointer samples. Text uses native client input and composition. Icon controls have accessible names and tooltips; the annotation picker and keyboard commands support selection, nudging, deletion and history. Mosaic is a visual effect; sensitive content requires opaque redaction, which remains above source-sampling mosaic regions.

Document geometry and export dimensions use source pixels. Preview zoom and client device pixel ratio do not change PNG resolution. Export flattens the current crop and annotations without selection handles or other editor UI. Copy writes an `image/png` item to the client clipboard; Download provides a local PNG when image clipboard access is unavailable or rejected. Failed export or copy retains the editor and edits for retry. Closing asks for confirmation when text editing or undo/redo history exists, then discards local edits; editor state and captured pixels are not persisted by Harness UI.

Remote input and plain-text clipboard synchronization are suspended while this viewer edits. Queued transfers and permission-delayed reads are invalidated. Copy waits for every already-issued text clipboard write, including writes from replaced connections, so an older write cannot overwrite the PNG. Successful copy closes the editor and returns focus to chat without focusing the remote desktop. The user explicitly pastes into the existing composer attachment flow or another application; capture and copy do not upload, attach or send content automatically. Existing attachment limits and upload errors remain owned by the composer.

## Presentation and Limits

Both viewer transports display native pixels rather than reconstructing DOM or streaming CDP screenshots. Chromium starts muted; the viewer does not transport audio.

The profile retains cookies, saved passwords and configuration subject to Chromium and its platform password store. Native takeover can operate browser-level UI, but third-party password managers, extensions, OS dialogs, file transfer and IME require their own end-to-end validation. Clipboard support does not imply file transport. Agent tools cover owned same-process and out-of-process frames, JavaScript dialogs, Host-path upload and observed downloads as defined by [Browser Use](../a13n-harness/23-browser-use.md). Native OS dialogs and extension management remain human browser workflows; direct file operations do not imply a client file-transfer bridge. Installed use requires no separately installed Node.js, and ordinary Files, Shell and chat do not allocate conversation browser pages.
