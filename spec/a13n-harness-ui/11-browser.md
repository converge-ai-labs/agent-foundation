# Host Browser and VNC Viewer

## Design Position

Harness UI owns one headed Chromium process and one persistent profile. Linux uses a private graphical session; macOS uses the logged-in user's existing Screen Sharing desktop. Each enabled root Thread owns its browser windows and tabs. The WebUI displays the complete desktop through VNC/noVNC, including Chromium's native address bar and browser chrome. Harness owns the [Browser Use Capability and cdp-use operation layer](../a13n-harness/23-browser-use.md); Harness UI owns startup, Thread ownership, human takeover, viewer admission and cleanup. No Playwright driver or additional Agent loop is used.

This optional Host facility requires WebUI computer sharing. Browser filesystem and network authority remain outside Agent Environment isolation. Native Host startup supports Linux and macOS. Windows supports browser discovery but not graphical startup. Scoped guest links expose neither preparation nor desktop APIs.

Model-facing Host browser tools require the Run's captured Full Control profile (`environment-native`). A Run-only Sandbox override omits those tools even when the Thread default remains Full Control and its browser binding stays enabled. Eligibility is captured at Run admission; subsequent default changes neither grant nor revoke Host browser access for that Run. A Run-only Full Control override can use an enabled binding on a Sandbox-default Thread. Owner viewer and lifecycle controls use instance authority rather than the next Run's Environment defaults. Thread availability, binding lifetime and human takeover remain dynamic checks.

## Host Preparation

Global `browser.executable` and `browser.vnc_executable` settings optionally bind absolute executable paths. Omitted or null paths select automatic discovery of compatible installed programs during preparation and startup, without rewriting configuration. Discovery uses its stable browser order and, on Linux, prefers a complete VNC adapter (TigerVNC, then x11vnc with Xvfb, then WayVNC with Sway and a non-root account). If no adapter is complete, preparation retains the first compatible candidate's missing-component diagnostics. Users can override either path in advanced browser settings or return it to Automatic. Invalid explicit bindings never fall back to another program. The browser profile is stored at `<data_root>/browsers/profile`, shared across Threads and Projects, with no separate profile-location setting. Saving executable bindings requires restarting Harness UI. Personal profiles are never imported. The [configuration contract](01-configuration-and-resource-catalog.md) owns source validation and publication.

The settings panel checks the current browser/VNC selection, including unsaved custom paths, without publishing configuration or starting a graphical session. It lists each component's purpose, detected path or missing-component guidance, and required or optional status. The same preparation rules own settings previews and Thread startup. TigerVNC includes its X display and optionally uses xrandr for viewport changes and an X11 window manager for window controls. Selecting x11vnc requires detecting Xvfb and keeps X11 window management optional. Selecting WayVNC requires detecting Sway and a non-root Host account; fixed-size adapters do not request xrandr. The panel lists components users prepare on the Host. Bundled Harness/WebUI libraries and TigerVNC’s integrated display server do not appear as separate installation requirements. Discovery success does not certify shared libraries, display permissions or successful runtime startup.

Chromium's sandbox is enabled by default, including when the Host runs as root. The startup flag `webui --browser-no-sandbox` or `A13N_HARNESS_UI_BROWSER_NO_SANDBOX=1` explicitly disables it; `--browser-sandbox` overrides that environment setting. Preparation and startup reject a root Host account without that explicit opt-out and explain both remedies: run as non-root or explicitly disable the sandbox. Harness UI never disables the sandbox automatically after a startup failure.

cdp-use is a regular Harness dependency. Harness UI detects prepared components, provides manual installation guidance and rechecking, and launches the configured programs. It never executes installation commands or downloads browsers. Preparation uses bounded executable version/help probes and does not create a graphical session. Linux distribution age alone does not override detected runtime capabilities; missing shared libraries or permissions can still fail startup.

Supported Linux display adapters are TigerVNC Xvnc, x11vnc with Xvfb, and WayVNC with a private headless Sway compositor. VNC uses owner-only Unix sockets, without public RFB listeners. X11 authentication cookies and native VNC credentials are generated inside Harness UI, without requiring xauth or vncpasswd executables. Window management is optional for X11. TigerVNC can resize with optional RandR utilities; x11vnc and WayVNC use a fixed desktop. Sway requires a non-root account. WayVNC variants must disable viewer-requested resizing or be recognized older versions without that facility. Arbitrary VNC URLs are not accepted.

On macOS, the Host attaches only to built-in Screen Sharing at `127.0.0.1:5900` using classic VNC password authentication. The user enables Screen Sharing and its VNC-password option manually. `A13N_HARNESS_UI_MACOS_VNC_PASSWORD` supplies the 1–8 character Latin-1, non-NUL password to the Host; it is excluded from Chromium's environment and never returned in viewer admission. `browser.vnc_executable` is unused on macOS. Preparation checks the RFB banner and password presence; startup authenticates. The Host neither starts nor stops the system sharing service. macOS exposes the entire logged-in desktop, including unrelated applications, and keeps the physical resolution unchanged. It requires the Host to run in that user's graphical session.

## Browser and Thread Lifecycle

Enable creates a process-local binding without launching programs. Explicit Start or an admitted first navigation starts the shared runtime and opens the Thread's independent native window. Before a Thread exists, the drawer asks the user to start a conversation. An existing eligible Thread exposes one Enable browser switch: turning it on enables the binding when needed and starts its window; turning it off performs Stop for that Thread. Opening the drawer alone does not run preparation probes or start programs. Required-component diagnostics and retry appear only after a failed attempt or runtime failure. Unsupported Hosts show the platform limitation without dependency-installation steps. Advanced settings retain manual executable overrides. Automatic selection does not replace a running shared browser or change other Threads' bindings. Harness's `CdpBrowserBackend` owns each Thread's exact target scope, selection, operation draining and document-bound references. Harness UI forwards the nine Browser Use tools through its authorization and human-control boundary. Browser tools use explicit page targets, a Thread selection lock and per-page locks without a browser-wide Agent task queue. The Thread lock prevents a tab switch racing its own in-flight action; independent Threads retain concurrent operation. Ordinary operations address their assigned page targets without explicitly activating a window. Chromium may still change native focus when dispatching input; windows do not isolate native focus, browser dialogs or shared profile state. Popups inherit their opener's Thread. During takeover the Host records newly created target IDs; handback admits those exact live targets to the controlling Thread unless already owned. Existing unowned targets are never claimed by matching their URL, title or native window. Tab selection is logical and does not activate the native tab. Tab listing, new/selection/close operations are restricted to the calling Thread. On handback, the Host synchronizes selection to an owned focused page or visible native tab before requiring fresh Agent observation. Viewer admission and takeover explicitly select the requesting Thread's window when doing so cannot interrupt another human controller.

Stop retires only the requesting Thread's binding, settles its in-flight tab mutations and closes the complete owned-target set. A tab returned by creation after retirement is cleaned up without subsequent tool navigation. Reset closes those targets and opens a fresh window with a new binding at a visible position. Other Threads and the shared process/profile remain alive. Closing the active tab selects another owned tab when one remains; closing the last owned tab leaves an empty, usable scope with the same binding, regardless of whether an Agent or human closed it. Tab listing returns an empty result, page operations request a new tab, and `browser_tabs` can create one in a new native window. Start is idempotent for this ready binding; Reset remains the owner UI action for creating a replacement window. Closing tabs never releases human control. Browser/display failure retires affected bindings and requires explicit Start. Old Runs cannot reopen a stopped binding or dispatch queued actions after retirement. Stop wakes that Thread's handback waiters even while another Thread remains under human control.

Run completion, Thread switching and viewer closure do not close the browser. An internal minimized/hidden window keeps Chromium alive when no conversation window remains. WebUI shutdown closes and settles viewer connections before requesting normal Chromium exit and waits for profile flushing before disconnecting and stopping graphical resources; termination is a bounded fallback. Persistent profile data is distinct from live page ownership and memory. Host restart restores neither live bindings nor input authority, and uncertain actions are never replayed. Profile locks are never removed or bypassed.

## Viewing and Human Control

Viewing is read-only by default and requires instance-owner authority. HTTP admission issues a bounded, short-lived single-use ticket tied to the Thread, binding generation and native input authority. API keys and private VNC socket paths do not enter viewer URLs. The authenticated WebSocket relays native RFB. noVNC serves both watching and controlling; the Host's desktop connection enforces read-only input independently of the client flag, through native VNC permissions on Linux and message filtering on macOS. At most eight viewers connect to the shared desktop.

TigerVNC/x11vnc use separate control and view-only native passwords, delivered only through authenticated admission and VNC authentication. WayVNC exposes separate private endpoints with input disabled on its read-only server. Takeover, handback and controller loss revoke established native connections and pending tickets. Linux native credentials rotate; retained key state is released before Agent operations resume. WayVNC waits for client destruction through its private control socket; x11vnc additionally clears held input through its synchronous native command. A replacement connection requests fresh admission. The viewer retains the previous picture until the new connection paints; retained pictures grant no input authority.

The macOS bridge terminates authentication before admitting noVNC and forwards native framebuffer data. Read-only connections discard keyboard, pointer and clipboard writes. It negotiates supported rendering capabilities without physical resize, power-control or alternate input extensions. Revocation disables forwarding, queues releases for held keys and pointer buttons, and waits for transport closure before Agent access resumes. This completes transport delivery, not an acknowledgement from the native input system. The system VNC password stays unchanged; only Host-issued viewer authority is renewed.

Take control blocks new Agent browser operations globally and settles existing operations. Failed or cancelled takeover settles all outstanding pauses and revokes native input before restoring Agent access. A broken browser or display retires bindings and requires explicit Start instead of leaving a global pause stranded. During human control all model-facing browser tools, including observations and screenshots, are unavailable. Human input bypasses model arguments and conversation history. Handback revokes native input, invalidates all references and requires fresh observation. Waiting tools return without replaying their pending action. Losing a controller revokes input but leaves the Agent pause until explicit handback; viewer closure never silently resumes page collection.

The viewer displays one shared desktop, so human users can see and operate other windows. Thread ownership scopes Agent tool routing and lifecycle, not desktop pixels, human desktop input or website storage. Shared login state is intentional.

## Viewer Controls

The drawer's activation row contains the Thread-scoped Enable browser switch. The compact viewer toolbar contains a labeled Take control / Hand back button, an icon button for Reset, and an options menu. It has no additional address bar because Chromium's native address bar is visible. Reset and disabling the browser affect the current Thread's windows; labels and descriptions explain their scope. A read-only click shows a temporary takeover hint; pointer movement alone does not show it.

The menu owns local display zoom and viewport presets. Fit centers the desktop without viewer scrollbars; numeric 50–200 percent zoom allows scrolling oversized desktop pixels without changing input authority. noVNC owns rendering and keyboard/pointer translation. Client Command shortcuts map to Linux Control shortcuts or macOS Command shortcuts according to the Host platform. macOS Option remains Option. Modifiers are released on focus loss, document hiding and viewer disposal.

During human control, local input methods compose in a client text entry target. Only committed text is pasted through the clipboard bridge; preedit keys remain local. This requires native Unicode clipboard support and an application that accepts paste. Committing does not write the client clipboard; the next successful focused clipboard sync restores its contents on the Host. Suitable Host fonts are needed to display committed characters. Handback and disconnection remove the text entry target.

The plain-text clipboard bridge runs only for the focused controller in a visible, focused WebUI. It uses noVNC's native clipboard API, bounds transfers to 65536 characters, stops on handback/disconnection and reports permission failures without blocking the viewer. Linux Unicode interoperability depends on server clipboard extensions. macOS uses an owner-only clipboard endpoint with the current binding and control token and requires a connected controller. Native UTF-8 pasteboard reads and writes settle under the control lock before handback; writes finish before the viewer sends the paste shortcut. Focused synchronization checks the native UTF-8 pasteboard as well as the local clipboard, so Unicode changes do not depend on legacy RFB notifications. A changed local clipboard takes precedence when both sides change between checks. Clipboard text remains outside model tools and conversation history. Rich clipboard and automatic file transfer are not provided; native file dialogs address Host files. Permission-delayed reads are discarded after revocation, while an already issued browser clipboard write cannot be cancelled.

Remote viewport changes require current human authority and desktop resizing support. Presets include desktop, laptop, tablet and phone orientations with fixed width and height. Presets request browser content dimensions, subject to native minimum window sizes; browser chrome remains visible. Desktop windows start maximized when an X11 window manager is available; fixed-size desktops place the browser at the origin and size it to fill the desktop. Other presets verify actual content dimensions after native window restoration, correct delayed decoration changes within a bounded wait, and report an error if the requested size cannot be reached. The shared desktop stays large enough for other owned windows. Unsupported adapters disable remote resizing while retaining local zoom. The preset belongs to the Thread binding and survives Stop/Reset within the WebUI process. It does not emulate mobile hardware or a mobile user agent.

## Local Screenshot Annotation

The viewer's capture action freezes the current rendered noVNC desktop in the client, including native browser chrome. It is available in read-only and controlling views after a frame arrives. Capture neither acquires human control nor pauses Agent operations; the captured frame stays fixed while the live browser continues. It uses no backend capture endpoint or CDP screenshot.

A local editor provides crop, arrows, rectangles, ellipses, freehand strokes, multiline text, mosaic and opaque redaction. Creating marks and crop regions requires a pointer. Marks can be selected, moved, resized and deleted. Undo/redo records completed edits, not pointer samples. Text uses native client input and composition. Icon controls have accessible names and tooltips; the annotation picker and keyboard commands support selection, nudging, deletion and history. Mosaic is a visual effect; sensitive content requires opaque redaction, which remains above source-sampling mosaic regions.

Document geometry and export dimensions use source pixels. Preview zoom and client device pixel ratio do not change PNG resolution. Export flattens the current crop and annotations without selection handles or other editor UI. Copy writes an `image/png` item to the client clipboard; Download provides a local PNG when image clipboard access is unavailable or rejected. Failed export or copy retains the editor and edits for retry. Closing asks for confirmation when text editing or undo/redo history exists, then discards local edits; editor state and captured pixels are not persisted by Harness UI.

Remote input and plain-text clipboard synchronization are suspended while this viewer edits. Queued transfers and permission-delayed reads are invalidated. Copy waits for every already-issued text clipboard write, including writes from replaced connections, so an older write cannot overwrite the PNG. Successful copy closes the editor and returns focus to chat without focusing the remote desktop. The user explicitly pastes into the existing composer attachment flow or another application; capture and copy do not upload, attach or send content automatically. Existing attachment limits and upload errors remain owned by the composer.

## Presentation and Limits

VNC displays actual graphical-session pixels rather than reconstructing DOM or streaming CDP screenshots. Chromium starts muted; the viewer does not transport audio.

The profile retains cookies, saved passwords and configuration subject to Chromium and its platform password store. Native takeover can operate browser-level UI, but third-party password managers, extensions, OS dialogs, file transfer and IME require their own end-to-end validation. Clipboard support does not imply file transport. Agent tools cover owned same-process and out-of-process frames, JavaScript dialogs, Host-path upload and observed downloads as defined by [Browser Use](../a13n-harness/23-browser-use.md). Native OS dialogs and extension management remain human browser workflows; direct file operations do not imply a client file-transfer bridge. Installed use requires no separately installed Node.js, and ordinary Files, Shell and chat do not start a browser or display.
