# Workbench Interaction

## Design Position

This document owns the browser's default interaction flow, action placement, and feedback. [Overview](00-overview.md) owns the product boundary; [collaborative conversations](01-collaborative-conversations.md), [output comments](05-output-comments.md), and [Host computer sharing](02-host-computer-sharing.md) own state and operation semantics. Layout never creates another authority or changes the selected execution target.

The primary experience is doing work in a conversation. Configuration is available when needed, and code or a terminal can be opened alongside that work. The interface does not require users to understand resource inheritance or runtime internals before sending a prompt.

The workbench uses the shared frontend design system with English interface text only. Controls describe user actions, such as Log in, Log out, Save changes, Connect account, and Reconnect, rather than internal credential-retention or publication operations. It has no language selector or translation runtime. Light and dark themes remain available; English-only interface text does not restrict the language of prompts, configuration content, names or comments.

## Coordinator Entry

Each ordinary project-bound root offers **Make Coordinator** in its conversation actions and details. Active, archived or pending-decision roots cannot be promoted. Confirmation explains that promotion is one-way, retains history and settings, and adopts no existing conversations. Success preserves the selected conversation URL. Workers do not offer promotion. Browsing and expanding Projects never create or promote Threads.

The composer places a **Coordinator** toggle beside **Goal**. It stages private intent without creating or changing a Thread, and can be turned off before Send. New conversations are created directly as Coordinators; existing ordinary roots are promoted before their message is submitted. Composer opt-in adds no confirmation dialog or persistent explanatory banner. Tooltips explain the irreversible role and prerequisites. Goal and Coordinator are independent choices. The toggle requires an available Project and, for existing conversations, ordinary promotion eligibility. Sending never silently falls back to ordinary execution when selected Coordinator intent is unavailable. Pending, unknown and preparing submissions lock the choice. Confirmed Coordinators show a non-toggle identity in its place, including after a failed submission. Narrow composers place the toggle in settings and retain an enabled removable chip or confirmed identity beside Send.

New-conversation restoration retains Coordinator intent, defaulting older drafts to off. Changing Project retains that intent; selecting no Project blocks Send until the intent is turned off or an available Project is chosen. Creation uses the retained Thread identity and the ordinary lost-acknowledgement recovery path. Promotion failure retains input and does not submit; an unknown promotion outcome is reconciled from Thread state before a later deliberate attempt. Creation/promotion and submission have separate completion boundaries: a failed Send does not undo a confirmed role, allocate another Thread, or automatically replay input. The role applies to future Runs and is never a steering mode.

Projects can show multiple Coordinator rows, each identified by a compact connected-nodes role mark independently of its editable title. The role mark, empty-conversation introduction and owned-worker grouping remain visible with Sidekick or automatic follow-up disabled. Each Coordinator offers **Pause automatic follow-up** / **Enable automatic follow-up** in its own actions and details, without a Project-level mode or demotion action.

A Coordinator title opens its conversation; its independent disclosure button expands only its owned workers. Workers initially remain collapsed, including on direct worker navigation, and are fetched lazily with `coordinator_thread_id`. Expanded groups reuse ordinary rows, showing active and selected workers and fresh unread observations without duplicates, with pagination, loading, empty and retry states. A worker never appears again as a top-level recent or active row. Root pagination, selected details and unread observations retain an owner anchor; a missing or archived owner is looked up by identity so its visible unarchived workers remain reachable. Archived owners offer explicit Restore. Unavailable Projects retain history navigation. Human search remains unfiltered by ownership and marks worker results **Coordinator worker**. Direct links never redirect to the owner.

A Coordinator appears once in the Project's **Running** group while either its own root or any unarchived owned worker is active, including while its worker disclosure is collapsed or its own row lies outside the current history page. When neither remains active, it returns to **New results** or **Recent** according to the ordinary unread rules. Worker activity changes navigation grouping only; it does not change the Coordinator's own execution status or available controls.

Promotion and follow-up controls use the ordinary Thread projections and invalidation. They do not allocate replacement conversations, rewrite titles, aggregate approvals, or add Project-wide execution state. Coordinators and workers retain the ordinary conversation renderer, composer, result tracking and pending-decision controls.

## Entry and Navigation

1. Open the instance URL and complete the existing key-entry flow if necessary.
2. Home resumes the browser's single New conversation draft with a centered welcome and a composer below it. A direct Thread link opens that saved conversation instead. Opening Home or New conversation does not create a persisted Thread.
3. A fresh installation automatically opens the route-backed `/setup` wizard before the Home composer. A configured installation opens the Home draft; an incomplete or broken existing configuration offers focused repair rather than reinitialization. Set up later dismisses automatic entry for this installation, with Continue setup available explicitly. Projectless conversation remains an explicit option.
4. Add Project and Project settings present one server directory per row, with explicit add/remove actions. When native sharing is enabled, each row can browse existing Host directories one level at a time through the paginated Host Files API, navigate to a parent or entered path, and explicitly select the current directory. Browsing does not publish configuration or create directories. Paths belong to the server/container. Without native sharing, manual path entry still works through validated Project configuration and does not enable a file-browsing API.
5. New conversation and each Project's plus action open the same local composer, without a creation form or title requirement. A plus action changes only the selected Project, retaining input and explicit Agent, Model, and Environment choices. Home resumes the current selection. The local route does not allocate a new identity on each visit, and there is no draft list or separate discard action; deleting input edits the one draft. Project selection sits above the composer. The editor has no placeholder text. Wide composers expose Goal, execution Environment, Agent, and Model shortcuts alongside attachments, Composer settings, and Send. When the composer's actual container becomes narrow, settings move into one panel, leaving attachments, draft synchronization status, Composer settings, and Send visible; an enabled Goal remains a removable chip. Responsive layout never resets the editor, draft, attachments, or selected configuration, and never hides errors or synchronization feedback. Closed controls show effective resource names and a supported Thinking summary, with compact Agent and Model labels where space permits to distinguish identically named resources without inheritance prefixes. Their expanded surfaces explicitly distinguish inherited defaults from concrete resources, including resources with identical names. The combined control exposes Thinking, reasoning mode, and Fast below the current Model, and opens a searchable Model list within the same popup; selecting a Model returns to its settings. Restoring default Thinking inherits authored settings rather than guessing an explicit equivalent. Unknown or unsupported Models show an explanation instead of invented effort controls. Long names remain inspectable. Composer settings uses one navigable surface for Goal, Environment, Agent, and Model, including Model search, Thinking, reasoning mode, and Fast. Desktop uses an anchored popover; mobile uses a bottom sheet with a fixed header and one scrolling body. Back returns to the settings overview without applying staged Environment edits. Closing returns focus to the settings trigger rather than reopening the editor keyboard. The Environment summary exposes the actual isolation mode inside the panel. These use the selected Project's effective creation defaults; incomplete configuration links to setup. Model defaults remain owned by Agent configuration. An explicit Model choice uses the existing single-Run override without rewriting Agent resources or sticky Thread configuration; it is retained privately with the browser draft and does not affect steering.

The Environment context strip follows [Device and Environment binding selection](../04a-devices-and-environment-bindings.md#webui-behavior): show local mode, added bindings and explicit default, with **Add environment** and clear Device/folder/availability labels. Remote-only Projects need no local directory row. Selection edits affect later admissions; active Run inspection shows its captured set. Host directory browsing never masquerades as remote Device browsing.

Thinking uses the selected Model's backend-owned [control descriptor](../02-agent-composition-and-snapshots.md#model-aware-thinking-controls), including configured-default summaries and disabled reasons. It is a private in-tab draft selection, not a shared composer field, persisted New-draft preference, or sticky Thread configuration. Explicit Agent or Model switches clear it. Submission captures it with the Model override before asynchronous preparation; steering never carries either override. Active work disables selection, and Run configuration inspection reports captured thinking separately from next-Run choices. Invalid or unavailable choices remain explicit until corrected rather than silently falling back.

A compact Fast toggle sits inside the shared Model settings panel in both New and saved conversations at every width. Its stable Fast label has two visual states: lit when explicitly enabled or inherited as on from the backend's [Fast descriptor](../02-agent-composition-and-snapshots.md#fast-request-controls), unlit otherwise. It exposes pressed state accessibly, without a third Default state or adjacent reset action. An untouched toggle inherits Model settings unchanged; unlit inherited default means Fast was not explicitly requested, not a claim about provider fulfillment. Clicking requests the opposite boolean and the tooltip warns that Fast can increase costs or credit usage. Fast shares Thinking's private in-tab selection and model/agent reset boundaries. Submission captures false as well as true before asynchronous preparation; steering never carries Fast. Unsupported controls explain why they are disabled. No durable preference or automatic fallback is added.

Reasoning mode uses the backend's [descriptor](../02-agent-composition-and-snapshots.md#reasoning-mode-controls) in the same desktop and compact Model settings panel. Standard and Pro are explicit choices; Use default clears the override and always names the selected Model's default target. Unset provider default is not labeled Standard, and a stale unavailable choice stays visible and resettable. Its private draft, capture-before-await, steering exclusion, and Agent/Model reset boundaries match Thinking and Fast. The Model editor separately edits the permanent native setting: Provider default removes `openai_reasoning_mode`, while presets preserve this independent setting. No ordinary setup question, automatic migration, or default opt-in is added.

The Tokens/Context/Cost/Cache/Time row also shows captured non-default reasoning mode and Fast On, Off, or Default from configuration inspection's immutable active or selected-continuation capture, never from the composer draft. Default does not imply Off. During preparation, a mismatched previous receipt is not presented as the current Run's setting. Missing capture is unavailable, and observation errors remain explicit. The tooltip/details identify this as a requested setting rather than proof of provider speed. Changing next-Run choices cannot relabel a captured Run.

The first explicit Send creates the Thread with a retained canonical identity, uploads locally staged files, synchronizes the existing shared draft, and invokes ordinary submission once. The New page keeps the composer and loading feedback in place until submission is acknowledged; it does not show a speculative input bubble or navigate on submission rejection or an unknown acknowledgement. An unknown submission offers explicit navigation to the retained Thread for operation/history review; unlocking a new submission remains on that review surface. After acceptance it opens the saved Thread through the destination's first-observation gate, without waiting for model output. Empty local pages do not appear as saved conversations. The browser keeps one local-storage snapshot per origin for the New draft's text, attachment references, creation identity, selections, and unresolved creation/submission state. Navigation, reload, and reopening the browser restore that snapshot; it is not a server Thread, an offline queue, or cross-tab collaborative editing. Local file bytes remain tab-local: reload keeps unavailable attachment markers and requires explicit removal or reattachment rather than silently sending without files. Storage failures retain in-tab editing and visibly disclose the recovery limitation. A positive submission receipt retires the persisted New slot, while the saved Thread retains its ordinary in-tab composer and any uncaptured edits. An interrupted submission restores as an unknown outcome, including when reopening the saved Thread directly. Once creation has been attempted, Project and creation selections stay frozen until the exact-identity outcome is resolved. Navigation away during preparation does not continue into an unobserved Send. A lost creation acknowledgement is reconciled by an explicit exact-identity read; an existing Thread opens for review without submitting. Definite rejection retains input for correction; an uncertain admission retains input and requires the existing deliberate outcome-review flow, never automatic replay.

The left sidebar groups root conversations under collapsible Projects without separate full-width New conversation or Add project buttons. Home and each Project's plus action resume the single New draft; a compact Add project action sits beside the Projects heading. Search and the Project-scope filter share a compact row. Each Project offers New conversation and a secondary menu for Rename project, Project settings, and local ordering. Quick rename changes only the display name through validated source publication, preserving Project identity, roots, defaults, and conversations; unsaved Project source drafts must be resolved in settings first. Project groups can be reordered by dragging their handles or using the keyboard; the browser remembers this presentation order without changing Project YAML, `position`, or any backend state. The default order places Projects whose first root exactly matches the server's current working directory first, retaining configured order within each group. Explicit browser ordering takes precedence; Reset restores this current-directory-first default. New Projects absent from the saved order follow the existing groups. Projectless conversations and conversations referencing unavailable Projects remain explicit, separate navigation groups; unavailable references are never silently reassigned.

A stable **Drafts** entry remains below conversation search and above Projects, including when no non-archived saved Threads have [unsent shared input](01-collaborative-conversations.md#unsent-input-discovery). A neutral count appears only when nonzero and includes the currently edited Thread. Draft changes never automatically open the list, move Projects, or take keyboard focus. Explicit activation opens a bounded, scrollable popover of conversation titles and Project names, without duplicating activity controls, participant avatars, or conversation action menus. Draft discovery remains independent of collapsed groups, recent pagination, search, and the Project-scope filter; these controls continue to scope the ordinary lists below it. Shortcuts are sorted newest empty-to-nonempty transition first, with Thread identity as a stable tie-breaker; typing does not continuously reorder them. Existing Project order and Thread grouping remain unchanged. Ordinary Thread rows show a quiet **Draft** text marker alongside rather than replacing activity and unread-result indicators. Selecting a shortcut closes the popover, opens the conversation, and focuses its composer, including when that conversation is already open; it does not acknowledge or remove the reminder. Dismissing the popover with Escape returns focus to its entry. Only clearing the input, including the normal accepted-capture clear, removes the reminder; concurrent uncaptured content keeps it present. Archiving hides its shortcut without deleting its draft. Discovery failures are indicated on the stable entry, with details and retry inside the popover; loading and failure are not presented as proof that no drafts exist. The popover identifies shared, unsent input without claiming private ownership or durable saving. The single not-yet-created Home draft retains its existing entry point and is not a saved-Thread shortcut.

Each expanded group owns its server-filtered root-Thread query, loaded pages, cursor, loading state, and retry. Every currently active root is displayed first, independently of the recent-page limit; preparing, running, and cancelling work remains visible until its operation becomes terminal. Below these roots, the initial recent page contains five inactive conversations; More fetches only that group's next inactive page and uses regular text weight. Activity and recent queries use persisted navigation touch time with creation-time fallback and the existing Thread-ID tie-breaker, before pagination. Browser-local new results are partitioned separately as described below. Progress and checkpoint updates refresh row content without changing order. A completed operation leaves Running and appears in New results while unread, otherwise in Recent according to its refreshed navigation touch time, not its original submission time. Threads cannot be manually reordered or dragged between Projects. Collapse preserves loaded pages, and expansion is a browser-local preference. Opening a Thread reveals its group. A selected Thread outside loaded pages remains reachable as an ordinary row in its activity section, without a temporary location caption or fetching preceding pages. Its detail observation can bridge a slower list refresh; appending an unrelated history page must not replace that observation with older loaded-row state. A genuinely refreshed page can advance the row again.

Search uses one independently paginated global server query, not only loaded rows or one request per Project. Search temporarily hides grouped navigation and its reorder controls; clearing it restores the groups and cached pages. Both views exclude archived conversations. An independent `/archived` page, reached from the sidebar, searches and paginates only archived conversations and offers direct Restore actions. The activity-list API retains omitted `project_id` as all Projects; explicit `project_scope=projectless` selects only null references, and `project_scope=unavailable` selects references absent from accepted configuration. A Project ID and a non-default scope are mutually exclusive. The activity-list API accepts `archived_only=true` to select archived roots before counting and pagination, independently of `include_archived`; existing defaults and inclusive queries remain unchanged. Grouped navigation requests `include_active=true`: `active_rows` contains every matching current-App active root, independently of `limit` and `cursor`, while `rows` and `next_cursor` paginate only matching inactive roots. `total` counts both collections. The ordinary activity list, global search, and archive page retain one paginated `rows` collection and an empty `active_rows`; all use navigation touch sorting. Current activity is captured once per response and is not inferred from saved status or another App process. Cursors bind the Project filter, both archive flags, search, sort, and active-separated query shape; cross-query reuse is rejected. Refetch reconciles active membership and recent pages after status changes without displaying a Thread twice. Reading an unavailable Project's Threads is allowed without making that Project runnable.

Normal navigation and the archive page have independent query identities and pagination; neither borrows the other's rows or cursor. Archived deep links remain readable without pinning archived rows into ordinary navigation. Initial group loads use a compact delayed indicator rather than replacing the sidebar with animated skeletons; subsequent refreshes keep rows and selection in place. Background group refreshes retain heading and action widths. Summary and focused realtime refresh hints are coalesced without cancelling pagination. Ordinary text, reasoning, and tool presentation events update the live display without HTTP refetches. Usage events refresh usage/context; checkpoints refresh Thread detail so saved queries follow the new continuation; lifecycle events refresh operation/detail and activity lists; child events refresh child projections. Healthy realtime does not also poll operation or usage endpoints during ordinary observation. An explicit unresolved Stop additionally reads its exact receipt until its terminal status is confirmed; this bounded-lifetime fallback does not replay cancellation. Elapsed time is a local clock. Fresh stream open/reset reconciles observations, with low-frequency foreground reconciliation while the summary connection is unavailable.

Conversation rows show title, activity, and attention-needed state. Running, waiting for a decision, and failed states remain distinguishable without opening every Thread. Each conversation row's secondary menu provides Rename, Share, Details, and Archive or Restore. These actions belong to that Thread, not to its Project's settings. Archive executes directly without confirmation, retains saved history, and honors the App's active-operation restriction and metadata version. Archiving the selected conversation opens the New draft with that conversation's Project selected; archiving another row does not change the current page. If the archived Thread owns an unresolved New draft, archiving detaches that draft to a fresh creation identity while retaining text and choices. Uploaded handles cannot cross Thread boundaries and remain unavailable markers requiring reattachment; unknown admission still requires outcome review. Archived conversations remain inspectable and restorable from the archive page; restoring removes the row from that page and makes it available in ordinary navigation. Failures remain visible without blind retries.

Application confirmations use the shared styled dialog surface, not native browser alert, confirm, or prompt calls. Potentially lossy draft disposal and uncertain-submission review keep their explicit confirmation; cancelling or dismissing these dialogs does not perform the action.

Selecting a different conversation is personal navigation. The browser retains each Thread's editing context without cancelling execution or causing collaborators to switch views. An update in another Thread marks its row rather than stealing focus.

## New Results in This Browser

A root Thread opened or started in this browser becomes followed. The first observed successful-completion version is its historical baseline, not a new-result alert; a newly created Thread starts at version zero. Local Send and decision submission wait for interest registration before admission so a fast first completion cannot become the baseline. A late first visit in another tab never raises an existing acknowledgement. Unopened collaborators' Threads do not become followed merely because they appear in navigation.

The server's [saved root completion marker](../03-local-storage-and-recovery.md#saved-root-completions) is the durable success authority. A version above this browser's acknowledged version means one unread result for that Thread. Multiple completions coalesce. Later running, suspended, failed, or cancelled work never clears an unseen success. This state is independent of transient notices, operation receipts, desktop permission, and navigation touch time.

Browser interest and acknowledgements use a small per-origin IndexedDB store keyed by Thread ID. Create-if-absent baseline registration and maximum-version acknowledgement are atomic across tabs; transaction completion, not individual request success, is the persistence boundary. Cross-tab messages are reread hints, not authoritative state. There is no bounded-interest eviction, server per-user read table, or notification-history log. Storage failures visibly disclose incomplete recovery without silently substituting localStorage or pretending an acknowledgement was saved. Clearing site data removes this browser's personal state.

Startup, reload, fresh summary subscriptions/resets, and foreground return reread browser state and reconcile followed roots through bounded batched identity lookup, independently of sidebar pages. Relevant summary events reconcile only dirty identities through the realtime connection; valid resume replays missed hints without a full refresh. Requests coalesce and completion versions never regress. Failed refreshes retain cached reminders and offer retry. Reopening a closed browser recovers unread markers without replaying a pile of old toasts; closed-page push delivery is not promised.

An acknowledgement requires the saved transcript to be rendered in the visible conversation, the document to be visible and focused, and the actual scroll position to have reached the bottom. Selecting a route, receiving live output, or starting smooth scrolling is insufficient. The browser acknowledges exactly the transcript snapshot's `completion_version`, never a newer detail or lookup marker. Checkpoints after that completion retain its version even when the selected continuation changes.

Ordinary Project groups display Running, New results, and Recent sections without duplicate Threads. Unread inactive roots remain reachable outside loaded recent pages; active roots keep their independent new-result dot. A collapsed group retains its unread-Thread count. Existing touch sorting, recent-page cursors, search pagination, and selection remain unchanged. Archived roots do not contribute to ordinary groups or counts; their new-result dots remain available on the archive page. Row dots have the accessible label and tooltip New result and do not replace activity, failure, or decision icons.

## Task Notifications

The authenticated workbench consumes terminal root-operation notices from the existing App-wide summary realtime, independently of the selected page and focused token stream. Completed root operations show an in-app notice unless the current route is already viewing that Thread. Suppressed completions still enter receipt deduplication, so replay after navigation does not produce a delayed notice. Failed and suspended root operations still notify on the current conversation. All three statuses notify for conversations never opened in that browser; there is no visited-Thread, focus, permission, opt-in, or six-hour activity filter. Notices contain actual result/request/failure previews and an explicit Open conversation action. Mobile notices use smaller spacing and icons, a one-line title, a two-line preview, and a compact Open action with the full accessible label. Reply previews combine prose and list items across paragraph breaks before applying their length bound. Reading saved history, initial connection, and stream resets do not synthesize notices; replayed receipt identities within an App epoch do not create duplicates. Child completion and explicit cancellation remain conversation activity rather than separate alerts.

Browser notification preference, browser permission, and push subscription are independent. The initial preference offers notifications through one persistent, non-modal setup toast; notification Settings shows guidance inline instead. Mobile keeps this reminder to a short title, Settings action, and dismissal control, with full explanations and enable actions available in Settings. Permission and first subscription require an explicit button: existing granted permission does not silently opt a device into Web Push. Dismissing the browser request retains the toast; denial changes it to browser-settings guidance. Unsupported or insecure contexts explain that only in-app notices are available. Regular iPhone/iPad tabs missing push APIs explain the iOS/iPadOS 16.4+ Home Screen web-app requirement, including Share → Add to Home Screen and reopening from that icon. Platform hints select guidance, not capability authority. Settings exposes the immediate browser-local preference, actual permission, subscription state, enable/reconnect action, and real push test. Setup prompts are suppressed throughout explicit setup and subscription checking, including retries after earlier failures.

A remembered subscription ID is opt-in/reconciliation intent, not proof of delivery health. Startup, foreground return, and network reconnect synchronize previously enabled subscriptions; pending or failed synchronization is explicit. Explicit reconnect replaces an expired browser endpoint. Disabling notifications removes the browser and server subscription and closes worker notifications on a best-effort basis. Failure of both removals remains explicit. Disabling suppresses setup prompts without disabling in-app notices or changing other browsers' preferences. Subscription mutations remain serialized where browser Web Locks are available; there is no separate native-display lock or browser delivery ledger.

System notifications have one path: the server sends Web Push and the notification-only Service Worker displays it. No page-native constructor, page-triggered worker notification, permission-only setup, or local test fallback exists. Push eligibility is unchanged by the selected page: completed operations may still send Push when their in-app notice is suppressed on the current Thread. Failed and suspended operations may show both Push and in-app notices, including in the focused current conversation. Unsupported or unreachable push services leave only in-app notices. Push tags provide best-effort replacement, not exactly-once delivery. Previews may expose result text on the desktop or lock screen, as disclosed in Settings. Clicking a push focuses a window already at the exact target or opens a new same-origin window; it never reloads another page and discards unsaved editors. The worker has no instance key and ordinary login still applies. Logout attempts subscription cleanup before disposing authenticated transport; access loss invalidates the browser subscription where possible. Notification state unmounts on logout/access loss, and failed cleanup leaves an explicit login-screen warning to block notifications in site settings.

An opted-in device reports activity only while its page is visible, immediately on startup, visible return, and successful setup, then approximately every 60 seconds. Visibility is sufficient: focus, keyboard/mouse idle detection, browser-persisted activity clocks, cross-tab activity coordination, and collaboration presence do not participate. Activity uses a lightweight authenticated update of an existing subscription and never creates or restores a removed row. Normal subscription reconciliation is not activity. Each recipient selection captures one server time and selects subscriptions whose server-recorded `last_active_at` is strictly newer than six hours before it. This is a selection rule, not a hard send/retry deadline or security lease. Each visible page may independently renew its device's activity.

The WebUI App queues settled root-operation notices independently of realtime observers. All recently active opted-in devices are eligible regardless of Thread visit history; missing or archived roots are skipped. A bounded in-memory queue and bounded concurrent HTTPS requests isolate failures from Run settlement. The sender retains Web Push encryption, persisted VAPID identity, supported browser push-service endpoints, no redirects, and at most two attempts for transient failures. Expired endpoints are removed, and subscription existence/keys are rechecked before send. Persistence and the separate 90-day retention rule are owned by [local storage](../03-local-storage-and-recovery.md#browser-push-subscriptions).

Authenticated `GET /api/push/configuration`, `PUT /api/push/subscription`, `DELETE /api/push/subscriptions/{subscription_id}`, `POST /api/push/subscriptions/{subscription_id}/activity`, and `POST /api/push/subscriptions/{subscription_id}/test` follow the existing same-origin API boundary. Configuration exposes only the public VAPID key. Subscription input contains endpoint, public encryption key, auth secret, and browser origin, with no Thread interest list. Activity returns 204 after recording server time, or not-found for a removed subscription. Inputs cannot direct server requests to arbitrary Host-network URLs. Explicit tests use the real push transport independently of the activity cutoff and report provider acceptance, not device display. The bundled client and server contract change together; an old open browser bundle must reload after upgrade.

Closed-page push requires recent device activity, a running WebUI server, push-service reachability, and browser/OS permission. Browser force-stop, battery policy, disconnection, or notification settings can delay or prevent delivery. Queue loss on shutdown is acceptable; there is no durable push outbox, delivery ledger, or historical replay. Push does not change execution lifetime or the separate browser-local new-result markers.

## First-Use Wizard

The browser first-use flow follows [Setup and Environment Readiness](../06-setup-and-environment-readiness.md#browser-first-use). It uses a large, centered, viewport-bounded dialog over the subdued workbench on desktop and the full viewport on narrow screens. Two steps share one stable progress header, scrollable content region, and persistent Back/Continue/save footer: Model and Workspace. Model combines connection, credential operations, and the same editor used in resource management. Step changes focus their heading; dismissal and first-conversation entry restore useful keyboard focus. The wizard uses the shared overlay and field primitives in both themes.

Subscription connection is inline and shares account operations with Accounts settings. Device authorization is the default; callback authorization is an explicit advanced option that explains server loopback reachability. The wizard presents verification URL, code/copy, waiting, success, cancellation, expiry, and retry without requiring a detour. API-key entry saves through the existing Host key API under a generated reference, with an explicit immediate-save explanation. Neither connection method treats browser identity as the owner of server credentials.

The Model step uses backend-owned release choices, reasoning/context defaults, and reviewed native-tool recommendations, with optional advanced controls. API connections expose provider, model ID, and applicable base URL instead of requiring raw route syntax. The Workspace step explains Full Control versus Sandbox, offers an optional existing server directory, and shows a concise summary with expandable generated files. Sandbox readiness is bound to every resolved preview path; failed or cancelled preparation never selects Full Control.

Save and start chatting explicitly publishes configuration, reconciles saved files, opens the first conversation once, and focuses its empty composer. It does not send a prompt or test the model. Connected account, saved configuration, prepared environment, and successful model request remain distinct observations. Unknown publication or conversation creation stays recoverable on refresh and never causes blind mutation replay.

## Participant Awareness

On first entry the browser generates a display name and remembers it as a local preference. The top-right header shows that name and opens editing; saving a nonempty replacement updates live presence and composer attribution, without rewriting existing saved attribution. This is a collaboration label, not an account or verified identity. The workbench exposes a compact participant directory showing reported current page and foreground, inactive, or disconnected/unknown participation. The current page shows its own participants rather than everyone with that Thread's draft open. The directory remains usable in Project settings and the configuration center without opening a conversation.

Separate tabs with the same display name remain distinguishable. A background tab can be shown as attached but is not labeled as confirmed current attention. Switching between Chat, a file, a diff, configuration, and a terminal updates the reported focused area without moving other users. Participants can explicitly open a collaborator's available page through ordinary navigation; it does not enable continuous following or synchronize scroll.

Same-page presence is an awareness indicator, not a blanket Edit permission or a claim that every surface uses CRDT. Chat retains its shared composer, saved output remains read-only, file changes use existing save rules, and terminal input uses explicit control ownership. realtime updates and refetches preserve the local focused area and do not recreate the editor's CRDT replica.

## Default Layout

| Region       | Default interaction                                                                                                        |
| ------------ | -------------------------------------------------------------------------------------------------------------------------- |
| Sidebar      | Projects and conversations, Overview, Settings, and footer participant/theme/session controls; a drawer on narrow screens  |
| Main area    | Chat remains the primary reading area with its shared composer                                                             |
| Right drawer | Files or Changes explorer and selected file/diff editor, closed until opened; file tabs stay inside the drawer             |
| Bottom panel | Resizable Host Terminal, closed until explicitly opened                                                                    |
| Header       | One compact conversation title with Files, Changes, and Terminal toggles plus the editable collaboration name at the right |

The application frame stays within the viewport. Conversation history, code, explorer contents, and Settings content scroll within their own available space rather than growing the document. Files and Changes share the right drawer; selecting a file or comparison opens its editor inside that drawer without replacing desktop Chat. Back returns to the explorer, and file tabs retain previously opened views. The drawer has a keyboard-accessible width separator and remembers its size locally; closing it returns focus to Chat without discarding private buffers. A small in-tab Project cache retains directory, file tabs, and selected terminal. File tabs identify full paths and dirty buffers; closing a tab retains its private buffer without saving or discarding it. Reading a file or comparison preserves the mounted explorer's filter and scroll. Files and Changes filter loaded paths only and explicitly disclose additional pages. A selected new-file line in an unstaged or untracked comparison can open the current working file at that line; staged and deleted-side lines do not claim an equivalent working-file position. Selecting an entry opens a unified comparison in the right drawer, with a clear baseline and a route to the current file. Text uses monospace code, separate old/new file gutters, and distinct light/dark additions, deletions, and hunk context. The reviewed patch remains complete: headers and no-newline notices stay readable, while unknown/combined metadata receives no invented file numbers. Selection and capture retain the original inclusive patch-line coordinates, not the displayed file gutters; a replacement diff revision clears the previous selection. Binary files and conflicts receive explicit presentation rather than misleading text diffs. Git-unavailable state retains ordinary Files and explains why Changes cannot be shown.

Add to prompt on a code selection or diff inserts a visible context item into the shared composer of the selected Thread. Participants can inspect and remove it before submission. It identifies the server/repository/path and captured content, and does not imply access to that path from a remote Agent Environment. Merely opening a file does not send it to the model.

Native mutations, returning focus, leaving terminal inspection, and root Run completion refresh the relevant status without overwriting a dirty editor buffer. Refresh observes the current checkout, not a per-Run snapshot, and unavailable or replaced comparisons remain explicit. The view is labeled Changes, not This Run's changes. Git mutation buttons, automatic commits, and automatic worktree creation are outside this interaction flow; deliberate Git commands remain available through Terminal.

## Terminal Interaction

Open Terminal lists only sessions associated with the selected conversation's Project. New terminal starts in the currently browsed directory and carries the selected Project ID; Files also offers Open terminal here for a directory, creating a new session rather than sending a shell command to an existing one. Without a Project and configured root, creation is unavailable. Switching Projects changes the visible session list and detaches the old view without closing its sessions, sending commands, changing their working directories, or claiming control. A creation completing after navigation cannot select its old-Project session in the new Project. Existing unassociated sessions remain available through the native API, not through another Project's list. Terminal links require the matching Project context; unavailable targets explain that requirement and do not publish terminal page focus. Starting a session displays its server/container location and initial directory. Terminal tabs have useful titles and an active input-controller indicator. Collapsing the panel does not stop sessions.

The creating browser requests control once on the new terminal's first authenticated frame when it has no controller, then focuses input only after server confirmation. It does not take over from a participant who already acquired control, and reconnecting never repeats this creation intent. A participant viewing another person's terminal sees read-only output and a Take control or Take over input action. Activating it transfers input control through the App, visibly updates both participants, and only enables keyboard input after confirmation of ownership. Losing control leaves the old viewer attached to output. It does not inject partially typed browser input. Viewers may open separate terminal sessions instead of taking over.

Disconnect shows a disconnected state rather than an apparently usable prompt. Reconnect restores available output and discloses gaps; it never repeats keystrokes. End session is distinct from closing its view and warns that it affects the shared process. Unsupported native PTY remains explicitly unavailable.

Terminal toolbar actions use icon-only buttons with accessible names and tooltips, including available shortcuts. Session tabs retain readable names, connection/control status remains visible as text, and the destructive End session confirmation retains its explicit action label. Ctrl+backtick toggles the panel; Ctrl+Shift+backtick creates a terminal through the same Project, pending-action, and unknown-outcome gates as the button. These workbench shortcuts are inactive in Settings, while a modal is open, during IME composition, or when native terminal sharing is disabled; holding the key does not repeat creation. Showing a selected terminal focuses its input without claiming control; collapsing returns focus to the conversation. While focus is inside the terminal panel, Ctrl+PageUp/PageDown switches sessions (Cmd+Shift+left/right bracket on macOS), without creating or ending sessions.

Terminal search operates on retained screen output, with previous/next matches; Ctrl+F (Cmd+F on macOS) opens or refocuses it. Enter/Shift+Enter advances/reverses matches, and Escape or Close search returns focus to terminal input without closing the panel. Ctrl+Shift+C/V copies/pastes in terminal input on Windows and Linux; macOS uses Cmd+C/V. These shortcuts leave ordinary text fields alone and preserve shell control sequences such as Ctrl+C. Paste requires confirmed input ownership, uses the emulator's bracketed-paste handling, and does not deliver a pending clipboard read after hide, disconnect, or control transfer. Clipboard denial is reported without retrying input. Copy selection leaves terminal input unchanged. HTTP links open separately; deterministic absolute path:line references open Host files, without guessing the shell's current directory or ambiguous wrapped/wide-character positions. Add selection to prompt appends attributed text to the current synchronized Thread draft for review, never auto-sends, and preserves existing input. A Return to conversation action focuses that draft. Terminal focus otherwise receives its native key bindings; browser-wide command shortcuts do not intercept shell control sequences. File-save shortcuts operate only in the file editor, not the shared prompt or terminal.

## Empty, Disabled, and Failure States

| Situation                                     | User-facing behavior                                                                                                                                      |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Computer sharing disabled                     | Hide active Files/Changes/Terminal controls and explain the startup option in instance information; no misleading Enable button without process authority |
| Missing/invalid model or extension            | Link the blocked conversation to its configuration diagnostic; preserve its prompt                                                                        |
| API key rejected                              | Request a valid key while distinguishing access failure from lost project data; do not repeat mutations after login                                       |
| Browser offline                               | Mark presence/output as disconnected, preserve recoverable local work, disable execution submissions                                                      |
| Draft synchronization failed                  | Show unsynchronized state and retain recoverable text; do not claim server persistence                                                                    |
| File changed externally                       | Preserve the local buffer and offer comparison/reload rather than silent overwrite                                                                        |
| Repository inspection failed                  | Explain unavailable Git state, not a clean checkout                                                                                                       |
| Run failed                                    | Show the owning operation error and retained evidence; keep deliberate recovery separate from retrying unknown effects                                    |
| Server restarted                              | Reload continuation and committed comments, disclose lost shared drafts and live authority, and never automatically resubmit input or recreate a terminal |
| Comment source or selected target unavailable | Preserve published comments or the local unpublished draft, explain the unavailable/stale target, and never silently attach to different output           |

## Verifiable Flows

01. A person opens a configured Project, starts a conversation, and submits without entering the configuration center.
02. Two browsers coedit one prompt, observe one accepted submission, and retain any uncaptured edits.
03. One collaborator reads a file/diff while another stays in Chat; adding context is visible to both, navigation is not synchronized.
04. A busy Thread permits next-prompt editing but does not silently queue or send it.
05. Applying Project defaults previews a bounded change and leaves an active Run's capture unchanged.
06. Native Files and Terminal remain on the server when the Agent uses E2B.
07. Terminal takeover changes input authority without disconnecting other viewers or replaying input.
08. Disabled sharing, missing Git, unsupported PTY, and authentication failures have distinct recovery paths.
09. Two people can see whether they are on the same Chat, file, or configuration page without being navigated there by each other; multiple/background tabs are distinguishable.
10. A participant comments on saved output while another Run executes; the comment survives reconnect, restart, and a later continuation without entering model history.
11. Streaming output cannot receive a published comment, and selecting a rendered range never silently anchors to different source text.
12. A lost comment acknowledgement is reconciled without a duplicate post; a missed live hint is repaired by an ordinary comment query.
