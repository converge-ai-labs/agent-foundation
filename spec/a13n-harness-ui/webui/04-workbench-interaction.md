# Workbench Interaction

## Design Position

This document owns the browser's default interaction flow, action placement, and feedback. [Overview](00-overview.md) owns the product boundary; [collaborative conversations](01-collaborative-conversations.md), [output comments](05-output-comments.md), and [Host computer sharing](02-host-computer-sharing.md) own state and operation semantics. Layout never creates another authority or changes the selected execution target.

The primary experience is doing work in a conversation. Configuration is available when needed, and code or a terminal can be opened alongside that work. The interface does not require users to understand resource inheritance or runtime internals before sending a prompt.

The workbench uses the shared frontend design system with English interface text only. Controls describe user actions, such as Log in, Log out, Save changes, Connect account, and Reconnect, rather than internal credential-retention or publication operations. It has no language selector or translation runtime. Light and dark themes remain available; English-only interface text does not restrict the language of prompts, configuration content, names or comments.

## Entry and Navigation

1. Open the instance URL and complete the existing key-entry flow if necessary.
2. Home resumes the browser's single New conversation draft with a centered welcome and a composer below it. A direct Thread link opens that saved conversation instead. Opening Home or New conversation does not create a persisted Thread.
3. A fresh installation automatically opens the route-backed `/setup` wizard before the Home composer. A configured installation opens the Home draft; an incomplete or broken existing configuration offers focused repair rather than reinitialization. Set up later dismisses automatic entry for this installation, with Continue setup available explicitly. Projectless conversation remains an explicit option.
4. Add Project and Project settings present one server directory per row, with explicit add/remove actions. When native sharing is enabled, each row can browse existing Host directories one level at a time through the paginated Host Files API, navigate to a parent or entered path, and explicitly select the current directory. Browsing does not publish configuration or create directories. Paths belong to the server/container. Without native sharing, manual path entry still works through validated Project configuration and does not enable a file-browsing API.
5. New conversation and each Project's plus action open the same local composer, without a creation form or title requirement. A plus action changes only the selected Project, retaining input and explicit Agent, Model, and Environment choices. Home resumes the current selection. The local route does not allocate a new identity on each visit, and there is no draft list or separate discard action; deleting input edits the one draft. Project and Environment selectors form a compact context strip above the input; separate Agent, Model, and Thinking selectors sit beside Send. Inherited defaults are explicitly named and remain distinguishable from concrete resources, including resources with identical names. The Environment's actual isolation mode remains visible beside the attachment action. These use the selected Project's effective creation defaults; incomplete configuration links to setup. Model defaults remain owned by Agent configuration. An explicit Model choice uses the existing single-Run override without rewriting Agent resources or sticky Thread configuration; it is retained privately with the browser draft and does not affect steering.

Thinking uses the selected Model's backend-owned [control descriptor](../02-agent-composition-and-snapshots.md#model-aware-thinking-controls), including configured-default summaries and disabled reasons. It is a private in-tab draft selection, not a shared composer field, persisted New-draft preference, or sticky Thread configuration. Explicit Agent or Model switches clear it. Submission captures it with the Model override before asynchronous preparation; steering never carries either override. Active work disables selection, and Run configuration inspection reports captured thinking separately from next-Run choices. Invalid or unavailable choices remain explicit until corrected rather than silently falling back.

The first explicit Send creates the Thread with a retained canonical identity, uploads locally staged files, synchronizes the existing shared draft, and invokes ordinary submission once. Empty local pages do not appear as saved conversations. The browser keeps one local-storage snapshot per origin for the New draft's text, attachment references, creation identity, selections, and unresolved creation/submission state. Navigation, reload, and reopening the browser restore that snapshot; it is not a server Thread, an offline queue, or cross-tab collaborative editing. Local file bytes remain tab-local: reload keeps unavailable attachment markers and requires explicit removal or reattachment rather than silently sending without files. Storage failures retain in-tab editing and visibly disclose the recovery limitation. A positive submission receipt retires the persisted New slot, while the saved Thread retains its ordinary in-tab composer and any uncaptured edits. An interrupted submission restores as an unknown outcome, including when reopening the saved Thread directly. Once creation has been attempted, Project and creation selections stay frozen until the exact-identity outcome is resolved. Navigation away during preparation does not continue into an unobserved Send. A lost creation acknowledgement is reconciled by an explicit exact-identity read; an existing Thread opens for review without submitting. Definite rejection retains input for correction; an uncertain admission retains input and requires the existing deliberate outcome-review flow, never automatic replay.

The left sidebar groups root conversations under collapsible Projects without separate full-width New conversation or Add project buttons. Home and each Project's plus action resume the single New draft; a compact Add project action sits beside the Projects heading. Search and the Project-scope filter share a compact row. Each Project offers New conversation and a secondary menu for Rename project, Project settings, and local ordering. Quick rename changes only the display name through validated source publication, preserving Project identity, roots, defaults, and conversations; unsaved Project source drafts must be resolved in settings first. Project groups can be reordered by dragging their handles or using the keyboard; the browser remembers this presentation order without changing Project YAML, `position`, or any backend state. The default order places Projects whose first root exactly matches the server's current working directory first, retaining configured order within each group. Explicit browser ordering takes precedence; Reset restores this current-directory-first default. New Projects absent from the saved order follow the existing groups. Projectless conversations and conversations referencing unavailable Projects remain explicit, separate navigation groups; unavailable references are never silently reassigned.

Each expanded group owns its server-filtered root-Thread query, loaded pages, cursor, loading state, and retry. Every currently active root is displayed first, independently of the recent-page limit; preparing, running, and cancelling work remains visible until its operation becomes terminal. Below these roots, the initial recent page contains five inactive conversations; More fetches only that group's next inactive page and uses regular text weight. Activity and recent queries use persisted navigation touch time with creation-time fallback and the existing Thread-ID tie-breaker, before pagination. Browser-local new results are partitioned separately as described below. Progress and checkpoint updates refresh row content without changing order. A completed operation leaves Running and appears in New results while unread, otherwise in Recent according to its refreshed navigation touch time, not its original submission time. Threads cannot be manually reordered or dragged between Projects. Collapse preserves loaded pages, and expansion is a browser-local preference. Opening a Thread reveals its group. A selected Thread outside loaded pages remains reachable as an ordinary row in its activity section, without a temporary location caption or fetching preceding pages. Its detail observation can bridge a slower list refresh; appending an unrelated history page must not replace that observation with older loaded-row state. A genuinely refreshed page can advance the row again.

Search uses one independently paginated global server query, not only loaded rows or one request per Project. Search temporarily hides grouped navigation and its reorder controls; clearing it restores the groups and cached pages. Both views exclude archived conversations. An independent `/archived` page, reached from the sidebar, searches and paginates only archived conversations and offers direct Restore actions. The activity-list API retains omitted `project_id` as all Projects; explicit `project_scope=projectless` selects only null references, and `project_scope=unavailable` selects references absent from accepted configuration. A Project ID and a non-default scope are mutually exclusive. The activity-list API accepts `archived_only=true` to select archived roots before counting and pagination, independently of `include_archived`; existing defaults and inclusive queries remain unchanged. Grouped navigation requests `include_active=true`: `active_rows` contains every matching current-App active root, independently of `limit` and `cursor`, while `rows` and `next_cursor` paginate only matching inactive roots. `total` counts both collections. The ordinary activity list, global search, and archive page retain one paginated `rows` collection and an empty `active_rows`; all use navigation touch sorting. Current activity is captured once per response and is not inferred from saved status or another App process. Cursors bind the Project filter, both archive flags, search, sort, and active-separated query shape; cross-query reuse is rejected. Refetch reconciles active membership and recent pages after status changes without displaying a Thread twice. Reading an unavailable Project's Threads is allowed without making that Project runnable.

Normal navigation and the archive page have independent query identities and pagination; neither borrows the other's rows or cursor. Archived deep links remain readable without pinning archived rows into ordinary navigation. Initial group loads use a compact delayed indicator rather than replacing the sidebar with animated skeletons; subsequent refreshes keep rows and selection in place. Background group refreshes retain heading and action widths. Summary and focused SSE refresh hints are coalesced without cancelling pagination. Ordinary text, reasoning, and tool presentation events update the live display without HTTP refetches. Usage events refresh usage/context; checkpoints refresh Thread detail so saved queries follow the new continuation; lifecycle events refresh operation/detail and activity lists; child events refresh child projections. Healthy SSE does not also poll operation or usage endpoints. Elapsed time is a local clock. Stream open/reset reconciles observations, with low-frequency foreground reconciliation while the summary connection is unavailable.

Conversation rows show title, activity, and attention-needed state. Running, waiting for a decision, and failed states remain distinguishable without opening every Thread. Each conversation row's secondary menu provides Rename, Share, Details, and Archive or Restore. These actions belong to that Thread, not to its Project's settings. Archive executes directly without confirmation, retains saved history, and honors the App's active-operation restriction and metadata version. Archiving the selected conversation opens the New draft with that conversation's Project selected; archiving another row does not change the current page. If the archived Thread owns an unresolved New draft, archiving detaches that draft to a fresh creation identity while retaining text and choices. Uploaded handles cannot cross Thread boundaries and remain unavailable markers requiring reattachment; unknown admission still requires outcome review. Archived conversations remain inspectable and restorable from the archive page; restoring removes the row from that page and makes it available in ordinary navigation. Failures remain visible without blind retries.

Application confirmations use the shared styled dialog surface, not native browser alert, confirm, or prompt calls. Potentially lossy draft disposal and uncertain-submission review keep their explicit confirmation; cancelling or dismissing these dialogs does not perform the action.

Selecting a different conversation is personal navigation. The browser retains each Thread's editing context without cancelling execution or causing collaborators to switch views. An update in another Thread marks its row rather than stealing focus.

## New Results in This Browser

A root Thread opened or started in this browser becomes followed. The first observed successful-completion version is its historical baseline, not a new-result alert; a newly created Thread starts at version zero. Local Send and decision submission wait for interest registration before admission so a fast first completion cannot become the baseline. A late first visit in another tab never raises an existing acknowledgement. Unopened collaborators' Threads do not become followed merely because they appear in navigation.

The server's [saved root completion marker](../03-local-storage-and-recovery.md#saved-root-completions) is the durable success authority. A version above this browser's acknowledged version means one unread result for that Thread. Multiple completions coalesce. Later running, suspended, failed, or cancelled work never clears an unseen success. This state is independent of transient notices, operation receipts, desktop permission, and navigation touch time.

Browser interest and acknowledgements use a small per-origin IndexedDB store keyed by Thread ID. Create-if-absent baseline registration and maximum-version acknowledgement are atomic across tabs; transaction completion, not individual request success, is the persistence boundary. Cross-tab messages are reread hints, not authoritative state. There is no bounded-interest eviction, server per-user read table, or notification-history log. Storage failures visibly disclose incomplete recovery without silently substituting localStorage or pretending an acknowledgement was saved. Clearing site data removes this browser's personal state.

Startup, reload, summary reconnect/reset, and foreground return reread browser state and reconcile followed roots through bounded batched identity lookup, independently of sidebar pages. Relevant summary events invalidate observations through the existing SSE connection. Requests coalesce and completion versions never regress. Failed refreshes retain cached reminders and offer retry. Reopening a closed browser recovers unread markers without replaying a pile of old toasts; closed-page push delivery is not promised.

An acknowledgement requires the saved transcript to be rendered in the visible conversation, the document to be visible and focused, and the actual scroll position to have reached the bottom. Selecting a route, receiving live output, or starting smooth scrolling is insufficient. The browser acknowledges exactly the transcript snapshot's `completion_version`, never a newer detail or lookup marker. Checkpoints after that completion retain its version even when the selected continuation changes.

Ordinary Project groups display Running, New results, and Recent sections without duplicate Threads. Unread inactive roots remain reachable outside loaded recent pages; active roots keep their independent new-result dot. A collapsed group retains its unread-Thread count. Existing touch sorting, recent-page cursors, search pagination, and selection remain unchanged. Archived roots do not contribute to ordinary groups or counts; their new-result dots remain available on the archive page. Row dots have the accessible label and tooltip New result and do not replace activity, failure, or decision icons.

## Task Notifications

The authenticated workbench consumes terminal root-operation notices from the existing App-wide summary SSE, independently of the currently selected page and focused token stream. Browser-local interest follows root conversations opened in this browser. Completed, failed, and suspended operations show an in-app notice with actual result/request/failure preview and an explicit Open conversation action. Completion banners are omitted for the currently open Thread; failure and input-needed notices remain visible. Reply previews combine prose and list items across paragraph breaks before applying their length bound, rather than stopping after an introductory line. Reading saved history, initial connection, and stream resets do not synthesize completion notices. Replayed receipt identities do not create duplicate notices. Child completion and explicit cancellation remain conversation activity rather than separate alerts.

Browser notification preference, browser permission, and background subscription are independent. The initial preference offers notifications: one persistent, non-modal permission toast appears after login until permission is granted or the user explicitly turns off reminders. Permission and first background subscription require an explicit button; existing granted permission does not silently opt a device into Web Push. Dismissing the browser request retains the toast; denial changes it to browser-settings guidance rather than repeated requests. Unsupported or insecure contexts explain unavailability. Settings → Notifications exposes the immediate browser-local preference, actual permission, background subscription state, enable/reconnect action, and test notification. Disabling notifications closes native notifications and removes the browser and server subscription on a best-effort basis. Failure of both removals remains explicit. It suppresses future permission prompts without disabling in-app notices or changing other browsers' preferences.

Native notifications show a shorter actual preview and may expose that text on the desktop or lock screen; Settings discloses this. Without a background subscription, automatic page-native delivery requires permission and a hidden or unfocused page; the explicit test remains available in the foreground. Same-origin tabs coordinate this fallback with Web Locks and a bounded receipt history where available. A subscribed browser suppresses page-native duplicates: its notification-only Service Worker always displays received pushes, including while the page is open. Receipt-based tags provide best-effort replacement, not exactly-once delivery. Clicking a notification focuses a window already at the exact target or opens a new same-origin window; it never reloads another page and discards its unsaved editors. The worker has no instance key and ordinary login still applies. Logout attempts subscription cleanup before disposing authenticated transport; access loss invalidates the local browser subscription where possible. Both close page-native notifications and unmount notification state. Failed cleanup leaves an explicit warning on the login screen to block notifications in browser site settings.

The WebUI App queues settled completed, failed, and suspended root-operation notices independently of SSE observers. Delivery uses the stored per-device subscription and most recent 256 opened root conversations; missing or archived roots are not notified. A bounded in-memory queue and bounded concurrent HTTPS requests isolate failures from Run settlement. The sender uses Web Push payload encryption and persisted VAPID identity, only supported browser push-service endpoints, no redirects, and at most two attempts for transient failures. Expired endpoints are removed. Subscription persistence and inactivity retention are owned by [local storage](../03-local-storage-and-recovery.md#browser-push-subscriptions).

Authenticated `GET /api/push/configuration`, `PUT /api/push/subscription`, `DELETE /api/push/subscriptions/{subscription_id}`, and `POST /api/push/subscriptions/{subscription_id}/test` follow the existing same-origin API boundary. Configuration exposes only the public VAPID key; subscriptions contain endpoint, public encryption key, auth secret, browser origin, and bounded Thread interests. Inputs cannot direct server requests to arbitrary Host-network URLs. The test uses the real push transport and reports provider acceptance, not device display. Page-native fallback tests distinguish browser request/shown/error events, likewise without promising an operating-system banner.

Closed-page push requires a running WebUI server, browser push-service reachability, and browser/OS permission. Browser force-stop, battery policy, disconnection, or notification settings can delay or prevent delivery. Queue loss on shutdown is acceptable; there is no durable push outbox, delivery ledger, or historical replay. Push does not change execution lifetime or the separate browser-local new-result markers.

## First-Use Wizard

The browser first-use flow follows [Setup and Environment Readiness](../06-setup-and-environment-readiness.md#browser-first-use). It uses a large, centered, viewport-bounded dialog over the subdued workbench on desktop and the full viewport on narrow screens. Three steps share one stable progress header, scrollable content region, and persistent Back/Continue/save footer: Connect, Choose a model, and Workspace. Step changes focus their heading; dismissal and first-conversation entry restore useful keyboard focus. The wizard uses the shared overlay and field primitives in both themes.

Subscription connection is inline and shares account operations with Accounts settings. Device authorization is the default; callback authorization is an explicit advanced option that explains server loopback reachability. The wizard presents verification URL, code/copy, waiting, success, cancellation, expiry, and retry without requiring a detour. API-key entry saves through the existing Host key API under a generated reference, with an explicit immediate-save explanation. Neither connection method treats browser identity as the owner of server credentials.

The Model step uses backend-owned release choices, reasoning/context defaults, and reviewed native-tool recommendations, with optional advanced controls. API connections expose provider, model ID, and applicable base URL instead of requiring raw route syntax. The Workspace step explains Full Control versus Sandbox, offers an optional existing server directory, and shows a concise summary with expandable generated files. Sandbox readiness is bound to every resolved preview path; failed or cancelled preparation never selects Full Control.

Save and start chatting explicitly publishes configuration, reconciles saved files, opens the first conversation once, and focuses its empty composer. It does not send a prompt or test the model. Connected account, saved configuration, prepared environment, and successful model request remain distinct observations. Unknown publication or conversation creation stays recoverable on refresh and never causes blind mutation replay.

## Participant Awareness

On first entry the browser generates a display name and remembers it as a local preference. The top-right header shows that name and opens editing; saving a nonempty replacement updates live presence and composer attribution, without rewriting existing saved attribution. This is a collaboration label, not an account or verified identity. The workbench exposes a compact participant directory showing reported current page and foreground, inactive, or disconnected/unknown participation. The current page shows its own participants rather than everyone with that Thread's draft open. The directory remains usable in Project settings and the configuration center without opening a conversation.

Separate tabs with the same display name remain distinguishable. A background tab can be shown as attached but is not labeled as confirmed current attention. Switching between Chat, a file, a diff, configuration, and a terminal updates the reported focused area without moving other users. Participants can explicitly open a collaborator's available page through ordinary navigation; it does not enable continuous following or synchronize scroll.

Same-page presence is an awareness indicator, not a blanket Edit permission or a claim that every surface uses CRDT. Chat retains its shared composer, saved output remains read-only, file changes use existing save rules, and terminal input uses explicit control ownership. SSE updates and refetches preserve the local focused area and do not recreate the editor's CRDT replica.

## Default Layout

| Region       | Default interaction                                                                                                        |
| ------------ | -------------------------------------------------------------------------------------------------------------------------- |
| Sidebar      | Projects and conversations, Overview, Settings, and footer participant/theme/session controls; a drawer on narrow screens  |
| Main area    | Chat remains the primary reading area with its shared composer                                                             |
| Right drawer | Files or Changes explorer and selected file/diff editor, closed until opened; file tabs stay inside the drawer             |
| Bottom panel | Resizable Host Terminal, closed until explicitly opened                                                                    |
| Header       | One compact conversation title with Files, Changes, and Terminal toggles plus the editable collaboration name at the right |

The application frame stays within the viewport. Conversation history, code, explorer contents, and Settings content scroll within their own available space rather than growing the document. Files and Changes share the right drawer; selecting a file or comparison opens its editor inside that drawer without replacing desktop Chat. Back returns to the explorer, and file tabs retain previously opened views. The drawer has a keyboard-accessible width separator and remembers its size locally; closing it returns focus to Chat without discarding private buffers. A small in-tab Project cache retains directory, file tabs, and selected terminal. File tabs identify full paths and dirty buffers; closing a tab retains its private buffer without saving or discarding it. Reading a file or comparison preserves the mounted explorer's filter and scroll. Files and Changes filter loaded paths only and explicitly disclose additional pages. Common source files receive syntax highlighting, with line wrap, go-to-line, and save shortcuts; this is not a full editor workspace. The header does not stack instance status, a global file-tab row, and a second conversation title. The browser document title follows the current conversation title with the suffix `a13n harness ui`; pages without a conversation use exactly `a13n harness ui`. The terminal is independently resizable/collapsible. Closing a panel closes the view, not its server-side terminal session or Agent Run.

Settings uses a dedicated content layout. It does not display Chat/Files/Changes/Terminal controls or native panes. Entering Settings detaches the selected terminal view without closing its session and retains private file/configuration drafts. Returning to the workbench restores retained tabs and automatically reattaches a previously visible terminal as a viewer, unless the participant explicitly disconnected it. A small bounded set of recent terminal screens remains in tab memory; evicted screens and server retention gaps do not imply recovered output.

On narrow screens, the right drawer or terminal temporarily takes the available work area rather than compressing simultaneous columns. Chat remains mounted, and closing the panel reveals it. Returning to Chat preserves the unsent draft and personal scroll. Desktop and narrow layouts expose the same operation outcomes and warnings.

## Conversation and Shared Composer

The transcript foregrounds prompts and Agent responses. Adjacent exploration calls, shell operations, web browsing, and file modifications form default-collapsed activity summaries such as **Explored**, **Ran commands**, **Browsed the web**, and **File changes**. Adjacent task/note operations and subagent operations use the same disclosure pattern under **Tasks & notes** and **Subagents**, with action-oriented operation names. Each group contains at most 16 calls. Visible prose, input, other activity, and category changes end a group; grouping never reorders or deletes source parts. Expanding a group exposes each operation's semantic description and details without another per-call disclosure. Routine result-received and Failed labels do not occupy collapsed headers. Failures remain inspectable in expanded operation details, including exact errors, exit codes, and stderr; pending, denied, interrupted, retry, and terminal-without-result states use quiet header text. Tool summaries use smaller, lighter type than conversation prose. Provider-exposed Reasoning opens by default and uses the same safe Markdown renderer and readable type scale as Agent text; users can collapse it. Adjacent reasoning parts, including loaded saved/live boundaries, share one disclosure without combining their Markdown documents or crossing intervening prose/tools.

Successful `ask_user_question` results show each question's short header, full question text, and recorded answer by default, including multiple selections and free text. Selected answers include the matching original option descriptions when available; free text and answers without matching options remain unchanged. A collapsed disclosure retains all original questions, options, and raw arguments/results. General responses remain visible; unavailable or unsuccessful results retain ordinary tool status rather than appearing answered. Live and saved transcripts use the same presentation.

Loaded saved calls and their following results are paired before grouping, across loaded entry boundaries. Provider-native and local function calls have separate identities. A result whose call is outside the loaded page remains inspectable. Native provider search snapshots update one correlated tool row, retain final arguments and provider identity, and use the same browsing summaries in live and saved views. Arguments completion does not establish execution completion.

A **File changes** group opens the observed before/after diff, including when a later tool result fails, and provides the existing Host file lookup alongside the operation. It is associated only by exact tool-call identity; proxy inner calls with independent identities remain separate observations. Root edit evidence retained under the [continuation storage contract](../03-local-storage-and-recovery.md#tool-presentation-evidence) survives the switch to saved history and reload. Omitted evidence is explicitly identified rather than reconstructed. Older historical edit and multi-edit replacement arguments display fragment diffs labeled as requested input, never represented as applied changes. Write shows the complete recorded after-content when available, otherwise the complete requested write/append content with that distinction. Declared code languages and recognizable file extensions receive static syntax highlighting; unknown or oversized code remains exact plain text. Applied edit diffs render all retained before/after content, with a full replacement diff when bounded minimal-diff computation cannot finish. The expanded detail block has a bounded height and internal scrolling rather than omitting large changes. Older omission markers remain explicit.

An absolute path can offer an explicit **Open on host** lookup when native files are enabled. This human action looks up the same path spelling on the WebUI server/container; it does not map Environment mounts or assert that a remote file is the Host file. It opens syntax-highlighted current Host content or the existing private editor buffer, not recorded historical bytes. Relative paths and Environment aliases are not automatically resolved.

Cross-root collaboration tools have action-oriented summaries for discovery, creation, continuation, messages, and steering. A known target Thread is an inline same-instance link outside the disclosure trigger; it remains usable without expanding raw arguments, including when creation succeeded but Run admission failed. Discovery results expose loaded conversation and Project links and compact Agent/Model identities. Clicking a link is personal navigation, not a new submission or a change of execution target. Admission/steer acceptance is not rendered as completion or saved delivery.

A compact Tasks, Notes, Subagents, and Processes strip sits above the composer. Its floating inspectors preserve the current conversation, shared draft, and reading position. Tasks foreground active work, show loaded completion counts, and expose status, ownership, and dependencies on expansion. The focused task snapshot and versioned root changes supply the current projection; stale task versions and child task changes cannot replace root task state. Unavailable projections and bounded omissions are explicit. Notes are identified as saved continuation notes, not an asserted live or durable view of unsaved changes.

Processes is a read-only, bounded projection of Run-scoped Shell observations from the focused root lineage, not a Host process inventory or a saved execution registry. Only returned running handles count as background work. It displays at most 16 of 128 retained observations with command, last observed status, process/Run identity, and known exit code; nonzero exits are failures. Completion cannot be overwritten by an earlier running tool result. Run boundaries and lost observation mark unfinished handles unavailable, not exited. Gaps and retention omissions remain explicit. Reload/reset rebuilds only from available live replay, never saved transcripts. Output remains in tool details and no process-control action is introduced.

The composer offers inline `$name` Skill completion over the existing App catalog, including the effective defaults of a not-yet-created conversation. Suggestions show descriptions; Up/Down select, Enter or Tab inserts ordinary editable text, and Escape dismisses without sending. An open completion consumes Enter instead of submitting. Send and steering attach deduplicated references for exact whitespace-delimited names recognized in the captured authored text; unknown dollar tokens remain ordinary text. The App validates references against the next-Run or active pinned catalog. Catalog failure preserves editable input, and an asynchronous lookup cannot submit after navigation cancels preparation. Neither this feature nor Processes adds slash commands to the browser.

Child execution appears as inspectable subordinate activity, not an unrelated root conversation. Subagents opens a paginated overview with one human-readable inspection panel per execution: default-collapsed tool groups, observed reasoning/text, and the latest saved complete result. It does not display raw events or a separate saved-output/comments disclosure. Current observed suffixes and explicitly labeled bounded activity previews remain distinct from saved results; none promises a complete historical tool replay. The latest complete result remains available through later failed/resumed segments, and long results load exact-source pages without a second storage truncation. Completion/checkpoint changes refresh an opened view. Child controls retain exact parent/execution targeting and unknown-acknowledgement safeguards. Pending questions and approvals remain adjacent to the relevant execution.

The composer uses a compact, fixed-height editor; longer prompts scroll within it instead of moving the surrounding layout. On phones it starts at one-line height with attachment, options, and Send controls; additional selectors open explicitly. The workbench fits the visible viewport above the software keyboard, including viewport panning and safe-area spacing. Resizing changes layout only, never the editor, shared CRDT replica, input composition, or presence connection. Keyboard and draft-lifetime guidance remains accessible without a separate help icon; actionable warnings remain visible. The composer shows collaborator cursors and selected context. Normal synchronization, Send receipts, and accepted Steer receipts do not occupy the default layout. Local input appears immediately without transient preparing, sending, accepted, or committed captions; successful acknowledgement does not add a banner or change the message's geometry. Acceptance remains distinct from confirmed application and saved history even though those internal transitions are not announced as prose. Short connection handshakes remain quiet; sustained synchronization delays, disconnection, rejection, and uncertain outcomes remain visible. The attachment and Send controls expose acquisition and keyboard hints without a separate help button. The editor exposes draft-lifetime guidance to assistive technology. Submitted messages use the neutral User label rather than the transport term Input. Native media attached by `view` or `read_media` is model-only supplemental content, marked `display: false` by its producer; its saved `UserPromptPart` container does not make it authored user input. Genuine user/steering media remains visible, including in mixed requests. Older unmarked media is not hidden by a shape-based heuristic. Synchronization is not a durable save. Participants can change their display name without creating an account. Names/colors provide interaction context, not verified identity or private workspaces.

Enter submits and Shift+Enter inserts a newline. Ctrl+Enter and Cmd+Enter remain submission shortcuts, as does the explicit Send button; IME composition never triggers submission. Submission requires the initiating browser's pending edits to synchronize; offline input remains editable but cannot start a Run. Routine edit acknowledgements do not toggle Send/Steer styling: explicit submission waits for synchronization while blocking duplicate sends, then captures input using the existing safeguards.

While submission is being resolved, the initiating browser shows Submitting and suppresses repeated sends. On confirmed acceptance, all participants see the same submitted snapshot and execution. A normal completed cutover presents an empty next prompt when there are no uncaptured edits. Edits outside the submitted snapshot remain recoverable under the collaboration contract; the UI never claims success by blindly clearing the editor. Rejected input stays editable with its error. An uncertain result offers status reconciliation, not an unqualified Retry button that starts a second operation. A confirmed failed root operation offers **Retry** when ordinary submission is available. It submits the fixed prompt `Continue completing the previous task.` as a new turn, preserving the shared composer text and attachments. It neither restores the failed Run nor repairs or replays history. Pending or uncertain submission disables repeated Retry.

A lightweight status row below the composer shows context occupancy from the latest reported root request, recorded root-agent model cost, cache-read / (input + output) rate matching the CLI, and current/latest operation elapsed time. Focused usage events update context immediately using request-local input plus output tokens, not cumulative Run usage or descendant usage; saved usage queries reconcile on reconnect. Time advances once per second while preparing or running and stops at the observed completion timestamp. Preparation uses the receipt's submission timestamp until a start timestamp exists. Missing observations remain unavailable rather than zero. Partial known cost subtotals are marked, and expanded details explain scope and refresh failures.

The composer has one bottom-right action icon with an accessible action label. With input and no active operation it sends a new prompt; with input during execution it steers the exact current receipt when supported. With no input during an active operation it becomes Stop. Pending attachments block submission and are still input, so they cannot accidentally turn that action into Stop. Enter, Ctrl+Enter, or Cmd+Enter submits or steers valid input but never stops an empty composer. Editing creates no queue or automatic submission. Both submission forms preserve the shared-draft snapshot and uncaptured-edit guarantees. No duplicate Running or Stop control appears in the conversation header.

New output smoothly follows the bottom only while the reader is following; upward scrolling or direct interaction interrupts the animation, and reaching the actual bottom or choosing New output resumes it. Content and reader-viewport resizing keep an active follower exactly at the bottom, including when the composer or status bars change height. Restored manual reading positions remain independent. Reduced-motion preferences use immediate positioning. Scrolling near the top automatically loads earlier saved messages while preserving the reading anchor. Short pages load until the viewport can scroll or history ends; failures offer an explicit retry rather than a repeated request loop. System/request context, stream diagnostics, and ordinary execution-completed notices do not appear in the transcript. Handoff and compaction summaries use distinct, softly colored, default-collapsed Summary and Compact Summary disclosures, not User bubbles. The collapsed header exposes lifecycle information and a short plain-text preview of the body, omitting generic summary headings. Expanding renders the complete available summary as one Markdown body with the ordinary message renderer. An operation keeps its disclosure identity and open state through live-to-saved cutover. Summarization and compaction append timeline content without clearing earlier messages, reordering retained input, or resetting the reader's scroll position. Recognition uses owned metadata rather than headings. Internal replacement reminders and model-recovery input remain hidden. Scheduled model recovery shows a neutral status with its retry count and retains the latest outcome after progress resumes or the Run ends, rather than fading away. Live-update reconnections likewise retain their count and restored state for the current open conversation view. Model recovery and the live-update connection remain separately labeled; neither asserts successful saving. Terminal failures instead show a concise reason in the output area, with longer error details collapsed, using the exact current operation or Run error observation. Running/preparing sidebar icons rotate gently; waiting and terminal states do not, and reduced-motion preferences disable the animation. Native background-process and async-child notifications are collapsed system activity based on canonical input metadata, never user bubbles or text-pattern guesses.

A new conversation retains its composer during creation, attachment upload, and admission, then opens the created Thread without waiting for detail or history reads. The conversation frame retains local input and its next-message composer while detail, history, and focused output load. An initial focused snapshot can supply the first detail and operation observation; a slower initial read cannot roll it back. Header and navigation titles may use the retained local input as a presentation-only fallback until the server supplies a title or excerpt. Sidebar rows keep their display identity when moving from active to recent or joining a refreshed page; the selected detail can update its row before a slower activity-list refresh without replacing pagination. Retained images in the transcript and composer open a viewport-sized preview on activation, initially fitting the entire image, with actual-size zoom, scrolling, download, and keyboard dismissal. A failed follow-up read remains on the created Thread with a read-only retry; it never changes an accepted input into a rejected one or replays admission.

When a request checkpoint advances saved history during execution, the browser suppresses only the live prefix identified by that checkpoint marker after the matching history has loaded. ## Terminal Interaction

Open Terminal lists only sessions associated with the selected conversation's Project. New terminal starts in the currently browsed directory and carries the selected Project ID; Files also offers Open terminal here for a directory, creating a new session rather than sending a shell command to an existing one. Without a Project and configured root, creation is unavailable. Switching Projects changes the visible session list and detaches the old view without closing its sessions, sending commands, changing their working directories, or claiming control. A creation completing after navigation cannot select its old-Project session in the new Project. Existing unassociated sessions remain available through the native API, not through another Project's list. Terminal links require the matching Project context; unavailable targets explain that requirement and do not publish terminal page focus. Starting a session displays its server/container location and initial directory. Terminal tabs have useful titles and an active input-controller indicator. Collapsing the panel does not stop sessions.

The creating browser requests control once on the new terminal's first authenticated frame when it has no controller, then focuses input only after server confirmation. It does not take over from a participant who already acquired control, and reconnecting never repeats this creation intent. A participant viewing another person's terminal sees read-only output and a Take control or Take over input action. Activating it transfers input control through the App, visibly updates both participants, and only enables keyboard input after confirmation of ownership. Losing control leaves the old viewer attached to output. It does not inject partially typed browser input. Viewers may open separate terminal sessions instead of taking over.

Disconnect shows a disconnected state rather than an apparently usable prompt. Reconnect restores available output and discloses gaps; it never repeats keystrokes. End session is distinct from closing its view and warns that it affects the shared process. Unsupported native PTY remains explicitly unavailable.

Terminal search operates on retained screen output, with previous/next matches; Ctrl/Cmd+F opens it without intercepting shell control sequences such as Ctrl+C. Copy selection leaves terminal input unchanged. HTTP links open separately; deterministic absolute path:line references open Host files, without guessing the shell's current directory or ambiguous wrapped/wide-character positions. ## Empty, Disabled, and Failure States

| Situation                                     | User-facing behavior                                                                                                                                      |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Computer sharing disabled                     | Hide active Files/Changes/Terminal controls and explain the startup option in instance information; no misleading Enable button without process authority |
| Missing/invalid model or extension            | Link the blocked conversation to its configuration diagnostic; preserve its prompt                                                                        |
| API key rejected                              | Request a valid key while distinguishing access failure from lost project data; do not repeat mutations after login                                       |
| Browser offline                               | Mark presence/output as disconnected, preserve recoverable local work, disable execution submissions                                                      |
| Draft synchronization failed                  | Show unsynchronized state and retain recoverable text; do not claim server persistence                                                                    |
| File changed externally                       | Preserve the local buffer and offer comparison/reload rather than silent overwrite                                                                        |
| Repository inspection failed                  | Explain unavailable Git state, not a clean checkout                                                                                                       |
| Run failed                                    | Show the owning operation error and retained evidence; keep deliberate recovery separate from retrying unknown effects                                    |
| Server restarted                              | Reload continuation and committed comments, disclose lost shared drafts and live authority, and never automatically resubmit input or recreate a terminal |
| Comment source or selected target unavailable | Preserve published comments or the local unpublished draft, explain the unavailable/stale target, and never silently attach to different output           |

## Verifiable Flows

01. A person opens a configured Project, starts a conversation, and submits without entering the configuration center.
02. Two browsers coedit one prompt, observe one accepted submission, and retain any uncaptured edits.
03. One collaborator reads a file/diff while another stays in Chat; adding context is visible to both, navigation is not synchronized.
04. A busy Thread permits next-prompt editing but does not silently queue or send it.
05. Applying Project defaults previews a bounded change and leaves an active Run's capture unchanged.
06. Native Files and Terminal remain on the server when the Agent uses E2B.
07. Terminal takeover changes input authority without disconnecting other viewers or replaying input.
08. Disabled sharing, missing Git, unsupported PTY, and authentication failures have distinct recovery paths.
09. Two people can see whether they are on the same Chat, file, or configuration page without being navigated there by each other; multiple/background tabs are distinguishable.
10. A participant comments on saved output while another Run executes; the comment survives reconnect, restart, and a later continuation without entering model history.
11. Streaming output cannot receive a published comment, and selecting a rendered range never silently anchors to different source text.
12. A lost comment acknowledgement is reconciled without a duplicate post; a missed live hint is repaired by an ordinary comment query.
