# Devices and Environment Bindings

## Design Position

Harness UI stores Device connections and Project/Thread working-directory selections. Each Run captures its bindings and supplies Host-owned Environment sources implementing `ensure_ready()`, which return fixed-target connectors for fresh execution scopes. EIP Sessions are internal execution resources, not user-managed Project or Thread resources.

[Projects and Threads](04-projects-threads-and-environments.md) owns local roots, sticky configuration and admission. [EIP](../a13n-envd/README.md) owns Device discovery, Sessions and resource cleanup.

## Devices

`devices/*.yaml` uses the ordinary accepted configuration generation. Each resource contains a stable Host Device ID, expected envd `device_id`, display name, transport configuration and authentication. Manually configured authentication references a Host environment variable or saved API key. Paired authentication stores only the daemon credential digest and its revocation state and requires reverse WebSocket transport. HTTP names an origin; reverse WebSocket names an expected attachment identity. Raw credentials, sockets, Session selectors and observed generations are not resource configuration.

### Self-registration

The App implements the [Host pairing protocol](../a13n-harness/08b-environment-providers.md#host-pairing). Only `POST /api/envd/pair` admits a daemon's narrow pairing credential without browser authentication. Pending requests grant no Device access and remain bounded, expiring process-local state. Their safe challenge is visible to authenticated users. Approval publishes an ordinary Device resource through validated configuration mutation; retried approval or polling resolves the approved resource, including after App restart. A native identity already registered with a different credential is a conflict, not implicit credential replacement.

The approved credential authenticates only that Device's reverse WebSocket attachment. Human management APIs retain normal browser authentication. Device discovery and Run preparation use the same digest-scoped connection without requiring recoverable credential bytes. Each daemon process selects one Host; independent envd instances on one physical machine have independent registration identities.

**Revoke** persists revoked trust before retiring its live connection. It denies later attachment and use through captured configurations, including after restart, and does not delete remote files, Project/Thread selections or Run history. Revocation is distinct from forgetting local configuration. A failed or revoked credential never triggers automatic replacement or approval.

Registration and connection checks are trusted Host actions. Catalog loading performs no connection or filesystem I/O. Online status and Device info are runtime observations. Missing or unavailable Devices never fall back to local execution. Paths use the selected Device's path format, not the UI server's filesystem.

## Directory Selection

The App obtains Device info, including the resolved default working directory and directory-discovery capability, without opening a Session. WebUI calls the App's authenticated API; the App invokes EIP `device.describe` and `directory.list`. Directory browsing has finite request bounds and ends on cancellation or timeout without retaining a Session.

Users select the default directory, enter a known path, or browse when discovery is enabled. Disabled discovery hides browsing but preserves default and explicit-path selection. A missing/inaccessible directory produces a visible failure, never silent replacement or creation. Directory selection creates no Run and reserves no future filesystem availability.

The accepted Project/Thread selection stores an explicit Device and working directory. It does not retain a symbolic "use current Device default" choice. Later daemon-default changes do not redirect existing selections. Users can explicitly select the new default.

## Bindings and Defaults

A Thread retains `environment_profile_id` for local Project roots and Thread files. Its ordered `environment_bindings` collection contains `device_id`, `working_directory`, a unique Run-local alias, an action ceiling, optional reference-only Session `egress`, and an optional `expected_boundary` requirement. Selecting a Device and path requires no separate Environment-definition resource.

`default_environment` names one alias in the complete mount set. Local-only selections retain their workspace or projectless Thread-files default. Remote-only and mixed sets record the default explicitly. Local workspace and Host auxiliary aliases are reserved against collision. An explicit empty collection removes added bindings; a Run-only local-profile override preserves them.

Project creation defaults and Thread patches use existing precedence and expected-version rules. Deferred-response admission retains the selected continuation's bindings and default unless explicitly patched. A Project may have no local roots when it selects remote bindings; CLI cwd matching considers only actual local roots. Projectless Threads may also use a remote default while retaining Host-managed Thread files.

A working directory supplies relative-path and omitted-cwd defaults. File operations may address other paths on the same Device under the action ceiling, native permissions and Device Sandbox grants. Selecting a working directory creates no filesystem sandbox.

## Admission and Execution

Before returning an admission receipt or scheduling preparation, the App captures:

- accepted resource generation and Thread configuration version;
- Project roots and local profile;
- selected Device identities and connection configurations without credential bytes;
- explicit working directories, aliases, effective action ceilings and default;
- Session destinations, credential source references and expected Device boundaries, never resolved secret values;
- selected Run Extensions.

Preparation uses only captured selections. Current credentials resolve through captured credential references at use time. Each envd binding verifies the captured boundary requirement and opens a fresh Session with its captured working directory and freshly resolved egress policy. Repeated operations reuse that Session within the same execution owner. Concurrent Runs, independent children and identical directory paths do not share initialized Sessions.

Short same-runtime reattachment may reuse the same live Session and generation. Expired Sessions, replacement execution owners and application restarts require fresh Sessions; native handles and uncertain effects are not recovered or replayed. Session close preserves the shared Device connection and working files.

New children inherit the parent's captured selections; existing child Threads resume from their own selections. Remote adapters use virtual aggregate routes, not Host-path-preserving routing. Skills and file guidance use the selected Environment. Configuration and user-Skill mounts stay Host-only. Remote shell execution does not implicitly receive Thread files; cross-mount copying uses Environment file operations.

## State and Connection Ownership

Environment-state lookup/publication uses the Thread, alias, normalized Provider configuration, Device identity/backend and working directory. Presentation-only changes do not affect binding identity. Local roots retain their existing equivalent key.

Device connections are App-owned process-local resources. Session selectors, daemon generations, keepalive tasks and native process/output references never enter persisted continuation. App shutdown closes owned Sessions before local daemons or connection managers. It does not stop external daemon infrastructure.

## Human-facing Resource Monitoring

The WebUI-mode App owns one bounded in-memory collector over configured remote Devices and already allocated local Envd runtimes. It borrows authenticated HTTP, reverse WebSocket and existing stdio connections without opening Sessions. Monitoring never resolves an executable, downloads, starts or restarts a local daemon. Direct and other non-Envd providers have no Envd metrics. Built-in local Sandbox, Envd and Desktop launches enable the daemon sampler at a 60-second interval. Root `envd.monitoring_interval_seconds` selects 10–60 seconds for App collection and built-in local samplers; it is captured at App startup and changes require restart. The Harness SDK launch default remains opt-in. Custom launch recipes control their own monitoring configuration.

The collector retains at most 64 Device targets. Each target has 60 minute slots for average and peak system CPU utilization, system memory used (total minus available), selected-cgroup memory, and TCP/UDP socket counts. Separate fixed rings retain receive/transmit byte rates for at most 64 interfaces and read/write byte and operation rates for at most 64 disks. Active sources keep their slots; new sources replace the least recently observed absent source. Excess rate sources are counted while all bounded native counters remain available in the latest sample. Numeric history stays below 42 MiB across all targets. Latest samples and system descriptors are each limited to 128 KiB, with at most 16 named and 16 discovered filesystems. Excess targets are counted and omitted. Each collection round has at most four requests in flight, a five-second per-target deadline, and a configured pause between rounds (60 seconds by default). App shutdown cancels collection before closing carriers. Observation requests have a separate single-slot client admission lane: an unanswered request keeps that slot until its reply or carrier closure, so polling deadlines cannot exhaust Session-open capacity. Monitoring credential reads are cancellable and permit at most one outstanding filesystem read, independent of execution credential access. Native sampler work is sequential; daemon resource reads skip contended locks and leave unavailable values absent. CLI-mode Apps start no monitoring loop.

A generation-local sequence contributes once. The Host assigns a sample to its receive wall-clock minute minus the reported monotonic sample age. Unavailable gauges remain absent; real zero remains zero. Samples older than the greater of 30 seconds and three daemon sampling intervals remain visible as stale but do not enter aggregates. Device generation changes begin a new chart segment and clear resource rate baselines and histories; missing minutes remain gaps. Rates use receive monotonic time minus reported sample age, distinct sample sequences, and one native source identity. Source identity changes discard that source's old history. Counter decreases, non-increasing time, missing fields, unavailable samples and gaps longer than the freshness window reset baselines. Cached-age and rate-gap tolerances also include three App collection intervals so a slow Host poll does not invalidate a healthy fast daemon. Recovery requires two valid observations rather than bridging an outage. Reconfiguration, removal and revocation discard that target's history. Process restart clears all monitoring history. Metrics never enter SQLite, Run checkpoints or Agent tools.

Authenticated `GET /api/environment-monitoring` returns the bounded catalog, latest observations and omitted count; `GET /api/environment-monitoring/{target_id}` returns one target and its minute history. These queries read App memory, including the Device inventory published after configuration acceptance, without configuration-storage or remote I/O. A configured remote Device uses its Host resource identity; each local daemon has a process-local identity and root summary. HTTP collection refreshes the descriptor so a replacement daemon can be reacquired through the existing runtime. Observations distinguish waiting, not started, monitoring disabled, ready, stale, offline and revoked. Last observations can remain visible offline, with their continuing age. Static system information is independent of sampler availability.

The workbench's Environment monitor is App-wide and independent of the current Thread's editable next-Run selection and native computer-sharing switches. It displays one entry per observed Device, not one per directory or policy group. Charts show Device-visible system usage and the explicitly selected cgroup; neither is attributed to a Run or summed across Devices. Visible category buttons group system overview, network/sockets, storage/filesystems and Envd-owned usage. Receive/transmit and disk read/write byte/operation charts are shown side by side within their categories; static identity and diagnostic counters are folded details. Native memory details, per-interface/disk counters, TCP state counts, bounded filesystem discovery and daemon counts preserve platform availability. Network and disk rates are selected per source; stacked interfaces/disks and shared APFS capacities are never summed. Pressure and optional native timing counters remain latest-only detail. Opening or closing the panel affects browser query polling, not the App collector's lifetime. The panel defaults to a rolling 15-minute window and 60-second browser refresh, pause and manual refresh. Shared time presets extend to one hour; dragging a chart or using zoom controls selects a fixed historical window across all charts. Refresh preserves that window until the user selects a relative preset or returns to live. Hover and keyboard inspection share a minute cursor across charts. Smooth lines pass through the recorded minute aggregates without overshooting adjacent values; missing minutes and generation changes remain gaps. Zoom does not increase the retained minute resolution.

## WebUI Behavior

Project, Thread and Composer surfaces share one Environment-and-directory selection model, editor and summary. The product hierarchy is Project working context, execution Environment, then working directories. One local Environment group contains the local profile and all local roots; the profile also controls Thread files. A remote Environment group contains one Device and one execution policy, with one or more working directories. Remote bindings with equal Device identity, action ceilings, Session egress and expected boundary requirements belong to the same group. Different policies remain separate groups even on the same Device. Omitted legacy action ceilings retain their existing meaning and are distinct from explicit Full Control. Grouping preserves stored binding order and policy values.

Directory counts and Environment counts are distinct. A local-only selection with two roots reads **Local · 2 directories**. Mixed and remote-only summaries count selected working Environment groups and directories; auxiliary mounts and local Thread files do not increase those working Environment counts. Local mode remains visible without roots because it controls Thread files. Internal mount aliases, execution scopes and EIP Sessions are routing and lifecycle details rather than user-facing Environment identities.

Project saves affect new Threads unless explicitly applied to an existing Thread; Thread saves are sticky; Composer overrides remain private to the tab until reset. Editing only the Project default preserves an unspecified binding collection. Editing paths preserves each binding's existing policy values. Explicit group-level Device or action changes apply to every directory in that group. Added directories inherit the group's policy, including egress and boundary requirements. Removing a selected directory, including an automatically selected first local root, requires a replacement default rather than silently retargeting an indexed alias.

**Add environment** selects an existing Device or opens **Connect new Device** inline, then chooses allowed actions and one or more working directories. **Add directory** extends an existing Environment with the same Device and policy. Device names and directory paths lead the presentation; directory aliases are generated automatically and editable under advanced routing. **Default working directory** is a shared selection outside individual Environment groups and uses readable Device names and paths; aliases disambiguate otherwise identical choices. Removing the last directory removes its remote working Environment group, not the Device registration. The surface exposes no Session creation, reuse or cleanup controls.

These groups are a lossless editing projection of existing local roots and remote directory bindings, not new persisted resources. Project YAML, Thread configuration, captured Runs, default aliases and per-mount execution ownership retain their existing schemas and semantics. Grouped editing requires no data migration or historical rewrite.

The shared Connect Device wizard is also available in Settings. It displays terminal-specific commands, installation and foreground-process prerequisites, reachable-origin requirements, explicit shell execution opt-in via `A13N_ENVD_FULL_CONTROL=1`, and an independent advanced desktop opt-in. The wizard shows pending verification challenges and requires explicit approval of the matching terminal code. The approval response's Host Device ID selects the subsequent Device-info observation; disappearance from the pending list never proves approval. The wizard waits for an available Device before returning it to the directory picker. Device registration is global and immediate, while the binding stays in the enclosing draft until saved. Closing before approval does not reject a request; closing after approval does not remove registration. Reconnection reuses identity and credentials, but saved Host connections do not save all daemon launch settings.

The browser generates the connect command from its current page origin; no separate server URL configuration is required by the wizard. The address must be reachable from the Device. Pairing responses use root-relative approval and connection paths, resolved by the daemon against its paired Host URL under the [Host pairing contract](../a13n-harness/08b-environment-providers.md#host-pairing). Reverse-proxy internal addresses do not determine the daemon's connection authority. The [listener boundary](05-runtime-subagents-and-surfaces.md#http-startup-and-access) independently controls admitted request addresses and authentication.

Edits use resource-save and expected-version Thread commands. Active Runs display captured selections separately from next-Run settings. Device online status and per-binding readiness remain distinct; a directory failure does not make the Device offline. Browser clients receive neither daemon credentials nor EIP resource selectors.

**Remove environment** edits the Project or Thread selection without contacting the Device. Removing the selected default requires an explicit replacement from the remaining working mounts in the same save. **Forget** in Settings removes a user-owned Device connection or local Environment profile through ordinary configuration-source deletion; remaining configuration references must be repaired first. It does not delete remote files or infrastructure, close execution-owned Sessions, cascade into Thread selections, or rewrite captured Runs and history. A Thread retaining a missing resource remains inspectable and supports an explicit valid replacement before its next Run.

### Desktop Access and Screenshots

**Allowed actions** offers **Read only** followed by **Full control**, with **Full control** selected for new bindings. Read only permits file observation without mutation, execution or desktop access. Full control stores an explicit ceiling containing all Environment actions, including desktop observation and control; separate desktop and file/execution bindings are unnecessary. The editor recognizes exact presets when reopening a binding. Other existing ceilings, including legacy omitted ceilings, remain unchanged unless the user selects a replacement; they are not silently widened or presented as Full control. Omitted ceilings in configuration retain legacy file/execution permissions.

Full control authorizes the binding's computer actions but does not enable daemon computer use or grant operating-system desktop access. Device pairing and connectivity alone do not authorize model computer tools. The selected Agent still needs Dynamic Environment tools and an image-capable model to use screenshots. The Full control description explains that desktop effects extend beyond the working directory and screenshots may reach the model and conversation history.

Computer screenshot tool returns reach the model as direct image content. The App independently stages a display copy in the owning root or child Thread's bounded scratch storage and correlates metadata to the native tool-call ID. Live events and saved transcript parts expose attachment metadata, never embedded image bytes or a synthetic user message. WebUI reads bytes through the existing authenticated Thread attachment endpoint and offers image preview. Scratch expiry or retention failure does not alter the model result, replay capture/input or substitute a new desktop image. The display copy follows Thread-files scratch retention rather than promising permanent history media; model continuation content retains its existing separate persistence semantics.
