# Setup and Environment Readiness

## Design Position

Harness UI offers a guided first-use workflow before asking a new user to author configuration manually. Setup selects usable Models and Agents, a default Agent and an Environment mode, with an optional explicitly selected Project, then publishes ordinary human-editable resource files. It creates no private alternate configuration, copied credential store, daemon, or execution queue.

`HarnessUiApp` owns credential-free discovery, starter composition, validation, and explicit publication. The standalone terminal workflow follows [Interactive CLI](07-interactive-cli.md). An unconfigured launch opens it automatically before full-terminal chat; `a13n-harness-ui setup` explicitly reopens it and returns to the command shell when finished. Chat has no setup command or setup mode. Existing valid installations are not rewritten or forced through setup after an upgrade.

## Discovery and Choice

Discovery is bounded and makes no provider requests. Copilot may persist its initial nonsecret account/source binding as defined by the account-store owner. It inspects accepted resources, default references, the launch directory, and the supported Codex, Grok, Copilot, and ChatGPT account statuses under [Model Authentication](02a-model-authentication-and-account-stores.md). It does not print, return, copy, refresh, or exchange credentials and never starts login, a model request, or envd merely to populate choices.

An account projection distinguishes available, missing, unsupported, and invalid state with safe guidance. An expiring credential with a refresh grant can be offered for reuse; discovery does not promise a successful provider request. One provider's absent or malformed store must not prevent configuring the other provider or selecting an already configured Agent.

The normal terminal subscription workflow selects a connection, a model, optional Agent tools through a preselected multi-choice step, and execution permissions. Completing the final question authorizes publication; there is no separate confirmation screen. The App still constructs and validates a preview before applying it. Reviewed context, reasoning, shell-review, and subagent defaults avoid mandatory fine-tuning questions; explicit `setup --advanced` exposes customization. Setup does not bind the invocation directory or publish a default Project. The terminal selects its cwd Project only when execution needs one; setup is not a Project management step. Full Control does not prepare a runtime. Explicit Sandbox publication requires successful preflight for every explicitly selected Project root, or the App's staging directory when setup selects no Project. The preview's `project_paths` reports these readiness targets; a staging probe does not create a Project or become a conversation workspace. Cancelling before publication leaves selected resource files untouched and does not mount chat.

The underlying setup API accepts one optional Model recipe containing ordinary `route`, `authentication`, `settings`, `model_configuration`, and `model_characteristics` fields. It can initialize an unconfigured Agent when the recipe is omitted. An Agent without a Model is valid configuration but cannot execute. Setup, Add Model, and Add Agent share this recipe contract rather than separate subscription and API-key request shapes. Each operation selects one connection and never treats missing credentials as a reason to substitute another connection.

The terminal labels existing compatible accounts and can preselect an available provider for the user's confirmation. Selecting an available account, including one requiring refresh with a refresh grant, needs no reauthentication; Copilot additionally offers explicit source/account reselection. Missing or invalid accounts offer their supported authorization, recheck, and configure-later actions. ChatGPT uses full callback URL paste first in the terminal and as a browser fallback; other providers retain device/browser choices. The terminal uses the same App login sessions as the browser, not a second OAuth implementation. Discovery never initiates authorization. A pending login can be resumed; another provider's active login is not silently cancelled. Cancelling waits for the actual login outcome and retains completed account writes. Discovery and account availability do not verify model entitlement.

Subscription authorization and hidden API-key storage are independent explicit operations under [Model Authentication](02a-model-authentication-and-account-stores.md). The external login CLI supports device and browser authorization with the callback reachability distinction. Setup accepts a stored-key reference, an environment-variable name, or a new API key through a hidden credential field. The field states that entering a new key immediately saves it under a fresh Host-local reference; the wizard and configuration retain only that reference. Cancelling setup does not undo a completed credential operation.

## Shared Model Authoring

One App-owned authoring contract supplies release-owned connection choices, settings recommendations, Model recipe preparation, and a bounded public directory. Authenticated HTTP exposes `GET /api/models/choices`, `GET /api/models/catalog`, `POST /api/models/options`, and `POST /api/models/prepare`. Options accept a connection ID, model ID, and optional endpoint; prepare additionally accepts authentication, a preset, and explicit native mappings. Preparation returns an ordinary Model recipe and never saves it. Setup status supplies generic defaults; setup preview/apply accept the same single recipe rather than connection-specific fields. Native-tool option descriptors reuse the Agent tool policy owner, with ordinary capability templates for parameter-free tools and explicit advanced configuration for parameterized tools. Connection IDs identify creation recipes, not persisted Provider resources. Each subscription connection declares its account provider, display label, supported login methods, source-selection capability, and explicit model-discovery capability in the same backend description. Browser account cards and terminal repair choices consume that description; unsupported login methods are rejected before creating a login session. ChatGPT subscription, Codex subscription, Grok subscription, Copilot subscription, supported API protocols, and custom HTTP endpoints remain distinct choices. Both clients use the same rules; conversations select saved Model resources, never unsaved directory entries.

The public directory is fetched by the backend and used only for API-model suggestions. Its context, modality, release-date, and tool metadata are explanatory, not authority to enable runtime capabilities or establish account entitlement. Subscription candidates come from their native adapters; ChatGPT and Copilot have no invented bundled inventory; ChatGPT offers explicit account-visible slug discovery and custom IDs. Copilot offers a separate explicit authenticated catalog action, filtered to Chat Completions IDs. Neither initial rendering nor account readiness starts that request. Catalog responses are discarded after source/account changes and never prepare or save a Model. Other xAI API rows do not expand Grok subscription choices. A process-local single-flight cache retains the last successful directory. Failed refreshes expose stale/unavailable status; bundled suggestions and manually entered IDs remain usable offline. Directory refresh never rewrites Models, defaults, Agents, or active Runs and never resolves credentials or constructs a runtime Model.

Options expand reviewed creation defaults. Unknown and older model IDs remain editable without guessed reasoning presets. Explicit settings, native configuration mappings, context policy, and empty capability selections remain authoritative. The endpoint URL must be unambiguous when supplied in both guided and native configuration fields. Model editing and cloning preserve native fields not represented by basic controls. Applying a settings preset is explicit; opening an editor is not permission to replace authored values.

Credentials are separate from Model publication. Model recipe readiness means the prepared recipe matches the current editor choices; account readiness is a separate fact. Add Model permits saving an unauthenticated subscription recipe with an explicit not-ready warning, but never saves an old recipe while unapplied connection or model choices are displayed. Inline Add Model publishes only the Model and selects its saved ID in the Agent draft. Cancelling that Agent draft does not roll back the independently saved Model. API-key references are selectable without reading secrets, and new keys use the existing Host-local key store. Subscription connections use their declared account store, login, refresh, and request transport. Copilot preserves its native Chat Completions profile without Codex fast mode, guessed context limits, native-tool recommendations, or a fabricated cheaper reviewer model. Codex keeps native session affinity, reasoning, Fast/Standard service tiers, and local working-context budgets; it receives no copied API output-token cap. Grok keeps its native subscription settings rather than inheriting the xAI API recipe. Account switching remains explicit and does not promise to replace an active Run's captured account.

Native tools belong to Agents. Model authoring may describe support but does not mutate referring Agents. Add Agent uses the selected saved Model's actual route/authentication/endpoint when proposing tools; choosing an existing Model does not duplicate or rewrite it.

## Browser First-Use

`/setup` presents two primary steps: Model (connection, independent credential operation, and the shared editor) and Workspace (execution Environment and optional Project directory). The App supplies connections, the public directory, and reviewed defaults; React does not own another provider/model inventory. API model options are computed locally from existing presets and bundled facts, including for custom model IDs, without provider requests. Discovery distinguishes a genuinely untouched configuration tree from incomplete authored resources; only an untouched installation automatically enters this flow. Existing broken/default-less configuration receives focused repair links and is not overwritten with starter defaults.

The browser stores only nonsecret selections, generated credential references, and the pending publication/first-Thread identity. The draft namespace combines the selected configuration location and data root, remains stable across server restarts, and separates disposable first-launch instances served at the same origin. Going back, refreshing, or completing authorization in another tab preserves these choices. Set up later suppresses repeated automatic entry while retaining explicit Continue setup. Secrets, OAuth codes, token contents, and verification URLs are not stored in this draft.

Subscription connection reuses the App's login sessions and provider-specific account stores. An authenticated read can recover the single active login after navigation, a lost start acknowledgement, or page refresh. Starting OAuth remains an explicit user operation. Account switching keeps the shared-account confirmation; cancellation uses the App's completion result and cannot relabel an already published login as cancelled. An absent session after restart offers status recheck and a new explicit login, not an automatic fallback.

The final action saves ordinary configuration and creates/opens an empty first conversation. Before publication, the browser retains the exact intended selection and preview files. An uncertain result is reconciled against those ordinary source files and accepted defaults; global `needed=false` alone is not proof that this publication succeeded. Missing or changed files require review and explicit retry. Conversation creation retains one preallocated, create-only Thread identity across uncertain responses and refreshes, reading that identity before retrying. It does not choose the newest conversation or change identity to hide uncertainty. No discovery, preview, account connection, environment check, configuration save, or Thread creation sends a prompt or incurs a model-request verification call.

## Reviewed Starter Configuration

When setup first materializes `security.shell_review`, it writes `guardian_credits: true` for a Codex subscription connection and `false` for API-key and other connections. Selecting an existing Model uses that Model's authentication kind. Existing root shell-review mappings are preserved without backfilling or overriding the option; Add Model never changes them. Runtime behavior follows the captured option rather than automatically enabling it from authentication. [Shell review composition](02-agent-composition-and-snapshots.md#shell-review-auxiliary-model) owns protocol compatibility and billing limits.

Initial setup materializes the [default-enabled Sidekick preference](01-configuration-and-resource-catalog.md) as `webui.sidekick: {}` in the root document when absent. Repeated setup preserves explicit null and authored Agent/Model selections; Add Model and Add Agent do not change this preference. This is a WebUI root preference, not an Agent Capability declaration or a request to start work.

Each supported subscription provider has a release-owned starter Agent template and three explicit coding Model choices under [Interactive CLI](07-interactive-cli.md#setup-and-context-management). An API-key starter selects a supported Pydantic AI provider/protocol, an explicit HTTP(S) base URL where applicable, a credential, a provider model ID, and a settings preset, in that order. The separate `xai:` native SDK route uses upstream's default gRPC endpoint and has no HTTP base-URL step or override; it is not the `grok:` Chat Completions recipe. The final Environment or Agent-name step shows the assembled route, endpoint, and expanded settings before publication. No model entitlement is inferred. The supported HTTP/API-key catalog includes OpenAI Responses and Chat Completions, Anthropic, Google Gemini API, OpenRouter, DeepSeek, Groq, Mistral, Together AI, Fireworks AI, and xAI's Grok Chat Completions API. It does not pretend that cloud IAM or subscription transports accept interchangeable URL/key inputs. Embedding callers can select no new connection to create an unconfigured default Agent; the terminal selects one connection. The templates use explicit authentication kinds and practical model-specific reasoning settings; they omit additional instructions unless the user supplies them. Every Agent receives the non-replaceable release-owned system prompt defined by [Agent composition](02-agent-composition-and-snapshots.md). Recommendations are based on official provider guidance and compatible upstream model catalogs rather than a runtime web search, benchmark slogan, or an automatically changing `latest` guess.

Every newly generated Model, including an auxiliary subscription reviewer, materializes known native media input capabilities into `model_characteristics.capabilities`. This applies equally to initial setup, Add Model, Add Agent with a new connection, and direct setup API calls. Objective model facts come from the release-pinned Harness official model catalog; Harness UI owns exact provider/protocol and reviewed routed-ID mapping and limits defaults to media supported by its selected transport. Google Gemini's native API can receive image, audio, and video bytes; the other setup transports seed verified image input only. Video URLs, frame extraction, live voice, and media generation do not establish native file-input support. Lookup is offline and does not verify endpoint compatibility, account entitlement, or model availability. Exact known IDs can be used behind a custom base URL; arbitrary deployment IDs, case variants, and unreviewed routed aliases remain unknown.

Only an omitted capabilities field is defaulted. An explicitly supplied set, including `[]`, remains authoritative; context budgets and summary/compaction thresholds remain independent. An absent catalog declaration means unknown, not verified text-only support. Unknown Models retain an empty set and require manual configuration or an explicitly configured media-understanding fallback. Publication writes a deterministically ordered list, never a catalog reference. Existing Models selected for reuse, edited resources, and historical captures remain unchanged; setup is not a migration or runtime inference mechanism.

The starter Agent enables native Harness file/shell tools and project-aware skills. Native runtime-context, handoff, and compaction capabilities are also selected. Task tools and native user interaction are supplied by the application composition defaults. Bounded child rosters can be authored through the ordinary composition catalog; setup does not invent new implementations for these features. It does not inject host-only collaboration through YAML, enable arbitrary external MCP servers, or bypass tool approval policy. The built-in system prompt encourages inspecting relevant sources, preserving unrelated edits, concise progress, validating changes, and reporting incomplete work honestly. The setup screen identifies the selected model and allows users to choose their default. Further connections are added as separate Models and Agents, without combining authentication or silently switching providers.

New Agent templates always include Host `web` for HTTP fetch/download. Native Web Search takes precedence over Host search, and native Web Fetch takes precedence over Host scrape, independently: setup writes `search.mode: off` when native search is selected and `host` otherwise; it writes `scrape.mode: off` when native fetch is selected and `host` otherwise. Codex subscription preselects live native Web Search (`external_web_access: true`) and `native_image_generation`. Grok subscription preselects native Web Search. Neither subscription adapter supports an independent native `WebFetchTool`, so both retain Host scrape. Compatible API connections preselect reviewed native search/fetch/image options; unknown Models, custom endpoints and incompatible combinations retain Host Web. The stock Host providers are keyless and require no credential step. Explicit Agent YAML remains authoritative and can independently compose both search mechanisms; these defaults are not a runtime fallback or a migration.

The normal landing and Add Agent workflows expose an editable multi-select with labels distinguishing provider execution from Host execution, recommendations, prerequisites and cost/resource hints. Empty selection means no native tools, retaining Host Web. Connections without native candidates skip the picker. API-key connections, including custom endpoints and model IDs outside the suggestions menu, expose candidates supported by their selected adapter and relevant model profile. Custom endpoints and unreviewed model IDs have no native recommendations preselected; the user must verify provider support before enabling them. A custom endpoint alone does not remove adapter candidates. Changing the Model connection resets tool selections and dependent resource inputs; backtracking within the same connection preserves them. Step position and total derive from the same currently applicable questions as navigation, including advanced and selected resource steps. The total may change after a branching choice; skipped steps are not counted, every visible question has progress, and the final question reports the total. Native candidates reuse upstream adapter declarations and relevant model profiles, with subscription-specific reviewed defaults; this is not another runtime support matrix. The image choice always selects the save-first image capability. File Search collects existing provider store IDs, provider-hosted MCP collects a public URL and server label, and Advisor collects its provider model ID. Setup neither uploads files nor creates stores, contacts MCP servers, invokes advisors, or verifies billing entitlement. Google File Search cannot be selected with other native tools. Image-only Gemini Models require a separately authored Agent without the coding starter's function tools.

Memory is not selectable without a Host-provided `memory` handler; serializing its native schema does not supply storage or execution. Native MCP authentication is not interpolated from Agent configuration: the stock wizard configures public servers only, and authenticated provider-hosted MCP requires trusted Host runtime credential wiring or the separate Host MCP integration. Provider tool execution does not become Host shell execution or inherit Host invocation approval semantics.

The setup API's optional `tool_capabilities` contains ordinary Capability selections for newly created Agents. Omission uses reviewed defaults; an explicit empty sequence disables these optional additions. Add Model rejects this field because Models do not own tool policy. All choices are editable creation-time suggestions; actual execution remains subject to provider support and account entitlement.

Existing Model reuse derives tool suggestions from that Model's actual route, authentication, and endpoint. After publishing a Model, the terminal offers a separate Add Agent flow preselecting that Model, including its tool picker; declining or cancelling that flow retains the saved Model. Add Model itself does not change Agents; reconnecting or upgrading existing Agents does not rewrite their capabilities. Recommendations do not place image generation into media-input `model_characteristics.capabilities`.

Codex defaults and explicit context choices are defined by [Interactive CLI](07-interactive-cli.md#setup-and-context-management). Grok defaults to `grok:grok-4.7`. These are reviewed, editable recommendations, not entitlement checks.

Setup initializes an absent root `security.shell_review` mapping with enabled shell review , `risk_threshold: extra_high`, `on_flagged: approval_required`, and `on_error: allow` by default for subscription and API-key connections. Existing root shortcut configuration is preserved in full, including disabled or partially authored values; no unused reviewer Model is generated when the root already owns the selection. API-key setup reuses its connected Model. Agent templates contain neither raw permission nor review Capability selections. This threshold is independent of the review Model's thinking effort. Existing Agent resources are not migrated. When Codex is selected, a separate `openai-codex:gpt-5.6-luna` resource with `thinking: low` supplies the reviewer, without changing another connection's authentication. Grok setup uses a separately named Grok shell review Model on Grok 4.7 with low reasoning; it does not claim a verified cheaper subscription tier. New reviewer display names explicitly include shell review. Existing names and recipes remain untouched. The enabled shortcut injects one `ToolPermissionsCapability` at capture time, defaulting to `on_flagged: approval_required` and `on_error: allow`: flagged shell calls require approval, while non-timeout review failures add no restriction beyond the effective invocation policy. Timeout always denies before execution, regardless of `on_error`. Setup does not rewrite existing Agent resources. The explicitly configured root shortcut overrides matching Agent policy fields during composition, while preserving unrelated rules. Shell review is not filesystem/process isolation, and disabling it is an explicit setup choice. Auxiliary-model recipes follow the frozen composition contract.

Setup explicitly materializes every `tools` field in the selected root YAML using the [root configuration defaults](01-configuration-and-resource-catalog.md), preserving any authored values, including disabled switches. Preview includes these fields before publication. Add Model leaves root configuration unchanged. Add Agent initializes an absent shell-review shortcut but preserves all existing root security settings and defaults.

Configuration is written into the selected tree: root YAML defaults and ordinary `models/`, `agents/`, and, when explicitly selected, `projects/` resources. A newly generated Project uses its root directory's basename as its display name, falling back to the root path for filesystem roots; setup does not rename existing Projects. Authentication fields reference the existing compatible store kind and contain no token bytes. The default Environment remains Full Control unless the user explicitly selects Sandbox; model recommendations do not change that omission default.

Templates seed files once. An explicit `connect_default` selection binds the selected existing Agent to the selected connection Model and optionally replaces its additional instructions when nonempty instructions are supplied. Its other fields are preserved. A changed subscription or API-key route/authentication gets a distinct Model resource rather than changing a Model shared with other Agents. An edited Model occupying a generated ID is checked against the requested route and authentication before reuse; a mismatch conflicts instead of trusting the ID. Unselected resources remain unchanged. Additional instructions never replace the built-in system prompt. Later releases, setup discovery, or ordinary startup never replace user-edited instructions, model routes, settings, tools, or resource names. Every new Run capture includes the current release system prompt alongside any non-empty additional instructions; frozen Runs retain the exact text already captured. Users can edit these files directly. The setup instruction editor targets new Agents; choosing an existing Agent preserves its instructions and does not submit stale text from another selection. The selected default affects new Threads only.

First-use landing creates the initial Model and Agent together; it does not offer an existing-Model selector. Subsequent resource creation has two separate terminal flows over the same candidate-validation and last-write-wins publication boundary:

- `add model` configures one new connection and publishes only its reusable Model resource. Its explicit new Model ID and name do not select or modify an Agent, default, Project, Environment, or auxiliary reviewer. Subscription context/reasoning customization remains Model configuration, not Agent configuration.
- `add agent` first selects an existing Model ID or a new connection. Reuse publishes only a new Agent referencing that exact Model, plus an absent subscription shell-review resource when needed; it does not copy or change the selected Model or its settings. A new connection publishes a distinct Agent/coding Model pair. Both paths allow Agent-specific instructions and initialization of an absent root shell-review shortcut, including API-key connections.

Generated resource names are plain stored text, not terminal presentation. One shared authoring rule supplies connection Model names and coding Agent names to both publication and name suggestions. It uses stable plain provider names and ASCII separators (`OpenAI - GPT-6 Astra`, `OpenAI - GPT-6 Astra - Coding`), never selector labels, status badges, decorative glyphs, or ANSI styling. Auxiliary review, default Agent, Project, and Environment names likewise use ordinary generated text; imported names and user-authored names remain authoritative. Terminal adapters may decorate a name when rendering it, but never persist that rendering as a resource name. YAML remains UTF-8: ASCII generated formatting does not prohibit Unicode in custom model IDs, authored names, or filesystem-derived names.

New resource-name prompts suggest these same names (or the selected existing Model's name plus the plain coding-role suffix for Agent reuse). Name collision suffixes remain ordinary numbers. Naming a new Agent does not replace its newly generated Model's descriptive connection name. No existing resource is renamed.

Each terminal invocation chooses an unused ID for its new resource, including when the display name or its normalized slug matches an existing resource; a repeated add is not a reconnect or reuse operation. The chosen ID stays stable across preview and publication retries. Both additions omit Project and root-default changes entirely; Add Agent may publish the root to initialize an absent shell-review shortcut. Existing identical new-resource content can be reused after partial publication; a conflicting Agent or coding Model cannot be repurposed. Matching auxiliary review resources retain their user-edited recipes. Adding does not prepare or change an Environment and does not reconnect the existing default Agent. Both terminal additions require initial usable setup first. New Model publication and new Agent publication never implicitly switch a running conversation; session selection is a separate terminal operation.

## Publication and Recovery

Setup receives an explicit selection without a source-generation precondition. Publication constructs a fresh candidate from that selection and current sources; the preview is informational, not a version token. It validates all chosen resource IDs, supported templates, default Agent membership, absolute Project roots, and Environment selection before source publication. No requested path can escape the fixed configuration tree. Existing resource IDs and destinations are reused only when they are the intended existing resource; a different existing file is a conflict, not a clobber opportunity.

Publication follows the shared source boundary:

- prepare and validate the complete candidate before writing;
- atomically write selected resources with last-write-wins replacement;
- update the explicitly selected Agent and root defaults while preserving unrelated fields observed when composing the candidate;
- publish defaults after the resources they reference;
- return completed source paths and reload the latest valid generation without requiring it to match the preview.

The candidate includes all primary source kinds, including optional global `AGENTS.md`, without rewriting preserved sources. Setup does not compare generations before, between, or after writes and does not report a concurrent save as a publication failure.

A filesystem tree is not a multi-file transaction. Interruption may leave newly created resource files without selecting new defaults. Such partial results are reported or found by the next discovery; retry reuses matching files instead of duplicating resources. Setup does not roll back completed writes, remove unrelated files, or treat an interrupted publication as completed. Selected files use the shared atomic replacement boundary; no old-file detachment or setup recovery directory is created. Legacy recovery directories are left untouched and do not block publication. Concurrent writes follow [File Mutation and Last-Write-Wins](01-configuration-and-resource-catalog.md#file-mutation-and-last-write-wins), including the possibility that another writer replaces a file immediately after setup saves it.

Cancel before configuration publication writes no resource selections; already saved credentials remain. Once publication starts, ordinary files are the reconciliation surface and cancellation does not imply rollback. An unknown apply result requires inspecting files and generating another preview before explicit retry. There is no permanent `setup_complete` flag that hides broken defaults.

## Environment Readiness

The effective selected Environment, not the operating system alone, determines preparation. Native/Full Control performs no envd download, launch, Bubblewrap probe, namespace change, or administrator action. Custom and remote profiles retain their owning Provider contracts; local Linux isolation checks must not be incorrectly applied to them.

When Local Envd/Sandbox is selected, the App validates the selected executable/version, supplies restricted grants and denied networking, verifies the effective Device boundary, then prepares a Session and verifies readiness. Envd owns platform worker preparation; the App does not implement a second sandbox launcher. Executable lookup alone is not proof that the selected boundary works.

Cancellation ends only the pending preparation and its newly owned resources, not an existing shared daemon serving other Sessions. Diagnostics distinguish executable, outer-launch, connection and Session-folder failures, with bounded output and no credentials. Launcher-specific instructions belong to the Host integration rather than envd policy. Windows Sandbox remains unavailable until a supported Host launcher exists; explicit saved selections stay blocked without fallback. Full Control retains native Windows execution under the [Direct Local contract](../a13n-harness/08a-environment-providers.md#direct-local). Readiness never advertises stronger containment or descendant cleanup than the actual Host launcher provides.

Failure offers explicit actions:

- view the copyable instructions and owning documentation;
- retry after fixing the prerequisite;
- cancel preparation while retaining the previous valid selection or blocked draft;
- explicitly choose Full Control, after explaining that it runs with the Host account and is not the Sandbox isolation boundary.

No retry, timeout, Escape, failed probe, or setup default silently downgrades Sandbox. The application never runs `sudo`, changes sysctls, installs system policy or silently disables the requested outer boundary. An explicit Full Control choice follows the normal draft, exact-version Thread mutation, or confirmed setup-default publication boundary. A change during a Run affects only the next Run.

## Responsiveness and Scope

Startup renders preparation status in the landing TUI before account discovery or runtime preparation. Loading, questions, external-login guidance, and publication status replace the current view rather than append terminal scrollback. Startup and chat share the same terminal Application, as defined by [Interactive CLI](07-interactive-cli.md#startup-and-terminal-ownership); only the active view changes when setup succeeds. Preparation runs outside terminal rendering and database transactions. Progress and cancellation remain usable; setup failures stay in the standalone workflow and startup failures return to the command shell rather than mounting chat. Each result is correlated to the effective profile and selection request, so a late probe cannot reselect an old profile after the user switches or exits.

Readiness is an observation, not a permanent guarantee: executable or host policy can change after a successful probe. Actual execution retains its normal validation and failure handling. All effective Project roots must pass; an ignored new-project path must never substitute for an existing Project's roots. An App-lifetime result may avoid redundant probes for the same effective selection, while explicit Retry always checks again. No persisted ready marker authorizes another process or machine.

The CLI owns the App lifetime in one task across standalone setup and chat. Terminal exit cancels work and waits for App cleanup; it does not detach a service.

## Verification Invariants

1. Empty and partially configured installations can reach setup without a model call or copied credentials.
2. Codex subscription, Grok subscription, API key, no connection, invalid-store, and existing-Model cases are explicit.
3. One prepared recipe produces ordinary editable Model fields; later additions preserve existing resources and defaults.
4. Reopening setup preserves unselected resources and validates resource identities; selected-path publication uses last-write-wins without version preconditions or post-write digest conflicts.
5. Partial publication and prompt admission have independent observable completion boundaries.
6. Native mode never prepares envd; Sandbox failure never silently selects Native.
7. Successful probe, missing runtime, isolation denial, retry, cancellation, and explicit Full Control are covered by tests.
8. The CLI exposes command-based recovery with bounded safe diagnostics and preserved selections.
9. Initial recommendations are release-owned defaults, not a promise of universal model superiority or account entitlement.

## Default Subagent Inclusion

Immediately after Environment selection, the wizard offers all release-owned subagents or none. Publication writes only the concrete `subagents.include` name list in root YAML; package definitions are not copied. The optional shared setup request `include_default_subagents` selects all when true, none when false, and preserves existing inclusion when omitted. Users discover names with `a13n-harness-ui config subagents` and edit individual selections manually.
