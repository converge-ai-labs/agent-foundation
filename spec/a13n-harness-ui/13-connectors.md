# WebUI Connectors

## Design Position

A Connector is an instance-wide, trusted Python integration owned by a WebUI-mode `HarnessUiApp`. It combines a discoverable declaration, human configuration and setup, private account state, optional native tools and shared programmatic services, and optional external input production. Multiple instances of one type represent independent accounts. Concrete providers define service-level configuration and setup. Remote MCP is a developer-facing library for implementing providers; it is not a built-in Connector type or a second generic MCP configuration surface.

This plane belongs to Harness UI, separately from Harness Plugins, Environment connectors, file-defined Agent MCP selections, and declarative Content Plugins. [Bot and Connector Ingress](12-bot-and-connector-ingress.md) owns automatic delivery and Bot publication; [Agent Composition](02-agent-composition-and-snapshots.md) owns immutable Run composition; Harness owns native Capability, ModelContext and ToolSearch behavior. Connectors add no Agent loop or general workflow engine.

## Discovery and Authority

The WebUI catalog combines built-in definitions, explicit `HarnessUiIntegrations.connectors` registrations and installed `a13n_harness_ui.connectors` entry points. An entry point constructs a no-argument `Definition` whose key matches its entry-point name. Declarations perform no network or credential I/O. Installed trusted types are available by default; installation creates no account, setup session, usable tool binding or Run. Duplicate keys are unavailable with a diagnostic rather than silently selecting an implementation. Broken installed definitions do not hide other types. Capture records retain implementation provenance; reconstruction fails explicitly if the captured implementation is missing or changed.

The owning WebUI App holds the same data-root local ownership lock as Bot. The lock spans producers, admitted root users, controller resources and cleanup. Another App can inspect saved facts but cannot configure, set up, submit input or use services. Terminal Apps do not construct this catalog or runtime. Automatic tools and context attach only to ordinary WebUI roots and Bot: children, Live and memory organization receive none. Bot still inherits no configured Agent instructions, children, MCP selections or Harness Plugins.

Python integrations are trusted Host code, with Host-account effects. The SDK's typed surface is a maintainability and ownership boundary, not a Python sandbox. Instance-key users administer all connections. Scoped guests have no Connector management, credential, setup-session or offer-query API authority. A shared intentional card is inert for guests.

## Declaration, Configuration and Rules

A declaration has API version `1`, stable type key, display name, description, configuration form schema, setup intents, optional event declarations and optional Bot delivery. Optional `brand` names a shared brand identity; optional `logo_url` supplies a public HTTPS image for integrations outside that registry. These presentation hints contain no credentials and grant no authority. The Host uses its shared brand renderer and generic fallback without provider-specific frontend registration. Each event has a key, display metadata and optional conditions schema. The Definition supplies Pydantic configuration and event-condition validators; conditions schemas agree with those validators. Types may declare conditions, event-only rules, or no events at all.

An instance has a never-reused ID, type key, editable display name, required editable `group_name`, enabled flag, default-false `deliver_to_bot`, human configuration version, independent private credential version, settings and ordered rules. A rule has a stable ID, declared event key, enabled flag and conditions value. The Host validates and persists these values and renders their forms. The plugin decides what matches and what work to perform; the Host has no universal matcher, condition language, provider scope or event operator registry. Historical `selected_events` remains decodable but grants no new filtering meaning.

A group name is a canonical lowercase ASCII slug, starts with a letter, uses letters, digits and single hyphen separators, and contains at most 32 characters. It is unique across all nondeleted instances, including disabled and incomplete accounts, independently of type and display name. The storage transaction enforces this reservation; deletion releases it. Display-name edits never implicitly change a saved group.

Human saves compare the expected configuration version; creation expects absence. Secret-changing saves also compare the private credential version. Refresh/rotation can change credentials independently without invalidating an open human form or a Run's captured configuration. Deleting clears private values, state and pending input, retires the instance ID permanently and prevents old captures from resolving a replacement account. Unknown plugin data is preserved as unavailable rather than reinterpreted as another type.

Credentials and private state are plaintext in the instance database under Host filesystem protection. Public instance reads expose safe settings, rule configuration and configured credential names, never credential values. Model context, captures, tool schemas, logs and durable setup offers contain no credentials or private state. Plugins own the safety of their status, context, setup and capture projections.

## Controller and Service Lifetime

A Definition opens one Controller per configured instance. Its async context enters and exits in one owning task, permitting ordinary async resources and task groups. The Controller remains available through root cleanup even if configuration disables or deletes the instance. Optional producers run for one configuration generation and stop before replacement. Shutdown seals admission and stops producers and setup, drains root users, then closes controller resources and relinquishes ownership.

The bound SDK Context exposes current private configuration, credential CAS, scoped JSON state, atomic state/input commits, configuration saves and typed shared-service lookup. It exposes no SQL session, Host Agent builder, root executor or raw HTTP adapter. Services use an explicit name and API version plus a consumer-checked type. They share a provider implementation and its current account authority rather than exporting token getters to consumers. Disabled or retired account checks remain at the provider operation boundary.

## Setup Interactions

Settings and conversation cards open the same backend-owned setup flow in a bounded modal dialog, with a narrow bottom-sheet presentation and reachable footer actions. Account lists lead with names, types and status; one Add connection chooser offers installed types. Creating an account first collects an editable display name and group name. The UI suggests a normalized group from the display name, falling back to the type key when necessary and using readable numeric suffixes for collisions. The group remains user-editable; once explicitly edited, later display-name edits preserve the group draft. Account settings edit the saved group independently and show format and collision errors beside the field. Closing an incomplete new account offers removal or retention for later. Beginning or reading setup starts no Run. A session owns an opaque ID, instance, intent, version, expiry and current Step. Steps describe title, explanation, safe values, optional form, optional bounded wait and actions: submit, explicit confirmation, open URL, copy or shared MCP OAuth authorization. State is `input`, `working`, `waiting`, `completed`, `failed`, `cancelled` or `expired`.

The bounded form profile supports objects, strings/passwords, numbers, integers, booleans, enums, nullable fields, repeatable arrays/rows and acyclic local `$defs` references. Conditional schemas, arbitrary unions, remote/recursive references, tuple schemas and open dictionary editors are unsupported. Unsupported declarations produce diagnostics; the UI does not substitute a raw JSON editor. Nested `writeOnly` values are removed from safe reads and cannot publish nonempty defaults. Private inputs exist only in component/request memory and are cleared on dispatch, without Query mutation caches or browser persistence. The root schema may list saved write-only JSON Pointer paths in `x-a13n-saved`; these expose presence, never values. Array controls may declare `x-a13n-add-label`; nullable selections may declare `x-a13n-null-label`, `x-a13n-selected-label` and `x-a13n-empty-label`. A read-only configuration schema projects safe settings for an account summary while setup owns their editing.

Actions may declare an optional `icon` semantic token: `edit`, `test`, `save`, `continue`, `done`, `refresh`, `open_url` or `copy`. The Host owns the glyph mapping, sizing and compact treatment; action IDs, labels and provider keys never select icons. Missing or unknown tokens preserve text controls; `open_url` and `copy` kinds supply their own default glyph. Icons do not change action kind, availability, confirmation or execution. [Connector presentation](webui/06-design-guidelines.md#connectors) owns the shared visual and copy rules.

Actions serialize per session and compare the observed version and action availability. Each request supplies an operation ID; an exact retry returns the retained safe result without repeating the action. A session retains at most 128 action outcomes and lives at most 30 minutes; the App retains at most 128 sessions. Individual actions have a 30-second deadline. Cancellation/shutdown can interrupt an action and closes the flow after that action exits. Interrupted or unknown external effects require inspection and a new deliberate decision, never automatic replay. Restart loses ephemeral sessions; saved configuration and credentials remain.

Wait reads are observational, bounded by the backend poll interval and deadline; a changed observed step changes the version. Expiry is explicit. A `completed` step closes the setup dialog after refreshing saved account state, without another confirmation. Failed, cancelled and expired steps remain visible for inspection and recovery. Closing a panel discards its private draft, not saved configuration or an already dispatched effect. Reopening reuses an active session; a terminal flow begins afresh. After an unknown response the UI refreshes status before enabling another action. A Host-projected action error remains visible without pretending that the underlying plugin step changed; a corrected submission uses the returned version directly. Dirty configuration conflicts preserve human drafts and require an explicit reload. Clean account drafts rebase to current saved configuration without reporting a conflict. Account settings and setup have separate surfaces and save paths.

## Captured Tools and Model Context

Root admission captures enabled, usable instances before publishing immutable composition. Each capture records instance/type identity, configuration version, implementation provenance and a plugin-authored safe binding recipe. Later status/setup changes do not add tools to that Run. Disabled, deleted or configuration-changed instances reject subsequent provider operations; a fresh deliberate Run can capture the new binding. Credential bytes resolve only at the provider transport boundary, independently of configuration capture.

Connector tools use native Capabilities and scoped ToolSearch with `discover_connector_tools`, `describe_connector_tool`, `call_connector_tool`, `list_connector_tools` and `list_connectors`. These controls coexist with Agent-owned ToolSearch. Real-target allowlists apply before discovery, including an explicit empty list. Each account uses its persisted `group_name` directly as its distinct search group, so native tools with identical upstream names remain unambiguous without inventing wrapper arguments or a per-tool provider facade. Captures retain the exact group and account display name for reconstruction. A group edit advances the configuration version: old captures reject subsequent provider operations, and a new Run captures the new group. Captures without an explicit group are unsupported. Model-visible group descriptions identify the service and captured account name, and current instance context maps captured accounts to their exact tool groups.

When CodeAct is enabled, the same five Connector controls are callable from its existing runners. The Remote MCP library explicitly declares typed CodeAct eligibility for its native local targets; arbitrary Connector plugins retain ownership of their target policy. Grouped upstream methods are not separate Python callables. Programs discover or describe schemas and invoke `call_connector_tool(group=..., tool=..., arguments=...)` through Harness's existing proxy bridge and original ToolManager. Target tool selection, permissions, account/configuration guards, native validation and usage remain authoritative. Inline-resolved approvals keep ordinary semantics; an unresolved approval or deferred call cannot suspend and later resume a Python execution point. It fails that runner under the existing CodeAct contract rather than replaying the program.

A changed-only ModelContext block describes current available types, safe instance status and context, captured membership, setup entry point and authority limits. It uses native visible-history matching, so A/A emits once, A/B/A emits each transition and loss through compaction permits reinjection. Context is an observation, not new tool authority.

`offer_connector_setup` accepts a type, optional same-type instance and human-facing text, never credentials. It writes a durable ordinary-Thread offer independently of folded CodeAct/tool output. The card appears outside collapsed work, beside its visible native-call turn when available and independently when its anchor is absent or compacted. Offering alone creates no connection or setup session. A human selects an existing account or deliberately creates another and enters the shared setup surface. The card keeps forms out of the transcript and derives its resolved state from a ready eligible account. Resolved cards name the account, offer Manage and ask for a new message. Setup success changes saved configuration; it replays no blocked operation.

For Bot, the same native tool intentionally publishes a typed setup offer using the existing Bot publication identity, deduplication and notification path. Its chat remains human messages, final replies and intentional publications, without tool-stream rendering. Ordinary final-answer and `finish_silently` semantics remain unchanged.

## Private State and Bot Ingress

Scoped state consists of bounded JSON documents with independent CAS versions. A plugin persists its own codec/version inside each value when needed. Deletion retains a state-version tombstone to prevent stale update acceptance after delete/recreate. No dynamic per-instance SQL table is created.

One short transaction atomically validates the enabled instance/configuration generation, compares state versions, changes state and retains plugin-decided Bot inputs. It admits at most 32 distinct state changes, 64 KiB per JSON document, 256 KiB total changed state and 32 inputs per commit. At most 1024 pending envelopes belong to one instance. Every fully serialized input fits the shared 60 KiB automatic batch boundary. A failed fence, CAS, size, capacity or delivery-policy check aborts the entire commit. Ignored upstream events can advance state without input; selected input cannot be lost while advancing a cursor.

Pending inputs deduplicate by instance and source-event identity and return the originally retained input ID. Deduplication is not a permanent provider event log. Provider I/O happens outside database transactions. Submission signals Bot immediately through a coalesced process-local wakeup; periodic delivery remains compensation. Bot off, pause, pending human decisions, capacity and native admission retain their existing gates. Rule edits never erase previously retained plugin decisions; disabling holds them, deletion clears them.

## Remote MCP Providers

The Remote MCP library supplies a reusable Controller for concrete service providers. Providers implement a safe connection recipe from their bound account configuration and own their Definition, service-level settings, authentication and setup flow. The library has no catalog registration, generic endpoint/header form or provider-key dispatch. Transport endpoints, private credential references, native tool allowlists, initialization timeouts and protocol choices are code-level provider decisions. Existing Agent-selected MCP resources retain their separate configuration surface. The Host and frontend do not reinterpret library capabilities as another MCP product entry.

The library reuses existing transport validation, FastMCP, native MCP Capability and ToolSearch execution. An omitted recipe tool allowlist permits all advertised tools; `[]` permits none. Private references resolve inside the bound account at the transport boundary and retain configuration-generation and enabled/retired-account fences. Plain HTTP retains the existing header-free loopback restriction. The library also supplies version `1` of the typed `mcp` shared service for programmatic list/call operations with the same authority and tool-selection checks. Native Agent tools execute through their native Capability rather than delegating through this service.

GitHub is a concrete provider built on this library. Its code fixes `https://api.githubcopilot.com/mcp/` and constructs a private PAT-derived Authorization header. Its user setup exposes only token entry, saved-token presence and explicit removal; common account name and enabled state remain Host-owned. It exposes no configurable endpoint, headers, protocol, transport timeout or generic MCP tool picker, including through direct configuration writes. The provider declares no events or proactive Bot delivery and implements no separate OAuth application, REST tool library or poller. Token type, organization policy and GitHub permissions determine usable tools. Saving is local, not verified connectivity. Saving a token, retaining an existing token or removing it completes the setup in the same action. Account management keeps editing and explicit Test connection available separately; opening the test flow offers Edit connection, Test connection when configured, and Done. Blank token input retains the saved token; replacement plus removal and token control characters are rejected.

Linear and Notion are thin concrete providers of the same library and [application-owned MCP OAuth](02-agent-composition-and-snapshots.md#mcp-oauth). Both use DCR and the shared backend/UI authorization interaction; they own no token store, refresh loop or frontend provider map. Linear defaults to read/write access through its standard endpoint and discovered scopes. The account's `access` setting selects `read_write` or `read_only`; read-only mode uses its read-only endpoint and exact `read` scope. Notion uses its fixed official endpoint and discovered scopes, with upstream consent determining permissions. Changing access settings retires the previous authorization. Completed authorization and explicit MCP connectivity testing are independent results. The providers declare no events or proactive Bot delivery. GitHub retains its PAT setup.

The bound SDK Context supplies the shared OAuth service. Remote MCP captures its opaque account generation, and both native tools and the typed service resolve current tokens at their transport boundary. Setup's `oauth` action renders the shared Connect/reconnect/pending/cancel/disconnect controls. Closing a setup flow cancels an unfinished login while preserving completed authorization.

## API and Compatibility

Instance-authenticated routes expose catalog and instance reads, conditional PUT/delete, begin setup, observational session reads, explicit actions and ordinary-Thread setup offers. The generated OpenAPI document owns exact payloads. These routes are absent from scoped guest admission. No Connector management YAML is added to Agent resources.

SQLite migrations supply human and credential versions, identity retirement, rules, scoped state, durable ordinary offers and persisted group names. Upgrading existing accounts deterministically backfills readable normalized groups from display names or type keys, resolving collisions with numeric suffixes while preserving IDs, credentials, settings and related state/input. Backfill runs once; later startups preserve saved groups. Existing unrelated resources, Bot behavior and checkpoints retain their semantics. Captured bindings use ordinary immutable composition persistence, including reconstruction and deferred execution; missing provenance or unsupported legacy settings fail unavailable rather than silently receiving new tools.
