升级已有 Service 部署时使用本页，新安装无需执行历史转换。按来源和目标版本选择适用的切换步骤，遵循[备份与迁移流程](operations.md)，确认数据、worker 和客户端兼容后再恢复任务接收。保留结果不明的外部操作，先核查再处理。

## 可组合记忆指引升级

默认及跟随预设的文件指引在持久化时省略可选的 `modules` 字段，冻结记忆挂载保持原有形状，因此已有记忆挂载的 Run 在滚动升级期间仍可读取。保存显式模块选择或启动新整理工作流之前，先升级所有 control 和 worker 副本。旧进程无法解析显式模块配置或执行新引入的工具。

回滚到不支持可组合指引的版本前，先使用当前 API 将显式选择重置为 `modules: null`，并排空新整理任务。已接受的 Run 继续保留兼容读取器；数据库回滚不会转换已接受的执行历史。自动整理要求策略配置者当前及已捕获的 `read`、`write`、`run` 权限；权限撤销会记录为接受失败，并遵循已配置的重试冷却时间。

## 自动记忆策略升级

迁移新增独立策略表和成功历史消费表，保留已有空间调度行、Memory 和 Space ID、文件、修订、会话绑定和已接受的 Run。迁移不回填数据、不扫描历史、不执行模型。新外键需要短暂锁定引用表；迁移超时限制锁等待，事务回滚后可重试。

配置策略 `instructions`、`history` 或使用独立自动整理前，先升级全部 control 和 worker。未设置的新字段在持久化时省略，默认策略保持原有形状；旧进程无法解析显式配置的新字段。回滚前关闭独立策略，清空空间的 `instructions` 和 `history`，并排空已接受的整理 Run。保留新增表及兼容读取器；删除这些表会丢失独立策略和历史消费进度。

历史自动整理要求显式会话白名单和起始封存时间。已有纯文件策略保留原有的修改触发行为；安装本身不会启用对话处理。

## Run 搜索部署

升级到引入运行搜索的版本时，迁移会添加默认空值的搜索列，并并发创建 GIN 索引，不回填历史内容。列和触发器修改仍需短暂表锁；迁移超时配置限制执行时间。索引构建失败后可重新运行：无效索引会删除，已完成的有效索引保留。

先升级所有 control 进程和读取端，再启用新 worker。当前 worker 写入检查点格式 4，并读取格式 1–4；旧 worker 会跳过无法继续的格式。写入新格式后，回滚仍需保留兼容的读取端、Console 和 worker。数据库降级会删除派生的搜索数据，但不会转换已保存对象。

## 转换旧版运行对象

仅在从最初的不分页运行显示升级，且迁移命令报告旧版指针时，使用此流程。Schema 迁移重命名数据库字段；独立的转换步骤添加消息序号并压缩对象。

1. 等待已接受和正在运行的任务结束，再停止**全部** control 和 worker 副本。
2. 完成 schema 迁移。随后出现的旧版对象错误表示还需执行转换步骤。
3. 使用数据库所有者权限，并在仓库之外准备持久私有备份目录。备份包含会话数据。
4. 检查一批对象，再执行转换：

```sh
a13n-service --config service.toml migrate-run-objects
a13n-service --config service.toml migrate-run-objects --apply --backup-dir /private/backups/a13n-run-objects
```

默认每批处理 100 条运行；`--limit` 接受 1–1000。命令先校验并备份原始对象和数据库指针，再替换每条运行的指针，保留消息 ID、顺序、内容、流覆盖范围及检查点载荷。已转换运行会跳过，因此中断的批次可以继续。

5. 重复执行 apply 命令，直到报告 `"converted": 0`。遇到拒绝时先调查原因：未完成的检查点清理、已有显示分页、对象缺失或损坏、历史已截断，都需要解决后再继续。
6. 检查部署迁移是否完成：

```sh
a13n-service --config service.toml migrate --check
```

7. 恢复副本，打开历史运行及其消息列表，再继续对话。

回退到旧版不分页读取端时，停止副本，并一起恢复备份的数据库指针和对象。后续清理可能删除原始对象，因此应独立保留私有备份。

## 内部平台工具

Service 0.1 之前可能引入破坏性变更，开发者须自行迁移已有数据。这次内部工具替换就是其中一次：所有此前保存过规范化配置的 Agent 都可能需要完整重写，即使被移除的工具条目原本处于禁用状态。此变更不提供兼容层，不保证新旧 Control/Worker 混合运行，也不保证恢复旧 Run。部署前应停止接收新任务及定时、手动调度，等待活动 Run 完成，并处理待审批、等待中的 Run 以及结果不明的外部操作。关闭旧部署，同步更新 Control 和 Worker，完成数据迁移或配置重写后，再恢复任务接收。

## 工具发现选择器

**Service 破坏性变更：** 将发现分组 `capabilities` 中的 `environment` 替换为 `files`、`shell` 和 `computer`，或其中需要的部分。运维人员需要自行修复受影响的 Agent 版本以及 Run、Inbox 和 Schedule 中冻结的配置。Service 不会迁移或转换这些数据。单独读取或复用不兼容记录时，接口返回 `409 conflict`，包含 `reason: configuration_unavailable` 和受影响的资源 ID。Agent 版本、Inbox 和 Schedule 列表保留正常记录，并通过 `unavailable` 列出不兼容记录；即使 `items` 为空，也应继续使用 `next_cursor` 翻页。会话的 thread 帧同样标记不兼容的 Run 和待处理条目，让其他线程继续刷新。此选择器变更不影响独立使用的 Harness 或 Harness UI 配置。

## Webhook 签名

对于 Standard Webhooks 签名启用前创建的订阅，以管理员身份通过 `PATCH` 换成有效的 `whsec_…` 密钥，或重新创建订阅。旧投递保留旧密钥，会以 `signing_secret_unavailable` 失败，重新投递无法修复。新投递使用替换后的密钥。接收端使用[签名说明中的 `webhook-*` 请求头](webhooks.md#payload-and-signature)；原来的 `X-A13n-*` 签名格式已不再发送。

## 桌面控制切换

此变更用环境级 Computer 控制替代运行级协助和暂停/恢复 API。请协调切换：

1. 在旧版本停止接收新任务和接管请求，等待活跃 worker 和保留工具执行结束。
2. 使用旧版本撤销并核对所有旧桌面授权和预留。完成并恢复旧桌面等待，或取消其当前 thread 头。保留已完成的历史运行。先解决清理结果不确定的问题，再继续。
3. 停止全部旧 control 和 worker 副本。备份数据库，通过受支持的迁移流程执行一次 schema 迁移。仍有活跃预留、未解决协助或可恢复的桌面等待时，迁移会拒绝执行。
4. 同步升级 control、worker 和客户端。启用人工访问前，将桌面访客环境准备为协议 v2。现有 v1 环境需要显式替换为兼容环境或由运维升级；连接操作不会升级环境。
5. 在已准备的目标上验证查看、接管和归还，再重新开放请求。

此切换不支持新旧副本混合运行。出现旧版本无法表达的新控制或交还历史后，数据库会拒绝降级。此时应向前修复。
